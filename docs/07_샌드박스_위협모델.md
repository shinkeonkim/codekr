# 07. 샌드박스 위협 모델과 검증 결과

이 문서는 **조사 결과**다. 샌드박스가 안전하다는 선언이 아니라, 무엇을 확인했고 무엇을
확인하지 못했는지를 구분해 남긴다 (#37).

> 배경 지식 없이 읽으려면 [`12_샌드박스_보안_해설.md`](12_샌드박스_보안_해설.md) 을 먼저
> 본다. 같은 내용을 개념부터 순서대로 설명한다.

- 검증 코드: `apps/executor/internal/selftest/` (실행기 바이너리와 테스트가 **같은 정의**를 쓴다)
- 로컬 실행: `CODEKR_SANDBOX_TEST=1 go test ./internal/selftest/ -v`
- 배포된 노드에서 실행: `executor --self-test` (§5)
- 마지막 실행 환경: Docker Desktop (Linux VM, cgroup v2), 2026-08-10

## 1. 위협 모델

### 보호 자산

| 자산 | 왜 지켜야 하는가 |
|---|---|
| 호스트/노드 커널과 파일 시스템 | 침해되면 클러스터 전체가 무너진다 |
| 다른 사용자의 실행 작업 | 남의 코드·입력·정답이 새면 채점 자체가 무의미해진다 |
| 히든 테스트케이스와 정답 코드 | 유출되면 문제가 죽는다 |
| 내부 네트워크와 클라우드 메타데이터 | 자격증명 탈취 경로 |
| 실행기·채점기의 가용성 | 한 사람의 코드가 큐 전체를 멈추면 안 된다 |

### 신뢰 경계

```
신뢰함  │ api · judge · executor 프로세스
────────┼──────────────────────────────────────
신뢰 안 함 │ 사용자 코드 (샌드박스 컨테이너 안에서 도는 모든 것)
```

사용자 코드는 **임의 코드 실행 권한을 이미 가진 공격자**로 본다. 취약점을 찾아 실행하는 것이
아니라, 처음부터 원하는 프로그램을 돌릴 수 있다. 그래서 "입력 검증"은 방어가 아니고,
**격리와 자원 제한만이 방어**다.

### 공격자가 할 수 있다고 가정하는 것

- 임의 프로세스 실행, fork, 파일 읽기·쓰기 시도
- 임의 네트워크 연결 시도, 임의 syscall 호출
- 자원 고갈(CPU·메모리·디스크·PID·출력)
- 컨테이너 탈출 시도 (커널·런타임 취약점 이용)

### 공격 표면

| 경계 | 표면 |
|---|---|
| 사용자 코드 → 커널 | syscall (seccomp 필터로 축소) |
| 사용자 코드 → 파일 시스템 | 마운트된 경로 |
| 사용자 코드 → 네트워크 | 네트워크 네임스페이스 |
| 사용자 코드 → 다른 작업 | 공유 자원(디스크·메모리·PID 네임스페이스) |
| 실행기 → 런타임 소켓 | 실행기 프로세스가 침해될 경우 (아래 4장) |

## 3. 확인된 것과 확인하지 못한 것

**확인된 것 (18개 항목).** 위 매트릭스에서 ✅ 표시된 항목은 실제로 코드를 돌려
방어가 걸려 있음을 관찰했다. 자동화되어 있어 언제든 다시 돌릴 수 있다.

**확인하지 못한 것.**

- **운영 노드의 실제 설정.** 여기 표는 로컬 Docker Desktop 에서 확인한 것이다.
  containerd 구현은 colima VM 안에서 같은 7개 검사를 통과했으나(#68), 운영 노드의
  커널·cgroup·LSM 설정은 그것과 다를 수 있다 — 노드에서 `--self-test` 를 돌려 확인한다.
  운영 클러스터에서 같은 결과가 나오는지는 클러스터가 서면 다시 돌려야 한다 (#16, #45).
- **커널 취약점을 이용한 컨테이너 탈출.** 검증 대상이 아니다. 컨테이너는 커널을 공유하므로
  커널 취약점 앞에서는 방어가 없다고 본다.
- **seccomp 기본 프로파일이 막지 못하는 syscall 조합.** 기본 프로파일이 적용돼 있음은
  확인했지만, 그 프로파일의 허용 목록이 이 서비스에 적절한지는 따로 검토하지 않았다.

## 4. 잔여 위험

### R1. 실행기가 컨테이너 런타임 소켓을 쥐고 있다 (높음)

샌드박스 **안**에서는 소켓이 보이지 않는다(항목 11). 그러나 실행기 프로세스 자체는
소켓을 쓴다. 실행기가 침해되면 호스트 root 와 동등한 권한을 갖는다.

#### 지금 걸려 있는 통제 (#47)

| 통제 | 구현 |
|---|---|
| 노드 격리 | `nodeSelector: codekr/workload=executor` + `codekr/executor` toleration |
| 네임스페이스 격리 | `executor.namespace` 로 분리 — hostPath 를 허용하는 privileged Pod Security 를 그 네임스페이스에만 연다 |
| egress 차단 | NetworkPolicy 로 **DNS 와 Redis 만** 허용 |
| 자격증명 없음 | 실행기가 아는 설정은 큐 주소뿐이다. DB 자격증명을 주지 않는다 (ADR-0004) |
| 파일시스템 | `readOnlyRootFilesystem: true` — 실행기는 자기 디스크에 아무것도 쓰지 않는다 |
| 권한 | `capabilities: drop ALL`, `allowPrivilegeEscalation: false`, `seccompProfile: RuntimeDefault` |
| 코드 실행 안 함 | 사용자 코드는 실행기 프로세스가 아니라 샌드박스 컨테이너에서 돈다 |

**egress 를 막는 것이 이 중 가장 값이 크다.** 침해된 실행기가 노드 root 권한을 얻어도,
밖으로 데이터를 보내거나 다음 단계를 내려받을 경로가 없으면 할 수 있는 일이 크게 준다.

레지스트리로 나가는 길은 열지 않았다 — **런타임 이미지를 받는 것은 노드의 컨테이너
런타임이지 실행기 파드가 아니다.** 소켓 너머에서 일어나는 일이라 NetworkPolicy 가 닿지 않는다.

ingress 는 막지 않는다. 실행기는 큐를 소비할 뿐 아무도 호출하지 않아 막을 것이 없고,
CNI 에 따라 kubelet 프로브까지 끊긴다.

#### 실행기가 쓰는 런타임 API 범위

이것이 실행기 침해 시 공격자가 **바로** 쓸 수 있는 API 다.

| 호출 | 쓰임 |
|---|---|
| `Ping` | 기동 시 소켓 확인 |
| `ContainerCreate` | 샌드박스 컨테이너 생성 |
| `ContainerStart` | 실행 시작 |
| `ContainerUpdate` | cgroup 제한 조정 |
| `ExecCreate` / `ExecAttach` | 컴파일·실행 명령과 stdio |
| `ContainerRemove` | 폐기 |

**이미지를 받는 API 는 쓰지 않는다.** 런타임 이미지는 노드에 미리 있어야 한다 (#96).

소켓 프록시로 이 목록만 통과시키는 방안은 검토했으나 넣지 않았다 — 프록시 자체가
소켓을 쥐게 되어 위험이 옮겨갈 뿐이고, `ContainerCreate` 하나만으로도 호스트 마운트가
가능해 목록을 좁혀도 실질적인 이득이 없다. 실질적인 축소는 containerd 네임스페이스
분리(#45)에서 온다.

#### 침해를 가정한 탐지·대응

**탐지**

- NetworkPolicy 밖으로 나가려는 시도 — CNI 의 거부 로그에 남는다. 실행기의 정상 동작에는
  DNS·Redis 외의 egress 가 없으므로 **한 건이라도 나오면 비정상**이다.
- 실행기가 만들지 않은 컨테이너가 실행 노드에 뜨는 것. 실행기가 만드는 컨테이너는
  이름 규칙과 라벨이 정해져 있다.
- 큐에 없는 제출에 대한 결과 이벤트 (`JudgeResultRecorder` 가 경고 로그를 남긴다).

**대응**

1. 실행기 Deployment 를 0 으로 내린다 — 어드민 스케일 제어(#40)로 즉시 가능하다.
   채점은 멈추지만 제출은 큐에 쌓이므로 유실되지 않는다.
2. 실행 전용 노드를 cordon 하고 격리한다. **다른 워크로드가 없으므로 노드를 통째로
   비워도 서비스의 나머지는 돈다** — 노드 격리를 해 둔 이유가 이것이다.
3. Redis 의 작업·결과 스트림을 보존한다 (사후 분석 자료).
4. 노드를 재생성한다. 침해된 노드를 고쳐 쓰지 않는다.
5. DB 는 실행기가 접근할 수 없으므로 제출 기록의 무결성은 별개로 확인한다 — 의심되면
   해당 기간의 제출을 재채점(#107)한다.

- 완화(현재): 위 표.
- 완화(현재): containerd 네이티브 구현 (#68). 실행기가 노드 위에서 직접 돌므로
  런타임 소켓을 컨테이너에 마운트할 필요가 없다.
- 후속: **#47** (이 절이 그 결과다)

### R2. seccomp 프로파일을 좁혔다 (#48, 해소)

`infra/sandbox/seccomp.json` — `defaultAction: SCMP_ACT_ERRNO` 의 허용 목록이고
**300개**를 연다. 런타임 기본 프로파일보다 좁다.

기본 프로파일이 열어 두지만 우리가 **닫은** 것:

| syscall | 왜 닫았나 |
|---|---|
| `ptrace`, `process_vm_readv/writev` | 같은 컨테이너 안 다른 프로세스의 메모리를 읽고 쓴다 |
| `userfaultfd` | 커널 취약점 악용에 널리 쓰인다. 페이지 폴트를 사용자 공간이 가로챈다 |
| `io_uring_setup/enter/register` | 커널 공격 표면이 넓고, 지원 언어 중 필요한 것이 없었다 |
| `kcmp`, `move_pages`, `mbind`, `set_mempolicy` | NUMA·프로세스 비교. 채점에 쓸 일이 없다 |
| `open_by_handle_at`, `name_to_handle_at` | 파일 핸들로 마운트 경계를 우회하는 고전적인 탈출 경로 |
| `seccomp` | 자기 필터를 다시 설치할 이유가 없다 |

`personality` 는 값별로 열었다 — 커널 에뮬레이션 모드 변경은 막고 런타임이 실제로 쓰는
값만 통과시킨다.

**14개 런타임 전부에서 기본 템플릿이 도는 것을 확인했다** (`make verify-runtimes` 가
이제 이 프로파일을 걸고 돈다). 회귀는 `make verify-seccomp` 가 막는다 — 허용 목록을
넓히다 보면 어느 순간 기본 프로파일과 다를 바 없어지는데, 그 사실은 아무도 눈치채지 못한다.

프로파일은 **ConfigMap 으로 배포한다.** 파드 스펙의 `securityContext.seccompProfile` 이
아닌 이유는, 이 프로파일이 실행기 파드가 아니라 실행기가 **만드는** 컨테이너에 걸리기
때문이다 — 쿠버네티스는 그 컨테이너를 모른다. 노드 파일에 두지 않은 이유는 노드를 늘릴
때마다 사람이 복사해야 하고, 프로파일과 코드의 버전이 갈라져도 아무도 모르기 때문이다.

파일이 없거나 망가지면 **실행기가 기동에서 실패한다.** 첫 제출에서 드러나지 않게.

### R3. user namespace 재매핑 (#130, containerd 에서 해소)

컨테이너의 UID 10001 이 호스트의 UID 10001 과 같으면, 탈출했을 때 그 UID 권한을 그대로
갖는다. 재매핑은 그 둘을 떼어 놓는다.

**containerd 런타임에서 켤 수 있다.** `CODEKR_USERNS_HOST_OFFSET` 에 호스트에서 내줄
UID 구간의 시작을 준다. 그러면 컨테이너의 0~65535 가 호스트의 offset~offset+65535 가
된다 — UID 10001 은 호스트에서 110001 이고, 그런 계정은 없다.

```
CODEKR_SANDBOX_RUNTIME=containerd
CODEKR_USERNS_HOST_OFFSET=100000
```

**기본은 꺼짐이다.** 어느 구간을 내줄지는 노드마다 다르고, 실제 계정이 쓰는 구간과 겹치면
재매핑이 오히려 권한을 **주는** 셈이 된다. 구간은 `/etc/subuid`·`/etc/subgid` 로 예약한다.

`0` 은 거부한다 — 켠 것처럼 보이지만 컨테이너의 root 가 호스트의 root 가 된다.

**엔진 API 에서는 켤 수 없다.** 그쪽은 daemon 설정(`--userns-remap`)이다. 그 런타임에서
이 환경 변수를 주면 실행기가 **기동에서 실패한다** — 조용히 무시하면 재매핑이 걸린 줄 알고
운영하게 된다.

#### 확인한 것

colima VM(리눅스 6.8, containerd 2.3, overlayfs)에서 `CODEKR_USERNS_HOST_OFFSET=100000`
으로 두고 돌렸다.

| 확인 | 결과 |
|---|---|
| 재매핑이 실제로 걸리는가 | ✅ 컨테이너 안 `/proc/self/{uid,gid}_map` 이 `0 100000 65536` (`TestLiveUserNamespaceRemapping`) |
| 환경 변수 값이 흘러가는가 | ✅ `200000` 으로 바꾸면 매핑도 따라 바뀐다 |
| `--self-test` 7개 | ✅ 전부 통과 |
| tmpfs 작업 디렉터리에 쓸 수 있는가 | ✅ 통과 (`TestLiveHardeningWorkDirIsWritableButIsolatedPerJob`) |
| 런타임 이미지 파일 소유권 / 컴파일 | ✅ 13개 런타임 통과. 나머지 2개는 이미지가 없어 실패한다 (#171) |
| SQL 런타임(initdb, 이미지 계정) | ✅ 통과 |
| 이미지 레이어 재전개 비용 | 관측되지 않았다 — 스냅샷 수(이미지 11개 / 레이어 50개)와 실행 시간이 재매핑 전후로 같다 |

마지막 항목이 **컨테이너별 매핑을 쓰는 이유**다. daemon 수준 재매핑은 레이어를 통째로 다시
풀어야(chown) 하지만, 컨테이너별 매핑은 스냅샷에 라벨을 달아 idmapped mount 로 붙인다.

#### 남은 것

**운영 노드에서는 아직 켜지 않았다.** 위 확인은 VM 에서 한 것이고, 노드의 커널이
idmapped overlayfs 를 지원하는지와 UID 구간 예약은 그 노드에서 확인해야 한다.
노드에서 `--self-test` 를 켠 채로 한 번 돌리는 것으로 충분하다.

### R4. 커널 공유 (수용)

컨테이너 격리는 커널 취약점 앞에서 무력하다. gVisor·Firecracker 같은 강한 격리는
홈랩 노드에서 운영 비용이 크다 (ADR-0003). **현재는 수용하고**, 실행 노드를 다른
워크로드와 분리하는 것으로 영향 범위를 제한한다.

### R5. `/dev/shm` 등 부수 tmpfs (낮음)

`/dev/shm` 이 쓰기 가능하다(기본 64MB). tmpfs 사용량은 컨테이너 메모리 한도에 포함되므로
자원 고갈로 이어지지 않고, 컨테이너와 함께 사라진다. **수용.**

## 5. 반복 실행 방법

### 로컬

```bash
cd apps/executor
CODEKR_SANDBOX_TEST=1 go test ./internal/selftest/ -v

# 좁힌 프로파일을 걸고 확인하려면 (#48)
make verify-seccomp    # 위험한 syscall 이 막히는지
make verify-runtimes   # 14개 런타임이 그 프로파일에서 도는지
```

### CI

`sandbox-live` 잡이 PR 마다 containerd 구현으로 위 검사를 돌린다 (#172). 러너는 리눅스라
클라이언트와 containerd 가 같은 커널을 쓰므로 macOS 의 FIFO 제약(#70)이 없다.

**통과 수를 센다.** 환경 변수를 빠뜨리면 전부 SKIP 인데 초록으로 보이는 것이 가장 나쁜
결과라, 잡이 실제로 돌아간 검사 수를 확인하고 모자라면 실패시킨다.

런타임 매트릭스는 아직 빠져 있다 — 15개 중 2개가 없는 이미지를 가리킨다 (#171).

**`make verify-runtimes` 는 이제 프로파일을 걸고 돈다.** 프로파일 없이 통과하는 것은
운영에서 통과한다는 뜻이 아니다.

### 배포된 노드

**여기서 통과하는 것이 실제로 중요한 쪽이다.** 방어의 상당수는 커널·cgroup·런타임
설정에 달려 있어서, 로컬에서 통과했다는 사실이 운영 노드에서 통과한다는 보장이 되지
못한다 (#45).

```bash
kubectl -n codekr-exec exec deploy/codekr-executor -- executor --self-test
```

같은 검사 정의를 쓰므로 위 테스트와 결과가 같은 의미를 갖는다. 하나라도 실패하면
종료 코드가 1 이고, 무엇이 뚫려 있는지 전부 출력한다 — 첫 실패에서 멈추지 않는다.

컨테이너 정리 확인:

```bash
docker ps -a --filter "ancestor=python:3.12-alpine"   # 비어 있어야 한다
```

## 6. 공개 범위

이 문서는 **방어가 걸려 있음을 확인한 결과**만 담는다. 실제 악용 가능한 취약점을 발견하면
공개 이슈에 재현 절차를 쓰지 않고 GitHub Security Advisory 로 전환한다 (#37 완료 조건).

이번 조사에서 악용 가능한 취약점은 발견되지 않았다. 잔여 위험 R1~R3 은 설계상 알려진
한계이며, 재현 코드가 아니라 구성 변경으로 다루는 항목이다.
