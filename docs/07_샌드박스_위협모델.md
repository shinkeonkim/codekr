# 07. 샌드박스 위협 모델과 검증 결과

이 문서는 **조사 결과**다. 샌드박스가 안전하다는 선언이 아니라, 무엇을 확인했고 무엇을
확인하지 못했는지를 구분해 남긴다 (#37).

- 검증 코드: `apps/executor/internal/sandbox/hardening_live_test.go`
- 실행: `CODEKR_SANDBOX_TEST=1 go test ./internal/sandbox/ -run TestLiveHardening`
- 마지막 실행 환경: Docker Desktop (Linux VM, cgroup v2), 2026-08-10

## 1. 위협 모델

### 보호 자산

| 자산 | 왜 지켜야 하는가 |
|---|---|
| 호스트/노드 커널과 파일 시스템 | 침해되면 클러스터 전체가 무너진다 |
| 다른 사용자의 실행 작업 | 남의 코드·입력·정답이 새면 채점 자체가 무의미해진다 |
| 히든 테스트케이스와 정답 코드 | 유출되면 문제가 죽는다 |
| 내부 네트워크와 클라우드 메타데이터 | 자격증명 탈취 경로 |
| 실행기·채점기의 가용성 | 한 사람의 코드가 큐 전체를 멈추면 안 된다 |

### 신뢰 경계

```
신뢰함  │ api · judge · executor 프로세스
────────┼──────────────────────────────────────
신뢰 안 함 │ 사용자 코드 (샌드박스 컨테이너 안에서 도는 모든 것)
```

사용자 코드는 **임의 코드 실행 권한을 이미 가진 공격자**로 본다. 취약점을 찾아 실행하는 것이
아니라, 처음부터 원하는 프로그램을 돌릴 수 있다. 그래서 "입력 검증"은 방어가 아니고,
**격리와 자원 제한만이 방어**다.

### 공격자가 할 수 있다고 가정하는 것

- 임의 프로세스 실행, fork, 파일 읽기·쓰기 시도
- 임의 네트워크 연결 시도, 임의 syscall 호출
- 자원 고갈(CPU·메모리·디스크·PID·출력)
- 컨테이너 탈출 시도 (커널·런타임 취약점 이용)

### 공격 표면

| 경계 | 표면 |
|---|---|
| 사용자 코드 → 커널 | syscall (seccomp 필터로 축소) |
| 사용자 코드 → 파일 시스템 | 마운트된 경로 |
| 사용자 코드 → 네트워크 | 네트워크 네임스페이스 |
| 사용자 코드 → 다른 작업 | 공유 자원(디스크·메모리·PID 네임스페이스) |
| 실행기 → 런타임 소켓 | 실행기 프로세스가 침해될 경우 (아래 4장) |

## 3. 확인된 것과 확인하지 못한 것

**확인된 것 (18개 항목).** 위 매트릭스에서 ✅ 표시된 항목은 실제로 코드를 돌려
방어가 걸려 있음을 관찰했다. 자동화되어 있어 언제든 다시 돌릴 수 있다.

**확인하지 못한 것.**

- **운영 환경(containerd)의 실제 설정.** 지금 검증은 전부 로컬 Docker Desktop 에서 했다.
  운영 클러스터에서 같은 결과가 나오는지는 클러스터가 서면 다시 돌려야 한다 (#16, #45).
- **커널 취약점을 이용한 컨테이너 탈출.** 검증 대상이 아니다. 컨테이너는 커널을 공유하므로
  커널 취약점 앞에서는 방어가 없다고 본다.
- **seccomp 기본 프로파일이 막지 못하는 syscall 조합.** 기본 프로파일이 적용돼 있음은
  확인했지만, 그 프로파일의 허용 목록이 이 서비스에 적절한지는 따로 검토하지 않았다.

## 4. 잔여 위험

### R1. 실행기가 컨테이너 런타임 소켓을 쥐고 있다 (높음)

샌드박스 **안**에서는 소켓이 보이지 않는다(항목 11). 그러나 실행기 프로세스 자체는
소켓을 쓴다. 실행기가 침해되면 호스트 root 와 동등한 권한을 갖는다.

- 완화(현재): 실행기는 사용자 코드를 자기 프로세스에서 실행하지 않고, DB 자격증명도 갖지 않는다.
- 완화(예정): 실행 전용 노드 격리와 NetworkPolicy (#16), containerd 네이티브 구현 (#45).
- 후속: **#47**

### R2. seccomp 가 기본 프로파일이다 (중간)

기본 프로파일은 범용이라 이 서비스에 필요 없는 syscall 도 열려 있다. 커널 공격 표면을
줄이려면 허용 목록을 좁혀야 한다.

- 후속: **#48**

### R3. user namespace 재매핑이 없다 (중간)

컨테이너의 UID 10001 은 호스트의 UID 10001 과 같다. 컨테이너 탈출이 일어나면
그 UID 권한을 그대로 갖는다. userns-remap 을 켜면 탈출 후 권한이 한 단계 더 낮아진다.

- 후속: **#48** 에 함께 다룬다.

### R4. 커널 공유 (수용)

컨테이너 격리는 커널 취약점 앞에서 무력하다. gVisor·Firecracker 같은 강한 격리는
홈랩 노드에서 운영 비용이 크다 (ADR-0003). **현재는 수용하고**, 실행 노드를 다른
워크로드와 분리하는 것으로 영향 범위를 제한한다.

### R5. `/dev/shm` 등 부수 tmpfs (낮음)

`/dev/shm` 이 쓰기 가능하다(기본 64MB). tmpfs 사용량은 컨테이너 메모리 한도에 포함되므로
자원 고갈로 이어지지 않고, 컨테이너와 함께 사라진다. **수용.**

## 5. 반복 실행 방법

```bash
make build-runtimes                       # 최초 1회
make pull-runtimes
cd apps/executor
CODEKR_SANDBOX_TEST=1 go test ./internal/sandbox/ -run TestLiveHardening -v
```

컨테이너 정리 확인:

```bash
docker ps -a --filter "ancestor=python:3.12-alpine"   # 비어 있어야 한다
```

## 6. 공개 범위

이 문서는 **방어가 걸려 있음을 확인한 결과**만 담는다. 실제 악용 가능한 취약점을 발견하면
공개 이슈에 재현 절차를 쓰지 않고 GitHub Security Advisory 로 전환한다 (#37 완료 조건).

이번 조사에서 악용 가능한 취약점은 발견되지 않았다. 잔여 위험 R1~R3 은 설계상 알려진
한계이며, 재현 코드가 아니라 구성 변경으로 다루는 항목이다.
