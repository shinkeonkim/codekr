# ADR-0006. MVP 범위 축소 결정

- 상태: 채택
- 날짜: 2026-08-10

## 배경

플랫폼 비전은 넓다(SQL·네트워크·OS·시스템 설계 문제, 랭킹, 대회 등).
MVP 는 "로컬에서 문제를 풀고 채점받을 수 있다" 를 증명하는 것이 목적이다.
무엇을 지금 만들지 않을지 명시적으로 정한다 — YAGNI.

## 결정

### 지금 만들지 않는 것

| 항목 | 이유 | 언제 |
|---|---|---|
| 소셜 로그인, 비밀번호 재설정, 이메일 인증 | 메일 발송 인프라가 필요하고 MVP 검증에 기여하지 않음 | M2 |
| 랭킹/티어/뱃지 | 문제 수가 적을 때 의미 없음 | 컨텐츠가 쌓인 뒤 |
| 커뮤니티(질문/풀이 공유) | 별도 도메인. 채점 파이프라인 검증과 무관 | 이후 |
| 대회 모드, 표절 검사 | 채점 파이프라인이 안정된 다음 문제 | 이후 |
| **SQL/시스템 설계 전용 채점기** | 유형마다 채점 방식이 다름. 먼저 stdin/stdout 유형으로 파이프라인을 검증한다 | 이슈 #17 이후 |
| 부동소수점 허용 오차 비교, 스페셜 저지 | 필요한 문제가 아직 없다 | 필요할 때 |
| Refresh 토큰 회전/블랙리스트 | MVP 는 만료 기반으로 충분 | M2 |
| 다국어(i18n) | 한국어 단일 | 이후 |

### 지금 만드는 것 (MVP)

기획서 3장의 G1~G7. 요약하면: 인증 → 문제 탐색 → 코드 실행 → 실시간 채점 →
어드민 문제 관리 → 로컬 전체 기동.

## 근거

MVP 의 위험은 UI 개수가 아니라 **채점 파이프라인이 실제로 동작하는가**에 있다.
큐, 샌드박스, 실시간 전달의 세 축이 붙어 돌아가는 것을 먼저 증명해야
나머지 기능이 의미를 갖는다. 위 목록은 전부 그 축을 검증한 뒤에 붙여도 늦지 않다.

문제 유형(카테고리)은 **스키마상 지금부터 표현**한다 — 나중에 컬럼을 추가하는 것보다
enum 값을 미리 두는 편이 마이그레이션 비용이 낮고, 유형별 채점기는
`Sandbox`/판정 로직 뒤에서 확장 가능하게 열어둔다.
