# ADR-0007. 문제·제출의 소프트 삭제

- 상태: 채택
- 날짜: 2026-08-10

## 배경

어드민이 문제를 지우면 그 문제로 남긴 제출 이력은 어떻게 되어야 하는가?
처음에는 "제출 이력이 있으면 삭제를 거부(409)"하는 방식이었지만, 그러면 잘못 등록한 문제를
아무도 지울 수 없게 된다 — 제출이 한 건만 있어도 영원히 남는다.

## 결정

문제·테스트케이스·문제별 초기 코드·제출은 **물리 삭제하지 않고 `deleted_at` 만 채운다.**

- 살아 있는 행만 봐야 하는 조회는 리포지토리에서 `deleted_at IS NULL` 을 **명시적으로** 건다.
- 모든 유니크 제약은 `WHERE deleted_at IS NULL` **부분 유니크 인덱스**로 만든다.
- 어드민의 문제 삭제는 딸린 테스트케이스·템플릿까지 함께 소프트 삭제한다.

## 근거

- 제출 이력은 **사용자의 기록**이다. 운영자의 문제 정리 때문에 사라지면 안 된다.
- 부분 유니크 인덱스가 없으면 삭제한 slug·순번·런타임을 다시 쓸 수 없다. 예를 들어
  테스트케이스를 교체할 때마다 순번 1이 이미 점유돼 있어 등록이 실패한다.
- Hibernate 의 전역 필터(`@SQLRestriction`)를 쓰지 않은 이유: 제출 이력 화면은
  **삭제된 문제까지 함께 보여야 한다.** 전역 필터를 걸면 이 경로에서 빠져나갈 방법이 없다.
  필터를 리포지토리 메서드 이름에 드러내면 어느 쿼리가 무엇을 보는지 호출부에서 바로 읽힌다.

## 감수하는 것

- 삭제된 행이 계속 쌓인다. 테스트케이스는 문제를 수정할 때마다 세대가 늘어난다.
  → **보관 정책과 정리 배치를 도입했다** (#46). 문제 90일, 문제 편집 부산물 30일.
    제출과 그 결과는 사용자의 기록이므로 지우지 않으며, 제출 이력이 남아 있는 문제도
    실제 삭제 대상에서 제외한다(CASCADE 로 이력이 함께 사라지기 때문).
- 모든 조회에 조건이 하나 더 붙는다. 대신 어떤 쿼리가 삭제된 행을 보는지가 코드에 드러난다.
- 사용자 계정은 소프트 삭제 대상이 아니다. 탈퇴 기능이 생길 때 개인정보 파기 정책과 함께
  따로 설계한다.


## 후속: 알림 보관 (#106)

읽은 알림만 90일 뒤 지운다. **안 읽은 알림은 지우지 않는다** —
읽지 않았다는 것은 아직 전달되지 않았다는 뜻이고, 오래됐다는 이유로 지우면 사용자는
그런 일이 있었다는 것 자체를 모르게 된다.

알림은 소프트 삭제하지 않는다. 되살릴 이유가 없고, 읽음 시각이 이미 "언제 전달됐는가" 를
남기고 있다.
