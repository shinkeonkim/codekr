# ADR-0004. DB 쓰기 주체를 api 하나로 제한

- 상태: 채택
- 날짜: 2026-08-10

## 배경

채점 결과를 PostgreSQL 에 남겨야 한다. judge 가 직접 쓰는 방법과,
api 가 이벤트를 받아 쓰는 방법이 있다.

## 결정

**PostgreSQL 에 쓰는 주체는 api 하나뿐이다.** judge/executor 는 DB 자격증명을 갖지 않는다.
judge 는 진행 상황을 `codekr:events` Pub/Sub 로 발행하고, api 의 구독자가
영속화 + WebSocket 중계를 함께 수행한다.

## 근거

- 스키마 지식이 한 곳에만 있으면 마이그레이션(Flyway)이 api 배포와 동기화된다.
  judge 가 DB 를 알면 두 서비스의 배포 순서에 스키마 호환성 제약이 생긴다.
- judge/executor 는 사용자 코드에 가장 가까운 서비스다. 여기에 DB 자격증명을 두지 않는 것이
  **보안 경계로서 의미가 크다** — 샌드박스 문제가 생겨도 DB 로 가는 길이 없다.
- 어차피 실시간 전달을 위해 이벤트 발행은 필요하다. 그 이벤트를 영속화 트리거로 겸용하면
  경로가 하나로 줄어든다(DRY).

## 감수하는 것 / 완화

- Pub/Sub 는 전달 보장이 없다. 이벤트가 유실되면 제출이 `JUDGING` 에 머문다.
  → api 에 **스위퍼**를 둔다: 일정 시간(기본 120초) 이상 `PENDING`/`JUDGING` 인 제출을
    `FAILED`(`SYSTEM_ERROR`)로 종결한다.
- 같은 이벤트가 두 번 도달할 수 있다(api 인스턴스 다중화).
  → `submission_testcase_results(submission_id, seq)` 유니크 제약 + UPSERT 로 멱등 처리.
