# ADR-0009. 정본 주소는 퓨니코드(`xn--hy1by51c.kr`)로 적는다

- 상태: 채택
- 날짜: 2026-08-13

## 배경

같은 사이트를 적는 방법이 둘이다.

| 표기 | 어디에 쓰이나 |
|---|---|
| `코드.kr` | 브라우저 주소창, 사람이 말하고 적는 것 |
| `xn--hy1by51c.kr` | Ingress `host`, CORS `Origin`, 인증서, 차트의 `publicHost` |

여기까지는 문제가 아니었다. 이제 `og:url`·`canonical`·`sitemap.xml` 에 주소를 **적어
넣기** 시작한다(#277·#278·#234·#271). **네 곳이 각자 정하면 같은 문서가 두 주소로
색인된다.**

## 먼저 확인한 것

### 1. 고를 수 없는 자리가 있다

`metadataBase` 는 `URL` 객체를 받고, JS 의 `URL` 이 IDN 을 퓨니코드로 정규화한다.

```
$ node -e 'console.log(new URL("https://코드.kr/problems").href)'
https://xn--hy1by51c.kr/problems
```

유니코드로 적어도 **나가는 것은 퓨니코드**다. 우회하려면 `metadataBase` 를 버리고
문자열을 직접 넣어야 하고, 그러면 파일 규약(`opengraph-image.jpg`)이 만들어 주는
절대 주소를 잃는다.

퍼센트 인코딩도 답이 아니다 — `encodeURI("https://코드.kr")` 는 **호스트까지**
`%EC%BD%94...` 로 만드는데, 그것은 호스트로서 유효하지 않다.

### 2. 구글은 둘을 같은 것으로 본다

> Google treats the Punycode version of a hostname as being equivalent to the
> unencoded version, so you don't need to redirect or canonicalize them separately.
> — [Google Search Central](https://developers.google.com/search/blog/2015/07/googles-handling-of-new-top-level)

**검색 결과에는 유니코드로 표시된다.** 즉 퓨니코드로 적어도 사람이 보는 것은 `코드.kr` 이다.

### 3. 서버가 받는 Host 도 이미 퓨니코드다

브라우저는 주소창에 `코드.kr` 을 보여주지만 **보내는 `Host` 헤더는 퓨니코드**다.
차트의 `publicHost` 도 그 값이다. `sitemap.xml`·`robots.txt` 는 요청의 Host 로 주소를
만들므로(#234), 이미 퓨니코드로 나가고 있다.

## 결정

**기계가 읽는 주소는 전부 퓨니코드로 통일한다** — `metadataBase`, `canonical`,
`og:url`, `sitemap.xml`, `robots.txt`.

**사람이 읽는 글자는 `코드.kr` 로 둔다** — 문서, 푸터, `og:site_name`, 화면의 문구.

한 곳에서 정한다: 차트의 `publicHost`(퓨니코드) → 웹의 환경 변수 → `metadataBase`.
네 이슈가 각자 적지 않는다.

## 감수하는 것

- **공유 카드에 낯선 문자열이 뜬다.** 카카오톡·슬랙은 `og:url` 의 호스트를 그대로
  보여 준다. `og:site_name` 을 `코드.kr` 로 두어 카드의 이름만은 한글로 읽히게 한다 —
  그것이 이 결정으로 잃는 유일한 것이고, 대신 얻는 것은 **중복 색인이 없다**는 것이다
- 유니코드로 적고 싶어지는 자리가 계속 생긴다. 그때마다 이 문서를 가리킨다

## 되돌린다면

구글 외의 크롤러가 둘을 다르게 다루는 것이 확인되면 다시 본다. 지금 근거는 구글
문서 하나이고, 카카오톡·슬랙이 `og:url` 을 **정규화하는지는 확인하지 못했다**
(실제로 공유해 봐야 알 수 있고, 그것은 배포 뒤에 가능하다).
