# ADR-0003. 코드 실행 샌드박스 런타임

- 상태: 채택
- 날짜: 2026-08-10

## 배경

임의의 사용자 코드를 실행해야 한다. 이것은 이 플랫폼에서 가장 위험한 지점이다.
요구사항은 "Golang 및 Containerd 환경을 활용하여 코드 실행 및 채점 환경을 구축한다" 이다.

## 결정

executor 내부에 **`Sandbox` 인터페이스**를 두고 런타임 구현을 교체 가능하게 한다.

```go
type Sandbox interface {
    Run(ctx context.Context, spec RunSpec) (RunResult, error)
}
```

구현체 이름에는 특정 런타임 제품명을 쓰지 않는다 (`containerSandbox`). 운영 환경의 런타임은
**containerd** 이고, 로컬 개발 환경은 같은 OCI 호환 엔진 API 를 노출하는 런타임을 쓴다 —
호출부는 어느 쪽인지 구분하지 않는다.

- **현재 구현**: OCI 호환 엔진 API 클라이언트. 실행기 컨테이너가 런타임 소켓을 마운트해
  형제 컨테이너를 띄운다.
- **다음 단계**: containerd 를 CRI 로 직접 다루는 구현. 로컬 개발 환경에서는 containerd 소켓이
  노출되지 않아 검증할 수 없으므로 별도 과제로 분리한다 (이슈 참조).

모든 구현이 지켜야 하는 제약:

| 제약 | 값 |
|---|---|
| 네트워크 | 완전 차단 (`none`) |
| rootfs | 읽기 전용, 작업 디렉터리만 쓰기 가능한 tmpfs |
| 사용자 | non-root 고정 UID (10001) |
| 권한 | 모든 capability drop, `no-new-privileges` |
| 메모리 | 문제별 제한, swap 비활성 (OOM 을 즉시 감지하기 위함) |
| CPU | 1 코어 |
| 프로세스 수 | 128 (fork bomb 방어) |
| 출력 | 64KiB 상한, 초과 시 `OUTPUT_LIMIT_EXCEEDED` |
| 실행 시간 | 문제별 제한 + 컴파일용 별도 상한 |

## 근거

- 인터페이스로 분리하면 로컬 개발 환경과 운영(containerd) 사이의 간극이
  executor 내부 한 파일에 갇힌다. 나머지 코드는 어느 쪽인지 모른다.
- gVisor/Firecracker 같은 더 강한 격리는 홈랩 노드에서 운영 비용이 크다.
  현 단계에서는 cgroup + namespace + capability drop 조합으로 충분하고,
  필요해지면 같은 인터페이스 뒤에서 교체할 수 있다.

## 감수하는 것

- **런타임 소켓 마운트는 실질적으로 호스트 root 권한이다.** 로컬 개발과
  실행 전용으로 격리된 노드에서만 허용한다. 이 사실을
  [로컬 개발 가이드](../05_로컬_개발_가이드.md)에 경고로 남긴다.
- 컨테이너 생성 오버헤드(수십~수백 ms)가 테스트케이스마다 발생한다.
  MVP 에서는 허용하고, 병목이 되면 케이스들을 한 컨테이너에서 순차 실행하는
  배치 모드를 같은 인터페이스 안에서 추가한다.
