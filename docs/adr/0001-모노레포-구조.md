# ADR-0001. 모노레포 구조

- 상태: 채택
- 날짜: 2026-08-10

## 배경

프론트엔드(Next.js), API(Kotlin), 실행기·채점기(Go) 네 개의 서비스가 하나의 제품을 구성한다.
이들을 어떻게 나눠 관리할지 정해야 한다.

## 결정

**단일 저장소(monorepo)** 에 `apps/<service>` 로 나란히 둔다. 언어별 빌드 도구는
각 앱 디렉터리 안에서 독립적으로 동작한다(Gradle / Bun / Go modules).
저장소 루트에는 `Makefile` 과 `infra/docker/compose.yml` 만 두어 진입점을 통일한다.

Nx·Turborepo 같은 모노레포 오케스트레이터는 **도입하지 않는다**. 언어가 넷이라
공통 태스크 러너가 얻는 이득보다 설정 복잡도가 크다. `make` 한 겹으로 충분하다.

## 근거

- API 계약 변경(문제 DTO, 이벤트 스키마)이 4개 서비스에 동시에 걸리는 일이 잦다.
  한 PR 에서 함께 바뀌는 편이 정합성 유지에 유리하다.
- 로컬 개발자가 저장소 하나만 clone 하면 전체가 뜬다.
- CI 는 경로 필터로 변경된 앱만 빌드하면 모노레포의 비용을 대부분 상쇄한다.

## 결과

- CI 워크플로에 `paths` 필터가 필수다 (없으면 매 PR 마다 4개 앱을 전부 빌드하게 된다).
- 배포는 앱별로 독립적이다 — 이미지 태그는 `codekr-api`, `codekr-web` 처럼 분리한다.
