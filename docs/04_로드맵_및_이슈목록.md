## 4. 브랜치 · PR 전략 (Stacked PR)

> 실제 작업 절차와 규칙은 [`docs/10_작업_방식.md`](10_작업_방식.md) 에 있다.
> 이 절은 개요만 남긴다.

작업이 밀려도 리뷰가 막히지 않도록 **스택 형태로 브랜치를 쌓고 PR 을 모두 열어둔다**.

```
main
 └─ feat/01-docs                 (PR → main)
     └─ feat/02-monorepo         (PR → feat/01-docs)
         └─ feat/03-api-core     (PR → feat/02-monorepo)
             └─ …
```

- 각 PR 은 이슈 하나에 대응하고 본문에 `Closes #N` 을 포함한다.
- 커밋 메시지 형식: `<type>(<scope>): <요약> (#<issue>)`
  - 예: `feat(api): JWT 인증 필터 및 로그인 API 추가 (#4)`
- 앞선 PR 이 머지되면 뒤따르는 PR 의 base 를 순서대로 옮긴다.

## 5. MVP 완료 정의 (Definition of Done)

- [ ] 클린 체크아웃에서 `make up` 으로 6개 서비스가 모두 healthy
- [ ] `make seed` 로 데모 계정과 시드 문제 3종 생성
- [ ] 브라우저에서 가입 → 로그인 → 문제 목록 → 상세 → 코드 실행 → 제출 → 실시간 채점 → 판정 확인
- [ ] 어드민 계정으로 문제 등록/수정/삭제, 큐 모니터링 화면 확인
- [ ] 무한 루프 제출이 `TIME_LIMIT_EXCEEDED` 로, 과다 메모리 할당이 `MEMORY_LIMIT_EXCEEDED` 로 판정
- [ ] api/judge/executor 의 헬스 엔드포인트가 모두 200
