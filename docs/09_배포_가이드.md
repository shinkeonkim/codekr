# 09. 배포 가이드 (k8s / GitOps)

코드.kr 을 홈랩 쿠버네티스 클러스터에 배포하는 방법. 원칙과 배경은
`oh-my-homelab/docs/service-dev-guide/` 를 따른다.

## 1. 두 저장소의 역할

```
codekr (이 저장소)
  ├ .github/workflows/ci.yml       이미지 빌드 → ghcr.io/shinkeonkim/codekr-*
  └ deploy/charts/codekr/          Helm 차트 (Deployment·Service·Ingress·RBAC)
        │
        │ ArgoCD 가 두 저장소를 함께 본다
        ▼
oh-my-homelab
  ├ helm-charts/apps/codekr.yaml            Application 정의
  ├ helm-charts/values/codekr.yaml          홈랩 전용 값 오버라이드
  ├ helm-charts/codekr/                     네임스페이스·CNPG DB 등 인프라
  ├ helm-charts/secrets/codekr/             SOPS 암호화 시크릿
  └ helm-charts/network-policies/codekr/    최소 egress
```

**차트가 이 저장소에 있는 이유:** 차트는 애플리케이션의 일부다. api 에 환경 변수가 하나
늘면 차트도 같이 바뀌어야 하는데, 저장소가 갈라져 있으면 두 PR 이 필요하고 그 사이에
배포가 깨진다. `oh-my-blog` 도 같은 구조를 쓴다.

## 2. 구성 요소

| 워크로드 | 종류 | 비고 |
|---|---|---|
| `codekr-api` | Deployment | Flyway 마이그레이션이 기동 시 실행 → `startupProbe` 를 넉넉히 |
| `codekr-web` | Deployment | |
| `codekr-judge` | Deployment | DB 자격증명 없음 (ADR-0004) |
| `codekr-executor` | Deployment | **실행 전용 노드·별도 네임스페이스**(§3) |
| `codekr-redis` | StatefulSet | 큐·실시간 이벤트. 단일 인스턴스 |
| PostgreSQL | CNPG Cluster | 홈랩 인프라 쪽에서 정의 |

## 3. 실행기 격리 — 필수 선행 작업

실행기는 컨테이너 런타임 소켓을 마운트한다. **이 권한은 노드 root 와 동등하다**
(docs/07 잔여 위험 R1). 두 겹으로 가둔다.

### 3.1 노드 격리 (더 중요한 겹)

```bash
kubectl label node <실행-전용-노드> codekr/workload=executor
kubectl taint node <실행-전용-노드> codekr/executor=true:NoSchedule
```

차트의 `executor.nodeSelector` 와 `tolerations` 가 이 라벨/테인트에 맞춰져 있다.
라벨이 붙은 노드가 없으면 실행기 파드는 스케줄되지 않는다 — **의도된 동작이다.**
격리되지 않은 노드에 실행기가 뜨는 것보다 뜨지 않는 편이 안전하다.

**어떤 노드를 고를지가 이 문서에서 가장 중요한 결정이다.** control-plane 노드를
고르면 탈출 시 etcd 와 apiserver 가 같은 노드에 있다 — 실행 전용 워커 노드를 쓴다.
홈랩의 구체적인 판단은 `oh-my-homelab/docs/setup/codekr_배포_요청사항.md` §0 에 있다.

### 3.2 네임스페이스 격리

hostPath 마운트는 Pod Security 의 `baseline` 을 통과하지 못한다. 그렇다고 codekr
네임스페이스 전체를 `privileged` 로 열면 api·web·judge 까지 같은 예외를 물려받는다.

그래서 실행기만 `codekr-exec` 에 두고, 그 네임스페이스만 `privileged` 로 연다
(`executor.namespace` 값). 나머지는 `baseline` 아래 남는다.

경계를 넘는 것은 둘뿐이고 둘 다 최소로 열려 있다.

| 방향 | 허용 범위 |
|---|---|
| 실행기 → Redis | `codekr` 네임스페이스의 redis 파드 6379 **하나**. 인터넷 egress 없음 |
| api → 실행기 | 쿠버네티스 API 의 `deployments/scale`, `codekr-executor` **하나** |

실행기는 DB 자격증명을 받지 않으므로(ADR-0004) 차트도 `codekr-config` 를 통째로
주입하지 않고 큐 주소만 넘긴다.

### 3.3 실행기 egress 차단 (#47)

위 표의 "인터넷 egress 없음"을 **정책으로도 강제한다.** 차트가 `codekr-executor-egress`
NetworkPolicy 를 만들어 DNS(kube-system 53)와 Redis(6379) 외의 나가는 트래픽을 막는다.

**CNI 가 NetworkPolicy 를 지원해야 한다.** 지원하지 않는 CNI(예: 기본 flannel)에서는
이 객체가 만들어지되 아무 효과가 없고, **경고도 나오지 않는다.** 배포 후 한 번은 실제로
막히는지 확인한다.

```bash
kubectl -n codekr-exec exec deploy/codekr-executor -- \
  timeout 5 wget -qO- https://example.com && echo "차단 실패" || echo "차단됨"
```

레지스트리로 나가는 길은 열지 않았다 — 런타임 이미지를 받는 것은 **노드의 컨테이너
런타임**이지 실행기 파드가 아니다. 이미지가 노드에 없으면 채점이 실패하므로 미리
받아 두어야 한다 (#96).

정책을 끄려면 `executor.networkPolicy.enabled=false`. 기본값은 켜짐이다.

## 4. 주소

| 주소 | 용도 | 경로 |
|---|---|---|
| `https://코드.kr` (`xn--hy1by51c.kr`) | **사용자에게 보이는 주소** | Cloudflare Tunnel → 클러스터 |
| `https://codekr.homelab.shinkeonkim.com` | 내부 관리 | Traefik + Tailscale |

둘 다 같은 Ingress 를 가리키고 경로 규칙도 같다. 갈라 두면 "터널로는 되는데 내부로는
안 되는" 차이가 생긴다.

**퓨니코드(`xn--hy1by51c.kr`)로 적는 이유:** Ingress 의 `host` 와 CORS 의 `Origin` 은
아스키만 받는다. 브라우저 주소창에는 `코드.kr` 이 보이지만 실제로 보내는 Host/Origin
헤더는 퓨니코드다. 한글로 적으면 매칭되지 않는다.

> Cloudflare Tunnel 의 public hostname 설정은 `oh-my-homelab` 쪽 작업이다.
> 터널이 붙기 전에는 내부 주소로만 접근한다.

**웹 이미지에는 주소를 박지 않는다.** `NEXT_PUBLIC_*` 은 빌드 시점에 번들로 들어가므로,
주소를 박으면 환경마다 이미지를 따로 빌드해야 하고 같은 이미지를 두 주소로 서비스할 수
없다(한쪽이 CORS 로 막힌다). 비워 두면 브라우저가 **자기가 열린 출처**로 API 를 부르고,
Ingress 가 `/api`·`/ws` 를 api 로 보낸다.

## 5. 배포 절차 — main 에 머지하면 나간다 (#246)

**보통 사람이 하는 단계는 없다.** 머지가 곧 배포다.

배포 경로는 **둘**이고, 의도가 다르다 (#348).

| 경로 | 언제 | 무엇이 다른가 |
|---|---|---|
| **자동** — main 머지 | 늘 | 이미지를 만들고 태그를 적는다 |
| **수동** — Actions → **배포** | 되돌릴 때, CI 가 태그를 못 적었을 때(#248) | **이미지를 만들지 않는다.** 이미 ghcr 에 있는 것을 가리킬 뿐이다 |

수동 배포는 §5.1 에 있다. 아래는 자동 경로다.

```
main 머지
  └─ CI: 테스트 → 이미지 push (:latest 와 :<커밋 sha>)
       └─ CI: deploy/charts/codekr/values-release.yaml 에 그 sha 를 적어 커밋
            └─ ArgoCD: 매니페스트가 바뀌었으므로 sync
                 ├─ PreSync : DB 덤프 (되돌릴 지점)
                 ├─ Sync    : 새 이미지로 교체, api 기동 중 Flyway 마이그레이션
                 └─ PostSync: 배포 후 검증 (기동·문제 목록)
```

**`latest` 가 아니라 커밋 sha 를 매니페스트에 적는 것이 핵심이다.** `latest` 는 새 이미지가
올라가도 매니페스트가 그대로라, ArgoCD 가 계속 "Synced" 라고 말하고 아무 일도 하지 않는다.

### 지금 무엇이 도는가

```bash
# 매니페스트가 가리키는 것
git log -1 --format='%h %s' -- deploy/charts/codekr/values-release.yaml
grep imageTag deploy/charts/codekr/values-release.yaml

# 클러스터가 실제로 도는 것
kubectl -n codekr get deploy codekr-api -o jsonpath='{.spec.template.spec.containers[0].image}'
```

둘이 다르면 sync 가 아직 안 끝났거나 실패한 것이다 (`kubectl -n argocd get application codekr`).

### 처음 켤 때 필요한 것 (한 번만)

`oh-my-homelab` 의 `helm-charts/apps/codekr.yaml` 이 배포 태그 파일을 읽어야 한다.

```yaml
      helm:
        valueFiles:
          - values.yaml
          - $values/helm-charts/values/codekr.yaml
          - values-release.yaml          # ← 이 줄. 마지막이어야 이긴다 (#246)
```

그리고 `helm-charts/values/codekr.yaml` 의 `global.imageTag: latest` 는 지운다 —
남아 있어도 위 파일이 뒤에 와서 이기지만, 두 곳에 적혀 있으면 어느 쪽이 진짜인지 헷갈린다.

## 5.1 되돌리기 (#246)

**되돌릴 것은 두 가지다: 이미지와 스키마.** 대부분은 이미지만 되돌리면 된다.

### 이미지 되돌리기 — Actions 에서 한 줄로 (#348)

**Actions → 배포 → Run workflow.**

| 입력 | |
|---|---|
| 배포할 커밋 sha | **비우면 직전 배포로 되돌린다** — 가장 흔한 경우다 |
| 사유 | **필수다.** 커밋 메시지와 실행 기록에 남는다 |

손으로 `git revert` 하는 것보다 나은 점이 둘 있다.

- **이미지가 있는지 먼저 본다.** 네 앱(api·web·judge·executor) 전부. 없으면 거기서
  멈춘다 — 없는 이미지를 가리키면 클러스터가 **ImagePullBackOff 로 멈춘다.**
  자동 경로에는 `needs: images` 라는 보호가 있지만 손으로 고칠 때는 없었다
- **같은 sha 면 그렇게 말한다.** 아래를 보라

배포 태그 파일의 git 이력은 **여전히 배포 이력이다.** 수동 배포도 같은 파일을 고치고,
커밋 메시지로 구분된다.

```bash
git log --oneline -- deploy/charts/codekr/values-release.yaml
# chore(deploy): a1b2c3d 수동 배포 (#348)     ← 손으로
# chore(deploy): 7e218fb 배포 (#246)          ← 머지로
```

**CI 는 이 커밋으로 다시 돌지 않는다** — 그 파일은 `paths-ignore` 에 있다.

손으로 고치는 옛 방법(`git revert` 또는 sha 직접 수정)도 그대로 동작한다.
Actions 에 닿지 못할 때 쓴다.

### 같은 버전을 다시 미는 것은 이 경로로 안 된다

클러스터가 매니페스트와 어긋나서 **같은 sha 를 다시 밀고 싶은 때**가 있다.
**이 워크플로로는 안 된다.**

```
파일이 안 바뀐다 → 커밋이 없다 → ArgoCD 는 아무것도 하지 않는다
```

그래서 워크플로가 **성공하지 않고 멈춘다.** 조용히 초록이면 사람은 배포된 줄 알고
돌아간다.

그 경우에 할 일은 **ArgoCD 쪽**이다 — Sync(또는 파드 Restart)를 누른다.
워크플로가 대신 눌러 주지 않는 이유는 **클러스터에 닿는 자격증명을 CI 에 두지 않기로**
했기 때문이다 (#246 이 피한 것이다).

### 컬럼을 지운 배포는 그 앞으로 되돌릴 수 없다 (#266)

expand/contract 의 **contract 단계**다. 컬럼을 지우고 나면 그 앞 이미지는 뜨지 못한다 —
옛 엔티티가 없는 컬럼을 매핑하고 Hibernate 가 `ddl-auto: validate` 이기 때문이다.

되돌려야 하면 **스키마까지 되돌린다**(§5.1 의 덤프 복원). 그래서 지우는 마이그레이션은
**여러 개를 한 배포에 묶는다** — 배포마다 하나씩 지우면 그 사이 배포가 전부 "되돌릴 수
없는 배포" 가 된다.

### 리비전 이력은 세 개만 남는다 (#320)

`kubectl rollout undo` 는 **이 저장소의 되돌리기가 아니다.** 위처럼 git 에서 되돌리고,
`rollout undo` 로 되돌려 봐야 ArgoCD 가 selfHeal 로 매니페스트 상태로 되돌려 놓는다.

그래서 워크로드마다 `revisionHistoryLimit: 3` 이다 (`_helpers.tpl` 의
`codekr.revisionHistoryLimit`). 0 이 아닌 이유는 **롤아웃 중 문제가 생겼을 때 손으로
급히 되돌릴 수단**은 남겨 두기 위해서다.

기본값 10 을 두면 빨리 찬다 — 앱 다섯이 하나의 태그를 공유하고 CD 가 머지마다 그
태그를 바꾸므로(#246), 웹만 고친 머지에도 다섯이 전부 새 리비전을 만든다.

| 무엇 | 어디에 | 값 |
|---|---|---|
| Deployment · StatefulSet 의 리비전 이력 | **이 저장소** (`_helpers.tpl`) | 3 |
| 덤프·검증 잡의 정리 | **이 저장소** (`ttlSecondsAfterFinished`) | 86400 (하루) |
| ArgoCD `Application` 의 `revisionHistoryLimit` | **`oh-my-homelab`** | 아직 정하지 않았다 |

**이력은 다음 롤아웃 때 정리된다.** 값을 넣자마자 줄지 않는다.

### 스키마는 어떻게 되나 — 대개 그대로 두면 된다

**옛 코드는 새 스키마에서 돈다.** 확인한 동작이다:

- Flyway 는 "스키마 버전이 로컬 마이그레이션보다 높다" 고 **경고만 하고 통과**한다
  (`Schema "public" has a version (30) that is newer than the latest available migration (29) !`)
- Hibernate `ddl-auto: validate` 는 **더 있는 컬럼·표를 문제 삼지 않는다**

그래서 **마이그레이션을 더하기만 하면**(expand) 이미지를 되돌리는 것으로 롤백이 끝난다.

| 이번 배포에서 하는 것 | 다음 배포에서 하는 것 |
|---|---|
| 컬럼·표 추가, 기본값 있는 NOT NULL, 인덱스 추가 | — |
| 새 컬럼에 쓰기 시작 (옛 컬럼도 함께 채움) | 옛 컬럼 읽기 중단 |
| — | **옛 컬럼 삭제·이름 변경** |

**지우기와 이름 바꾸기는 그것을 쓰지 않는 코드가 이미 배포된 다음에 한다.** 이 규칙을
어긴 배포만이 아래의 덤프 복원을 필요로 한다.

### 스키마까지 되돌려야 할 때 — 덤프 복원

배포 직전 덤프가 NFS(`codekr-db-dumps`)에 남아 있다. **이름이 그 배포의 커밋 sha 다.**

```bash
# 1. 무엇이 있는지 본다
kubectl -n codekr run dumps --rm -it --restart=Never --image=busybox:1.37 \
  --overrides='{"spec":{"containers":[{"name":"c","image":"busybox:1.37","command":["ls","-lht","/dumps"],
  "volumeMounts":[{"name":"d","mountPath":"/dumps"}]}],"volumes":[{"name":"d",
  "persistentVolumeClaim":{"claimName":"codekr-db-dumps"}}]}}'

# 2. 앱을 멈춘다 — 복원 중에 쓰기가 들어오면 안 된다
kubectl -n codekr scale deploy codekr-api codekr-judge codekr-judge-contest --replicas=0

# 3. 복원 (⚠️ 그 덤프 이후에 쌓인 데이터는 사라진다)
#    --clean --if-exists 로 기존 객체를 지우고 덤프 상태로 되돌린다
kubectl -n codekr exec -it codekr-db-1 -- bash -c \
  'pg_restore --clean --if-exists --no-owner --dbname=codekr /dumps/<sha>.dump'

# 4. 이미지도 그 배포 이전으로 되돌린 뒤 앱을 올린다
kubectl -n codekr scale deploy codekr-api codekr-judge codekr-judge-contest --replicas=1
```

**3번은 자동화하지 않는다.** 그 사이에 쌓인 사용자 데이터를 지우는 일이라, 무엇을 잃는지
아는 사람이 판단해야 한다.

> ⚠️ 위 3번은 DB 파드에 덤프 PVC 가 붙어 있어야 한다. 붙어 있지 않으면 덤프 PVC 를 마운트한
> 일회용 파드에서 `pg_restore --host=codekr-db-rw` 로 돌린다.

## 6. 배포 후 검증

**자동으로 도는 것과 사람이 도는 것이 다르다** (#246).

| 언제 | 무엇이 | 실패하면 |
|---|---|---|
| 매 sync 뒤 (PostSync 훅) | api 기동 확인 + 문제 목록 조회 | ArgoCD sync 가 실패로 표시된다 |
| 실행기 파드 기동 때 | 샌드박스 방어 7개 (`selfTestOnStart`) | 파드가 뜨지 않는다 — 앞 버전이 계속 돈다 |
| 사람이 (노드를 바꿨을 때) | `--verify-runtimes`, 채점 흐름 스모크 | 아래 절차 |

실행기 자체 검사를 기동에 붙인 이유: 자동 배포에는 사람이 `--self-test` 를 돌려 보는
단계가 없다. **뚫린 채로 채점을 받는 것보다 파드가 뜨지 않는 편이 낫다.**

아래는 노드를 바꾸거나 의심스러울 때 사람이 도는 절차다.

```bash
# 1. 샌드박스 방어가 이 노드에서도 걸리는지. 여기서 실패하면 배포를 되돌린다.
#    로컬 테스트와 같은 검사 정의를 쓴다 (docs/07 §5).
kubectl -n codekr-exec exec deploy/codekr-executor -- executor --self-test

# 2. 정의 파일의 런타임이 이 노드에서 실제로 도는지 (#218).
#    언어마다 컴파일이 돌아가 몇 분 걸린다.
kubectl -n codekr-exec exec deploy/codekr-executor -- executor --verify-runtimes

# 3. 로그인부터 채점까지 흐름
CODEKR_API=https://codekr.homelab.shinkeonkim.com bash scripts/smoke.sh
```

**1 과 2 는 다른 질문이다.** 1 은 "신뢰할 수 없는 코드가 빠져나가는가"(격리), 2 는
"정의 파일이 가리키는 것이 여기 준비돼 있는가"(준비 상태)다. 2 가 실패했다는 것은
그 언어를 채점할 수 없다는 뜻이지 방어가 뚫렸다는 뜻이 아니다.

`--self-test` 도 정의 파일의 이미지 참조를 쓴다 (#218). 전에는 이미지를 박아 두어서,
정의 파일과 노드가 어긋나 채점이 전부 SYSTEM_ERROR 가 나는 상황에서도 7개 검사가
전부 통과했다 (PR #217). 다만 그 검사는 파이썬 하나만 싣는다 — 나머지 언어의 준비
상태는 2 로 확인한다.

실행기는 기동할 때 런타임에 닿는지 먼저 확인하고, 닿지 못하면 뜨지 않는다. 즉
`codekr-executor` 가 Running 이면 최소한 런타임 연결은 성립한 것이다. 방어가 실제로
걸렸는지는 위 `--self-test` 로 따로 확인해야 한다.

## 6.1 오브젝트 스토리지 (#115)

**홈랩에 띄운 MinIO 를 쓴다. AWS S3 를 쓰지 않는다.** MinIO 가 S3 프로토콜을 말하므로
표준 클라이언트를 그대로 쓸 뿐이고, 데이터는 홈랩 밖으로 나가지 않는다.

`storage.endpoint` 를 채우면 켜진다. 비우면 업로드만 막히고 나머지는 돈다.

```yaml
storage:
  endpoint: http://minio.storage.svc.cluster.local:9000
  bucket: codekr
```

MinIO 자체의 기동은 이 차트가 하지 않는다 — 저장소는 애플리케이션보다 오래 살아야 하고,
릴리스를 지울 때 함께 지워지면 안 된다.

**자격증명은 차트에 두지 않는다.** `storage.secretName` 이 가리키는 시크릿에서 읽는다 —
`values.yaml` 은 저장소에 남는다.

```bash
kubectl -n codekr create secret generic codekr-storage \
  --from-literal=CODEKR_STORAGE_ACCESS_KEY=... \
  --from-literal=CODEKR_STORAGE_SECRET_KEY=...
```

버킷은 **처음 올릴 때 만들어진다.** 미리 만들어 두어도 되고, 그때는 아무 일도 하지 않는다.

### 올릴 수 있는 이미지

| 항목 | 값 |
|---|---|
| 원본 용량 상한 | 5MB — 넘으면 **디코딩하기 전에** 413 |
| 화소 수 상한 | 4천만 — 헤더만 읽고 판단한다 (압축 폭탄 차단) |
| 아바타 | 가운데를 정사각형으로 잘라 256px PNG |
| 본문 첨부 | 비율을 유지한 채 최대 변 1600px, JPEG 품질 80 |

**저장되는 크기는 원본과 무관하다.** 무엇을 올리든 위 규격으로 다시 인코딩하므로,
상한은 저장 용량이 아니라 **디코딩에 쓸 메모리**를 제한하는 값이다.

## 6.2 런타임 이미지 미러링 (#96)

실행 노드가 런타임 이미지를 **자체 레지스트리에서** 받게 한다. 태그는 다시 붙을 수 있어서,
우리가 검증한 것과 다른 것이 노드에 들어갈 수 있다 — 격리가 이미지 내용에 기대는 이 프로젝트에서는
검증 결과의 뜻이 약해진다.

방법은 둘이고, **레지스트리가 sync 를 지원하면 그쪽이 낫다.**

### 자체 빌드 런타임(kotlin·csharp)은 클러스터 안에서 만든다

업스트림이 없으므로 sync 로 가져올 수 없다. buildkit Job 이 클러스터 안에서 만들어
레지스트리에 넣는다 — 매니페스트는 `oh-my-homelab` 에 있다.

**클러스터 안에서 만드는 이유는 아키텍처다.** 실행 노드가 amd64 인데 손으로 만들면 만든
사람의 아키텍처(예: 개발용 맥의 arm64)가 따라온다. 같은 클러스터에서 만들면 그럴 일이 없다.

buildkit 으로 zot 에 밀 때는 **`oci-mediatypes=true` 가 필요하다.** 기본값(Docker 미디어
타입)으로 밀면 매니페스트 PUT 이 `415 Unsupported Media Type` 으로 거절된다.

### (권장) 레지스트리가 당겨오게 한다 — zot sync

zot 의 `extensions.sync` 를 켜면 요청받을 때 업스트림에서 직접 끌어온다. 사람이 미리 밀어
넣을 필요가 없다.

```json
"extensions": { "sync": { "enable": true, "registries": [{
  "urls": ["https://registry-1.docker.io"], "onDemand": true, "pollInterval": "24h",
  "content": [{ "prefix": "/library/*", "destination": "/", "stripPrefix": true,
                "tags": { "regex": "^(3\\.12-alpine|…)$" } }]
}]}}
```

`stripPrefix` 는 **글로브가 있는 prefix 에서만** 쓸 수 있다 (`/library/*`). 업스트림의
`library/python` 을 우리 주소의 `python` 으로 맞추기 위한 것이다 — `runtimes.yaml` 이
짧은 이름을 쓰기 때문이다.

### (대안) 밀어 넣는다 — crane

sync 가 없는 레지스트리에서는 이 방법뿐이다.

```bash
CODEKR_RUNTIME_REGISTRY=registry.example.com make mirror-runtimes ARGS=--pin
```

**앞단에 CDN 이나 리버스 프록시가 있으면 막힐 수 있다.** 홈랩에서 실제로 겪은 것:

| 증상 | 원인 |
|---|---|
| blob `PUT` → 400 | CDN 을 지나는 경로에서 업로드가 깨진다 |
| 큰 레이어 → 502, 레지스트리 로그에 `latency 1m0s` + `unexpected EOF` | 리버스 프록시 기본 read timeout 60초 |

작은 이미지는 올라가고 큰 이미지만 실패하므로, **일부만 미러링된 상태를 눈치채기 어렵다.**

### 다이제스트

`infra/runtimes/runtimes.yaml` 의 `digest` 가 채워져 있으면 실행기가 태그 대신 그것으로 받는다.
공개 이미지 11종은 채워져 있다.

**자체 빌드 런타임(kotlin·csharp)은 비어 있다.** 그 둘은 업스트림이 없고 클러스터 안에서
만들므로, 고정할 값이 만들 때마다 달라진다. 만든 다이제스트를 적어 두려면 빌드 Job 의
출력을 받아 적어야 하는데, 그것은 사람이 확인하고 올리는 편이 낫다 (#171).

다이제스트는 업스트림에서 읽은 값이다. 미러가 매니페스트를 그대로 복사하므로 미러에서도 같은
값이 나온다 — 홈랩 zot 에서 두 이미지로 확인했다.

```
python:3.12-alpine             미러 = 업스트림  sha256:6d43704b…
eclipse-temurin:21-jdk-alpine  미러 = 업스트림  sha256:1ff76308…
```

## 6.3 시드 문제를 운영에 넣는다 (#342)

저장소에 문제 열둘이 있는데(#280·#313) **운영에 넣을 경로가 없었다.**
`make seed` 는 주소가 `localhost` 로 박혀 있고, 데모 계정을 만들고, `docker exec` 로
DB 에 붙는다 — 셋 다 로컬 전제다.

그래서 **계정 준비와 문제 주입을 갈랐다.**

| 스크립트 | 무엇을 하나 | 어디서 |
|---|---|---|
| `scripts/seed.sh` (`make seed`) | 데모 계정을 만들고 → 아래를 부른다 | **로컬만** |
| `scripts/seed-problems.sh` | 문제와 알고리즘 분류를 넣는다 | 로컬·운영 |

**운영에 데모 계정이 만들어지는 길을 옵션이 아니라 구조로 막았다.** 주입 스크립트에는
가입 코드가 아예 없다 — 옵션은 실수로 켜지지만, 없는 코드는 켜지지 않는다.

### 절차

```bash
# 1. 무엇이 들어가는지 먼저 본다. 아무것도 보내지 않는다.
CODEKR_API=https://xn--hy1by51c.kr scripts/seed-problems.sh --dry-run

# 2. 어드민 토큰을 파일로 받는다 (셸 히스토리에 남기지 않는다)
scripts/seed-problems.sh --api https://xn--hy1by51c.kr --token-file ~/.codekr-token
```

**토큰을 인자로는 받지 않는다.** `--token` 이 없는 것은 빠뜨린 것이 아니라 결정이다 —
명령줄 인자는 히스토리에 남고 `ps` 에도 보인다. 환경 변수(`CODEKR_ADMIN_TOKEN`)나
파일로만 받는다. 쓰고 나면 파일을 지운다.

### 알아 둘 것

- **여러 번 돌려도 안전하다.** 이미 있는 문제는 `409` 로 돌아오고 건너뛴다
- **덮어쓰지 않는다.** 운영의 문제는 손으로 고쳐졌을 수 있고, 시드가 그것을 되돌리면
  고친 사람은 이유를 알 수 없다. 고칠 일이면 어드민 화면에서 고친다
- **넣는 순서가 곧 문제 번호다** (#204). 파일 이름으로 정렬해 넣으므로 어디서 돌리든
  같은 순서다 — `--dry-run` 이 그 순서를 그대로 보여 준다
- 하나라도 실패하면 **거기서 멈춘다.** 절반만 들어간 상태로 조용히 끝나지 않는다

### 넣은 뒤

**실제로 채점되는지 한 번 확인한다.** 운영 실행기는 로컬과 다르고, #251 이 "지금까지
채점을 한 번도 안 해 봤을 뿐" 으로 드러난 자리다. 아무 문제나 하나 골라 제출해 보고
`ACCEPTED` 가 나오는지 본다.

## 7. 필요한 시크릿

### ⚠️ 이 저장소는 public 이다

시크릿을 넣을 자리를 고를 때 이것이 첫 번째 사실이다. **한 번 커밋에 들어가면
지워도 소용없다** — 되돌린 커밋도 남고, 그 사이에 누군가 이미 봤다고 보아야 한다.
그래서 **들어가기 전에 막는 것**만이 방법이다.

| 자리 | 어떻게 |
|---|---|
| `deploy/charts/codekr/values.yaml` | **시크릿 이름만** 적는다. 값은 절대 적지 않는다 |
| `.env.example` | 로컬용임이 한눈에 드러나는 값이거나 **빈 값** |
| PR 본문·이슈·커밋 메시지 | 값을 붙여넣지 않는다. "발급했다" 까지만 |
| 셸 히스토리 | `export ...=값` 을 치지 않는다. 파일에서 읽거나 앞에 공백을 둔다 |

값은 전부 **SOPS 로 암호화한 시크릿**(`codekr-secrets`)에만 둔다.

actuator 로는 새지 않는다 — `include` 가 `health,info,metrics,prometheus` 라
`env`·`configprops` 가 열려 있지 않다. **그 둘을 열면 설정값이 그대로 보인다.**

| 키 | 설명 |
|---|---|
| `CODEKR_DB_USERNAME`, `CODEKR_DB_PASSWORD` | CNPG 가 만든 자격증명 |
| `CODEKR_JWT_SECRET` | 32바이트 이상 랜덤 값 |
| `CODEKR_MAIL_USERNAME` | 발송 계정. **발신 주소(`mail.from`)와 같아야 한다** |
| `CODEKR_MAIL_PASSWORD` | 메일 제공자가 발급한 앱 비밀번호 |
| `CODEKR_DRAFT_API_KEY` | 문제 초안 도구의 모델 키 (#230). **없으면 그 기능만 꺼진다** |

### 메일 (#233, #355)

`mail.host` 가 비면 **이메일 인증이 통째로 꺼진 채 뜬다.** 사고가 아니라 설계다 —
보낼 수 없으면 요구하지도 않는다(#115). 켜려면 `values.yaml` 에 host·port·ssl·from 을
주고, 자격증명을 시크릿에 넣는다.

**발신 주소는 "어느 주소로 보이고 싶은가" 가 아니라 "어느 주소로 보낼 수 있는가" 다.**
인증 계정과 다른 주소로 보내면 대개 제공자가 거부하고, 통과하더라도 SPF/DKIM 정렬이
깨져 스팸함으로 간다. `no-reply@` 를 쓰고 싶으면 제공자 쪽에서 그 별칭을 만들고
**발신 권한이 있는지 확인**해야 한다. 없으면 발송 주소는 인증 계정 그대로다.

**465 는 붙자마자 TLS 다.** `ssl: true` 를 켜지 않으면 평문 EHLO 를 보내고 서버는
핸드셰이크를 기다려, 타임아웃까지 매달렸다가 실패한다. 그리고 발송은 예외를 삼키므로
**가입은 성공하고 메일만 조용히 안 간다.**

기동할 때 SMTP 에 한 번 붙어 보고 결과를 남긴다. 배포 뒤 api 로그에서 이 줄을 찾는다:

```
메일 준비됨 host=... port=465 ssl=true
```

없거나 `메일 서버에 붙지 못했습니다` 가 보이면 **켜지지 않은 것이다.**

#### 앱 비밀번호가 샜다면

1. 제공자 관리 화면에서 **그 앱 비밀번호를 폐기**한다. 바꾸는 것이 아니라 폐기다
2. 새로 발급해 SOPS 시크릿을 고치고 배포한다
3. 발송 이력을 확인한다 — 우리 이름으로 나간 메일이 있는지

절차를 모르면 새고도 손을 못 쓴다. **폐기가 먼저다.**

## 8. 남은 것

- **노드에서의 `--self-test`** — 실행기는 두 런타임을 지원한다. 운영 노드는
  `CODEKR_SANDBOX_RUNTIME=containerd` 로 두고, 소켓 경로는 `CONTAINERD_ADDRESS` 로 준다
  (기본 `/run/containerd/containerd.sock`). 소켓에 닿지 못하면 **기동에서 실패한다** —
  조용히 뜬 뒤 제출마다 실패하지 않는다.

  검증은 colima VM 안에서 통과했으나(#68) 노드의 커널·cgroup·LSM 설정은 다를 수 있으므로,
  **노드에서 `executor --self-test` 를 한 번 돌려 7개 검사를 확인하고 배포한다.**

- **런타임 이미지를 노드에 미리 둔다** — 실행기는 이미지가 이미 있으면 레지스트리에 묻지
  않는다 (#171). 미리 받아 두면 제출마다 붙던 레지스트리 왕복이 사라지고, 익명 pull 제한과
  레지스트리 장애가 채점을 멈추지 못한다.

  공식 이미지가 없는 두 런타임(kotlin, csharp)은 노드에서 직접 만들 수도 있다.

  ```bash
  CODEKR_IMAGE_BUILDER=nerdctl sudo -E bash scripts/build-runtimes.sh
  ```

  **빌더를 잘못 고르면 이미지를 못 찾는다.** `docker build` 로 만든 것은 엔진 저장소에
  들어가는데, containerd 구현은 containerd 의 `codekr` 네임스페이스를 본다.

- **비공개 레지스트리의 런타임 이미지** — `executor.runtimeRegistrySecret` 에
  `kubernetes.io/dockerconfigjson` 시크릿 이름을 준다 (#171). 파드 이미지용
  `imagePullSecrets` 와 **다르다** — 그쪽은 kubelet 이 쓰고 실행기에게는 보이지 않는다.
  실행기는 런타임 이미지를 자기가 직접 받으므로 자기 몫이 필요하다.

  ```bash
  kubectl create secret docker-registry codekr-runtime-pull \
    --docker-server=ghcr.io --docker-username=<이름> --docker-password=<토큰> \
    -n <실행기 네임스페이스>
  ```

- **user namespace 재매핑** — `executor.usernsHostOffset` 으로 켠다 (#130, `docs/07` R3).
  켜기 전에 그 UID 구간을 `/etc/subuid`·`/etc/subgid` 에 예약하고, 노드의 커널이 idmapped
  overlayfs 를 지원하는지 확인한다. 켠 채로 `--self-test` 가 통과해야 켠 것으로 친다.
- 관측 연동(Prometheus ServiceMonitor), 백업, 코드.kr 도메인 연결은 클러스터 정책에 맞춰
  후속 작업으로 다룬다.
