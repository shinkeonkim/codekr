# 01. 아키텍처

## 1. 전체 구성

```
                 ┌──────────────────────────────────────────┐
  브라우저  ───▶ │ web (Next.js, Bun)                       │
                 │  - SSR 문제 목록/상세, Monaco 에디터      │
                 └───────────────┬──────────────────────────┘
```

## 2. 컴포넌트 책임

| 컴포넌트 | 책임 | 하지 않는 것 |
|---|---|---|
| **web** | 화면, 입력 검증(1차), 실시간 표시 | 채점 로직, 권한 판단의 최종 근거 |
| **api** | 인증/인가, 도메인 영속화, 큐 발행, 이벤트 중계 | 코드 실행, 샌드박스 관리 |
| **judge** | 채점 워크플로 — 테스트케이스 분해·집계·판정 | 코드 실행, DB 쓰기 |
| **executor** | 코드 1회 실행 — 컴파일/실행/자원 제한/결과 수집 | 정답 비교, 판정 |

**DB 쓰기 주체는 api 하나뿐이다.** judge/executor 는 PostgreSQL 에 접근하지 않는다.
채점 결과는 이벤트로 발행되고, api 가 그것을 받아 영속화한다
([ADR-0004](adr/0004-단일-DB-쓰기-주체.md)).

```

  ├───────────────────▶│                   │                  │                 │

  │ 202 {submissionId} │                   │ XREADGROUP       │                 │
  │◀───────────────────┤                   │◀─────────────────┤                 │
  │                    │                   │                  │                 │

  │                    │                   │                  │                 │ run

  │        ⋮ (테스트케이스 수만큼 반복)        │                  │      ⋮          │
  │                    │                   │ publish COMPLETED│                 │
  │  최종 판정          │ UPDATE submission │◀─────────────────┤                 │
  │◀ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┤                   │                  │                 │
```

### 3.1 큐 설계 (Redis Streams)

| 키 | 타입 | 생산자 | 소비자 | 용도 |
|---|---|---|---|---|
| `codekr:judge` | Stream + consumer group `judge-workers` | api | judge | 채점 작업 |
| `codekr:exec` | Stream + consumer group `exec-workers` | judge | executor | 실행 작업 |
| `codekr:exec:res:{jobId}` | Stream (TTL 300s) | executor | judge | 실행 결과 반환 |
| `codekr:events` | Pub/Sub 채널 | judge | api | 진행 이벤트 |

Consumer group 을 쓰기 때문에 judge/executor 는 **인스턴스를 늘리면 그대로 수평 확장**된다.
같은 메시지는 그룹 내 한 컨슈머에게만 전달된다.

미처리(pending) 메시지는 `XPENDING` 으로 관측 가능하며, 이것이 큐 모니터링 API 의 근거가 된다.

### 3.2 왜 요청/응답을 큐로 하는가

요구사항이 "코드 실행기와 코드 채점기 사이에는 queue 를 통해 통신한다" 로 못박혀 있다.
직접 HTTP 호출이 아니라 큐를 두면:

- executor 인스턴스 주소를 judge 가 알 필요가 없다 (서비스 디스커버리 불필요)
- executor 가 죽어도 작업이 사라지지 않는다 (pending 으로 남아 재처리)
- 실행 워커만 따로 스케일 아웃할 수 있다 (실행이 가장 무거운 자원)

응답은 작업마다 고유한 `codekr:exec:res:{jobId}` 스트림으로 되돌려받는다.
judge 는 그 스트림을 블로킹 read 하며, 타임아웃이 지나면 `SYSTEM_ERROR` 로 종결한다.

## 4. 실시간 전달 경로

judge → `codekr:events` (Pub/Sub) → api 의 구독자 →
(1) 결과 영속화, (2) `/ws/submissions` 로 연결된 세션 중 해당 제출을 구독하는 세션에 push.

api 인스턴스가 여러 개여도 Pub/Sub 는 **모든 구독자에게 브로드캐스트**되므로,
WebSocket 이 어느 인스턴스에 붙어 있든 이벤트가 도달한다.
영속화 중복을 막기 위해 결과 저장은 `(submission_id, testcase_id)` 유니크 제약 +
UPSERT 로 멱등하게 처리한다.

## 5. 샌드박스 실행 모델

executor 는 실행 작업 하나당 컨테이너 하나를 만든다.

```
컨테이너 런타임 실행 옵션
  --network none                 # 네트워크 완전 차단
  --read-only                    # rootfs 읽기 전용
  --tmpfs /tmp:rw,size=64m,noexec-불가(컴파일 산출물 실행 필요시 workdir 별도)
  --memory <limit> --memory-swap <limit>   # swap 비활성 → OOM 즉시 감지
  --cpus 1.0 --pids-limit 128
  --user 10001:10001             # non-root
  --cap-drop ALL --security-opt no-new-privileges
```

- **시간 초과**: 컨테이너에 wall-clock 타임아웃을 걸고 초과 시 강제 종료 → `TIME_LIMIT_EXCEEDED`
- **메모리 초과**: cgroup OOM(exit code 137) 감지 → `MEMORY_LIMIT_EXCEEDED`
- **런타임 에러**: 그 외 비정상 종료 코드 → `RUNTIME_ERROR` (stderr 동봉)
- **컴파일 에러**: 컴파일 단계 실패 → `COMPILE_ERROR`

출력은 크기 상한(기본 64KiB)을 두고 잘라낸다. 무한 출력으로 인한 메모리 고갈을 막는다.

실행기는 OCI 호환 엔진 API 로만 런타임과 이야기한다. 코드에는 특정 런타임 이름을 남기지 않고
`Sandbox` 인터페이스 뒤에 가둔다 — [ADR-0003](adr/0003-샌드박스-런타임.md).

## 6. 런타임 레지스트리

지원 언어/버전은 코드가 아니라 **설정 파일**로 정의한다.

```yaml
runtimes:
  - id: python:3.12
    image: codekr/runtime-python:3.12
    sourceFile: main.py
    run: ["python3", "main.py"]
  - id: cpp:17
    image: codekr/runtime-cpp:13
    sourceFile: main.cpp
    compile: ["g++", "-O2", "-std=c++17", "-o", "main", "main.cpp"]
    run: ["./main"]
```

언어나 버전을 추가하는 일은 이미지 + 항목 한 줄 추가로 끝난다.

## 7. 관측

- api: Spring Boot Actuator (`/actuator/health`, `/actuator/metrics`, `/actuator/prometheus`)
- judge/executor: `/healthz`, `/metrics` (Prometheus 포맷)
- 큐: `GET /api/v1/admin/queues` — 스트림 길이, pending 수, consumer 별 처리량

### 워커가 내보내는 지표 (#678)

**대시보드가 이 이름에 매인다.** 이름을 바꾸면 그래프가 조용히 빈다 — 패널은 그대로
그려지고 선만 사라지므로, 보는 사람은 "채점이 없었나 보다" 로 읽는다. 그래서 이름은
`libs/gocontract/metrics.go` 에 계약으로 둔다.

| 이름 | 종류 | 라벨 | 어디서 |
|---|---|---|---|
| `codekr_judge_verdicts_total` | counter | `verdict`, `runtime` | judge |
| `codekr_judge_duration_seconds` | histogram | `kind` | judge |
| `codekr_exec_duration_seconds` | histogram | `runtime` | executor |
| `codekr_exec_reclaims_total` | counter | `outcome` (`reclaimed`/`dropped`) | executor |

**라벨은 `runtime` 으로 통일한다** — 작업이 실제로 들고 다니는 값이 런타임 id
(`python:3.12`)고, 거기서 "언어" 를 뽑는 것은 잃는 변환이다. 언어별로 보고 싶으면
대시보드에서 `label_replace` 로 자르면 되지만 반대는 못 한다. `runtimes.yaml` 이 25개라
카디널리티는 닫혀 있다. **`problem_id` 는 절대 라벨로 두지 않는다.**

**차선(lane)도 라벨이 아니다.** `judge` 와 `judge-contest` 는 파드가 다르고, PodMonitor 가
`app.kubernetes.io/component` 를 지표에 붙인다(#677). 여기서 또 붙이면 같은 것을 두 곳이
말하게 된다.

> 큐 대기 수와 stale 종결 수는 여기 없다. 둘 다 **api 가 이미 아는 값**이라 채점기가
> 또 세면 같은 수를 세는 곳이 둘이 된다 — 별도 이슈로 api 쪽에 붙인다.

**무엇이 토큰 없이 열려 있는가** (#676). api 에서 인증 없이 닿는 것은 `health`·`info` 와
**`prometheus` 하나뿐**이다. Prometheus 는 토큰을 들고 다니지 않으므로 그렇지 않으면
`up=0` 만 쌓인다. `metrics` 는 열지 않았다 — 긁는 쪽이 읽는 것은 `prometheus` 이고,
열면 클러스터 안 아무 파드나 지표를 읽는다. `env`·`configprops` 는 `exposure.include`
에 애초에 없다.

> 이 선택이 성립하는 근거는 **인그레스가 `/actuator` 를 api 로 보내지 않는다**는 것
> 하나뿐이다. 관리 포트를 따로 두는 길도 있었지만 프로브·Service·시험이 함께 움직여서
> 택하지 않았다. 대신 그 전제를 `scripts/check-ingress-paths.py` 가 CI 에서 지킨다.

## 8. 보안 경계

| 경계 | 통제 |
|---|---|
| 브라우저 → api | JWT 검증, CORS 화이트리스트, 요청 바디 크기 제한, Bean Validation |
| api → DB | JPA 파라미터 바인딩(문자열 연결 금지), 최소 권한 DB 계정 |
| judge → executor | 큐 메시지 스키마 검증, 코드 길이 상한 |
| executor → 런타임 | 네트워크 차단, non-root, 자원 제한, 읽기 전용 FS |
| 히든 테스트케이스 | 공개 API 응답에서 항상 제외 (DTO 수준에서 차단) |

## 실행 큐도 차선으로 나눈다 (#639)

**채점기만 나누는 것으로는 부족했다.** 대회 전용 채점기(#62)와 전용 큐가 있어도 그 뒤의
실행 큐가 한 벌이라, 평소 제출이 몰리면 대회도 함께 밀렸다.

```
                  ┌── codekr:judge:high ──┐
api ── 제출 ──────┼── codekr:judge:normal ┼─ judge(일반) ──→ codekr:exec:general ──┐
                  ├── codekr:judge:low ───┘                                        ├─ executor
                  └── codekr:judge:contest ─ judge-contest ─→ codekr:exec:contest ─┘  (대회부터 읽는다)
```

**어느 실행 큐에 넣을지는 채점기 프로세스가 정한다.** 대회 채점기
(`CODEKR_JUDGE_LANE=contest`)는 대회 큐로, 일반 채점기는 일반 큐로 보낸다 — 메시지 안의
값이 아니라 **보내는 쪽이 누구인가**로 갈리므로 조작할 자리가 없다. 채점 큐(#102)가
등급을 스트림에 둔 것과 같은 이유다.

**전용 실행기를 따로 두지 않았다.** 대회가 없는 동안 그 실행기가 놀고, 있는 동안에는
나머지가 논다. 우선순위로 두면 대회가 없을 때 모든 실행기가 평소 제출을 처리한다.

**굶주림은 채점기와 같은 방식으로 막는다** — 20번에 한 번은 평소부터 읽는다. 대회는
몇 시간씩 이어지므로 "잠깐이면 괜찮다" 가 성립하지 않는다.

**옛 큐(`codekr:exec`)를 계속 읽는다.** 배포는 파드마다 굴러가므로 그 사이에 옛 채점기가
거기로 넣는 순간이 있다 — 안 읽으면 그 제출은 응답을 못 받고 시스템 오류가 된다.

실측(같은 순간·같은 부하): **대회 중앙 2.6초 · 평소 중앙 5.3초.**
