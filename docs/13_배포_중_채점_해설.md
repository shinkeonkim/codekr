# 13. 배포해도 채점을 잃지 않는 법 — 처음부터 끝까지

이 문서는 **#415 를 왜 그렇게 고쳤는지를 처음부터 설명하는 해설서**다.

- [이슈 #415](https://github.com/shinkeonkim/codekr/issues/415) 와 [PR #441](https://github.com/shinkeonkim/codekr/pull/441) 은 **결과**를 적는다 — 무엇이 문제였고 무엇을 바꿨는지의 목록이다.
- 이 문서는 그 목록을 **읽을 수 있게** 만든다. Go 를 몰라도, Redis Streams 를 처음
  들어도, 쿠버네티스가 파드를 어떻게 죽이는지 몰라도 순서대로 읽으면 이해되도록 썼다.

읽는 순서는 **쉬운 것 → 어려운 것**이다. 1~3장은 배경이고, 4장부터가 실제로 고친 것이다.

## 1. 무슨 일이 일어났나

### 1.1 증상 한 줄

**배포할 때마다, 그 순간 채점 중이던 제출이 `SYSTEM_ERROR` 로 끝났다.**

사용자 입장에서는 이렇다. 코드를 제출했다. 화면에 "채점 중" 이 떴다. 3분쯤 기다렸다.
그런데 결과가 **"시스템 오류"** 다. 자기 코드에는 아무 문제가 없다.

### 1.2 왜 이것이 심각한가

이 서비스에서 **판정은 기록으로 남는다.** 그 위에 정답률이 쌓이고(#84), 랭킹 점수가
쌓이고(#57), 스트릭이 쌓인다(#36).

`SYSTEM_ERROR` 는 "맞았다" 도 "틀렸다" 도 아니라서 점수에는 안 들어가지만,
**사용자가 잃는 것은 신뢰다.** "이 사이트는 가끔 이유 없이 실패한다" 가 한 번 박히면
다음부터는 자기 코드를 의심하지 않는다.

### 1.3 왜 아무도 몰랐나

**제출이 0건이었기 때문이다.** 아직 운영을 시작하기 전이라 배포할 때 채점 중인
제출이 없었다. 결함은 처음부터 있었고 **아직 물지 않았을 뿐**이었다.

그래서 이 이슈를 지금 한 것이다 — 잃은 제출도 없고, 정리할 찌꺼기도 없다.

## 2. 알아야 할 개념 세 가지

이 세 가지를 알면 3장부터가 전부 이해된다.

### 2.1 SIGTERM — "그만 하세요" 이지 "지금 멈춰" 가 아니다

쿠버네티스가 파드를 지울 때 프로세스를 곧바로 죽이지 않는다. 먼저 **신호**를 보낸다.

```
쿠버네티스: "SIGTERM. 정리하고 나가세요."
              ↓  (기다린다 — 기본 30초)
프로세스:   (정리를 마치고 스스로 끝나면 여기서 끝)
              ↓  (기다려도 안 끝나면)
쿠버네티스: "SIGKILL." → 프로세스가 그 자리에서 사라진다
```

**SIGTERM 의 뜻은 "새 일을 그만 받아라" 이지 "하던 일을 끊어라" 가 아니다.**
이 문장이 이 문서 전체의 핵심이다. 우리 코드는 그것을 반대로 알아들었다.

### 2.2 컨텍스트(context) — Go 에서 "그만" 을 전달하는 방법

Go 에서는 "이 작업 그만해라" 를 **`context`** 라는 물건으로 전달한다.

리모컨 하나를 여러 사람이 나눠 갖고 있다고 생각하면 된다. 누가 버튼을 누르면
**그 리모컨을 든 모두가 동시에 "그만" 을 안다.**

```go
ctx, cancel := context.WithCancel(...)
// ... 이 ctx 를 채점에도 넘기고, DB 호출에도 넘기고, Redis 호출에도 넘긴다

cancel()   // 버튼. 이 순간 ctx 를 받은 모든 곳이 멈춘다
```

편리한데, **그래서 위험하다.** 리모컨 하나를 너무 많은 곳에 나눠 주면
"새 일 그만 받기" 를 누르려다 **"하던 일도 멈춤" 까지 눌러 버린다.**

### 2.3 Redis Streams 와 PEL — 읽어 간 일은 손을 들어야 지워진다

채점 큐는 Redis Streams 로 되어 있다(ADR-0002). 동작이 우체통과 비슷하다.

```
① 채점기가 큐에서 일을 하나 꺼낸다 (XReadGroup)
      ↓
   Redis: "너한테 줬다" 고 적어 둔다  ←── 이 목록이 PEL
      ↓
② 채점기가 채점을 끝낸다
      ↓
③ 채점기가 "다 했어요" 라고 손을 든다 (XACK)
      ↓
   Redis: PEL 에서 지운다. 이제 끝
```

**PEL** (Pending Entries List) = "줬는데 아직 다 했다는 말을 못 들은 일" 의 목록이다.

이 구조가 좋은 이유: ②에서 채점기가 죽어도 **일이 사라지지 않는다.** PEL 에 남아 있다.
누군가 되찾아 가면 된다.

이 구조가 위험한 이유: **아무도 되찾지 않으면 영원히 거기 있는다.**

#### 소비자 이름이 파드 이름이다

Redis 는 "누구에게 줬는지" 를 **소비자 이름**으로 기록한다. 우리는 그 이름을
**파드 이름**으로 쓴다 (`codekr-judge-7d9f8b-xk2p9` 같은 것).

파드 이름은 배포할 때마다 새로 만들어진다. 그래서 —

> **배포하면 그 소비자 이름은 영영 돌아오지 않는다.**
> 그 이름 앞으로 남은 PEL 은 스스로는 절대 정리되지 않는다.

## 3. 왜 끊겼나 — 고리 세 개가 이어져 있었다

이제 사고를 순서대로 볼 수 있다. **하나가 아니라 세 개가 이어져서** 일어났다.

### 3.1 첫째 고리 — 종료 신호가 채점을 끊었다

채점기는 SIGTERM 을 받으면 `ctx` 의 버튼을 눌렀다. 그런데 **그 `ctx` 를 채점에도
넘기고 있었다.**

```
SIGTERM → cancel() → 큐 읽기가 멈춘다     ← 이건 의도한 것
                   → 진행 중인 채점도 멈춘다  ← 이건 사고
```

2.1 에서 말한 그대로다. "새 일 그만 받기" 를 누르려다 하던 일까지 껐다.

### 3.2 둘째 고리 — 손을 들 수 없었다

채점이 끊긴 뒤, 코드는 그래도 `XACK` 을 부르려 했다. **그런데 그 `XACK` 도 같은
`ctx` 를 쓰고 있었다.**

이미 눌린 리모컨을 든 호출은 **시작조차 못 한다.** Go 가 "이 ctx 는 이미 취소됐다" 며
곧바로 거절한다.

```
채점 끊김 → XACK 시도 → ctx 가 이미 취소됨 → 거절
                                          ↓
                          메시지가 PEL 에 남는다
```

### 3.3 셋째 고리 — 되찾는 사람이 없었다

PEL 에 남았어도 **누군가 되찾으면** 다시 채점되고 끝날 일이었다.
그런데 그 코드가 없었다. 그리고 2.3 에서 본 대로 **소비자 이름이 파드 이름**이라
그 파드는 영영 안 돌아온다.

### 3.4 그래서 마지막에 무슨 일이

API 에는 안전망이 하나 있다 — `StaleSubmissionSweeper`. **3분 넘게 "채점 중" 인 제출을
`SYSTEM_ERROR` 로 확정하는 장치**다. 원래 목적은 **멈춘 화면을 막는 것**이다.
결과가 영영 안 오면 사용자는 그 화면을 계속 보고 있어야 하니까.

그 장치가 제 할 일을 했다. 3분 뒤 그 제출을 `SYSTEM_ERROR` 로 끝냈다.

```
배포 → 채점 끊김 → ack 실패 → PEL 에 남음 → 아무도 안 되찾음
                                              ↓ (3분)
                                    SYSTEM_ERROR 로 확정
```

**어느 한 곳도 "버그" 라고 부르기 애매하다.** 각자는 합리적으로 동작했다.
셋이 이어졌을 때만 사고가 된다.

## 4. 고침 1 — 시계를 둘로 나눈다

### 4.1 생각

3.1 의 문제는 **리모컨이 하나뿐**이었다는 것이다. 그러면 두 개로 나누면 된다.

| 리모컨 | 무엇을 멈추나 | 언제 눌리나 |
|---|---|---|
| **읽는 ctx** | 큐에서 새 일을 꺼내는 것 | SIGTERM 이 오는 즉시 |
| **일하는 ctx** | 채점 자체와 ack | **유예 시간이 다 지난 뒤에만** |

### 4.2 코드로는

```go
// 일하는 ctx 는 읽는 ctx 의 취소를 물려받지 않는다.
workCtx, stopWork := context.WithCancel(context.WithoutCancel(ctx))
```

`context.WithoutCancel` 이 핵심이다. **"부모가 취소돼도 나는 안 따라간다"** 는 뜻이다.
그래서 SIGTERM 이 와도 `workCtx` 는 살아 있다.

### 4.3 그래도 상한은 둔다

영원히 기다릴 수는 없다. 어차피 유예 시간이 지나면 쿠버네티스가 SIGKILL 로 끊는다.
**그럴 바에는 그 전에 스스로 정리하는 편이 낫다.**

```go
go func() {
    <-ctx.Done()                              // 종료 신호를 기다린다
    log.Info("종료 신호를 받았습니다. 하던 채점을 마치는 중입니다")
    select {
    case <-time.After(drain):                 // 유예 시간이 다 지났다
        log.Warn("유예 시간이 지나 남은 채점을 끊습니다")
        stopWork()                            // 이제야 일하는 ctx 를 끈다
    case <-workCtx.Done():                    // 그 전에 다 끝났다
    }
}()
```

읽어 보면 그대로다 — **"종료 신호가 오면 로그를 남기고, 유예 시간만큼 기다렸다가,
그때도 안 끝났으면 끊는다."**

### 4.4 루프마다 ctx 가 또 있다

한 가지 더 있다. 채점기는 **워커 여러 개**를 동시에 돌린다(#390 으로 그 수를 살아 있는
채 바꿀 수 있게 됐다). 그래서 ctx 가 실제로는 셋이다.

```
읽는 ctx (종료 신호)
   └─ 루프 ctx (워커 하나를 줄일 때)   ← 큐 읽기를 멈춘다
일하는 ctx (유예 뒤에만)                ← 채점과 ack
```

워커 수를 줄일 때도 같은 원칙이 적용된다 — **줄이라는 신호는 "지금 처리 중인 것을
끝낸 뒤" 빠져나가게 한다.** 하던 채점을 끊지 않는다.

## 5. 고침 2 — 손 흔드는 것은 끊기면 안 된다

3.2 의 문제다. `XACK` 은 **종료 중에도 반드시 나가야 하는 호출**이다.
"다 했어요" 를 말하지 못하면 PEL 에 남는다.

```go
func (c *Consumer) ack(ctx context.Context, stream, id string) {
    // 취소되지 않는 ctx 로 하되, 영원히 매달리지는 않게 5초를 준다.
    ackCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), ackTimeout)
    defer cancel()
    if err := c.redis.XAck(ackCtx, stream, contract.GroupJudge, id).Err(); err != nil {
        c.log.Error("ack 실패", ...)
    }
}
```

두 가지가 같이 들어 있다.

- **`WithoutCancel`** — 종료 신호에 안 끊긴다
- **`WithTimeout(5초)`** — 그렇다고 영원히 매달리지도 않는다. Redis 가 안 받으면 포기한다

포기하면 어떻게 되나? **6장이 되찾는다.** 그래서 여기서는 로그만 남기고 넘어가도 된다.

## 6. 고침 3 — 죽은 사람이 들고 간 일을 되찾는다

### 6.1 왜 4·5장으로 부족한가

4·5장을 다 갖춰도 **프로세스가 강제로 죽는 경우**가 남는다.

- **OOM** — 메모리를 다 써서 커널이 죽인다. 신호도 없다
- **노드 장애** — 서버가 그냥 꺼진다
- **유예 시간 초과** — 90초 안에 안 끝나면 SIGKILL

이때는 정리할 기회 자체가 없다. **PEL 에 남고, 그 파드 이름은 안 돌아온다.**

### 6.2 Redis 가 주는 도구 둘

Redis Streams 에는 정확히 이 상황을 위한 명령이 있다.

| 명령 | 무엇 |
|---|---|
| `XPENDING` | "PEL 에 뭐가 남았니? **얼마나 오래 놀고 있니?**" |
| `XCLAIM` | "그거 내가 가져갈게" |

**"얼마나 오래 놀고 있니"(idle)** 가 핵심이다. 이 값으로 **죽은 것과 일하는 중인 것을
구분**한다.

### 6.3 되찾는 흐름

채점기는 **1분마다** 이렇게 한다.

```
① XPENDING — "10분 넘게 놀고 있는 것 있니?"  (한 번에 최대 10개)
      ↓  있다
② 배달 횟수가 3을 넘었나?
      ├─ 넘었다 → 포기하고 ack 한다 (7장)
      └─ 아니다 ↓
③ XCLAIM — 내 이름으로 가져온다
      ↓
④ 다시 채점하고 ack 한다
```

### 6.4 10분이라는 숫자는 어디서 왔나

**이 값이 이 장에서 가장 조심스러운 부분이다.**

너무 짧으면 무슨 일이 생기나? **멀쩡히 일하고 있는 워커의 작업을 빼앗는다.**
그러면 같은 제출을 두 워커가 동시에 채점한다.

> **10분은 "채점 한 건이 걸릴 수 있는 시간" 보다 넉넉히 길어야 한다.**

문제마다 시간 제한이 다르고(#97), 테스트케이스가 여러 개고, 컴파일 시간도 있다.
그래도 한 건이 10분을 넘기지는 않는다. 넉넉히 잡은 값이다.

### 6.5 3분 안전망은 왜 그대로 두었나

여기서 궁금해진다. `StaleSubmissionSweeper` 가 **3분**에 `SYSTEM_ERROR` 로 끝내는데,
회수는 **10분**에 온다. 그러면 3분에 실패로 확정되고 나서 10분에 다시 채점되는 것 아닌가?

**그렇다. 그리고 그것이 의도다.**

두 장치의 목적이 다르기 때문이다.

| 장치 | 목적 | 시간 |
|---|---|---|
| `StaleSubmissionSweeper` (3분) | **멈춘 화면을 막는다** | 짧아야 한다 |
| 회수 (10분) | **판정을 되찾는다** | 안전해야 한다 |

그래서 순서는 이렇게 된다.

```
0분   제출 → 채점기가 물어 감 → 파드가 죽음
3분   화면: "채점 중" → "시스템 오류"     ← 사용자가 멈춘 화면에서 풀려난다
10분  회수가 다시 채점 → 판정을 덮어쓴다   ← 진짜 결과가 들어온다
```

사용자는 3분 뒤 "시스템 오류" 를 잠깐 보지만, **10분 뒤에는 진짜 판정으로 바뀐다.**
`SYSTEM_ERROR` 인 채로 영원히 남는 것보다 낫다.

## 7. 고침 4 — 세 번까지만 다시 해 본다

### 7.1 무한 재시도의 위험

6장을 그대로 두면 문제가 하나 생긴다. **정말로 채점기를 죽이는 제출**이 있다면?

```
채점기가 그 제출을 물어 감 → 채점기가 죽음 → PEL 에 남음
   → 10분 뒤 회수 → 다시 물어 감 → 또 죽음 → ...
```

**영원히 돈다.** 그리고 도는 동안 그 채점기의 자리 하나가 계속 막힌다.

### 7.2 배달 횟수로 센다

Redis 가 이것도 세어 준다. `XPENDING` 이 돌려주는 `RetryCount` 가 **"이 메시지가 몇 번
배달됐는지"** 다.

```go
if entry.RetryCount > maxDeliveries {   // maxDeliveries = 3
    c.log.Error("여러 번 실패한 채점 작업을 포기합니다", ...)
    c.ack(workCtx, stream, entry.ID)    // 포기하고 ack — PEL 에서 지운다
    continue
}
```

포기하면 그 제출은 어떻게 되나? **API 의 3분 안전망이 `SYSTEM_ERROR` 로 끝낸다.**
그리고 **로그가 어느 제출이었는지 말한다** — 사람이 찾아볼 수 있다.

이것이 맞는 결말이다. 정말 시스템 오류이기 때문이다.

---

## 8. 파드가 기다려 주어야 한다

### 8.1 앱만 고쳐서는 안 된다

4장에서 "유예 시간(drain) 동안 하던 채점을 끝낸다" 고 했다. 그런데 **쿠버네티스가
그만큼 기다려 주지 않으면** 아무 소용이 없다.

기본값이 **30초**다. 채점 한 건도 못 끝낸다.

### 8.2 두 값의 관계

```
프로세스가 쓰는 시간 (drainSeconds)         90초
파드가 기다리는 시간 (terminationGrace)    120초
                                          ────
                                          여유 30초
```

**파드가 기다리는 시간이 더 길어야 한다.** 그래야 프로세스가 스스로 정리를 마칠 수 있다.
반대면 정리하는 도중에 SIGKILL 이 온다.

차트가 그 관계를 강제한다 — 한쪽만 고치는 실수를 막는다.

```
{{- define "codekr.terminationGrace" -}}
terminationGracePeriodSeconds: {{ add .Values.workers.drainSeconds 30 }}
{{- end }}
```

`values.yaml` 에서 고치는 값은 **하나뿐**이다.

```yaml
workers:
  drainSeconds: 90
```

### 8.3 왜 90초인가

**길수록 안전하지만 배포가 그만큼 느려진다.** 그리고 이 저장소는 앱 다섯이
`global.imageTag` 하나를 공유해서 **머지 한 번에 다섯이 함께 뜬다**(#320).
유예가 길면 그 다섯이 다 그만큼 기다린다.

그래서 기준은 이것이다 — **"채점 한 건의 최대 시간" 을 넘겨 잡을 이유는 없다.**

## 9. 시간표 — 배포하면 무슨 일이 순서대로 일어나는가

지금까지의 것을 한 장으로 모으면 이렇다.

```
0초    ArgoCD 가 새 파드를 띄우고 옛 파드에 SIGTERM 을 보낸다
       │
       ├─ 읽는 ctx 취소   → 큐에서 새 일을 안 꺼낸다
       │                    회수 루프도 멈춘다 (새로 물어 오는 일이니까)
       │
       └─ 일하는 ctx 살아 있음 → 진행 중인 채점 계속

0~90초 하던 채점을 끝낸다 → ack 한다 (취소 안 되는 ctx 라 나간다)
       전부 끝나면 프로세스가 스스로 종료 → 여기서 깨끗하게 끝
       │
90초   (아직 안 끝났으면) 일하는 ctx 를 끊는다
120초  쿠버네티스가 SIGKILL
       │
       └─ 못 끝낸 것이 PEL 에 남는다
              ↓
3분    API 안전망: 화면을 SYSTEM_ERROR 로 푼다
              ↓
10분   새 파드의 회수 루프가 XPENDING 으로 찾아낸다
       → XCLAIM 으로 가져와 다시 채점 → 판정을 덮어쓴다
```

**대부분의 배포는 90초 안에 끝난다.** 아래쪽 경로는 OOM·노드 장애처럼
정리할 기회가 없었던 경우를 위한 것이다.

---

## 10. 같은 제출을 두 번 채점해도 왜 안전한가

### 10.1 두 번 채점될 수 있는 경우

6장의 회수에는 이런 경우가 숨어 있다.

> 채점은 다 끝났는데 **ack 만 실패**했다. 그러면 PEL 에 남고, 10분 뒤 회수가
> 그 작업을 다시 가져와 **또 채점한다.**

판정이 두 번 쓰인다. 괜찮은가?

### 10.2 괜찮다 — 세 가지 이유

**첫째, 같은 결과가 다시 쓰일 뿐이다.** `JudgeResultRecorder` 는 판정을 **덮어쓴다.**
같은 코드를 같은 테스트케이스로 채점하면 같은 답이 나온다.

**둘째, 점수는 최초 1회만 오른다.** 랭킹 점수(#85)는 `user_problem_scores` 가
**사용자 × 푼 문제 = 1행**이다. 이미 있으면 다시 안 더한다.

**셋째, 문제 통계는 증분이 아니다.** 정답률(#205)은 "맞은 수를 1 더한다" 가 아니라
**다시 센다.** 두 번 세도 같은 값이다.

### 10.3 이것을 부르는 이름

이런 성질을 **멱등(idempotent)** 이라고 한다 — **몇 번을 해도 결과가 같은 것.**

회수 같은 장치는 **멱등이 아닌 시스템 위에서는 만들 수 없다.** 다행히 이 저장소는
그렇게 되어 있었다. 설계할 때 의도한 것은 아니었지만, 결과적으로 이 고침을
가능하게 했다.

> 되찾기를 만들기 전에 **"두 번 해도 되는가" 를 먼저 확인해야 한다.**
> 안 되면 되찾기가 아니라 중복 방지 장치부터 만들어야 한다.

## 11. 어떻게 "확인" 했는가

### 11.1 진짜 검증은 못 했다 — 그것부터 적는다

이슈가 이렇게 적었다.

> **일부러 배포 중에 제출해 보는 것이 유일한 검증이다.**

그것이 맞다. 그리고 **그것을 하지 못했다** — 클러스터에 접근할 수 없었다.

대신 **miniredis**(메모리에서 도는 Redis 구현) 위에서 같은 상황을 만들었다.
가짜 객체가 아니라 **실제 스트림과 실제 PEL** 로 돈다.

### 11.2 네 가지 시험

| 시험 | 무엇을 막는가 |
|---|---|
| `TestShutdownFinishesRunningJudge` | 종료 중에도 채점이 끝까지 가고 **PEL 이 비는가** |
| `TestShutdownCutsAfterDrain` | 유예에도 **끝이 있는가** |
| `TestReclaimsAbandonedJob` | 죽은 파드가 놓고 간 작업을 **다시 채점하는가** |
| `TestReclaimGivesUpAfterTooManyDeliveries` | 상한을 넘기면 **포기하고 ack 하는가** |

### 11.3 시험이 진짜로 잡는지 확인했다

시험을 쓰고 나면 **"이 시험이 정말 무언가를 막는가"** 를 확인해야 한다.
통과만 하는 시험은 아무것도 안 지킨다.

그래서 일부러 **고침을 되돌려 봤다** — 일하는 ctx 를 종료 신호에 다시 묶었다.
첫 시험이 **"하던 채점이 끊겼습니다"** 로 잡았다.

### 11.4 miniredis 의 한계도 적어 둔다

**miniredis 는 PEL 의 idle 시간을 세지 않는다** (항상 0). 그래서 회수 시험은
임계값을 0 으로 두고 **"회수한 뒤 다시 채점하고 ack 하는가" 만** 본다.

즉 **10분이라는 값 자체는 시험이 아니라 6.4 의 근거로 정했다.**

## 12. 아직 안 막은 것

정직하게 남긴다.

### 12.1 대회 중 배포

이 고침으로 배포가 채점을 끊지 않게 됐다. 하지만 **90초 안에 못 끝내는 채점**이 있으면
여전히 끊긴다. 대회 중이라면 그것이 그대로 사고다.

**대회 중 배포를 막는 것은 별도 문제**라 이 PR 에서 손대지 않았다.

### 12.2 PEL 크기가 화면에 없다

큐 모니터링(#13)에 "지금 PEL 에 몇 개 남아 있는가" 가 없다.
**회수가 자동으로 도니까 막히지는 않는다.** 필요해지면 그때가 붙일 자리다.

### 12.3 실행기도 같은 구조다

같은 문제를 실행기도 갖고 있었고 같은 방식으로 고쳤다. 다만 **실행기는 채점기가
직접 부르는 쪽**이라 성격이 조금 다르다 — 이 문서는 채점기를 기준으로 썼다.

## 13. 용어 사전

| 말 | 뜻 |
|---|---|
| **SIGTERM** | "정리하고 나가라" 는 신호. 무시할 수 있고, 기다려 준다 |
| **SIGKILL** | "지금 죽어라". 무시할 수 없고, 정리할 기회도 없다 |
| **유예 종료 (graceful shutdown)** | SIGTERM 을 받고 하던 일을 마친 뒤 스스로 끝나는 것 |
| **terminationGracePeriodSeconds** | 쿠버네티스가 SIGTERM 뒤 SIGKILL 까지 기다리는 시간 |
| **드레인 (drain)** | 새 일을 안 받고 하던 일만 빼내는 것. 여기서는 90초 |
| **context** | Go 에서 "그만" 을 전달하는 물건. 리모컨 |
| **WithoutCancel** | "부모가 취소돼도 나는 안 따라간다" 는 context |
| **Redis Streams** | 큐. 읽어 간 메시지를 ack 할 때까지 들고 있는다 |
| **PEL** | Pending Entries List. "줬는데 다 했다는 말을 못 들은" 목록 |
| **XACK** | "다 했어요". PEL 에서 지운다 |
| **XPENDING** | "PEL 에 뭐가 남았니, 얼마나 놀고 있니" |
| **XCLAIM** | "그거 내가 가져갈게" |
| **소비자 이름** | Redis 가 "누구에게 줬는지" 기록하는 이름. 우리는 파드 이름을 쓴다 |
| **배달 횟수 (RetryCount)** | 그 메시지가 몇 번 배달됐는지. 3을 넘으면 포기한다 |
| **멱등 (idempotent)** | 몇 번을 해도 결과가 같은 것. 되찾기의 전제 |
