# 06. 실행 제약 계약

문제마다 정한 시간·메모리 제한이 **어드민 입력부터 샌드박스 실행까지** 값이 바뀌거나
누락되지 않고 전달되는지, 어디서 강제되는지를 정리한다.

## 1. 값이 흐르는 경로

```
어드민 입력            api                     Redis            judge          executor        샌드박스
POST /admin/problems   Bean Validation
{timeLimitMs,          허용 범위 검사
 memoryLimitMb}   ──▶  problems 테이블
                       (time_limit_ms,
                        memory_limit_mb)
                            │
                            │ 제출/실행 시 문제에서 읽어 메시지에 싣는다
                            ▼
                       JudgeJobMessage ──▶ codekr:judge ──▶ JudgeJob
                       ExecJobMessage  ──▶ codekr:exec  ─────────────▶ ExecJob
                                                                        │ ValidateLimits
                                                                        ▼
                                                                  Sandbox.Spec
                                                                  ├ TimeLimitMs   → timeout -k 1 <초>
                                                                  └ MemoryLimitMb → cgroup memory/swap
```

**단일 출처는 문제다.** 실행(`/run`)과 채점(`/submissions`) 모두 문제를 읽어 같은 값을
싣는다. 클라이언트가 보낸 제한 값은 어디서도 받지 않는다 — 사용자가 자기 제출의 시간
제한을 늘릴 수 있으면 안 되기 때문이다.

### 런타임별 오버라이드 (#97)

언어마다 속도가 다르다. C++ 로 200ms 에 도는 풀이가 Python 으로는 2초가 걸린다.
문제 제한 하나로 모든 언어를 재면 한쪽은 아예 못 풀고 다른 쪽은 틀린 풀이도 통과한다.

```
problems (기본)  +  problem_runtime_limits (예외만)
        │                      │
        └──────┬───────────────┘
               ▼
      Problem.limitsFor(runtimeId)   ← 제출·실행·정답 검증이 모두 여기를 지난다
```

- `problem_runtime_limits` 에 **행이 없으면 문제 기본값**을 쓴다. 이 표는 예외만 담는다 —
  모든 문제 × 모든 런타임을 채우면 런타임이 하나 늘 때마다 전부 손봐야 한다
- 오버라이드도 **같은 허용 범위** 검사를 받는다. 범위를 벗어나면 실행기가 거부하는 값을
  어드민이 저장할 수 있게 된다
- 런타임 id 가 `언어:버전`(`python:3.13`)이므로 **언어별과 버전별이 같은 장치로 해결**된다
- 런타임별 제한은 정답 코드 검증 지문(`verificationSignature`)에도 들어간다.
  제한이 바뀌면 판정이 바뀌므로, 빠뜨리면 검증이 낡지 않은 것으로 남는다

## 2. 허용 범위와 기본값

| 항목 | 최소 | 최대 | 기본값 | 단위 |
|---|---|---|---|---|
| 시간 제한 | 100 | 30,000 | 2,000 | 밀리초 (ms) |
| 메모리 제한 | 16 | 2,048 | 256 | 메가바이트 (MB) |

같은 숫자가 두 언어에 존재한다.

- Kotlin: `codekr.api.problem.entity.ExecutionLimits`
- Go: `libs/gocontract/limits.go`

두 값이 갈라지면 api 가 받아들인 문제가 실행 직전에 거부되는, 찾기 어려운 고장이 난다.
그래서 **테스트가 두 파일의 숫자가 같은지 확인한다** (`QueueContractTest`).

## 3. 어디서 거부되는가

| 지점 | 검사 | 실패 시 |
|---|---|---|
| 어드민 문제 등록/수정 | Bean Validation (`@Min`/`@Max`) | 400 `VALIDATION_ERROR` + 필드 오류 |
| DB | `CHECK (difficulty_level BETWEEN 1 AND 30)` 등 컬럼 제약 | 저장 실패 |
| judge | `contract.ValidateLimits` | 테스트케이스를 하나도 실행하지 않고 `SYSTEM_ERROR` 로 종결 |
| executor | `contract.ValidateLimits` | 해당 실행만 `SYSTEM_ERROR` |

큐 메시지를 **신뢰할 수 없는 입력으로 다룬다.** 발행자(api)가 이미 검사했더라도,
버전이 다른 발행자나 손상된 메시지가 그대로 샌드박스 설정이 되면
컨테이너가 만들어지지 않거나(메모리 0) 워커가 오래 붙잡힌다.

judge 가 먼저 걸러내는 이유는, 그러지 않으면 테스트케이스 수만큼 같은 오류를 반복하기 때문이다.

## 4. 컴파일 자원은 문제의 제한과 분리한다

**결정:** 컴파일 단계와 실행 단계의 **시간과 메모리를 모두** 분리한다.

| | 실행 단계 | 컴파일 단계 |
|---|---|---|
| 시간 | 문제별 `timeLimitMs` | `EXECUTOR_COMPILE_TIMEOUT_MS` (기본 15초) |
| 메모리 | 문제별 `memoryLimitMb` | `EXECUTOR_COMPILE_MEMORY_MB` (기본 1024MB) |

**근거:** 컴파일에 드는 자원은 문제의 난이도가 아니라 툴체인이 정한다. `go build` 하나가
수백 MB 를 쓰기 때문에, 문제의 메모리 제한을 컴파일에까지 적용하면 **"256MB 문제"는 Go 로
아예 풀 수 없다.** 시간도 마찬가지다 — C++ 컴파일이 2초 걸린다고 "2초 제한 문제"를 못 푸는 것은
문제 설정의 의미를 왜곡한다.

**구현:** 컨테이너를 넉넉한 메모리로 만들어 컴파일한 뒤, 실행 직전에 컨테이너의 메모리 한도를
문제의 값으로 **낮추고** 사용자 프로그램을 실행한다 (`ContainerUpdate`). 그래서 실행 단계에서는
문제의 제한이 그대로 강제된다.

작업 디렉터리는 tmpfs 라 사용량이 메모리 한도에 포함된다. 그래서 컴파일 단계 끝에서
빌드 캐시(`.gocache` 등)를 지운다 — 그러지 않으면 캐시가 실행 단계의 메모리를 잡아먹는다.

컴파일 실패와 시간 초과가 다른 판정(`COMPILE_ERROR` / `TIME_LIMIT_EXCEEDED`)으로
구분되는 것도 이 분리 덕분이다.

컨테이너 전체 수명은 `컴파일 제한 + 실행 제한 + 여유(10초)` 로 잡는다. 이 수명이 먼저
끝나면 계측 줄이 남지 않고, 실행기는 그것을 시간 초과로 해석한다.

## 5. 언어별 보정 계수 — 지금은 두지 않는다

**결정:** 언어마다 시간 제한을 배수로 보정하는 장치를 도입하지 않는다. **보류한다.**

**근거:** 보정 계수는 "Python 은 3배" 같은 숫자를 어딘가에 박아 넣는 일인데, 그 숫자의
근거를 만들려면 언어별 실행 시간 분포 데이터가 필요하다. 지금은 문제도 런타임도 적어
데이터가 없다. 근거 없는 계수는 나중에 바꾸기도 어렵다.

대신 **문제마다 제한을 정할 수 있게** 해 두었다. 특정 언어로 풀기 빠듯한 문제가 생기면
그 문제의 제한을 늘리는 것으로 대응하고, 그런 사례가 쌓이면 그때 데이터를 근거로
보정 정책을 설계한다 (#17 의 언어 확장 이후).

## 5.1 셸 런타임에 무엇이 들어 있는가 (#456)

**문제 지문이 도구의 동작을 전제하게 되므로 처음에 정하고 고정한다.**

`bash:5` 런타임의 이미지는 `debian:13-slim` 이다. 공식 `bash:5`(alpine, 26MB)를 쓰지
않은 이유: 그쪽의 `awk`·`sed`·`grep`·`sort` 는 전부 **busybox** 라 GNU 와 동작이 다르다
(`sed -i`, `\+` 정규식 확장, `sort -h`, `grep -P`). 셸 문제는 실무의 그 도구들을 묻는
것이므로 실무 쪽(GNU)으로 맞췄다. 값은 이미지 139MB 이고, 노드마다 한 번 받는 비용이다.
#394 가 아희 구현을 고르고 고정한 것과 같은 판단이다.

| 있는 것 | 없는 것 |
|---|---|
| bash 5.2, GNU coreutils, GNU sed 4.9, GNU grep, findutils | `gawk` (그래서 `gensub` 불가) |
| `awk` = mawk 1.3.4 | `jq`, `curl`, `wget`, `python`, `sudo` |

**stdin/stdout 만 한다.** "이 디렉터리의 `.log` 중 가장 큰 것" 처럼 **파일 시스템이
입력인** 셸 문제는 채점 모델이 다르다 — 끝난 뒤의 상태를 봐야 한다. #453 이 SQL 에서
그 길(`verifySql`)을 냈고, 파일 시스템 판은 그 위에 얹는다.

**프로세스 수는 셸에서도 같은 값(`pids-limit 128`)이 걸린다.** 셸은 `|` 하나가 프로세스
둘이라 다른 언어보다 쉽게 늘어난다 — 그래서 `--self-test` 에 셸 사례를 따로 뒀다
(docs/07 매트릭스 23·24).

## 5.2 인터랙티브 문제에서 시간 제한의 뜻 (#474)

**도는 중에 주고받는다.** 그래서 시간 제한이 재는 것이 달라진다 — 제출 하나가 아니라
**채점 코드와 제출이 함께 도는 시간**이다. 둘 다 같은 컨테이너 안에 있으므로 제한도
컨테이너 전체에 걸린다.

| 상황 | 어떻게 갈리나 |
|---|---|
| 제출이 답을 찾음 | 채점 코드가 **0** 으로 끝난다 |
| 규칙을 어김(질의 초과 등) | 채점 코드가 **1** 로 끝낸다 → 오답 |
| 제출이 아무것도 안 보내고 끝남 | 채점 코드가 EOF 를 보고 **3** → **교착** |
| 둘 다 상대를 기다림 | 컨테이너 시간 제한 → 시간 초과 |

**교착과 시간 초과를 가르는 이유**: 이 유형에서 가장 흔한 원인은 **출력을 flush 하지
않은 것**이고, 사용자 잘못이지만 사용자가 알기 어렵다. "시간 초과" 로 보이면 엉뚱한
곳(알고리즘)을 고치게 된다.

**제출은 버퍼 없이 돈다** (`python3 -u`). 첫 판을 파이썬으로 여는 이유 중 하나다 —
둘이 같은 컨테이너에서 동시에 돌아야 하는데 컨테이너 이미지는 제출 언어의 것이고,
자바 이미지에는 파이썬이 없다.

### 파이프를 잇는 데 함정이 둘 있다

라이브 시험이 이것을 지킨다. 둘 다 실제로 겪었다.

- **FIFO 는 여는 것 자체가 상대를 기다린다.** 채점 코드가 읽기로 열면서 멈추고 제출도
  읽기로 열면서 멈춰 **둘 다 시작하기 전에 교착**한다 → 하네스가 먼저 하나씩 잡는다
- **자식이 물려받은 서술자를 닫아야 한다.** 안 닫으면 쓰는 쪽이 남아 있는 셈이라
  **EOF 가 영원히 오지 않고**, 아무것도 안 보내고 끝난 제출이 교착으로 갈리지 않는다

## 6. 작업 간 격리

실행기는 작업마다 `Sandbox.Spec` 을 새로 만들고 컨테이너도 새로 만든다. 워커 사이에
공유하는 실행 상태가 없으므로, 서로 다른 제한을 가진 작업이 동시에 돌아도 설정이 섞이지 않는다.

이 성질은 테스트로 고정한다 — `RunAppliesEachJobsOwnLimitsUnderConcurrency`.

## 8. 남은 것

- 제한이 다른 두 문제에 대한 종단간 검증은 스모크 스크립트가 담당한다. CI 에서 돌리려면
  컨테이너 런타임이 있는 러너가 필요하다 (#16 이후).
- 출력량 제한(`EXECUTOR_MAX_OUTPUT_BYTES`)은 아직 전역 설정이다. 문제별로 다르게 둘
  이유가 생기면 같은 경로로 확장한다.
- 컴파일 자원 한도도 전역이다. 언어마다 다르게 둘 근거가 쌓이면 런타임 정의로 옮긴다.

## 함수형 문제의 하네스 (#421, #445)

`ExecJob.harnessSource` 가 있으면 실행기는 **파일을 둘 놓는다.**

| 무엇 | 어디에 | 누가 정하나 |
|---|---|---|
| 하네스 | `functionHarness.file` (파이썬: `main.py`) | 출제자 |
| 사용자 코드 | `functionHarness.sourceFile` (파이썬: `solution.py`) | 푸는 사람 |
| 실행 명령 | `functionHarness.run` | 런타임 정의 |

**문자열로 이어 붙이지 않는다.** `{{USER_CODE}}` 같은 자리에 끼워 넣으면 사용자 코드의
줄 번호가 하네스 길이만큼 밀리고, **틀린 곳을 못 찾는 오류 메시지는 없는 것만 못하다.**

`functionHarness` 가 없는 런타임으로 하네스가 오면 **거부한다**(SYSTEM_ERROR). 조용히
사용자 코드만 돌리면 "함수만 구현했는데 아무 출력이 없다" 가 되고 그 이유를 아무도 모른다.

### 하네스가 새지 않게 하는 것

하네스에는 정답의 일부나 판정 방식이 들어간다. 네 갈래로 샐 수 있고 지금 셋을 막는다.

| 새는 길 | 막는 법 | 상태 |
|---|---|---|
| 사용자 코드가 파일을 읽는다 | 로더가 **읽자마자 지운다** (`os.remove`) | 파이썬 확인됨 |
| 표준 오류·트레이스백 | 하네스를 가리키는 프레임을 **사실만 남기고** 지운다 | 확인됨 |
| 컨테이너 경로 | `/work/` 를 지운다 | 확인됨 |
| 컴파일 산출물의 디버그 심볼 | — | **컴파일 언어를 지원할 때 본다** |

**줄 번호는 그대로다.** 지운 뒤에도 `compile(src, "main.py", ...)` 이라 트레이스백의
줄 번호가 유지되고, 파일이 없으므로 파이썬이 하네스의 소스를 함께 찍지도 못한다 —
지우는 것이 두 겹으로 듣는다.
