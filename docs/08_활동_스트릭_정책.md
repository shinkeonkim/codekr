# 08. 활동 집계와 스트릭 정책

꾸준한 문제 풀이를 일별로 집계해 현재·최장 스트릭과 활동 그래프로 보여준다 (#36).
이 문서는 **무엇을 활동으로 셀지**와 **하루를 어디서 자를지**를 정한다.

## 1. 무엇을 활동으로 세는가

**결정: 채점이 완료된 제출(`status = COMPLETED`) 하나를 활동 1회로 센다.**

검토한 대안과 기각 사유:

| 후보 | 기각 사유 |
|---|---|
| 모든 제출 | 채점되지 못한 제출(인프라 장애)까지 활동으로 잡힌다. 사용자가 한 일이 아닌 것이 섞인다 |
| 일별 최초 **정답**만 | 어려운 문제에 하루 종일 도전하고 못 푼 날이 빈칸이 된다. 스트릭은 성과가 아니라 **꾸준함**의 지표다 |
| 문제 조회·로그인 | 학습 활동이라 보기 어렵고, 늘리기가 너무 쉽다 |

정답 코드 검증 제출(#39)은 사용자의 활동이 아니므로 제외한다 (`kind = 'USER'` 조건).
소프트 삭제된 제출도 제외한다.

**감수하는 것:** 의미 없는 제출을 반복해 활동 수를 늘릴 수 있다. 스트릭에는 영향이 없고
(하루는 하루로만 센다) 그래프 강도만 부풀릴 수 있다. 랭킹처럼 경쟁 보상이 걸리면
방어가 필요해지므로, 그때 #41 에서 함께 다룬다.

## 2. 하루의 경계

**결정: `Asia/Seoul` 고정.**

UTC 로 자르면 한국 시간 오전 9시 이전의 제출이 전날로 잡힌다. 밤에 문제를 푸는 사용자가
"어제 푼 것으로 표시되는" 경험을 하게 된다. 서비스 대상이 한국어권이므로 고정한다.

사용자별 시간대 설정은 두지 않는다 — 계정에 시간대 정보가 없고, 스트릭 계산이 사용자마다
달라지면 캐시·집계를 나중에 도입하기 어려워진다. 필요해지면 그때 계정 설정과 함께 넣는다.

응답에 `timeZone` 을 함께 내려, 화면이 서버와 같은 기준으로 "오늘"을 계산할 수 있게 한다.

## 3. 계산 규칙

| 값 | 규칙 |
|---|---|
| 일별 활동량 | 그날 채점 완료된 제출 수 |
| 활동한 날 | 활동량이 1 이상인 날 |
| **현재 스트릭** | 오늘부터 거슬러 올라가며 연속된 활동일 수. **오늘 활동이 없어도 어제까지 이어져 있으면 유지** |
| **최장 스트릭** | 조회 기간 안에서 가장 길게 이어진 연속 일수 |

> 같은 날 여러 번 제출해도 스트릭은 **하루로만** 센다. 활동량(그래프 강도)에는 모두 반영된다.

### 현재 스트릭에 어제를 포함하는 이유

오늘 아직 문제를 풀지 않았다고 해서 스트릭이 0 으로 보이면, 아침에 접속한 사용자에게
사실과 다른 좌절을 준다. 하루가 끝나기 전까지는 유지하고, 이틀이 비면 끊는다.

## 4. API

```
GET /api/v1/users/me/activity?from=2025-08-11&to=2026-08-10   🔒
```

- 기본 기간은 최근 365일, 최대 3년.
- 활동이 있었던 날만 `days` 에 담는다. 없는 날은 화면이 0 으로 그린다.
- 시작일이 종료일보다 늦으면 400.

```json
{
  "from": "2025-08-11", "to": "2026-08-10",
  "days": [ { "date": "2026-08-10", "count": 3 } ],
  "totalCount": 3, "activeDayCount": 1,
  "currentStreak": 1, "longestStreak": 4,
  "timeZone": "Asia/Seoul"
}
```

## 5. 접근성

- 각 칸은 색만으로 정보를 주지 않는다. `title` 과 스크린 리더용 텍스트로
  **날짜와 정확한 활동 횟수**를 함께 제공한다.
- 표(`table`)로 그려 행/열 구조가 보조 기술에 드러나고, `caption` 에 기간과 기준 시간대를 담는다.
- 범례는 색 견본과 함께 각 단계의 의미를 글로도 적는다.
- 좁은 화면에서는 그래프만 가로 스크롤되고 페이지 자체는 넘치지 않는다.

## 6. 검증

| 무엇 | 어디서 |
|---|---|

시간대 정책이 깨지면 바로 드러난다.

## 연도별 보기 (#81)

스트릭은 몇 년에 걸쳐 이어진다. 그래서 **보는 범위와 계산 범위를 분리한다.**

| 값 | 범위 |
|---|---|
| 활동 그래프(`days`) | 조회한 기간 (연도를 고르면 그 해 1/1~12/31) |
| 활동한 날·채점 완료 수 | 조회한 기간 |
| **현재·최장 스트릭** | **전체 기간** |

연도별로 스트릭을 자르면 두 가지가 깨진다.

- 2026년만 보고 있다고 최장 기록이 2026년 안으로 잘린다 — 작년의 30일 연속이 사라진다
- 12/31~1/1 로 이어진 연속이 **연도 경계에서 끊겨 보인다**

그래서 스트릭은 항상 그 사용자의 활동 날짜 전체를 보고 센다. 화면도 라벨에 "전체 기간"을
붙여 연도를 바꿔도 값이 그대로인 이유를 밝힌다.

**연도 선택지는 활동이 있는 해 + 올해**다. 가입 전 연도는 선택할 이유가 없고, 올해는
활동이 없어도 보여준다 — 빈 그래프는 "아직 아무것도 안 했다"는 정보다.


## 집계는 별도 표에 있다 (#105)

활동과 스트릭은 `submissions` 를 직접 훑지 않고 `user_daily_activity` 를 읽는다.

```
submissions          →  user_daily_activity  →  활동 그래프 · 스트릭
(가장 빨리 커진다)       (사용자 × 활동한 날)
```

`submissions` 는 사용자 한 명이 하루 수십 건씩 쌓는다. 화면을 열 때마다 그것을 사용자
단위로 훑는 구조는 오래 못 간다. 특히 #81 이후 스트릭은 **조회 범위와 무관하게 전체
기간**을 보므로 부담이 더 크다.

### 어긋났을 때 되돌리는 방법 — 이게 없으면 저장하면 안 된다

집계를 저장하면 원자료와 갈라질 수 있다. 그래서 두 장치를 함께 둔다.

1. **갱신은 다시 세어 덮어쓴다.** 증분(+1)이 아니다 — 재채점(#107)은 같은 제출을 다시
   COMPLETED 로 만드는데, 증분이었다면 그때마다 활동이 늘어난다.
   하루치를 다시 세는 것은 인덱스가 있어 싸다
2. **전체 재계산 경로**가 있다: `POST /api/v1/admin/users/{id}/activity/recompute`.
   값을 일부러 망가뜨린 뒤 복구되는 것을 테스트가 확인한다

> 문제 통계(#84)에서는 **저장하지 않는 쪽**을 골랐다. 거기는 문제 단위라 데이터가 작았고,
> 여기는 사용자 단위로 전체 기간을 읽는다는 점이 다르다.

하루의 경계(`Asia/Seoul`)는 **저장 시점에 확정**한다. 읽는 쪽이 다시 변환하지 않는다.
