# 뱃지 달성 규칙 DSL 기획 (#200)

> 이 문서는 **무엇을 만들지 정하는 글**이다. 구현은 #201(정의를 데이터로) ·
> #202(규칙 엔진) · #203(어드민 편집기)이 나눠 맡는다.

## 1. 왜 지금 정하는가

뱃지를 하나 늘리려면 배포해야 한다 — 이름·설명이 `Badge.kt` 의 enum 에 있고 조건이
`BadgeAwarder.kt` 의 SQL 에 있다. 뱃지는 **운영이 손대는 물건**인데(이벤트를 열고,
문구를 다듬고, 시즌마다 바꾼다) 그때마다 코드를 고친다.

**DSL 은 한 번 정하면 저장된 규칙이 그 문법에 묶인다.** 스키마보다 바꾸기 어렵다 —
이벤트 목록을 잘못 잡으면 나중에 표현할 수 없는 뱃지가 생기고, 그때는 이미 규칙이
데이터로 쌓여 있다. 그래서 먼저 쓴다 (#41·#42·#43 과 같은 이유).

## 2. 무엇을 잃는가 — 뒤집는 판단

`Badge.kt` 의 주석은 문구를 코드에 두는 것을 **의식적으로 고른 결과**다.

> 코드만 DB 에 저장하고 이름·설명은 여기서 갖는다 — 문구를 고치려고 마이그레이션하지
> 않는다. 뜻이 달라지면 새 코드를 쓴다.

이 판단을 뒤집는다. **잃는 것을 적어 둔다.**

| 잃는 것 | 어떻게 다루는가 |
|---|---|
| 문구가 git 이력에 남지 않는다 | 규칙 표에 `updated_at`·`updated_by` 를 두고 변경을 관리 기록(#225)에 남긴다 |
| 코드를 읽어 "무슨 뱃지가 있는지" 알 수 없다 | 어드민 목록(#203)이 그 자리를 대신한다. 시드 마이그레이션에 지금 넷을 넣어 **빈 상태로 시작하지 않는다** |
| 컴파일러가 오타를 못 잡는다 | 규칙을 저장할 때 검증하고, **미리보기로 결과를 보여준다**(#203) |

## 3. 이벤트 — 규칙이 언제 돌아가는가

지금 트리거는 `onAccepted` 하나뿐이다. 이벤트를 늘리는 것이 DSL 만큼 중요하다 —
**이벤트가 없으면 그 순간을 조건으로 쓸 수 없다.**

| 이벤트 | 언제 | 실려 오는 것 |
|---|---|---|
| `PROBLEM_ACCEPTED` | 정답이 확정될 때 (지금 있는 것) | `problemId`, `category`, `difficulty` |
| `STREAK_UPDATED` | 활동 집계가 갱신될 때 (#105) | `currentStreak`, `longestStreak` |
| `CONTEST_FINISHED` | 대회가 끝나고 순위가 확정될 때 (#61) | `contestId`, `rank`, `participants` |
| `POST_CREATED` | 게시글을 쓸 때 (#137) | `postId`, `board` |
| `PROBLEM_PUBLISHED` | 문제가 공개될 때 (출제자용, #236) | `problemId` |

**처음에 다 만들지 않는다.** `PROBLEM_ACCEPTED` 와 `STREAK_UPDATED` 둘로 시작하고,
나머지는 그 기능이 붙을 때 함께 낸다. 다만 **이벤트 이름과 실려 오는 값의 모양은
지금 정해 둔다** — 나중에 바꾸면 저장된 규칙이 깨진다.

## 4. 조건 언어 — 지표(measure)와 임계값

세 후보 중 **②구조화된 JSON 규칙 트리**를 고른다. ③(SQL 조각)은 어드민 화면이 사실상
DB 콘솔이 되고, 규칙을 저장하는 순간 임의 조회 창구가 열린다.

다만 그냥 JSON 트리로는 `FIRST_SOLVER` 같은 **전역 비교**를 담을 수 없다. 그래서
언어의 뼈대를 이렇게 잡는다.

> **조건의 재료(지표)는 코드가 정하고, 조합·임계값·문구는 데이터가 정한다.**

이것이 하이브리드의 선이다. "무엇을 셀 수 있는가" 는 코드가 늘리고(그때는 배포한다),
"얼마나 세면 주는가·뭐라고 부르는가" 는 배포 없이 바뀐다. 운영이 실제로 자주 하는
일은 후자다.

### 4.1 지표 두 갈래

| 갈래 | 뜻 | 예 |
|---|---|---|
| **사용자 지표** | 그 사람의 누적값. 이벤트와 무관하게 언제든 계산된다 | `accepted_problem_count`, `longest_streak_days`, `accepted_in_category` |
| **이벤트 지표** | **이번 이벤트에 대해서만** 뜻이 있는 값 | `is_first_solver`, `contest_rank` |

`FIRST_SOLVER` 가 이 구분을 요구한다 — 내 기록만 봐서는 판정할 수 없고, "방금 맞힌
그 문제에 대해 내가 처음인가" 이기 때문이다. 이벤트 지표는 **그 이벤트가 왔을 때만**
평가되고, 소급 적용(§7)에서도 다시 계산되지 않는다.

### 4.1.1 대회 지표 (#463)

**대회에 나가도 뱃지가 붙지 않았다.** `PROBLEM_ACCEPTED` 는 대회 제출에도 도는데,
규칙이 **"대회였는가" 를 볼 방법이 없었다** — 사건에 대회 id 가 실리지 않았기 때문이다.

**대회 전용 사건을 새로 만들지 않았다.** 대회에서 맞힌 것도 문제를 맞힌 것이고, 사건에
대회 id 를 실으면 지표를 늘리는 것으로 끝난다.

| 지표 | 갈래 | 뜻 |
|---|---|---|
| `is_contest_submission` | 이벤트 | 이번에 맞힌 것이 대회 제출인가 |
| `contest_registered_count` | 사용자 | 등록한 대회 수 — **나오지 않아도 센다** |
| `contest_participated_count` | 사용자 | 제출해 본 대회 수 — **맞히지 못해도 센다** |
| `contest_accepted_count` | 사용자 | 대회에서 맞힌 문제 수 (대회 × 문제) |

**셋을 다 둔다.** "등록만" · "제출은 했다" · "맞혔다" 는 서로 다른 문턱이고, 어느 것을
인정할지는 **규칙이 고를 일**이다 — 엔진이 데이터 기반인 이유가 그것이다. 여기서 하나로
정해 버리면 배포 없이 뱃지를 만든다는 약속이 반만 지켜진다.

**성적(1등·상위 10%)은 아직 지표가 아니다.** 순위는 프리즈(#86)와 재채점(#107)으로
바뀌므로 **확정 시점을 먼저 정해야 한다.**

### 4.2 규칙의 모양

```json
{
  "event": "PROBLEM_ACCEPTED",
  "all": [
    { "measure": "accepted_in_category", "op": ">=", "value": 10 }
  ],
  "groupBy": "problem_category",
  "code": "CATEGORY_10_{group}"
}
```

- `all` / `any` — 조건 묶음. 중첩은 **한 단계까지만** 허용한다. 두 단계를 넘어가면
  편집기에서 읽을 수 없고, 그런 규칙이 필요하면 지표를 새로 만드는 편이 낫다
- `op` — `>=`, `>`, `==` 셋. 뺄셈·나눗셈 같은 산술은 없다. 필요하면 지표로 만든다
- `groupBy` — 파라미터화된 뱃지(§5)
- `code` — 부여할 뱃지 코드. `{group}` 만 치환한다

## 5. 지금 있는 네 종류를 적어 본다

**이것이 설계의 시험대다.** 하나라도 안 적히면 언어를 다시 잡는다.

### FIRST_ACCEPT — 조건 없음

```json
{ "event": "PROBLEM_ACCEPTED", "all": [], "code": "FIRST_ACCEPT" }
```

조건이 비어 있으면 **이벤트가 곧 달성**이다. 뱃지는 한 번만 부여되므로(`award` 가
멱등) "처음" 이 저절로 성립한다 — 지금 코드가 하는 일과 같다.

### STREAK_7 / STREAK_30 — 다른 도메인의 값

```json
{ "event": "STREAK_UPDATED",
  "all": [{ "measure": "longest_streak_days", "op": ">=", "value": 7 }],
  "code": "STREAK_7" }
```

지표가 활동 집계(#105)를 읽는다. **제출을 다시 훑지 않는다** — 지금 코드의 규칙을
그대로 지킨다. 30일도 `value` 만 다른 같은 규칙이다.

### CATEGORY_10_* — 파라미터화

```json
{ "event": "PROBLEM_ACCEPTED",
  "all": [{ "measure": "accepted_in_category", "op": ">=", "value": 10 }],
  "groupBy": "problem_category",
  "code": "CATEGORY_10_{group}" }
```

`groupBy` 는 **이번 이벤트가 속한 그룹 하나만** 본다 — 정답 하나가 확정될 때 모든
카테고리를 다시 세지 않는다(지금 코드도 그렇다). 그래서 `{group}` 은 이벤트에서 온다.

문구도 파라미터를 받는다: `"{category} 문제 10개를 맞혔습니다"`.

### FIRST_SOLVER — 전역 비교

```json
{ "event": "PROBLEM_ACCEPTED",
  "all": [{ "measure": "is_first_solver", "op": "==", "value": true }],
  "code": "FIRST_SOLVER" }
```

**이벤트 지표**다. 지표 자체는 코드가 계산한다(지금의 `isFirstSolver` SQL 그대로).
데이터가 정하는 것은 "그 지표를 쓸지" 와 "무슨 뱃지를 줄지" 다.

**넷 다 적힌다.** 대신 넷 모두 지표를 하나씩 요구한다 — 그것이 이 설계의 정직한 값이다.
DSL 이 없애는 것은 *새 임계값·새 문구·새 조합* 이지 *새 종류의 셈* 이 아니다.

## 6. 평가 — 언제, 얼마나 자주

- **이벤트마다 즉시.** 주기적으로 훑는 방식은 "언제 받았는지" 가 흐려지고, 뱃지는
  받은 순간이 뜻인 물건이다
- **그 이벤트를 구독하는 규칙만 돌린다.** 규칙 표에 `event` 가 있으므로 인덱스 하나로
  걸러진다
- **지표는 규칙당 한 번만 계산하고 이벤트 안에서 캐시한다.** 같은 이벤트에 `STREAK_7`
  과 `STREAK_30` 이 함께 걸리면 스트릭을 두 번 읽지 않는다
- **이미 가진 뱃지는 지표를 계산하기 전에 건너뛴다.** 정답을 100번 맞힌 사람에게
  `FIRST_ACCEPT` 조건을 100번 확인할 이유가 없다 — 지금 코드에 없는 최적화이고,
  규칙 수가 늘면 이것이 가장 크게 듣는다

**정답 확정은 채점 경로 위에 있다**(#57). 규칙 평가가 느려지면 채점이 밀리므로,
지표 하나당 질의 하나를 넘지 않게 하고 규칙 수 상한(예: 이벤트당 50개)을 둔다.

## 7. 규칙을 고치면 어떻게 되는가

| 상황 | 결정 | 왜 |
|---|---|---|
| 조건을 좁혔다 | **이미 받은 사람은 그대로** | #41 의 "회수하지 않는다" 를 규칙 변경에도 그대로 적용한다. 받은 것을 뺏는 순간 뱃지는 자랑거리가 아니라 불안거리가 된다 |
| 조건을 넓혔다 | **소급하지 않는다**(기본) | 소급은 전체 사용자를 훑는 일이라 비용이 크고, 조용히 도는 사이에 알림이 쏟아진다 |
| 그래도 소급하고 싶다 | **어드민이 명시적으로 실행한다** | #177·#105 의 재계산과 같은 모양 — 누른 사람과 시각이 기록에 남는다(#225) |
| 규칙을 지웠다 | **이미 받은 뱃지는 남는다** | `Badge.describe` 가 "모르는 코드도 죽지 않게" 다루는 지금 규칙을 그대로 지킨다. 규칙과 부여 기록은 별개의 표다 |

## 8. 안전 — 운영자가 쓴 것을 서버가 실행한다

| 위험 | 막는 법 |
|---|---|
| 임의 조회 | **지표는 코드가 정한 목록에서만 고른다.** 자유 SQL 이 들어갈 자리가 없다 |
| 무한 루프 | 규칙이 이벤트를 만들지 못한다. 뱃지 부여는 이벤트가 아니다 |
| 전체 스캔 | 지표마다 질의가 고정돼 있고, 인덱스를 붙여 놓은 것만 지표가 된다 |
| 남의 데이터 | 지표는 **평가 대상 사용자 id 를 반드시 인자로** 받는다. 전역 지표(`is_first_solver`)도 그 사람 기준이다 |
| 규칙 폭주 | 이벤트당 규칙 수 상한. 넘으면 저장이 거절된다 |

## 9. 기존 넷을 옮기는 방법

1. #201 이 표를 만들고 **시드 마이그레이션으로 지금 넷을 넣는다** — 빈 상태로 시작하면
   그 배포에서 아무도 뱃지를 못 받는다
2. #202 가 엔진을 붙이고 `BadgeAwarder` 를 **엔진 호출로 바꾼다.** 지표 넷
   (`accepted_problem_count`·`longest_streak_days`·`accepted_in_category`·`is_first_solver`)
   은 지금 코드를 그대로 옮긴다
3. 옮긴 뒤 `Badge` enum 은 **describe 의 폴백으로만** 남는다 — 규칙이 지워져도 옛 코드가
   읽히게

**옮기지 못하는 것은 지금 없다**(§5). 앞으로 안 되는 것이 나오면 **지표를 늘리는 것이
정상 경로**이고, 그때는 배포가 필요하다는 것을 받아들인다.
