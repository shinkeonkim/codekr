# 복수 문제 유형과 전용 채점 방식 기획

- 상태: 초안 확정 (구현 전)
- 근거 이슈: #42
- 선행: #17(런타임 확장), #37(샌드박스 검증), #38(실행 제약), #39(정답 코드 검증)

## 1. 왜 지금 설계하는가

`ProblemCategory` 는 이미 7가지 유형을 표현하지만, **채점은 stdin/stdout 하나뿐**이다
(ADR-0006). 유형마다 입력·정답·실행 환경·비교 방식·보안 경계가 다르므로, 하나의 구현으로
뭉치기 전에 **공통 계약과 확장 지점**을 정한다.

가장 나쁜 결과는 SQL 문제를 억지로 stdin/stdout 에 끼워 맞춰, 나중에 되돌릴 수 없는
데이터 모양을 만드는 것이다.

## 2. 유형별 비교

| 유형 | 풀이 입력 | 실행 환경 | 정답 표현 | 채점 방식 | 자동화 |
|---|---|---|---|---|---|
| **알고리즘 / 자료구조** | 소스 코드 | 언어 런타임 | 기대 stdout | 문자열 비교 | 완전 |
| **SQL** | SQL 쿼리 | 격리 PostgreSQL·MySQL | 기대 결과 집합 | 결과 집합 비교 | 완전 |
| **Redis** | **명령의 연속** | 격리 Redis | **끝난 뒤의 상태** | 확인 명령의 출력 비교 | 완전 |
| **프로그래밍 언어** | 소스 코드 | 언어 런타임 | 기대 stdout / 예외 | 기존 파이프라인 | 완전 |
| **네트워크 / 운영체제** | 객관식·단답·소스 코드 | 없음 또는 런타임 | 정답 값 / 기대 출력 | 값 비교 | 완전(개념), 부분(실습) |
| **시스템 설계** | 서술형 + 다이어그램 | 없음 | 평가 기준(루브릭) | 사람 검수 + 체크리스트 | 불가 |

### 도입 순서

1. **SQL** — 자동 채점이 가능하고 수요가 크다. 실행 격리 모델도 기존과 유사하다.
2. **개념형(네트워크·OS·언어)** — 객관식·단답. 실행기가 아예 필요 없어 가장 싸다.
3. **실습형(네트워크·OS)** — 컨테이너 안에서 명령을 실행하고 상태를 검증. 격리 요구가 가장 높다.
4. **시스템 설계** — 사람 검수가 전제. 마지막.

**놀랍게도 2번이 1번보다 싸다.** 그럼에도 SQL 을 먼저 두는 이유는 수요와 학습 가치가
훨씬 크고, 개념형은 언제든 끼워 넣을 수 있기 때문이다.

## 3. 공통 계약과 확장 지점

### 유지하는 것

`Problem` 의 slug·제목·카테고리·난이도·지문·공개 여부·소프트 삭제는 **모든 유형이 공유**한다.
목록·검색·난이도·랭킹이 유형과 무관하게 동작해야 하기 때문이다.

### 확장하는 것

```
problems
  └ problem_kind            (JUDGE_STDIO | JUDGE_SQL | QUIZ | MANUAL)   ← 신규
  └ (기존 컬럼들)

problem_stdio_spec          기존 problem_testcases 를 이 유형의 확장으로 재해석
problem_sql_spec            초기 스키마·시드 데이터·정답 쿼리·비교 옵션(순서 무시 등)
problem_quiz_spec           보기·정답·해설
problem_manual_spec         평가 루브릭
```

**결정: 유형별 데이터를 JSON 한 컬럼에 몰지 않고 테이블로 나눈다.** JSON 은 시작이 빠르지만
어드민 검증·마이그레이션·조회가 모두 애플리케이션 몫이 된다. 유형 수가 5개 안쪽으로
예측되므로 테이블 분리가 낫다.

### 채점기 확장

```
judge
 ├ StdioJudge   (현재)  — 실행기에 코드+stdin 을 보내고 stdout 비교
 ├ SqlJudge            — 실행기에 스키마+쿼리를 보내고 결과 집합 비교
 └ QuizJudge           — 실행기를 쓰지 않는다. api 에서 즉시 채점
```

`Verdict` 는 그대로 쓴다. SQL 의 "결과가 다름"은 `WRONG_ANSWER`, 문법 오류는 `COMPILE_ERROR`
로 대응된다 — 새 판정 값을 늘리기 전에 기존 값으로 표현되는지 먼저 본다.

## 4. SQL 유형 상세

| 항목 | 결정 |
|---|---|
| 실행 환경 | 문제마다 **새 DB 컨테이너**(PostgreSQL·MariaDB). 네트워크 차단, 실행 후 폐기 |
| 어느 DB 인가 | **문제 하나에 DB 하나** (#454). 허용 목록(#419)으로 정한다 |
| 스키마·데이터 | 문제가 소유. 컨테이너 기동 시 주입 |
| 정답 | **정답 쿼리**를 저장하고, 채점 시 정답 쿼리와 제출 쿼리의 결과를 비교 |
| 비교 | 열 이름·순서, 행 순서 무시 여부를 문제별 옵션으로 |
| 금지 | `DROP`/`ALTER`/`COPY` 등은 읽기 전용 롤로 차단 (문자열 필터가 아니라 권한으로) |
| 쓰기 문제 (#453) | 문제별로 **연다**. 열면 상태를 읽는 쿼리로 견준다 (§8.2) |
| 시간·메모리 | `statement_timeout` + 컨테이너 제한 (#38 의 제약을 그대로 재사용) |

**정답을 결과 집합이 아니라 쿼리로 저장하는 이유:** 시드 데이터가 바뀌면 기대 결과도 바뀐다.
쿼리를 저장하면 데이터 변경에 자동으로 따라간다. #39 의 정답 코드 검증과 같은 구조다.

## 8.1 SQL 유형의 실행 방식 (#60, 구현됨)

**문제마다 새 PostgreSQL 을 샌드박스 컨테이너 안에서 띄운다.** 서버를 미리 띄워 두지
않는 이유: 제출끼리 같은 인스턴스를 나눠 쓰면 한 사람의 쿼리가 다른 사람의 결과에
영향을 준다. 컨테이너와 함께 사라지는 편이 안전하다.

이 방식의 이점은 **기존 샌드박스를 그대로 쓴다**는 것이다. 네트워크 차단, 읽기 전용
rootfs, tmpfs, cgroup 제한, seccomp(#48)가 전부 그대로 걸린다. SQL 전용 격리를 따로
만들었다면 그 방어들을 다시 증명해야 했다.

| 요소 | 어디에 |
|---|---|
| 실행 하네스(`run-sql.sh`) | **실행기 바이너리**에 `go:embed`. 스크립트와 코드의 버전이 갈라지지 않게 |
| 스키마·시드·정답 쿼리 | 채점기가 `extraFiles` 로 싣는다. 문제가 소유하는 자료다 |
| 제출 쿼리 | `query.sql`. 기존 `sourceFile` 자리 그대로 |
| 실행 계정 | `70:70` — `initdb` 는 UID 가 `/etc/passwd` 에 없으면 거부한다 |

**쓰기 차단은 문자열 필터가 아니라 권한으로 한다.** 제출 쿼리는 `solver` 롤로 돌고,
그 롤은 `SELECT` 만 갖고 `default_transaction_read_only = on` 이며 슈퍼유저가 아니다.
필터는 우회되지만 권한은 우회되지 않는다. 라이브 시험이 확인하는 것:

| 시도 | 막히는 이유 |
|---|---|
| `DROP TABLE` / `CREATE TABLE` / `DELETE` | 읽기 전용 트랜잭션 |
| `COPY … FROM PROGRAM` | `pg_execute_server_program` 롤이 없다 |
| `pg_read_file('/etc/passwd')` | 함수 실행 권한이 없다 |
| `SELECT … FROM pg_authid` | 테이블 권한이 없다 |

`statement_timeout` 은 롤에 걸어 둔다. 컨테이너의 시간 제한과 별개로 서버 쪽에서도
끊어야, 쿼리 하나가 서버를 붙잡아 정리가 실패하는 일이 없다.

**정답은 결과 집합이 아니라 쿼리로 저장한다.** 시드 데이터가 바뀌면 기대 결과도 따라간다.
채점 시 정답 쿼리를 슈퍼유저로 먼저 돌려 기대 결과를 만들고, 제출 쿼리의 결과와 비교한다.
출력은 `--- codekr:expected` / `--- codekr:actual` 로 나뉘어 나온다.

### 비교 옵션

기획서는 "열 이름·순서, 행 순서 무시 여부를 문제별 옵션으로" 라고 적었지만, **실제로 둔
옵션은 행 순서 하나뿐이다.**

하네스는 `psql -tA -F'|'` 로 튜플만 출력한다. 열 이름이 출력에 없으므로 "열 이름 비교"는
켜고 끌 대상이 아니고, 열 순서는 SELECT 목록 그 자체라 무시할 방법이 없다. 쓰이지 않을
옵션을 만들어 두면 출제자는 그것이 무엇을 하는지 알 수 없다.

행 순서는 **기본이 무시**다. 문제가 정렬을 요구하지 않는데 순서를 비교하면 맞는 답이
틀린 것으로 나온다. 정렬이 문제의 일부인 경우에만 끈다.

꼬리 공백과 빈 줄은 항상 무시한다 — psql 출력의 부수적인 차이이고, 그것으로 오답을 주면
사용자는 무엇이 틀렸는지 알 수 없다.

### 판정 대응

| 상황 | 판정 | 왜 |
|---|---|---|
| 결과가 다름 | `WRONG_ANSWER` | |
| 쿼리 문법 오류·권한 거부 | `COMPILE_ERROR` | 새 판정 값을 늘리기 전에 기존 값으로 표현되는지 먼저 본다 |
| 시간·메모리 초과 | 기존과 동일 | 그 뜻은 유형과 무관하다 |
| **정답 쿼리나 스키마가 잘못됨** | `SYSTEM_ERROR` | 사용자 잘못이 아니다. 오답으로 처리하면 출제자의 실수가 사용자 기록에 남는다 |

**실행 환경 목록은 유형으로 갈린다.** SQL 런타임이 알고리즘 문제의 선택지로 새면
사용자는 고를 수 있지만 채점되지 않는 조합을 만난다. `GET /api/v1/runtimes?problemKind=`
가 걸러 주고, 제출 시에도 서버가 다시 본다 — 화면을 거치지 않는 경로가 생겨도 막히게.

## 8.2 상태를 바꾸는 SQL 문제 (#453, 구현됨)

`SELECT` 문제는 **결과 집합**을 견주면 됐다. `INSERT`·`UPDATE`·`CREATE TABLE` 은
결과 집합이 없다 — 바뀌는 것은 **DB 의 상태**다. 그래서 두 가지를 문제가 정한다.

| 값 | 뜻 |
|---|---|
| `verifySql` | **끝난 뒤의 상태를 읽는 쿼리.** 비면 지금까지처럼 결과 집합을 견준다 |
| `allowWrite` | 제출에게 쓰기 권한을 줄지. 기본은 거짓 |

**무엇을 정답으로 볼지가 먼저다.** 상태를 견주려면 상태를 읽는 방법이 있어야 하는데,
"바뀐 행을 전부 나열하라" 같은 규칙은 문제마다 다르다. 그래서 **읽는 쿼리를 출제자가
쓴다** — `#452` 의 채점 코드와 같은 생각이고, SQL 문제에서는 SQL 로 충분하다.

검사 쿼리가 있으면 하네스는 **데이터베이스를 둘** 만든다:

    expected ← schema.sql + answer.sql  → verify.sql 로 기대 상태를 읽는다
    actual   ← schema.sql + query.sql   → verify.sql 로 실제 상태를 읽는다

`initdb` 는 여전히 **한 번**이다 — 같은 클러스터의 두 데이터베이스라 기동 비용이 늘지
않는다. 그리고 제출은 `actual` 에만 붙으므로 기대 상태를 건드릴 수 없다. 출력은 기존과
같은 `--- codekr:expected` / `--- codekr:actual` 이라 비교와 판정은 그대로다.

**여는 것도 권한으로 한다.** `allowWrite` 는 `solver` 롤에 `INSERT`·`UPDATE`·`DELETE`,
시퀀스 사용, `CREATE ON SCHEMA public` 을 주고 `default_transaction_read_only` 를 끈다.
슈퍼유저는 여전히 주지 않으므로 `COPY … FROM PROGRAM`·`pg_read_file`·`pg_authid` 는
그대로 막힌다. 남의 테이블은 `postgres` 소유라 `DROP` 도 되지 않는다 — 제출이 만든
자기 테이블만 지울 수 있다.

**쓰기를 열려면 검사 쿼리가 있어야 한다** (API 검증 + DB `CHECK`). 하나만 켜 두면
채점이 조용히 결과 집합 비교로 돌아가는데, `UPDATE` 의 결과 집합은 비어 있으니
**아무 답이나 통과한다.** 출제자는 자기 문제가 무엇을 재는지 모르게 된다.

반대(검사 쿼리만 두고 읽기 전용)는 막지 않는다. 트랜잭션이 끝난 뒤의 상태를 묻되
제출은 읽기만 하는 문제가 있다.

**신호도 파일로 보낸다.** `verify.sql` 과 `allow-write` 는 스키마·정답이 가는 길과 같은
`extraFiles` 로 간다. 환경 변수를 새로 뚫으면 그 값이 어디서 오는지 아는 곳이 하나 는다.

## 8.3 SQL 은 하나가 아니다 (#454, 구현됨)

한 DB 만 있으면 **"SQL 을 배웠다" 가 "PostgreSQL 을 배웠다" 가 된다.** 배우는 사람이
실제로 만나는 것은 회사가 쓰는 DB 이고, 같은 질문도 문법이 다르다.

구조는 이미 여러 개를 받고 있었다 — `problemKind` 로 걸러지므로 런타임을 더 두면 목록에
함께 나온다. **막는 것은 하네스였다.** `run-sql.sh` 는 PostgreSQL 전용이라 DB 마다
하나씩 필요하다 (`run-mariadb.sh`).

| 하는 일 | PostgreSQL | MariaDB |
|---|---|---|
| 빈 DB | `initdb` | `mariadb-install-db` |
| 주입 | `psql -f` | `mariadb <` |
| 읽기 전용 | `default_transaction_read_only = on` + `SELECT` 만 | **그런 스위치가 없다** — `SELECT` 만 주는 것이 곧 막는 것 |
| 출력 | `psql -tA -F'\|'` | `mariadb -N -B` 뒤 탭을 `\|` 로 |

**채점기는 DB 를 모른다.** 하네스가 무엇이든 `--- codekr:expected` / `--- codekr:actual`
와 `|` 구분 행을 내므로, 비교 규칙은 하나로 남는다. 상태를 묻는 문제(#453)의 약속
(`verify.sql`·`allow-write`)도 그대로 지킨다.

### 위험한 것은 DB 마다 다르다

**PostgreSQL 의 목록을 그대로 옮기지 않는다.** 옮기면 막았다고 믿는 것과 실제로 막힌
것이 어긋나고, 새 DB 가 샌드박스의 구멍이 된다. MariaDB 에서 확인한 것 (라이브 시험):

| 시도 | 막히는 이유 |
|---|---|
| `DELETE`/`CREATE TABLE`/`DROP TABLE` | 권한을 주지 않았다 (`command denied`) |
| `… INTO OUTFILE` / `LOAD DATA INFILE` | `FILE` 권한 없음 + `--secure-file-priv=NULL` |
| `SELECT … FROM mysql.user` | 시스템 데이터베이스 권한 없음 |
| `CREATE FUNCTION … SONAME` (UDF) | `mysql` 데이터베이스에 쓸 수 없다 |
| `SET GLOBAL …` | `SYSTEM_VARIABLES_ADMIN` 없음 |
| `LOAD_FILE('/etc/passwd')` | **오류가 아니라 `NULL`** 이다 — 그래서 따로 확인한다 |
| `SHOW PROCESSLIST` | `PROCESS` 없음 — 자기 세션만 보인다 |

뒤의 둘이 요점이다. **오류를 내지 않는 것은 "막혔다" 로 보이지 않는다** — 값이 나오는지
직접 봐야 한다.

### 문제 하나에 DB 하나

같은 문제를 여러 DB 로 풀게 하려면 스키마도 정답 쿼리도 DB 마다 있어야 한다
(`problem_sql_specs` 가 DB 마다 하나가 된다). 지문도 어차피 갈라진다. 그래서 **허용
목록(#419)으로 문제를 DB 하나에 묶는다.**

이것은 기존 동작을 바꾼다: SQL 문제는 이제 **비워 둘 수 없다.** 비워 두면 PostgreSQL
문법으로 쓴 스키마가 MySQL 제출에서도 돌아 **출제자의 스키마가 먼저 깨지고**, 제출자는
자기 잘못이 아닌 `SYSTEM_ERROR` 를 받는다. 지금 있는 문제는 이관에서 PostgreSQL 로
적어 둔다.

### MySQL 이 아니라 MariaDB 다

처음에는 MySQL 8.4 로 만들었고 로컬(Docker)에서는 전부 통과했다. **CI(containerd + user
namespace 재매핑)에서만** 초기화가 실패했다 — `mysqld --initialize` 가 작업 디렉터리에
디렉터리를 만들지 못하고(`errno 13`), 셸이 만들어 준 **빈** 디렉터리도 `unusable` 로
거절했다. 같은 컨테이너·같은 계정에서 **셸의 `mkdir` 은 된다**는 것을 확인으로 가려냈다.

운영 노드는 재매핑을 켠다(#130). 거기서 뜨지 않는 런타임을 내보내면 **문제를 낼 수는
있는데 아무도 못 푸는 상태**가 된다. 이슈가 "MySQL 과 MariaDB 는 거의 같아서 둘 다 넣을
이유가 약하다" 고 적었으므로, 목적(방언을 하나 더)이 같은 둘 중 **되는 쪽**을 골랐다.
MariaDB 는 초기화가 셸 스크립트(`mariadb-install-db`)라 그 단계가 아예 없다.

곁들여 알게 된 것 둘:
- 이미지의 `my.cnf` 에 `user=mysql` 이 있어 서버가 권한을 내려놓으려 든다 —
  `--no-defaults` 로 통째로 무시한다. 채점 환경이 이미지 개정에 흔들리지 않는 값이기도 하다
- MariaDB 는 `--secure-file-priv=NULL` 도, 없는 경로도 받지 않는다(서버가 뜨지 않는다).
  **빈 디렉터리 하나**로 가둔다

### 기동 비용을 먼저 쟀다

| | 컨테이너 시작부터 결과까지 |
|---|---|
| PostgreSQL 16 | **0.4초** |
| MariaDB 11 | **3.5초** |

**기동도 문제의 시간 제한 안에서 흐른다** — 제한은 컨테이너 전체에 걸리기 때문이다.
그래서 런타임 정의에 `startupMs` 를 적고, **API 가 등록할 때 막는다**: 시간 제한이
`startupMs + 1초` 보다 빠듯하면 거부한다. 그러지 않으면 출제자는 "쿼리는 순식간인데
무엇을 내도 시간 초과" 를 만나고 그 이유를 짐작할 방법이 없다.

웜풀(미리 띄워 두기)은 **하지 않는다.** 제출끼리 인스턴스를 나눠 쓰면 한 사람의 쿼리가
다른 사람의 결과에 영향을 준다 — 그것이 §8.1 에서 컨테이너마다 새로 띄우기로 한 이유다.
3초는 그 값을 포기할 만큼 크지 않다.

## 8.4 Redis — 채점 모델이 다르다 (#455, 구현됨)

`JUDGE_SQL` 은 **"쿼리 하나를 던져 결과 집합을 받는다"** 를 전제한다. Redis 는 그 모양이
아니다 — 제출이 **명령의 연속**이고, 남는 것은 결과가 아니라 **상태**다. 그래서 런타임을
더하는 것으로 되지 않고 **유형이 따로**다 (§9 의 절차대로 `JUDGE_REDIS` 을 더했다).

| | JUDGE_SQL | JUDGE_REDIS |
|---|---|---|
| 제출 | 쿼리 하나 | 명령의 연속 (한 줄에 하나) |
| 스펙 | `schema` / `answer` | `seed` / `answer` / **`verify`** |
| 정답 | 정답 쿼리의 결과 집합 | **확인 명령이 읽은 상태** |
| 순서 | 기본 **무시** (행 순서) | 기본 **지킴** (정렬 집합·리스트는 순서가 자료다) |

**`verify` 가 선택이 아닌 이유:** 명령의 연속에는 견줄 결과 집합이 없다. `HINCRBY` 가
돌려주는 값은 문제가 묻는 것의 일부일 뿐이라, 그것을 정답으로 삼으면 같은 상태에 이르는
다른 풀이가 오답이 된다. 그래서 **무엇을 정답으로 볼지를 출제자가 쓴다** — #453 이 SQL
에서 낸 길과 같고, Redis 에서는 그것이 기본이다.

**바꾸지 않은 것:** 하네스의 출력 형식과 비교 함수다. `--- codekr:expected` /
`--- codekr:actual` 로 나뉜 줄을 내므로 **채점기는 무엇이 돌았는지 몰라도 된다.**

### Redis 부터인 이유

기동이 가장 싸고(실측 0.4초) 명령이 단순하다. 채점 모델(명령의 연속 → 끝난 뒤의 상태)을
먼저 세우고 MongoDB 를 얹는 편이 안전하다 — 모델이 흔들리는 채로 무거운 제품을 들이면
둘 다 고쳐야 한다.

### 우리가 큐로도 쓰는 제품이다

**문제용 인스턴스가 운영 인스턴스와 절대 닿으면 안 된다** (ADR-0002). 하네스는
`--port 0` 으로 **TCP 를 아예 열지 않고** 유닉스 소켓만 쓴다. 샌드박스가 네트워크를
끊지만(ADR-0003) 같은 제품을 우리도 쓰는 이상 한 겹만 믿지 않는다.

### 인스턴스를 둘 띄운다

번호 DB(`-n 1`)로 나누지 않는다. **Redis 의 ACL 은 키 패턴으로만 걸리고 번호 DB 를
가르지 못하므로**, 제출이 기대 상태를 건드릴 수 있다. 프로세스를 둘 띄우는 값은
밀리초 단위라 나눌 이유가 더 크다. 라이브 시험이 실제로 그것을 확인한다.

### 위험한 명령은 Redis 의 것으로

`-@admin -@dangerous -@scripting -@pubsub` 를 뺀 계정으로 제출을 돌린다. **읽기 전용이
아니다** — Redis 문제는 상태를 바꾸는 것이 문제 자체이기 때문이다. 라이브 시험이 확인한 것:

| 시도 | 막히는 이유 |
|---|---|
| `CONFIG SET` / `MODULE LIST` / `CLIENT LIST` | `-@admin` |
| `FLUSHALL` / `KEYS *` / `ACL SETUSER` | `-@dangerous` |
| `EVAL`(Lua) | `-@scripting` |
| `SHUTDOWN` | `-@admin` |

**막힌 명령은 오답이 아니라 오류로 돌려준다.** `redis-cli` 는 `NOPERM` 을 받아도 0 으로
끝나므로, 하네스가 그것을 찾아 실패로 만든다 — 그러지 않으면 아무것도 못 한 제출이
"돌았는데 상태가 다르다" 로 읽혀 사용자는 무엇이 틀렸는지 모른다.

### Redis 에는 주석이 없다

`redis-cli` 는 `#` 으로 시작하는 줄도 명령으로 읽는다. 시작 코드에 설명 한 줄만 있어도
모든 제출이 실패한다는 뜻이라, 하네스가 **줄 전체가 주석인 것과 빈 줄**을 걷어낸다.
값 안의 `#`(`SET tag "#codekr"`)은 건드리지 않는다.

## 8.5 여러 파일로 내는 제출 — 실행기 쪽 (#457, 구현됨)

**설계를 물으려면 파일이 여럿이어야 한다.** 클래스 몇 개가 서로를 쓰는 구조, 인터페이스와
구현, 모듈 경계 — 한 파일에 몰아넣으면 묻고 싶은 것이 사라진다.

이 절은 그중 **실행기가 맡는 부분**이다. #421(함수만 구현하는 문제)도 같은 능력을 쓰고,
이슈가 "둘 중 먼저 하는 쪽이 만들고 나중이 얹는다" 고 적어 두었다.

| 값 | 뜻 |
|---|---|
| `ExecJob.SourceFiles` | **사용자가 쓴 파일들.** 비면 지금까지처럼 `SourceCode` 하나 |
| `ExtraFiles` | 문제가 소유하는 자료 (#60). 이름이 겹치면 **제출 쪽이 거부된다** |

**주인을 나눠 둔 이유:** 둘을 한 자리에 섞으면 "이 파일을 사용자가 고칠 수 있는가" 를
실행기가 알 수 없다. 그러면 제출이 스키마나 정답을 덮어쓰고 통과하는 길이 열린다.

**진입점은 제출 안에 있어야 한다.** 없으면 무엇을 컴파일·실행할지가 없고, 그대로 돌리면
빈 파일을 짠 결과가 판정으로 남는다. 실행기가 거부한다.

### 언어마다 파일을 잇는 방식이 다르다

놓기만 해서 되는 언어와 그렇지 않은 언어가 있다. 실측으로 갈랐다.

| 언어 | 잇는 방법 | 정의 파일을 고쳤나 |
|---|---|---|
| Python·JavaScript | `import` / `require` | 아니다 |
| Java | `javac Main.java` 가 형제 클래스를 따라간다 | 아니다 |
| C·C++ | 각 `.cpp` 를 컴파일해 링크해야 한다 | **그렇다** (`*.cpp`) |
| Go·Kotlin | 같은 패키지의 형제 파일을 명령이 집어야 한다 | **그렇다** (`*.go`, `*.kt`) |

파일이 하나뿐이면 결과는 지금까지와 같다 — 라이브 시험이 여섯 언어에서 **두 파일짜리
프로그램**을 실제로 돌려 확인한다.

## 9. 새 유형을 추가할 때 손대는 곳 (#59 이후)

`problem_kind` 와 채점기 분기가 들어간 뒤로는 아래 지점만 건드리면 된다.

| 순서 | 위치 | 하는 일 |
|---|---|---|
| 1 | `ProblemKind` (api) | 값을 추가하고 `ready = true` 로 바꾼다. **구현이 끝나기 전에는 `false`** — 어드민이 고를 수 있게 두면 채점되지 않는 문제가 만들어진다 |
| 2 | `V__*.sql` (api) | `problem_<유형>_spec` 테이블과 `problem_kind` CHECK 제약 |
| 3 | `contract.Kind*` (libs/gocontract) | 유형 상수. 작업 메시지에 필요한 필드가 있으면 여기 |
| 3.5 | `runtimes.yaml` + `harness/` (executor) | 전용 실행 환경이 필요하면. `problemKind` 로 선택지를 가른다 |
| 4 | `judging.Kind` 구현 (judge) | 새 파일 하나. `Service` 의 `kinds` 맵에 등록 |
| 5 | `SELECTABLE_KINDS` (web) | 어드민 폼의 선택지 |
| 6 | 어드민 폼 (web) | 유형별 입력 묶음 |

**진행/완료 이벤트, 실행 제약 검증, 실패 처리는 건드리지 않는다.** `judging.Service` 가
공통으로 맡는다 — 유형마다 완료 이벤트 모양이 달라지면 api 쪽 처리가 유형을 알아야 한다.

작업 메시지에 `kind` 가 **없으면 `JUDGE_STDIO`** 로 읽는다. api(Kotlin)와 채점기(Go)가
같게 읽고, 양쪽 시험이 같은 고정 JSON 으로 그것을 확인한다.
