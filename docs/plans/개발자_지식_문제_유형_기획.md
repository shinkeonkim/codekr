# 개발자가 실제로 하는 일을 연습하는 문제 유형

- 상태: 초안
- 이어받는 것: [`문제_유형_확장_기획.md`](문제_유형_확장_기획.md) (#42), M21
- 방향: 도구·환경 / 읽고 고치기 / 테스트 쓰기 / 개념 퀴즈

## 1. 지금까지와 무엇이 다른가

M21 까지 늘린 유형은 **"무엇으로 푸는가"** 를 늘린 것이다 — SQL, Redis, MongoDB, 셸,
함수, 인터랙티브. 묻는 것은 그대로였다: **주어진 입력에서 정답을 만들어 내는가.**

여기서 늘리려는 것은 **"무엇을 묻는가"** 다.

| | 지금 | 여기서 |
|---|---|---|
| 사용자가 만드는 것 | 답을 내는 코드 | **고친 코드 · 시험 코드 · 명령의 연속 · 고른 보기** |
| 채점이 보는 것 | 출력이 같은가 | **숨긴 시험이 통과하는가 · 심은 버그를 잡는가 · 끝난 뒤 상태 · 값이 맞는가** |
| 처음부터 쓰는가 | 그렇다 | **아니다** — 남의 코드에서 시작하는 것이 절반이다 |

**이 차이가 중요한 이유는 실제 일이 그렇기 때문이다.** 개발자가 하루에 하는 일 중
빈 파일에서 시작하는 것은 적다. 대부분은 남이 쓴 것을 읽고, 왜 안 되는지 알아내고,
안 깨지게 고치고, 그것을 지킬 시험을 쓴다.

## 2. 네 방향

| 방향 | 제출하는 것 | 채점이 보는 것 | 무엇이 새로 필요한가 |
|---|---|---|---|
| **개념 퀴즈** | 고른 보기 · 짧은 답 | 값이 맞는가 | **실행기가 필요 없다.** api 가 즉시 채점 |
| **읽고 고치기** | 고친 파일들 | 숨긴 시험이 통과 + **안 바꿔야 할 것이 그대로** | 여러 파일(#457) + 보존 검사 |
| **테스트 쓰기** | 시험 코드 | **심은 버그를 잡는가**, 정상 구현은 통과하는가 | 한 제출을 **구현 여럿에** 돌린다 |
| **도구·환경** | 명령의 연속 · 설정 파일 · 정규식 | 끝난 뒤 상태 | 도구별 하네스 |

### 왜 이 순서인가

**개념 퀴즈 → 읽고 고치기 → 테스트 쓰기 → 도구·환경.**

싼 것부터가 아니다(그것도 맞지만). **뒤로 갈수록 "정답이 무엇인가" 를 정하기 어렵다.**
퀴즈는 정답이 값이고, 고치기는 시험이고, 테스트 쓰기는 **시험을 시험하는 것**이고,
도구·환경은 도구마다 다시 정해야 한다.

## 3. 개념 퀴즈 (`QUIZ`)

**자리는 이미 잡혀 있다.** `ProblemKind.QUIZ("객관식 · 단답", ready = false)` 가
#59 때 들어갔고 그 뒤로 비어 있다. `ProblemCategory` 에도 `NETWORK`·`OS`·`LANGUAGE`·
`SYSTEM_DESIGN` 이 이미 있다 — **분야는 있는데 그 분야의 문제를 낼 방법이 없다.**

정할 것:

- **부분 점수.** 보기 넷 중 둘을 고르는 문제에서 하나만 맞으면? #473 이 부분 점수를
  다루므로 **그 결론을 따른다.** 먼저 하면 두 곳에서 다르게 정해진다
- **답이 새는 것.** 정답이 api 응답에 실려 나가면 개발자 도구로 보인다.
  **채점만 서버에서 하고 정답은 채점 뒤에만 준다**
- **단답의 비교 규칙.** 대소문자·공백·동의어(`TCP` / `tcp` / `전송 제어 프로토콜`).
  **정규화 규칙을 문제가 갖는다** — 전역 규칙 하나로는 못 한다
- **다시 풀기.** 코드 문제는 몇 번 내도 되지만 4지선다는 **네 번이면 맞는다.**
  틀리면 해설을 보여 주고 **그 문제는 그날 다시 못 풀게** 하는 쪽을 본다

**랭킹에 넣지 않는 것을 먼저 생각한다.** 점수(#57)가 "푼 문제의 난이도 합" 인데,
찍어서 맞는 문제가 그 합에 들어가면 랭킹의 뜻이 옅어진다.

## 4. 읽고 고치기 (`JUDGE_PATCH`)

> 돌아가지 않는 코드 · 느린 코드 · 읽기 나쁜 코드를 주고 **고치게** 한다.

**재료는 대부분 있다.** 여러 파일(#457·#497·#498)이 파일 여럿을 주고받는 길을 냈고,
함수형 하네스(#421)가 **보이지 않는 코드를 함께 컴파일하는 방법**을 이미 정했다 —
숨긴 시험은 그 하네스와 같은 자리에 놓인다.

**새로 필요한 것은 하나다: 무엇을 안 바꿨는지 보는 것.**

세 종류가 각자 다른 것을 요구한다.

| 종류 | 통과 조건 | 추가로 필요한 것 |
|---|---|---|
| **디버깅** | 숨긴 시험이 통과한다 | 없음 — #457 + #421 로 선다 |
| **성능** | 통과 + **시간 안에** | 큰 입력. 지금 시간 제한으로 된다 |
| **리팩터링** | 통과 + **겉이 안 바뀌었다** | **공개 API 보존 검사** |

**리팩터링이 어렵다.** "읽기 좋게 고쳐라" 는 채점할 수 없다. 채점할 수 있는 형태로
바꾸면 이렇게 된다 — *동작을 유지한 채, 이 함수를 없애라* / *이 파일을 셋으로 나눠라* /
*이 중복을 하나로 만들어라*. 그러면 **검사할 수 있는 명제**가 된다.

> **가장 나쁜 설계는 "코드 스타일 점수" 다.** 그것은 사람마다 다르고,
> 다르다는 것을 사용자가 안다. 채점이 취향으로 보이는 순간 문제를 믿지 않게 된다.

**코드 리뷰**(문제의 코드에서 결함을 찾아 지적)는 여기 두지 않는다 —
제출이 코드가 아니라 **글**이라 `MANUAL`(사람 검수) 쪽이다. 다만 *"몇 번 줄이 문제인가"*
로 좁히면 `QUIZ` 가 된다. **그 쪽이 먼저다.**

## 5. 테스트 쓰기 (`JUDGE_TEST`)

> 구현을 주고 **그것을 지킬 시험**을 쓰게 한다.

**채점 방식이 뒤집혀 있어서 재미있다.** 지금까지는 우리가 시험을 숨기고 사용자가
구현을 냈다. 여기서는 **사용자가 시험을 내고 우리가 구현을 숨긴다.**

```
사용자의 시험 ─┬─→ 올바른 구현        → 통과해야 한다   (안 그러면 시험이 틀린 것)
               ├─→ 버그 심은 구현 1   → 실패해야 한다
               ├─→ 버그 심은 구현 2   → 실패해야 한다
               └─→ …                              (뮤테이션 테스팅)
```

**정답 = 심은 버그를 전부 잡고, 멀쩡한 구현은 통과시키는 시험.**

이것이 좋은 이유는 **"시험을 잘 썼다" 를 취향 없이 잴 수 있기 때문이다.**
`assert(true)` 는 멀쩡한 구현을 통과시키지만 버그를 하나도 못 잡는다.
모든 것을 실패시키는 시험은 멀쩡한 구현에서 걸린다.

정할 것:

- **실행 횟수가 구현 수만큼이다.** 구현 다섯이면 제출 하나에 실행 다섯이다.
  실행기 부하가 유형 중 가장 크다 — **구현 개수 상한**을 문제 형식에 둔다
- **어느 시험 도구를 쓰는가.** 언어마다 다르다(pytest·JUnit·go test).
  **함수형 하네스(#421)와 같은 판단**이 이미 있다: 합치는 방법을 런타임 정의가 안다
- **무한 루프와 시간 제한.** 사용자의 시험이 안 끝날 수 있다. 지금 제한이 그대로 쓰인다
- **버그를 심은 구현이 새면 답이 보인다.** 채점 로그·실행 응답에 실리지 않아야 한다
  (#525 가 SQL 에서 겪은 것과 같은 자리)

## 6. 도구·환경

**넷을 한 덩어리로 보면 안 된다.** 각각 필요한 것이 다르고, **하나는 지금 할 수 없다.**

### 6.1 정규식 — 가장 싸다

제출이 패턴 하나다. 채점은 "이 문자열들은 맞고 저것들은 아니다".

**실행기를 새로 만들 것이 없다** — 이미 있는 런타임에서 그 언어의 정규식 엔진으로
돌리면 된다. 다만 **엔진마다 문법이 다르므로** 문제가 엔진을 정해야 한다
(#454 가 SQL 에 MariaDB 를 더할 때 한 판단과 같다).

> ⚠️ **재앙적 백트래킹(ReDoS)이 여기서는 사용자 입력이다.** 지금 시간 제한이
> 그것을 잡지만, **잡는다는 것을 확인해야 한다** — `(a+)+$` 를 실제로 내 봐야 안다.

### 6.2 Git — 상태 비교로 선다

제출이 명령의 연속이고 채점이 **끝난 뒤 저장소 상태**다 — **Redis 유형(#455)과 정확히
같은 모양**이다. 하네스가 시드 저장소를 만들고, 사용자 명령을 흘려 넣고,
확인 명령(`git log --format=...`, `git rev-list`)의 출력을 견준다.

`harness/run-git.sh` 하나가 `run-redis.sh` 자리에 들어간다. **새 구조가 없다.**

정할 것: **커밋 해시가 매번 다르다.** 시각과 작성자를 고정해야 결과가 재현된다
(`GIT_AUTHOR_DATE`·`GIT_COMMITTER_DATE` 고정). 안 하면 **같은 답이 때에 따라 틀린다** —
#605 가 Redis 만료에서 겪은 것과 같은 종류다.

### 6.3 Docker · Kubernetes — **지금은 못 한다**

컨테이너 안에서 컨테이너를 돌리는 일이다. 그것은 특권 컨테이너나 소켓 마운트를
요구하고, **이 저장소의 샌드박스 위협 모델(docs/07, #48)이 정확히 막으려는 것**이다.
"연습 문제를 내려고 샌드박스를 연다" 는 맞바꿈이 아니다.

**대신 할 수 있는 것이 둘 있고, 그것으로 배울 것의 상당 부분이 덮인다.**

| 대신 | 무엇을 묻나 | 무엇이 필요한가 |
|---|---|---|
| **정적 검사** | 이 Dockerfile·매니페스트가 옳은가 | 파서 + 규칙. 실행 없음 |
| **개념 퀴즈** | 이 상황에서 파드가 왜 안 뜨나 | §3 으로 선다 |

**"실제로 빌드해 봐야 아는 것" 은 못 묻는다.** 그것을 인정하고 적어 둔다 —
할 수 있다고 이름 붙이면 다음 사람이 속는다 (#455 가 `JUDGE_NOSQL` 을 피한 이유).

## 7. 유형을 새로 만들 것인가

**유형(`ProblemKind`)은 채점 방식이 다를 때만 는다.** 이 문서의 넷을 그 기준으로 보면

| 방향 | 유형 |
|---|---|
| 개념 퀴즈 | **`QUIZ`** — 이미 있다. `ready = true` 로 바꾸는 일 |
| 읽고 고치기 | **`JUDGE_PATCH`** (새로) — 채점이 "숨긴 시험 + 보존" 이라 다르다 |
| 테스트 쓰기 | **`JUDGE_TEST`** (새로) — 한 제출을 구현 여럿에 돌린다. 실행 모델이 다르다 |
| 정규식 | **`JUDGE_STDIO`** 로 된다 — 굳이 나누지 않는다 |
| Git | **`JUDGE_GIT`** (새로) — Redis 와 같은 모양이되 **이름을 좁게 둔다** |
| Docker · K8s | 없음 (§6.3) |

**분야(`ProblemCategory`)는 따로 늘어난다.** #592 가 이미 겪은 문제다 — 유형은
늘었는데 분야가 안 따라와 Redis 문제가 `ALGORITHM` 에 있었다. 이번에는 **함께 정한다**:
`VERSION_CONTROL`, `REGEX`, `TESTING`, `DEBUGGING`.

> ⚠️ **`CATEGORY_10` 뱃지가 분야별로 센다**(V45). 분야를 늘리는 것은 안전하지만
> **기존 문제를 옮기는 것은 이미 받은 뱃지의 근거를 바꾼다.** #592 가 남긴 경고 그대로다.

## 8. 하지 않기로 한 것

- **채점을 사람이 하는 유형을 늘리지 않는다.** `MANUAL` 은 이미 있고 `ready = false` 다.
  **검수할 사람이 없는 채로 열면 제출이 영원히 대기 상태**가 된다
- **코드 스타일 점수를 매기지 않는다** (§4)
- **Docker · K8s 실습을 지금 열지 않는다** (§6.3)
- **부분 점수를 여기서 정하지 않는다.** #473 이 그 자리다
