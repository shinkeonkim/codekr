# 랭킹 · 티어 · 뱃지 기획

- 상태: 초안 확정 (구현 전)
- 근거 이슈: #41
- 선행: #34(전체 제출), #36(활동 집계)

## 1. 무엇을 해결하려는가

**문제:** 지금은 "내가 얼마나 늘고 있는지" 알 방법이 제출 목록뿐이다. 활동 그래프(#36)가
꾸준함은 보여주지만 **실력의 성장**은 보여주지 못한다.

**목표:** 학습자가 자기 위치와 성장을 확인하고, 다음에 무엇을 풀지 판단할 근거를 준다.

**성공 지표**

| 지표 | 왜 이것인가 |
|---|---|
| 랭킹 진입 후 7일 내 재방문율 | 랭킹이 다시 오게 만드는가 |
| 사용자당 **서로 다른 문제** 풀이 수 | 같은 문제 반복이 아니라 폭이 넓어지는가 |
| 자기 티어보다 높은 난이도 시도 비율 | 도전을 유도하는가 |

**하지 않을 것:** 상위 1%를 위한 경쟁 장치. 이 서비스는 학습 도구이고, 랭킹은 그 수단이다.

## 2. 무엇을 세는가 — 점수 규칙

### 후보 비교

| 후보 | 장점 | 악용 방식 | 판단 |
|---|---|---|---|
| 정답 수 | 이해하기 쉽다 | 쉬운 문제만 반복 | ✗ 단독 사용 불가 |
| **난이도 가중 정답 수** | 어려운 문제를 풀 이유가 생긴다 | 난이도 인플레 유도 | ✅ 채택 |
| 시도 횟수 대비 정답률 | 신중한 풀이를 유도 | 확실할 때만 제출 → 학습 위축 | ✗ |
| 실행 시간 순위 | 최적화 동기 | 언어별 유불리가 크다 | ✗ (문제별 랭킹에서만) |
| 최초 해결 보너스 | 새 문제 유입 | 신규 문제 알림을 받는 소수에게 쏠림 | △ 대회에서만 |

### 채택안

**문제당 점수 = 난이도 레벨 기반 값. 한 문제는 최초 정답 1회만 점수를 준다.**

```
문제 점수 = round(10 × 1.25^(난이도레벨 - 1))
  브론즈 5(레벨 1)  = 10점
  실버 5(레벨 6)    = 31점
  골드 5(레벨 11)   = 93점
  플래티넘 5(레벨 16) = 284점
  다이아 5(레벨 21)  = 867점
  루비 1(레벨 30)   = 6,462점
```

- 지수는 "티어 하나를 올리면 대략 3배"가 되도록 잡았다. 난이도 차이를 체감할 만큼 벌리되,
  상위 티어 한 문제가 하위 전체를 압도하지 않는 선이다.
- **같은 문제를 다시 풀어도 점수는 늘지 않는다.** 반복 제출로 점수를 얻을 수 없다.
- 오답에는 감점이 없다. 감점은 제출을 두려워하게 만들고, 학습 도구에서는 해롭다.
- **총점은 상위 100문제만 합산한다** (#85 에서 수정). 처음에는 푼 문제를 전부 더할
  생각이었으나, 그러면 브론즈 1,000문제(10,000점)가 루비 한 문제(6,462점)를 이긴다.
  쉬운 문제를 대량으로 푸는 것이 가장 효율적인 전략이 되고, 그때 이 숫자는 실력이 아니라
  **누적 시간**을 나타낸다. solved.ac 의 ac-rating 이 상위 일부만 반영하는 것과 같은 이유다.
- 공개되지 않은 문제는 점수를 주지 않는다. 준비 중인 문제로 점수를 벌 수 있으면
  출제자와 그 지인만 유리해진다.

### 지표는 하나가 아니다 (#85)

| 지표 | 정의 | 무엇을 보는가 |
|---|---|---|
| 실력 점수 | 가장 어려운 100문제의 난이도 점수 합 | 도달한 난이도 |
| 푼 문제 수 | 맞힌 서로 다른 문제 수 | 꾸준함 |

지표를 하나만 두면 그 지표에 맞춘 행동만 유도한다. 두 지표를 나란히 두면 "많이 푼 사람"과
"어려운 걸 푸는 사람"이 각자의 자리를 갖는다. 지표 목록은 **서버가 알려준다** —
지표가 늘어날 때 화면을 같이 고쳐야 하는 구조를 만들지 않는다.

### 동점 처리

1. 총점 → 2. 서로 다른 해결 문제 수 → 3. **최초 해결 시각이 이른 순** → 4. 사용자 ID

마지막 키까지 결정적이어야 페이지 사이에서 순서가 흔들리지 않는다 (#34 에서 겪은 문제).

이 규칙은 순서를 끝까지 정하므로 **공동 순위가 생기지 않는다.** 같은 점수여도 등수는 갈린다.

### 점수를 어떻게 저장하는가

`user_problem_scores` 는 (사용자, 문제) 당 한 행이다. 순위 표는 따로 두지 않고 그 위에서
집계한다 — 두면 원자료와 갈라지고, 갈라진 것을 되돌리는 장치를 또 만들어야 한다.

갱신은 **증분이 아니라 제출 기록에서 다시 세어 덮어쓴다** (#105 의 활동 집계와 같은 방식).
재채점(#107)으로 정답이 오답이 되면 점수는 **내려가야 하는데**, 증분 방식에는 내려갈 길이
없어서 잘못된 점수가 영구히 남는다. 점수가 내려간 사용자에게는 재채점 알림에 그 사실을
함께 담는다 — 알림을 따로 보내면 같은 일을 두 번 알리는 소음이 된다.

## 3. 랭킹 단위와 노출 위치

| 단위 | 1차 출시 | 이유 |
|---|---|---|
| 전체 누적 | ✅ | 가장 단순하고 이해하기 쉽다 |
| 월간 | ✅ | 신규 사용자도 상위권에 닿을 수 있다 |
| 카테고리별(알고리즘/SQL/…) | ⏸ 2차 | 문제 수가 카테고리마다 충분해진 뒤 |
| 문제별(실행 시간) | ⏸ 2차 | 언어별 유불리 보정이 먼저 필요 |

노출: `/ranking` 전용 화면, 사용자 프로필, 문제 상세의 "이 문제를 푼 사람" (2차).

## 4. 티어와 뱃지

**사용자 티어는 문제 난이도 티어와 이름을 공유하되 다른 개념이다.** 혼동을 막기 위해
화면에서는 "실력 티어"와 "문제 난이도"로 구분해 표기한다.

- 사용자 티어 = 누적 점수 구간. 브론즈~루비 6단계 × 5스텝(#19 의 30레벨 체계 재사용).
  구간은 `round(50 × 1.35^(레벨-2))` — 한 단계마다 약 1.35배, 티어 하나(5단계)마다 약 4.5배다.
  문제 점수(1.25배)보다 가파른 이유는, 티어를 올리려면 더 어려운 문제를 **더 많이** 풀어야
  하기 때문이다. 같은 기울기면 문제 하나를 풀 때마다 티어가 올라간다.
- 한 문제도 못 푼 사람은 **티어가 없다.** 브론즈 5 로 시작시키면 "아직 시작하지 않음"과
  "가장 낮음"이 구분되지 않는다.
- **강등 없음(1차).** 학습 도구에서 강등은 이탈 사유가 된다. 시즌제를 도입하면 그때 재검토한다.
  구현: 티어는 현재 점수가 아니라 **도달했던 최고 점수**(`users.peak_score`)로 정한다.
  현재 점수와 갈라질 수 있고 그게 의도다 — 재채점(#107)으로 점수가 내려가도 티어는 남는다.
  우리 잘못(잘못된 테스트케이스)으로 남의 티어를 깎아서는 안 된다.
- **한 번 준 뱃지는 회수하지 않는다** — 단, **규칙을 좁힌 경우는 예외다** (2026-08-15, #558).

  원래 판단은 이랬다: 그때 실제로 한 일이고, 나중에 조건이 깨져도 그날 그 일을 한 것은
  사실이다. 회수하면 화면에서 뱃지가 사라지는데 사용자는 이유를 알 길이 없다.

  **재채점으로 정답이 뒤집힌 경우에는 이 판단이 그대로다.** 사용자가 아무것도 안 했는데
  사라지는 것이라 성격이 더 나쁘다.

  **운영자가 규칙을 좁힌 경우만 거둔다.** 그대로 두면 "자격 없는 사람이 가진 뱃지" 가
  남아 규칙이 무엇을 뜻하는지 흐려진다. 대신 **거두면서 반드시 알린다** — 원래 반대
  근거가 "이유를 알 길이 없다" 였으므로, 알리지 않으면 뒤집을 이유가 없어진다.
- ~~**랭킹 비참여 설정**~~ — **없앴다** (#207). 배려처럼 보였지만 만드는 것은 *일부만 보이는
  순위표*였다. 빠진 사람이 있는 순위에서 "3위" 는 무엇의 3위인지 알 수 없다.
  **탈퇴한 사람만 뺀다** — 없는 사람이 순위에 있으면 눌렀을 때 갈 곳이 없다.
- 뱃지는 **행동 기반**으로만 준다: 첫 정답, 7일·30일 연속(#36), 카테고리 10문제, 신규 문제 최초 해결.
  점수 기반 뱃지는 티어와 중복이라 두지 않는다.

## 5. 재계산 규칙

점수는 **파생 데이터**다. 원본(제출·문제)이 바뀌면 다시 계산할 수 있어야 한다.

| 사건 | 처리 |
|---|---|
| 문제 난이도 변경 | 그 문제로 얻은 모든 점수 재계산 |
| 문제 삭제(소프트) | 그 문제의 점수 제외. 제출 이력은 남는다(ADR-0007) |
| 테스트케이스 수정 | 그 자체로는 점수를 건드리지 않는다. 재채점을 실행해야 반영된다 (아래) |
| 판정 정정(재채점) | **점수도 함께 바뀐다. 내려갈 수도 있다** (아래) |
| 회원 탈퇴 | 랭킹에서 제외, 점수 이력은 보존 |

### 재채점은 점수를 내릴 수 있다

**재채점 결과 답안이 틀렸다면 그 문제로 얻은 점수를 회수한다** (#107).

처음에는 "사용자 잘못이 아닌 이유로 점수가 사라지면 신뢰를 잃는다" 는 이유로 과거 정답을
지키려 했으나, 그러면 **잘못된 판정 위에 랭킹이 남는다.** 틀린 풀이로 얻은 점수를 지키는
것이 오히려 랭킹 전체의 신뢰를 깎는다 — 그 순위표는 실력을 나타내지 않게 된다.

지키는 것은 점수가 아니라 **납득 가능성**이다.

- 테스트케이스 수정만으로는 아무것도 바뀌지 않는다. **운영자가 재채점을 실행해야** 반영된다
- 점수가 내려간 사용자에게 **왜 내려갔는지와 함께 알린다** (#106).
  순위가 이유 없이 바뀌면 그때 신뢰를 잃는다
- "한 번 오른 점수는 내려가지 않는다" 는 규칙을 둔다면 **이 경우는 예외**여야 한다

## 6. 제외 대상

- 정답 코드 검증 제출(#39) — `kind != USER`
- 소프트 삭제된 제출
- **탈퇴한 사용자** (`withdrawn_at IS NOT NULL`)

관리자 계정도 **빼지 않는다** (#207 이 #188 을 뒤집었다). 어드민이 정답을 보고 푸는 것이
문제라면 그것은 운영 규율의 문제이지 순위표를 접을 이유가 아니다.

## 7. 부정행위 최소 방어

랭킹이 생기는 순간 어뷰징 유인이 생긴다. 1차에서는 **탐지보다 구조적 무력화**를 택한다.

| 위험 | 구조적 방어 |
|---|---|
| 같은 문제 반복 제출 | 문제당 1회만 점수 → 무의미 |
| 다계정 | 점수는 계정 간 이전 불가. 순위표에만 영향 → 1차 수용, 이상 패턴만 로깅 |
| 남의 코드 복사 | #33 공개 범위로 노출을 사용자가 통제. 표절 검사는 별도(#43 비범위) |
| 무의미한 대량 제출 | 점수에 영향 없음. rate limit 은 대회(#43)에서 함께 |

## 8. 계산 방식

| 대안 | 정합성 | 성능 | 운영 비용 | 판단 |
|---|---|---|---|---|
| 조회 시 실시간 집계 | 항상 정확 | 사용자·제출이 늘면 급격히 악화 | 낮음 | ✗ |
| **이벤트 기반 증분 + 주기적 전체 재계산** | 증분이 틀려도 재계산이 바로잡는다 | 좋음 | 중간 | ✅ 채택 |
| 배치 전용(1일 1회) | 단순 | 좋음 | 낮음 | ✗ 반영이 늦어 동기 부여가 약하다 |

**채택:** 채점 완료 이벤트(이미 존재)에서 `user_problem_scores` 를 갱신하고,
`user_rankings` 를 증분 반영한다. 하루 1회 전체 재계산으로 드리프트를 바로잡는다.

예상 규모(1년): 사용자 1만, 문제 1천, 제출 100만 → `user_problem_scores` 최대 1천만 행.
현재 PostgreSQL 한 대로 충분하다.

## 9. 출시 선행 조건

랭킹은 **컨텐츠가 얇을 때 켜면 해롭다** (ADR-0006 의 판단). 문제가 몇 개 없으면 순위가
실력이 아니라 "언제 시작했는가"를 나타내고, 한번 그렇게 굳으면 되돌리기 어렵다.

전제 조건은 **난이도를 믿을 수 있는가** 하나다 — #39 정답 코드 검증이 문제 등록 절차에
자리 잡아야 한다. 난이도가 흔들리면 어떤 공식을 써도 순위가 흔들린다.

> 이전 판에는 "공개 문제 150개, 30일 활성 50명" 같은 숫자를 적어 두었으나 걷어냈다.
> 근거 없이 정한 숫자는 판단을 돕지 않고, 충족 여부를 재는 순간 목적이 바뀐다.

### 난이도 투표가 점수에 닿는 자리 (#477)

이 문서의 점수 공식은 전부 `난이도레벨` 위에 서 있다. 그 값이 어디서 오는지가 오래
비어 있었다 — 출제자 한 사람의 감이었다.

- **푼 사람만, 문제당 한 표**, 언제든 바꿀 수 있다
- 표는 `UNRATED` 문제에만 난이도를 붙인다. 문턱은 설정값이고 **중앙값**을 쓴다
- 난이도가 붙는 순간 **이미 맞힌 사람들의 점수를 다시 계산한다**(#194) — 그러지 않으면
  같은 문제를 푼 두 사람의 점수가 푼 시점에 따라 갈린다
- `RATED` 문제는 표로 움직이지 않는다. 사람이 정한 값을 투표가 덮으면 **이미 매겨진
  점수가 소급해서 흔들린다**
