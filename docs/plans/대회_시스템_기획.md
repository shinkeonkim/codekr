# 대회 시스템 기획

- 상태: 초안 확정 (구현 전)
- 근거 이슈: #43
- 선행: #16(k8s 배포), #34(제출 목록), #40(실행기 스케일)

## 1. 왜 별도 도메인인가

대회는 평소 문제 풀이와 **부하 모양과 운영 요구가 다르다.**

- 제출이 시작 직후와 마감 직전에 몰린다 (평소의 수십 배가 몇 분에)
- 순위 동결, 재채점, 이의 제기처럼 평소에 없는 운영 행위가 있다
- 문제가 **시작 시각까지 감춰져야** 한다 — 공개 여부만으로는 표현되지 않는다

그래서 채점 파이프라인은 그대로 재사용하되, 도메인은 분리한다.

## 2. 생명주기

```
DRAFT ──▶ SCHEDULED ──▶ RUNNING ──▶ ENDED ──▶ ARCHIVED
  │            │            │
  └── 삭제      └── 취소      └── 취소(진행 중 중단)
```

| 상태 | 참가 등록 | 문제 공개 | 제출 | 순위표 |
|---|---|---|---|---|
| `DRAFT` | 불가 | 어드민만 | 불가 | 없음 |
| `SCHEDULED` | 가능 | 감춤 | 불가 | 없음 |
| `RUNNING` | 가능(설정) | 참가자에게 공개 | 가능 | 실시간(동결 전) |
| `ENDED` | 불가 | 전체 공개 | 불가(연습 제출은 별도) | 확정 |
| `ARCHIVED` | 불가 | 전체 공개 | 연습 제출만 | 보존 |

권한: 대회 생성·상태 전이는 어드민. 1차에서는 대회별 운영자 위임을 두지 않는다.

## 3. 1차 출시 범위

| 항목 | 1차 | 이후 |
|---|---|---|
| 공개 대회 | ✅ | |
| 비공개·초대 | | ✅ |
| 개인 참가 | ✅ | |
| 팀 참가 | | ✅ |
| 채점 방식 | 점수형 | ACM/ICPC형 |
| 순위 동결 | ✅ | |
| 이의 제기 | 공지·질의만 | 정식 이의 절차 |

**점수형을 먼저 하는 이유:** ACM 형은 패널티 시간 계산과 동점 규칙이 복잡하고, 규칙을
잘못 구현하면 대회 중에 바로잡을 수 없다. 점수형은 규칙이 단순해 첫 대회의 위험이 작다.

## 4. 참가와 제출

- **참가 등록**은 시작 전·중 모두 가능(설정). 등록하지 않으면 문제를 볼 수 없다.
- **문제 공개**는 `RUNNING` 진입 시점에 일괄. 예약 시각과 실제 전이의 오차를 줄이기 위해
  스케줄러가 아니라 **조회 시점의 시각 비교**로 판정한다 (스케줄러 지연이 곧 사고가 되지 않게).
- **마감**: 마감 시각 이후 제출은 거부. 마감 직전에 접수된 제출은 **채점이 늦어도 유효**하다.
  접수 시각 기준으로 판단한다 — 채점 지연이 참가자 불이익이 되면 안 된다.
- **지각 제출**: 1차에서는 허용하지 않는다.

## 5. 채점과 순위

### 점수형 규칙

- 문제마다 배점을 어드민이 정한다 (난이도 자동 배점이 아니라 명시 — 대회 설계의 자유도).
- 부분 점수는 1차에서 없다. 전부 통과해야 배점을 얻는다.
- **동점 처리**: 총점 → 마지막 득점 시각이 이른 순 → 참가 등록 시각 → 사용자 ID.

### 순위표

- `RUNNING` 중에는 실시간. **동결 시각**(기본: 종료 30분 전)부터 순위 변화가 참가자에게 감춰진다.
- 어드민은 동결 중에도 실제 순위를 본다.
- 종료 후 **해제**하면 최종 순위가 공개된다.
- 순위표 조회는 캐시한다. 대회 중 가장 많이 호출되는 화면이다.

세부 규칙은 **§5.1 프리즈** 에서 정한다 (#86).

## 5.1 프리즈 — 규칙 정의 (#86)

프리즈 규칙을 잘못 만들면 **대회 중에 바로잡을 수 없다.** 참가자에게는 규칙이 바뀐
것으로 보이고, 그 대회의 결과 전체가 의심받는다. 그래서 구현 전에 여기서 못 박는다.

### 기존 대회들은 어떻게 하는가

| | ICPC | Codeforces | BOJ 대회 |
|---|---|---|---|
| 프리즈 시점 | 종료 1시간 전(5시간 대회) | 종료 30분 전(보통) | 주최자 설정 |
| 감춰지는 것 | 프리즈 이후의 **판정 결과** | 같음 | 같음 |
| 시도 사실 | **보인다** (칸이 "시도 중"으로 표시) | 보인다 | 보인다 |
| 내 결과 | **본인은 본다** | 본인은 본다 | 본인은 본다 |
| 해동 연출 | 시상식에서 아래 등수부터 하나씩 | 없음(즉시 공개) | 없음 |
| 패널티 | 맞기 전 오답 1회당 20분 | 대회 형식마다 다름 | 형식마다 다름 |

**세 곳 모두 "시도했다는 사실"은 감추지 않는다.** 감추면 순위표가 대회 후반에 아무
정보도 주지 않게 되고, 관전의 재미도 사라진다. 감추는 것은 **결과**뿐이다.

### 우리의 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 기본 프리즈 시각 | 종료 **30분 전**. 대회마다 조정 가능하고 **0으로 두면 프리즈 없음** | 짧은 대회(2시간)가 많을 것이라 1시간은 과하다 |
| 감추는 것 | 프리즈 이후 제출의 **판정과 점수** | |
| 감추지 않는 것 | **누가 어느 문제를 시도했는지, 몇 번 냈는지** | 순위표가 후반에 무의미해지지 않게 |
| 본인 결과 | **본인에게는 그대로 보인다** | 자기 제출 결과를 못 보면 다음 판단을 할 수 없다. 부정행위 방지 효과도 없다 |
| 순위 자체 | 프리즈 시점의 순위로 **고정** | |
| 어드민 | 프리즈 중에도 실제 순위를 본다. **같은 화면에서 전환**한다 | 화면을 둘로 나누면 어느 쪽을 보고 있는지 헷갈린다. 전환 상태를 화면에 크게 표시한다 |
| 해동 연출 | **1차에서 하지 않는다** | 오프라인 시상식이 있을 때만 값이 있다. 종료 후 즉시 전체 공개한다 |
| 풍선 | **하지 않는다** | 오프라인 요소다. 온라인에서는 순위표의 색으로 충분하다 |

### 상태별로 누가 무엇을 보는가

| 상태 | 참가자(남의 결과) | 참가자(본인 결과) | 시도 사실 | 어드민 |
|---|---|---|---|---|
| `RUNNING`, 프리즈 전 | 실시간 | 실시간 | 보임 | 실시간 |
| `RUNNING`, 프리즈 후 | **프리즈 시점 그대로** | 실시간 | 보임 | 실시간(전환) |
| `ENDED`, 해제 전 | 프리즈 시점 그대로 | 실시간 | 보임 | 실시간(전환) |
| `ENDED`, 해제 후 | 최종 | 최종 | 보임 | 최종 |
| `ARCHIVED` | 최종 | 최종 | 보임 | 최종 |

**해제는 자동이 아니라 어드민의 행위다.** 종료와 동시에 자동 공개하면, 종료 직후
발견된 문제(테스트케이스 오류 등)를 바로잡을 틈이 없다.

### 패널티는 1차에서 두지 않는다

이 대회는 **점수형**이다 (§5). ICPC 의 20분 패널티는 "모든 문제의 배점이 같다"는 전제
위에서 동작한다 — 배점이 다르면 분 단위 패널티와 점수를 어떻게 견줄지가 임의의 선택이 된다.

대신 **동점 처리에 시각을 쓴다**: 총점 → 마지막 득점 시각이 이른 순 → 참가 등록 시각 →
사용자 ID. 이러면 "빨리 푼 사람이 앞선다"는 성질은 유지되면서 임의의 환산이 없다.

오답에 대한 불이익이 필요한 형식(ICPC 연습)이 생기면 그때 대회 설정으로 추가한다.
**형식을 늘리는 것은 나중에 할 수 있지만, 규칙을 바꾸는 것은 대회 중에 할 수 없다.**

### 프리즈 중에 재채점·문제 제외가 일어나면

| 사건 | 처리 |
|---|---|
| 재채점 | 순위표에 **"재채점 진행 중"** 을 표시하고, 완료 후 일괄 반영한다. 프리즈 중이면 참가자에게는 여전히 프리즈 시점 순위가 보인다 |
| 문제 제외 | **즉시 반영한다** — 프리즈로 감추지 않는다. 없어진 문제를 계속 푸는 것은 시간 낭비이고, 그것을 알리지 않는 것이 더 불공정하다 |
| 제외로 순위가 바뀜 | 참가자에게 공지한다. 프리즈는 "결과를 감추는" 장치이지 "규칙 변경을 감추는" 장치가 아니다 |

**프리즈 시점의 순위는 그때 계산해 저장한다.** 그 뒤의 재채점이 과거 순위를 바꾸면
참가자가 본 화면과 기록이 달라진다 — 무엇이 진짜였는지 아무도 증명할 수 없게 된다.

### 순위표는 일반 랭킹과 다른 화면이다

일반 랭킹(#57, #85)은 누적 실력이고, 대회 순위표는 **그 대회 안에서의 순위**다.
지표도 다르고(총점·마지막 득점 시각 vs 실력 점수·푼 문제 수), 보는 시점도 다르다.
코드를 공유하지 않는다 — 공유하면 대회 규칙 변경이 일반 랭킹을 건드리게 된다.

### 재채점과 정합성

| 사건 | 처리 |
|---|---|
| 테스트케이스 오류 발견 | 어드민이 **해당 문제 전체 재채점**을 실행. 순위는 재채점 완료 후 일괄 반영 |
| 특정 제출 판정 취소 | 그 참가자만 재계산 |
| 문제 자체가 잘못됨 | 문제를 대회에서 제외. 그 문제의 점수를 전원에게서 제거 |
| 대회 취소 | 순위 미확정으로 종결. 제출 이력은 보존 |

#### 판정은 나빠지는 방향으로도 바뀐다

**재채점 결과 답안이 틀렸다면 오답으로 바꾼다.** 이미 맞은 것으로 되어 있어도 그렇다.

그러지 않으면 "한번 맞으면 영원히 맞음" 이 되고, 잘못된 테스트케이스로 통과한 풀이가
그대로 남는다. 그 위에 정답률(#84)·랭킹(#85)·대회 순위가 쌓이므로 **틀린 것을 맞은 채로
두면 그 위의 모든 숫자가 틀린다.**

바뀌는 것: 그 제출의 판정, 푼 문제 수, 정답률, 랭킹 점수, 대회 점수와 순위.

이 규칙은 **대회 밖에서도 같다.** 재채점은 대회만의 일이 아니다 — 평소 문제의
테스트케이스를 고쳐도 기존 제출을 다시 채점해야 한다.

#### 결과가 바뀐 사람에게 알린다

모르는 사이에 자기 기록이 바뀌는 것은 받아들이기 어렵다. **결과가 바뀐 사람에게 알림을
보낸다** (웹 내 알림, 카테고리 "채점").

- 알림에 **왜 바뀌었는지**를 담는다 (예: "이 문제의 테스트케이스가 수정되었습니다")
- **결과가 바뀌지 않은 사람에게는 보내지 않는다.** 소음이다
- 재채점 한 번에 수천 명분이 생길 수 있으므로 한꺼번에 만드는 경로가 필요하다

**재채점 중에는 순위표에 "재채점 진행 중" 을 표시한다.** 중간 상태의 순위를 보여주면
참가자가 잘못된 정보로 판단한다.

#### 남은 판단

- **소급 범위.** 몇 년 전 제출까지 다시 채점할 것인가. 런타임 이미지가 그때와 다르면
  같은 코드가 다른 결과를 낼 수 있다 (#96 이미지 다이제스트 고정과 얽힌다)
- 스트릭은 어떻게 할지. 판정이 뒤집혀도 **그날 활동한 사실 자체는 있었다**
- 재채점 실행이 큐를 점유한다. 일반 제출보다 우선순위를 낮춰야 한다 (#102)

세부는 #107 에서 다룬다.

## 6. 운영 안정성

이 부분이 대회의 본체다.

| 위험 | 대응 |
|---|---|
| 시작 직후 제출 폭증 | 실행기 사전 스케일 아웃(#40). 대회 시작 N분 전 자동 확장 |
| 큐 적체 | 대회 제출을 **별도 큐**로 분리해 평소 제출과 서로 굶기지 않게 한다 |
| 참가자별 과다 제출 | 참가자·문제당 rate limit (예: 30초에 1회) |
| 워커 장애 | 미처리 메시지는 pending 으로 남는다(ADR-0002). 워커 복귀 시 자동 재처리 |
| 채점 지연 | 접수 시각 기준 판정이므로 참가자 불이익 없음. 순위표에 지연 표시 |
| 대회 중 배포 | 대회 기간에는 배포를 금지한다 (운영 규칙) |

**별도 큐 결정:** 같은 큐를 쓰면 대회 제출이 평소 사용자의 채점을 몇 분씩 밀어낸다.
`codekr:judge:contest` 를 두고 워커를 나눈다 — 큐 구조는 이미 그렇게 되어 있어 추가 비용이 작다.

## 7. 공지·질의·부정행위

- 공지: 대회 상세에 시간순. 진행 중 추가 시 참가자에게 표시하고 **알림도 보낸다**
  (카테고리 "대회", #106). 대회 중 공지는 놓치면 손해가 되므로 화면에만 두지 않는다.
- 질의: 참가자 → 운영자 비공개 질문. 답변은 공개/비공개 선택. 답변이 달리면 질문자에게 알림.
- 부정행위: 1차에서는 **감사 이력만 남긴다** (제출 시각·IP·User-Agent).
  탐지·제재 자동화는 하지 않는다 — 오탐의 대가가 크다.
- 표절 검사는 별도 범위다. 다만 **나중에 검사하려면 데이터가 필요하므로**,
  대회 제출의 소스 코드는 공개 범위(#33)와 무관하게 보존한다. 보존 기간과
  개인정보 경계는 그때 정한다.
