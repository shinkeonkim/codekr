# 02. 도메인 모델

## 1. ERD

```
┌───────────────┐          ┌────────────────────┐        ┌──────────────────────┐
│ users         │          │ problems           │        │ problem_testcases    │
├───────────────┤          ├────────────────────┤        ├──────────────────────┤
│ id (PK)       │          │ id (PK)            │──1:N──▶│ id (PK)              │

│ password_hash │          │ title              │        │ seq                  │

│ role          │          │ difficulty_level   │        │ expected_output      │
│ created_at    │          │ description        │        │ visibility           │
│ updated_at    │          │ input_description  │        │ deleted_at           │
└───────┬───────┘          │ output_description │        └──────────────────────┘
        │                  │ time_limit_ms      │        ┌──────────────────────┐
        │                  │ memory_limit_mb    │──1:N──▶│ problem_templates    │
        │                  │ published          │        ├──────────────────────┤
        │                  │ created_by (FK)    │        │ id (PK)              │
        │                  │ deleted_at         │        │ problem_id (FK)      │
        │                  │ created_at         │        │ runtime_id           │
        │                  │ updated_at         │        │ source_code          │
        │                  └─────────┬──────────┘        │ deleted_at           │
        │                            │                   └──────────────────────┘
        │                            │
        │        ┌───────────────────┘
        │        │ 1:N
        ▼        ▼
┌──────────────────────────┐        ┌──────────────────────────────┐
│ submissions              │──1:N──▶│ submission_testcase_results  │
├──────────────────────────┤        ├──────────────────────────────┤
│ id (PK)                  │        │ id (PK)                      │
│ user_id (FK)             │        │ submission_id (FK)           │
│ problem_id (FK)          │        │ testcase_id (FK)             │
│ runtime_id               │        │ seq                          │
│ source_code              │        │ verdict                      │
│ status                   │        │ runtime_ms                   │
│ verdict                  │        │ memory_kb                    │
│ passed_count             │        │ stderr_excerpt               │
```

`(U*)` 는 **부분 유니크 인덱스**다 — `deleted_at IS NULL` 인 행에만 적용된다.

## 2. 테이블 정의

### 2.1 `users`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | BIGSERIAL | PK | |
| `email` | VARCHAR(255) | UNIQUE, NOT NULL | 로그인 ID |
| `password_hash` | VARCHAR(100) | NOT NULL | BCrypt 해시 |
| `nickname` | VARCHAR(30) | UNIQUE, NOT NULL | 표시 이름 |
| `role` | VARCHAR(20) | NOT NULL | `USER` \| `ADMIN` |
| `created_at`, `updated_at` | TIMESTAMPTZ | NOT NULL | |

평문 비밀번호는 어디에도 저장/로깅하지 않는다.

### 2.2 `problems`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | BIGSERIAL | PK | |
| `slug` | VARCHAR(120) | NOT NULL, 부분 UNIQUE | URL 식별자. 삭제된 문제의 slug 는 다시 쓸 수 있다 |
| `title` | VARCHAR(200) | NOT NULL | |
| `category` | VARCHAR(30) | NOT NULL | `ALGORITHM`, `DATA_STRUCTURE`, `SQL`, `NETWORK`, `LANGUAGE`, `OS`, `SYSTEM_DESIGN` |
| `difficulty_level` | INT | NULL 가능, 1~30 | 난이도(아래 3장). 미평가·평가안함이면 NULL |
| `difficulty_state` | VARCHAR(16) | NOT NULL | `RATED`/`UNRATED`/`NO_RATE` (#195) |
| `description` | TEXT | NOT NULL | 지문 (Markdown) |
| `input_description` | TEXT | | 입력 형식 |
| `output_description` | TEXT | | 출력 형식 |
| `time_limit_ms` | INT | NOT NULL, 기본 2000 | 테스트케이스당 |
| `memory_limit_mb` | INT | NOT NULL, 기본 256 | |
| `published` | BOOLEAN | NOT NULL, 기본 false | 미공개 문제는 목록에서 제외 |
| `created_by` | BIGINT | FK → users | |
| `deleted_at` | TIMESTAMPTZ | | 소프트 삭제 시각 |

인덱스는 모두 `WHERE deleted_at IS NULL` 부분 인덱스다: `(category, difficulty_level)`, `(published, created_at DESC)`, `slug` 유니크.

### 2.2-1 `tags` · `problem_tags` — 문제 분류의 두 축 (#232)

**`category` 와 태그는 다른 축이다. 둘의 경계를 지키지 않으면 같은 것이 두 곳에 생긴다.**

| | 묻는 것 | 개수 | 예 |
|---|---|---|---|
| `problems.category` | **무엇에 대한 문제인가** | 문제당 하나 | `SQL`, `NETWORK`, `OS`, `ALGORITHM` |
| 태그 | **어떤 기법으로 푸는가** | 문제당 여럿 | 다이나믹 프로그래밍, 이분 탐색, 최단 경로 |

규칙: **카테고리 값과 같은 뜻의 태그를 만들지 않는다.** "SQL" 은 카테고리이지 태그가
아니다. 반대로 "이분 탐색" 은 카테고리가 될 수 없다 — 그것으로 푸는 문제가 여러
카테고리에 걸친다.

| 표 | 컬럼 | 설명 |
|---|---|---|
| `tags` | `slug` | URL·필터 파라미터에 쓰는 이름. **만든 뒤 바꾸지 않는다** — 링크가 그것을 가리킨다 |
| | `name` | 화면에 보이는 이름. 바꿀 수 있다 |
| | `description` | 무엇을 뜻하는 태그인지. 비슷한 태그가 둘 생기는 것을 막는 유일한 수단 |
| `problem_tags` | `(problem_id, tag_id)` | PK. 반대 방향 조회를 위해 `tag_id` 에 인덱스를 하나 더 둔다 |

**평평하다.** "그래프 > 최단 경로 > 다익스트라" 같은 계층은 필터를 곱절로 복잡하게
만든다(상위를 고르면 하위까지 포함하는가). 필요해지면 `parent_id` 를 더하는 편이
이 표를 쪼개는 것보다 싸다.

**태그는 답의 일부다.** "이 문제는 DP" 를 알고 푸는 것과 모르고 푸는 것은 다른 문제다.
그래서 화면은 기본으로 접어 두고 펼쳤을 때만 보여 준다. 서버가 감추지는 않는다 —
"푼 뒤에만 보여 주기" 로 하면 태그로 공부할 문제를 고르는 일 자체가 불가능해진다
(#139 에서 정답 코드에 대해 같은 이유로 그 안을 버렸다).

### 2.3 `problem_testcases`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | BIGSERIAL | PK | |
| `problem_id` | BIGINT | FK, NOT NULL, ON DELETE CASCADE | |
| `seq` | INT | NOT NULL | 1부터 |
| `input` | TEXT | NOT NULL | stdin |
| `expected_output` | TEXT | NOT NULL | 기대 stdout |
| `visibility` | VARCHAR(10) | NOT NULL | `PUBLIC`(예제) \| `HIDDEN` |
| `deleted_at` | TIMESTAMPTZ | | 소프트 삭제 시각 |

`HIDDEN` 케이스의 `input`/`expected_output` 은 공개 API 응답 DTO 에 **필드 자체가 존재하지 않는다**.

유니크 인덱스 `(problem_id, seq) WHERE deleted_at IS NULL` — 살아 있는 케이스 안에서만 순번이 유일하다.

### 2.3-1 `problem_templates`

문제가 언어/버전별로 제공하는 초기 코드다. 지정하지 않은 실행 환경은
런타임 레지스트리(`infra/runtimes/runtimes.yaml`)의 기본 템플릿을 쓴다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | BIGSERIAL | PK | |
| `problem_id` | BIGINT | FK, NOT NULL | |
| `runtime_id` | VARCHAR(40) | NOT NULL | 예: `python:3.12` |
| `source_code` | TEXT | NOT NULL | 에디터 초기 코드 |
| `deleted_at` | TIMESTAMPTZ | | 소프트 삭제 시각 |

유니크 인덱스 `(problem_id, runtime_id) WHERE deleted_at IS NULL`.

### 2.3-2 `problem_runtime_limits`

문제의 실행 제한을 언어/버전별로 덮어쓴다 (#97). **행이 없으면 문제 기본값을 쓴다** —
이 표는 예외만 담는다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | BIGSERIAL | PK | |
| `problem_id` | BIGINT | FK, NOT NULL | |
| `runtime_id` | VARCHAR(40) | NOT NULL | 예: `python:3.12` |
| `time_limit_ms` | INT | NOT NULL, 100~30,000 | |
| `memory_limit_mb` | INT | NOT NULL, 16~2,048 | |
| `deleted_at` | TIMESTAMPTZ | | 소프트 삭제 시각 |

유니크 인덱스 `(problem_id, runtime_id) WHERE deleted_at IS NULL`.
제한을 고르는 규칙은 `docs/06_실행_제약_계약.md` 에 있다.

### 2.4 `submissions`

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGSERIAL | |
| `user_id`, `problem_id` | BIGINT FK | |
| `runtime_id` | VARCHAR(40) | 예: `python:3.12` |
| `source_code` | TEXT | 상한 64KB (애플리케이션 검증). **진입점 파일의 내용이다** |
| `source_files` | TEXT | 파일이 여럿인 문제의 나머지 파일 (#457). JSON, 없으면 NULL |
| `status` | VARCHAR(20) | `PENDING` → `JUDGING` → `COMPLETED` \| `FAILED` |
| `verdict` | VARCHAR(30) | 아래 판정표 |
| `passed_count` / `total_count` | INT | |
| `max_runtime_ms` / `max_memory_kb` | INT | 전체 케이스 중 최댓값 |
| `compile_error` | TEXT | 컴파일 실패 시 메시지 |
| `score` / `max_score` | INT | 부분 점수 (#473). 묶음이 없는 문제는 **NULL** |
| `deleted_at` | TIMESTAMPTZ | 소프트 삭제 시각 |

인덱스: `(user_id, created_at DESC)`, `(problem_id, created_at DESC)` — 모두 `WHERE deleted_at IS NULL`.

**`score` 가 0 이 아니라 NULL 인 이유**: 묶음이 없는 문제에 0 을 넣으면 만점짜리 정답이
화면에서 "0점" 으로 보인다. 없는 것과 0 은 다른 말이다.

### 2.4-1 파일이 여럿인 문제 (#457)

`problem_files` 가 **런타임마다** 채워야 할 파일 목록을 갖는다 — 같은 문제라도 자바는
`Main.java`·`Helper.java`, 파이썬은 `main.py`·`helper.py` 다. 목록이 없으면 지금까지처럼
파일 하나짜리 문제다.

| 컬럼 | 무엇 |
|---|---|
| `runtime_id`, `name` | 어느 언어의 어떤 파일인가 (`UNIQUE(problem_id, runtime_id, name)`) |
| `template` | 그 파일의 시작 코드 |
| `editable` | 거짓이면 **제출에 실리지 않는다** — 문제의 시작 코드가 그대로 쓰인다 |

제출은 진입점을 `source_code` 에, 나머지를 `source_files`(JSON)에 담는다. **한 벌로 두지
않은 이유**: 기존 제출 수만 건이 `source_code` 하나로 저장돼 있고, 재채점(#107)이 그것을
그대로 읽는다. `source_files` 는 **조회하지 않는 값**이라 JSONB 가 아니라 TEXT 다.

### 2.4-2 부분 점수 (#473)

`problem_testcase_groups` 가 묶음마다 점수를 갖고, `problem_testcases.group_no` 가 각
케이스를 묶음에 넣는다. **묶음 하나가 통째로 맞아야 그 점수를 받는다** — 한 케이스라도
틀리면 그 묶음은 0점이고, 남은 케이스는 돌리지 않는다.

**랭킹에는 반영하지 않는다.** 만점만 "풀었다" 로 본다(#57). 부분 점수의 교육적 값은
"어디까지 왔는지" 를 보여 주는 데서 대부분 얻어지고, 랭킹까지 열면 점수·티어·뱃지가
모두 다른 규칙을 갖게 된다.

### 2.5 `submission_testcase_results`

테스트케이스 단위 결과. `UNIQUE(submission_id, seq)` 로 **이벤트 재전달 시에도 멱등**하게 UPSERT 된다.

### 2.5-1 정답 코드와 검증 (#39)

문제는 선택적으로 **정답 코드**를 가진다 (`problems.solution_runtime_id`,
`problems.solution_source_code`). 어드민만 볼 수 있으며, 공개 DTO 에는 필드 자체가 없다.

검증은 별도 파이프라인을 만들지 않고 **사용자 제출과 같은 채점 큐**를 쓴다.
대신 `submissions.kind` 로 종류를 구분하고, 사용자에게 보이는 모든 조회에서 걸러낸다.

| 컬럼 | 설명 |
|---|---|
| `submissions.kind` | `USER` \| `SOLUTION_VERIFICATION` |
| `problems.verification_submission_id` | 마지막 검증 실행 |
| `problems.verified_signature` | 검증 시점의 "채점에 영향을 주는 내용" 지문 |

`verified_signature` 는 테스트케이스(순번·입력·기대 출력), 실행 제한, 정답 코드로 만든
SHA-256 지문이다. 수정 시각을 쓰지 않는 이유는, 검증 기록을 저장하는 것만으로 수정 시각이
바뀌어 결과가 항상 낡은 것으로 표시되기 때문이다.

**정책:** 검증하지 않아도 문제를 공개할 수 있다(경고만). 강제하면 검증이 불가능한 유형
(SQL·시스템 설계 등, #42)을 나중에 막게 되고, 운영자가 급하게 문제를 고칠 길도 없어진다.

## 2.6 소프트 삭제 규칙

문제·테스트케이스·템플릿·제출은 물리 삭제하지 않고 `deleted_at` 만 채운다 (ADR-0007).

- 살아 있는 행만 보는 조회는 리포지토리에서 `deleted_at IS NULL` 을 **명시적으로** 건다.
- 제출 이력 화면은 삭제된 문제도 함께 보여야 하므로 이 필터를 걸지 않는다.
- 유니크 제약은 전부 부분 인덱스라, 삭제한 slug·순번·런타임을 다시 쓸 수 있다.

## 3. 난이도 체계

solved.ac 형식을 따른다 — **6티어 × 5단계 = 30레벨**이며 5단계가 가장 쉽다.

| 티어 | 레벨 구간 | 표기 예 |
|---|---|---|
| 브론즈 | 1~5 | 브론즈 5 … 브론즈 1 |
| 실버 | 6~10 | 실버 5 … 실버 1 |
| 골드 | 11~15 | 골드 4 |
| 플래티넘 | 16~20 | 플래티넘 2 |
| 다이아몬드 | 21~25 | 다이아몬드 1 |
| 루비 | 26~30 | 루비 1 |

DB 에는 정수 `difficulty_level` 을 저장한다. 정렬과 티어 범위 검색이 인덱스로 처리되고,
enum 이름(`GOLD_4`)은 애플리케이션에서 이 정수를 옮긴 표현일 뿐이다.

### 난이도가 없는 문제 (#195)

`difficulty_state` 가 셋 중 하나다.

| 상태 | 뜻 | 레벨 |
|---|---|---|
| `RATED` | 난이도가 매겨졌다 | 1~30 |
| `UNRATED` | **아직 모른다** — 사람들이 풀어 봐야 아는 값이다 | `NULL` |
| `NO_RATE` | **해당 없다** — 튜토리얼·설문형처럼 난이도로 표현되지 않는다 | `NULL` |

**보초값(0·-1)을 쓰지 않는다.** 그러면 정렬과 범위 검색이 조용히 깨진다 — 틀린 결과가
아니라 *그럴듯한* 결과가 나온다. DB 제약이 상태와 레벨을 묶어 둔다(`RATED` ⟺ 레벨 있음).

두 상태의 규칙은 하나다 — **문제 수에는 세고 점수에는 넣지 않는다.**

- 푼 사람 입장에서 "푼 문제" 인 것은 사실이다 (프로필의 푼 문제 수, 랭킹의 `SOLVED_COUNT`)
- 점수는 난이도에서 나온다. 근거가 없는 것에 점수를 매기지 않는다 — `user_problem_scores`
  에 **행은 남기고 점수만 0** 이다
- 뱃지·스트릭·정답률은 그대로 센다. 그것들은 활동을 재는 것이지 난이도를 재는 것이 아니다

### 난이도 투표 (#477)

`problem_difficulty_votes` — **사용자 × 문제 = 1표**, 언제든 바꿀 수 있다. 눈금은
`difficulty_level` 과 같은 1~30 이다.

바꿀 수 있게 둔 이유: 문제가 고쳐지면(테스트케이스가 늘거나 지문이 명확해지면) 옛 판단이
더는 맞지 않는다. 처음 낸 표에 묶어 두면 **고쳐진 문제에 옛 평가가 그대로 남는다.**

**표가 난이도를 바꾸는 자리는 하나뿐이다**: `UNRATED` 문제에 표가 문턱(설정값)만큼
모이면 **중앙값**으로 난이도가 붙고, 그때 이미 맞힌 사람들의 점수를 다시 계산한다(#194).
`RATED`·`NO_RATE` 문제는 표가 아무리 쌓여도 난이도가 움직이지 않는다 — 사람이 정한 값을
투표가 덮으면 이미 푼 사람의 점수가 소급해서 흔들린다.

**투표하기 전에는 분포를 감춘다.** 먼저 보면 뒤에 오는 사람이 끌려가고, 그러면 모인
숫자는 문제의 난이도가 아니라 처음 몇 표의 메아리가 된다. 그리고 **푼 사람만 투표한다.**

**정렬에서는 양쪽 끝 모두 뒤로 간다.** 쉬운순에서도 어려운순에서도 마지막이다 —
순서가 없는 값을 정수 정렬에 우연히 섞이게 두지 않는다. SQL 의 기본은 내림차순에서
`NULLS FIRST` 라, 그냥 두면 "어려운순" 맨 앞이 미평가 문제로 찬다.

**티어 필터로는 잡히지 않는다** (레벨이 없어 `BETWEEN` 에 안 든다). `difficultyState` 로
따로 고른다 — 고를 방법이 없으면 미평가 문제가 목록에서 사라진다.

새 문제의 기본은 **미평가**다. 브론즈로 두면 "아직 안 정했다" 와 "쉽다" 가 구분되지 않는다.

## 4. 판정(Verdict) 값

| 값 | 의미 |
|---|---|
| `ACCEPTED` | 모든 테스트케이스 통과 |
| `WRONG_ANSWER` | 출력이 기대와 다름 |
| `TIME_LIMIT_EXCEEDED` | 시간 제한 초과 |
| `MEMORY_LIMIT_EXCEEDED` | 메모리 제한 초과 |
| `RUNTIME_ERROR` | 비정상 종료 |
| `COMPILE_ERROR` | 컴파일 실패 |
| `OUTPUT_LIMIT_EXCEEDED` | 출력 크기 초과 |
| `SYSTEM_ERROR` | 채점 인프라 장애 |

출력 비교 규칙: 각 줄의 **오른쪽 공백을 제거**하고, 끝의 빈 줄을 무시한다. 그 뒤는
문제가 정한 방식으로 비교한다 (#279, ADR-0010).

| `output_comparison` | 무엇 |
|---|---|
| `EXACT` (기본) | 그대로 정확히 맞춘다 |
| `FLOAT` | 공백으로 쪼갠 **토큰마다** 숫자로 읽히면 `float_epsilon` 안에서 비교한다 |
| `CHECKER` | **출제자가 쓴 코드가 판정한다** (#452). 정답이 여럿인 문제의 자리다 |

`FLOAT` 는 절대·상대 오차 중 **하나만 만족해도** 맞다고 본다 — 답이 0 근처일 때와 아주
클 때 같은 잣대를 쓸 수 없다. 토큰 개수가 다르면 틀린 답이고, `nan`·`inf` 는 숫자로
읽지 않는다(글자 그대로 같을 때만 맞다).

`CHECKER` 는 채점 코드에 **입력·제출 출력·정답 출력**을 파일로 주고 **종료 코드**로 답을
받는다(0=맞음, 1=틀림). 그 코드가 죽거나 약속하지 않은 코드로 끝나면 **오답이 아니라
`SYSTEM_ERROR`** 다 — 출제자의 실수를 푼 사람에게 떠넘기지 않는다.

**기본값이 지금 동작인 이유**: 이미 등록된 문제의 판정이 하나도 바뀌면 안 된다.
비교 방식이 바뀌면 재채점(#107)에서 판정이 뒤집힌다.

## 5. 상태 전이

```
PENDING ──(judge 수신)──▶ JUDGING ──(전체 케이스 종료)──▶ COMPLETED
   │                          │
   └──────(큐 타임아웃)────────┴──────(인프라 장애)────────▶ FAILED (verdict=SYSTEM_ERROR)
```

`COMPILE_ERROR` 는 테스트케이스를 하나도 실행하지 않고 즉시 `COMPLETED` 로 종결된다.

## 6. 큐 메시지 스키마

### 6.1 채점 작업 (`codekr:judge`)

```json
{
  "submissionId": 1024,
  "problemId": 7,
  "runtimeId": "python:3.12",
  "sourceCode": "...",
  "timeLimitMs": 2000,
  "memoryLimitMb": 256,
  "testcases": [
    { "id": 31, "seq": 1, "input": "1 2\n", "expectedOutput": "3\n" }
  ]
}
```

채점에 필요한 데이터를 메시지에 담아 보낸다 — judge 가 DB 를 읽지 않아도 되게 하기 위함이다.

### 6.2 실행 작업 (`codekr:exec`)

```json
{
  "jobId": "01J...ULID",
  "runtimeId": "python:3.12",
  "sourceCode": "...",
  "stdin": "1 2\n",
  "timeLimitMs": 2000,
  "memoryLimitMb": 256,
  "replyStream": "codekr:exec:res:01J...ULID"
}
```

### 6.3 실행 결과 (`codekr:exec:res:{jobId}`)

```json
{
  "jobId": "01J...",
  "status": "OK",
  "exitCode": 0,
  "stdout": "3\n",
  "stderr": "",
  "runtimeMs": 24,
  "memoryKb": 8192,
  "truncated": false
}
```

`status` 는 `OK` | `TIME_LIMIT_EXCEEDED` | `MEMORY_LIMIT_EXCEEDED` | `RUNTIME_ERROR`
| `COMPILE_ERROR` | `OUTPUT_LIMIT_EXCEEDED` | `SYSTEM_ERROR`.

```json
{ "type": "JUDGING",   "submissionId": 1024, "totalCount": 10 }
{ "type": "TESTCASE",  "submissionId": 1024, "seq": 1, "verdict": "ACCEPTED",
  "runtimeMs": 24, "memoryKb": 8192 }
{ "type": "COMPLETED", "submissionId": 1024, "verdict": "WRONG_ANSWER",
  "passedCount": 7, "totalCount": 10, "maxRuntimeMs": 120, "maxMemoryKb": 20480 }
```
