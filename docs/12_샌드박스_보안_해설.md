## 1. 이 문제가 왜 특별히 어려운가

### 1.1 우리는 모르는 사람의 프로그램을 우리 서버에서 돌린다

코드.kr 은 문제 풀이 플랫폼이다. 사용자가 코드를 제출하면 **우리 서버가 그 코드를
실제로 실행한다.** 이것이 이 서비스에서 가장 위험한 지점이다.

보통의 웹 서비스에서 "사용자 입력"은 게시글 제목이나 검색어다. 위험한 문자가 섞이지
않았는지 검사해서 걸러내면 된다. 그런데 우리가 받는 입력은 **프로그램 그 자체**다.

```
보통의 웹 서비스           코드.kr
─────────────────         ─────────────────────────────
사용자 입력 → 검사 → 저장   사용자 입력 = 실행할 프로그램
                            ↓
                          검사할 것이 없다. 실행하는 순간
                          공격자가 원하는 코드가 이미 돈다
```

### 1.2 "입력 검증"은 방어가 아니다

"위험한 코드를 걸러내면 되지 않나?" 라고 생각하기 쉽지만, 이것은 통하지 않는다.

- `open("/etc/passwd")` 를 금지어로 막아도, 문자열을 쪼개서 이어 붙이면 그만이다.
- 파일을 여는 방법은 언어마다 수십 가지다. 15개 언어를 지원하는데 전부 막을 수 없다.
- 애초에 정상적인 풀이도 파일을 읽고 쓴다 (표준 입력, 임시 파일).

그래서 위협 모델은 이렇게 시작한다:

> 사용자 코드는 **임의 코드 실행 권한을 이미 가진 공격자**로 본다.
> 취약점을 찾아 실행하는 것이 아니라, 처음부터 원하는 프로그램을 돌릴 수 있다.

공격자는 이미 안에 들어와 있다. 남은 방어는 **"들어온 뒤에 아무것도 못 하게 하는 것"**
하나뿐이다. 이것을 **격리(isolation)** 라고 부른다.

### 1.3 공격자가 하려는 일

구체적으로 무엇을 막아야 하는지 알아야 방어를 설계할 수 있다.

| 하려는 일 | 왜 위험한가 |
|---|---|
| 서버의 파일을 읽는다 | 설정 파일에 DB 비밀번호가 있다 |
| 인터넷에 접속한다 | 히든 테스트케이스와 정답을 자기 서버로 보낸다 |
| 내부 네트워크에 접속한다 | DB·Redis 에 직접 붙는다 |
| 클라우드 메타데이터에 접속한다 | `169.254.169.254` — 클라우드 자격증명이 여기 있다 |
| 무한 루프를 돈다 | 채점 큐 전체가 멈춘다 (다른 사람이 채점받지 못한다) |
| 프로세스를 무한히 만든다 (fork bomb) | 서버가 마비된다 |
| 다른 사람의 채점 결과를 훔쳐본다 | 남의 코드·정답이 샌다 |
| **컨테이너 밖으로 탈출한다** | 서버 전체가 넘어간다 |

이 목록의 각 항목에 대응하는 방어가 4장부터 나온다.

## 2. 알아야 할 개념

여기서 나오는 개념들은 4장 이후 계속 쓰인다. 급하면 읽으면서 이 장으로 돌아와도 된다.

### 2.1 프로세스와 커널

**프로세스**는 실행 중인 프로그램 하나다. 파이썬 코드를 돌리면 `python3` 프로세스가
하나 생긴다.

**커널(kernel)** 은 운영체제의 핵심이다. 하드웨어를 직접 다루는 유일한 주체다.
파일을 읽고, 메모리를 나눠 주고, 네트워크로 데이터를 보내는 일을 전부 커널이 한다.

> 프로세스는 하드웨어를 **직접** 만질 수 없다. 반드시 커널에게 부탁해야 한다.

### 2.2 syscall — 커널에게 부탁하는 창구

프로세스가 커널에게 부탁하는 방법이 **syscall(시스템 콜)** 이다.

식당 비유가 정확하다.

```
손님(프로세스)  ──[주문서]──▶  주방(커널)  ──▶  재료·불(하드웨어)
                  = syscall
```

손님은 주방에 들어갈 수 없다. 주문서를 내야만 한다. 주문서의 종류가 syscall 이고,
리눅스에는 **300~400개 정도**가 있다.

| syscall 이름 | 하는 일 |
|---|---|
| `open` | 파일을 연다 |
| `read` / `write` | 읽고 쓴다 |
| `socket` / `connect` | 네트워크 연결을 만든다 |
| `fork` / `clone` | 새 프로세스를 만든다 |
| `mmap` | 메모리를 받는다 |
| `ptrace` | **다른 프로세스의 메모리를 들여다본다** |

파이썬으로 `open("a.txt")` 를 쓰든, Go 로 `os.Open("a.txt")` 를 쓰든, C 로 쓰든,
결국 커널에 도착하는 것은 똑같은 `open` syscall 이다.

**이것이 중요한 이유:** 언어별로 막는 것은 불가능하지만(1.2절), syscall 수준에서
막으면 **모든 언어에 한 번에** 걸린다. 7장의 seccomp 가 정확히 이것을 한다.

### 2.3 컨테이너 — 격리된 실행 환경

**컨테이너**는 "프로세스에게 가짜 세계를 보여 주는 것"이다. 마법이 아니라 리눅스
커널의 기능 세 가지를 조합한 것이다.

| 기능 | 하는 일 | 비유 |
|---|---|---|
| **namespace** | 무엇이 **보이는지**를 가른다 | 창문에 커튼을 친다 |
| **cgroup** | 얼마나 **쓸 수 있는지**를 정한다 | 전기 계량기에 한도를 건다 |
| **capability** | 무엇을 **할 수 있는지**를 정한다 | 열쇠 꾸러미에서 열쇠를 뺀다 |

namespace 는 종류별로 나뉜다.

- **mount namespace** — 보이는 파일 시스템. 컨테이너 안에서 `/` 는 호스트의 `/` 가 아니다.
- **network namespace** — 보이는 네트워크 카드. 새로 만들면 아무 카드도 없다 = 인터넷 없음.
- **PID namespace** — 보이는 프로세스 목록. 밖의 프로세스가 안 보인다.
- **user namespace** — UID 를 안팎에서 다르게 매핑한다 (8장의 주제).

### 2.4 컨테이너와 가상 머신(VM)의 결정적 차이

이 차이가 이 문서 전체를 관통한다.

```
가상 머신                          컨테이너
─────────────────                 ─────────────────
 게스트 앱                          앱      앱
 게스트 커널  ← 각자 커널             \      /
 하이퍼바이저                      호스트 커널  ← 커널을 공유한다!
 호스트 커널                        호스트 하드웨어
```

**컨테이너는 호스트의 커널을 그대로 쓴다.** 가볍고 빠른 이유이자, 격리가 VM 보다
약한 이유다.

> 컨테이너 안의 프로세스가 `open` 을 부르면, 그 코드는 **호스트 커널 안에서** 실행된다.
> 커널에 버그가 있고 그 버그를 특정 syscall 로 건드릴 수 있다면, **컨테이너 격리는
> 소용이 없다.** 이것을 "컨테이너 탈출(container escape)" 이라고 부른다.

그래서 우리는 커널에 닿는 창구(syscall)의 수 자체를 줄인다. 이것이 7장이다.

### 2.5 root 와 UID

리눅스의 모든 사용자는 숫자 **UID** 를 갖는다. `UID 0` 이 **root** — 무엇이든 할 수 있는
관리자다. 일반 사용자는 1000 이상의 번호를 받는다.

우리 샌드박스는 **UID 10001** 로 코드를 돌린다. 존재하지도 않는 계정 번호다.

### 2.6 이미지, 컨테이너 런타임, 소켓

- **이미지(image)** — 컨테이너의 재료. `python:3.13-alpine` 처럼 이름과 태그로 부른다.
  파이썬 인터프리터와 최소한의 리눅스 파일들이 들어 있는 압축 꾸러미라고 보면 된다.
- **컨테이너 런타임** — 이미지로 컨테이너를 만들어 돌려 주는 프로그램. 우리는
  **containerd** 를 쓴다 (로컬 개발은 Docker 도 쓴다).
- **소켓(socket)** — 프로그램끼리 이야기하는 통로. `/run/containerd/containerd.sock`
  파일에 명령을 보내면 containerd 가 컨테이너를 만들어 준다.

> **이 소켓을 쥔 프로그램은 서버 전체를 쥔 것과 같다.** "호스트의 `/` 를 통째로 마운트한
> 컨테이너를 root 로 만들어 줘" 라고 부탁할 수 있기 때문이다. 10장의 주제다.

### 2.7 seccomp — 주문서 검열

**seccomp**(secure computing mode)는 "이 프로세스는 이 syscall 만 부를 수 있다"를
커널에 등록하는 기능이다.

2.2절의 식당 비유로 돌아가면, seccomp 는 **주방 입구에 붙은 주문 가능 목록**이다.
목록에 없는 주문서를 내밀면 주방은 아예 받지 않는다.

한 번 걸면 **되돌릴 수 없다.** 나중에 만들어지는 자식 프로세스에도 그대로 따라간다.
그래서 사용자 코드가 스스로 풀 수 없다.

## 3. 우리 시스템의 모양

### 3.1 제출부터 실행까지

```
브라우저 ──▶ api (Kotlin) ──▶ Redis 큐 ──▶ judge (Go) ──▶ Redis 큐 ──▶ executor (Go)
                                                                            │
                                                              컨테이너 런타임 소켓
                                                                            │
                                                                            ▼
                                                              ┌──────────────────────┐
                                                              │  샌드박스 컨테이너      │
                                                              │  ← 사용자 코드가 도는 곳 │
                                                              └──────────────────────┘
```

- **api** — 제출을 받고 DB 에 기록하고 큐에 넣는다.
- **judge** — 테스트케이스 단위로 쪼개서 실행 큐에 넣고, 결과를 모아 판정한다.
- **executor** (실행기) — 실행 큐를 소비해서 **샌드박스 컨테이너를 만들고** 코드를 돌린다.

### 3.2 가장 헷갈리는 지점 — 실행기와 샌드박스는 다른 것이다

```
┌─ 실행 전용 노드 (서버 한 대) ────────────────────────────┐
│                                                        │
│  ┌─ executor 파드 ─────────┐                            │
│  │ 실행기 프로세스           │                            │
│  │ (우리가 만든 Go 프로그램)  │                            │
│  │ **신뢰한다**             │                            │
│  └───────────┬─────────────┘                            │
│              │ 소켓으로 "컨테이너 만들어 줘"                 │
│              ▼                                          │
│  ┌─ containerd ────────────┐                            │
│  └───────────┬─────────────┘                            │
│              │ 만든다                                     │
│              ▼                                          │
│  ┌─ 샌드박스 컨테이너 ────────┐                             │
│  │ 사용자 코드                │                            │
│  │ **신뢰하지 않는다**         │                            │
│  └─────────────────────────┘                            │
└────────────────────────────────────────────────────────┘
```

**사용자 코드는 실행기 안에서 돌지 않는다.** 실행기는 컨테이너를 만들라고 부탁만 하고,
사용자 코드는 그 옆에 새로 만들어진 컨테이너에서 돈다. 둘은 형제 관계다.

이 구분이 왜 중요한가:

- 4~9장의 방어는 **샌드박스 컨테이너**에 걸린다. 대상은 사용자 코드다.
- 10장의 방어는 **실행기 파드**에 걸린다. 대상은 "실행기가 만약 뚫린다면" 이다.
- 쿠버네티스 설정(`securityContext`)은 **실행기 파드**에만 걸린다. 샌드박스 컨테이너는
  쿠버네티스가 만든 것이 아니라 실행기가 만든 것이라, 쿠버네티스는 그 존재를 모른다.
  → 7장에서 seccomp 프로파일을 ConfigMap 으로 배포하는 이유가 이것이다.

### 3.3 신뢰 경계

```
신뢰함     │ api · judge · executor 프로세스
──────────┼──────────────────────────────────────
신뢰 안 함 │ 사용자 코드 (샌드박스 컨테이너 안에서 도는 모든 것)
```

### 3.4 방어를 여러 겹으로 쌓는 이유

아래 4~9장은 하나하나가 완전한 방어가 아니다. **한 겹이 뚫려도 다음 겹이 남도록**
쌓는 것이 목적이다. 이것을 심층 방어(defense in depth)라고 부른다.

예를 들어 seccomp 프로파일은 `socket` 과 `connect` 를 **허용한다**. 네트워크 연결을
만드는 syscall 인데도 열어 둔 이유는, 어차피 네트워크 namespace 에 네트워크 카드가
하나도 없어서 연결할 곳이 없기 때문이다. seccomp 에서 굳이 막지 않아도 4장의 방어가
이미 막는다. 반대로 4장이 어떤 이유로 실패해도 실제로 나갈 수 있는 곳은 없다.

## 4. 1층 — 컨테이너로 얻는 격리

여기서부터 실제 방어다. 각 절은 **무엇을 막는가 / 어떻게 했는가 / 어디에 있는가**
순서로 읽으면 된다.

관련 코드는 두 벌이다. 같은 방어를 두 런타임에 각각 적용한다.

| 구현 | 파일 | 언제 쓰나 |
|---|---|---|
| 엔진 API (Docker 등) | `apps/executor/internal/sandbox/container.go` | 로컬 개발 |
| containerd | `apps/executor/internal/sandbox/containerd_spec.go` | 운영 노드 |

두 구현은 **같은 검증 기준**을 통과해야 한다 (12장).

### 4.1 실행마다 새 컨테이너를 만들고 버린다

**막는 것:** 이전 제출이 남긴 파일을 다음 제출이 읽는 것. 다른 사람의 코드·정답이 새는 것.

**어떻게:** 실행 1회 = 컨테이너 1개다. 끝나면 강제로 지운다.

```go
// container.go
defer s.remove(containerID)   // 이 함수를 빠져나갈 때 반드시 컨테이너를 지운다
```

> `defer` 는 Go 문법이다. "이 함수가 어떻게 끝나든(정상 종료든 오류든) 이 줄을 마지막에
> 실행하라"는 뜻이다. 오류가 나서 중간에 튕겨 나가도 컨테이너 정리가 빠지지 않는다.

작업 디렉터리 `/work` 는 **tmpfs** 다 — 디스크가 아니라 메모리 위의 임시 파일 시스템이라
컨테이너와 함께 사라진다.

### 4.2 root 가 아닌 계정으로 돌린다

**막는 것:** 컨테이너 안에서 root 권한으로 할 수 있는 온갖 일. 그리고 탈출에 성공했을 때
호스트에서 root 가 되는 것.

**어떻게:** UID/GID 를 `10001:10001` 로 고정한다.

```go
const sandboxUser = "10001:10001"
```

이미지에 그런 계정이 없어도 되도록 **이름이 아니라 숫자**로 지정한다.

### 4.3 파일 시스템을 읽기 전용으로 잠근다

**막는 것:** 시스템 파일 변조, 악성 실행 파일 심기.

**어떻게:** 루트 파일 시스템 전체를 읽기 전용으로 만들고, **작업 디렉터리만** 열어 준다.

```go
ReadonlyRootFilesystem: true,
Tmpfs: map[string]string{
    workDir: "rw,exec,mode=1777,size=512m",   // /work — 여기만 쓸 수 있다
    "/tmp":  "rw,mode=1777,size=256m",
},
```

`/etc`, `/usr/bin`, `/`, `/root` 어디에도 쓸 수 없다. 검증 코드가 실제로 네 곳에
써 보고 전부 거부되는지 확인한다 (`selftest/checks.go`).

> **곁가지:** 이 결정 때문에 코드를 컨테이너에 **넣는** 방법이 특이해졌다. 읽기 전용
> rootfs 컨테이너에는 런타임의 파일 복사 API 가 통하지 않는다. 9장에서 다룬다.

### 4.4 네트워크를 완전히 끊는다

**막는 것:** 히든 테스트케이스 유출, 내부 서비스 접근, 클라우드 자격증명 탈취,
공격 도구 내려받기.

**어떻게:** 네트워크 namespace 를 새로 만들되 **네트워크 카드를 하나도 붙이지 않는다.**

```go
NetworkDisabled: true,
NetworkMode:     "none",
```

"방화벽으로 막는다"가 아니라 **"랜선이 아예 없다"** 에 가깝다. 방화벽은 규칙에 구멍이
생길 수 있지만, 네트워크 인터페이스가 없으면 나갈 방법 자체가 없다.

검증은 네 곳에 실제로 접속해 본다.

| 대상 | 왜 이것을 확인하나 |
|---|---|
| `1.1.1.1:53` | 일반 인터넷 |
| `169.254.169.254:80` | **클라우드 메타데이터** — 자격증명이 여기 있다 |
| `127.0.0.1:8080` | 호스트 루프백 |
| `host.docker.internal:80` | 컨테이너에서 호스트를 부르는 관용 주소 |

### 4.5 실행기의 환경 변수를 물려주지 않는다

**막는 것:** 큐 주소·비밀번호 같은 설정이 사용자 코드에 그대로 보이는 것.

**어떻게:** 컨테이너에 넘기는 환경 변수는 **이미지가 정한 것뿐**이다 (툴체인 경로 등).
실행기 프로세스의 환경 변수는 한 개도 넘어가지 않는다.

검증은 `SECRET`, `TOKEN`, `PASSWORD`, `REDIS`, `CODEKR`, `DB_` 가 이름에 들어간
환경 변수를 전부 찾아보고, 결과가 빈 목록인지 본다.

### 4.6 런타임 소켓을 컨테이너에 노출하지 않는다

**막는 것:** 2.6절의 그 문제 — 소켓이 보이면 사용자 코드가 "호스트를 통째로 마운트한
root 컨테이너"를 만들 수 있다. 즉시 완전 탈출이다.

**어떻게:** 마운트하지 않는다. 검증은 알려진 네 경로를 확인한다.

```
/var/run/docker.sock
/run/docker.sock
/run/containerd/containerd.sock
/run/crio/crio.sock
```

## 5. 2층 — 자원 제한

### 5.1 자원 제한이 왜 "보안"인가

무한 루프는 데이터를 훔치지 않는다. 그래도 보안 문제다. **가용성(availability)** 이
보안의 세 축 중 하나이기 때문이다.

한 사람의 무한 루프가 워커를 붙잡으면 다른 모든 사람이 채점받지 못한다. 결과는
"한 명이 서비스를 멈춘 것"이고, 이것은 공격이다 (DoS).

자원 제한은 **cgroup**(2.3절)으로 건다.

### 5.2 걸어 둔 한도

| 자원 | 한도 | 근거 |
|---|---|---|
| 메모리 | 문제별 (기본 256MB) | 문제 설정에서 온다 |
| **swap** | **끔** (아래 설명) | 초과를 즉시 드러내기 위해 |
| CPU | 1 코어 | `NanoCPUs: 1_000_000_000` |
| 프로세스 수 | **128개** | fork bomb 방어 |
| 출력량 | 64 KiB | 넘으면 잘라 버린다 |
| 실행 시간 | 문제별 (기본 2초) | |
| 컨테이너 수명 | 컴파일 제한 + 실행 제한 + 10초 | 어떤 경우에도 이 시간 안에 죽는다 |

### 5.3 swap 을 끄는 이유가 조금 특이하다

**swap** 은 메모리가 모자랄 때 디스크를 메모리처럼 쓰는 기능이다. 보통은 켜 두는 것이
좋지만 여기서는 끈다.

swap 이 켜져 있으면 메모리 제한을 넘긴 프로그램이 **죽지 않고 느려진다.** 그러면
"메모리 초과"가 "시간 초과"로 둔갑해서 사용자에게 엉뚱한 판정이 나간다.

swap 을 끄면 한도를 넘는 순간 커널이 프로세스를 죽인다(OOM kill). 그래야
`MEMORY_LIMIT_EXCEEDED` 로 정확히 판정할 수 있다.

```go
Memory:     memoryBytes,
MemorySwap: memoryBytes,   // 둘을 같게 = swap 0
```

### 5.4 fork bomb 과 PID 제한

fork bomb 은 자기 자신을 무한히 복제하는 프로그램이다. 몇 줄이면 서버를 마비시킨다.

```python
import os
while True:
    os.fork()
```

프로세스 수를 128개로 제한하면 129번째 `fork` 가 실패하고 끝난다. 검증 코드는 500번
fork 를 시도해서 500개가 다 만들어지지 **않는지** 확인한다.

### 5.5 출력 폭주

`print` 를 무한히 부르면 실행기가 그것을 다 받아 메모리에 쌓는다. **샌드박스 안이 아니라
실행기가 죽는다.** 그래서 받는 쪽에서 상한을 걸고 넘는 부분은 버린다.

```go
stdcopy.StdCopy(
    limitedWriter{&outBuf, limit},   // 64KiB 를 넘으면 그냥 버린다
    limitedWriter{&errBuf, limit},
    attached.Reader,
)
```

### 5.6 컴파일과 실행의 자원을 분리한다

이것은 보안이라기보다 **정확성** 문제지만, 자원 제한과 얽혀 있어 여기서 설명한다.

`go build` 한 번이 수백 MB 를 쓴다. 문제의 메모리 제한(256MB)을 컴파일에까지 적용하면
**"256MB 문제"는 Go 로 아예 풀 수 없다.** 문제 설정의 의미가 왜곡된다.

그래서 2단계로 나눈다.

```
① 컨테이너를 넉넉한 메모리(기본 1024MB)로 만든다
      ↓
   소스를 심고, 컴파일한다
      ↓
② 컨테이너의 메모리 한도를 문제의 값(256MB)으로 **낮춘다**
      ↓
   사용자 프로그램을 실행한다  ← 여기서는 문제의 제한이 그대로 강제된다
```

컨테이너를 지우고 다시 만드는 것이 아니라, 돌고 있는 컨테이너의 한도를 바꾼다
(`ContainerUpdate`).

한 가지 함정이 있다. `/work` 가 tmpfs(= 메모리)라서 **컴파일 캐시가 메모리 한도를
잡아먹는다.** 그래서 컴파일 스크립트 마지막에서 캐시를 지운다.

```sh
rm -rf /work/.gocache /work/.compile /work/obj
```

자세한 내용은 [`06_실행_제약_계약.md`](06_실행_제약_계약.md) 에 있다.

## 6. 3층 — 권한 제거

### 6.1 capability — root 권한을 잘게 쪼갠 것

옛날 리눅스는 이분법이었다. root 는 전능하고, 나머지는 아무것도 못 한다.

그런데 "1024번 미만 포트를 열고 싶다"는 이유만으로 웹 서버를 root 로 돌려야 하는 것은
과했다. 그래서 root 의 권한을 **capability** 라는 40여 개의 조각으로 쪼갰다.

| capability | 할 수 있는 일 |
|---|---|
| `CAP_NET_BIND_SERVICE` | 1024번 미만 포트 열기 |
| `CAP_SYS_ADMIN` | 마운트 등 관리 작업 (거의 root 와 동급) |
| `CAP_SYS_PTRACE` | 다른 프로세스 들여다보기 |
| `CAP_DAC_OVERRIDE` | 파일 권한 무시하고 읽고 쓰기 |
| `CAP_CHOWN` | 파일 소유자 바꾸기 |

**우리는 전부 뺀다.** 채점용 프로그램이 필요로 하는 것이 하나도 없다.

```go
CapDrop: []string{"ALL"}          // 엔진 API 구현
oci.WithCapabilities(nil)         // containerd 구현
```

검증은 `/proc/self/status` 의 `CapEff` 를 읽어 `0000000000000000` 인지 본다.
40여 개의 capability 를 비트 하나씩으로 표현한 값이라, 전부 0 이면 하나도 없다는 뜻이다.

### 6.2 no-new-privileges — 권한 상승 사다리 제거

**setuid** 라는 오래된 리눅스 기능이 있다. 특정 실행 파일에 표시를 해 두면, 누가
실행하든 **파일 소유자의 권한으로** 돈다. `passwd` 명령이 대표적이다 — 일반 사용자가
실행해도 root 권한으로 돌아야 `/etc/shadow` 를 고칠 수 있다.

공격자에게 이것은 **사다리**다. 이미지 안 어딘가에 취약한 setuid 파일이 하나라도 있으면,
그것을 딛고 권한을 올릴 수 있다.

`no-new-privileges` 는 커널에 이렇게 말한다.

> 이 프로세스와 그 자손은 **어떤 방법으로도 지금보다 큰 권한을 가질 수 없다.**

한 번 켜면 되돌릴 수 없다. 사다리 자체가 사라진다.

```go
SecurityOpt: []string{"no-new-privileges"}   // 엔진 API
oci.WithNoNewPrivileges                       // containerd
```

검증은 `/proc/self/status` 의 `NoNewPrivs` 가 `1` 인지 본다.

## 7. 4층 — seccomp (PR #141 의 본체)

여기가 이 문서의 핵심이다. 앞의 개념(2.2 syscall, 2.4 커널 공유, 2.7 seccomp)이
전부 여기서 쓰인다.

- 이슈: **#48**
- PR: **#141**
- 프로파일: `infra/sandbox/seccomp.json`

### 7.1 4~6장을 다 했는데 왜 부족한가

지금까지의 방어는 전부 **커널이 제공하는 기능**이다. namespace 도 cgroup 도 capability 도
커널이 지켜 준다.

그런데 2.4절을 다시 보자. **컨테이너는 호스트 커널을 공유한다.** 사용자 코드가 부르는
syscall 은 호스트 커널 안에서 실행된다.

> 만약 커널의 어떤 syscall 구현에 버그가 있다면?
> 그 버그를 건드리면 커널 자체가 공격자의 손에 넘어간다. 커널이 넘어가면 namespace 도
> cgroup 도 capability 도 **커널이 지켜 주던 것이므로 전부 무의미해진다.**

이것이 컨테이너 탈출이고, 실제로 매년 여러 건의 CVE 가 나온다. 우리가 커널 버그를
없앨 수는 없다. 대신 할 수 있는 일이 있다.

> **커널에 닿는 창구의 수를 줄인다.**

400개 syscall 중 100개만 열어 두면, 나머지 300개에 있는 버그는 애초에 건드릴 수 없다.
이것을 **공격 표면 축소(attack surface reduction)** 라고 부른다.

### 7.2 런타임 기본 프로파일로는 왜 부족한가

Docker 나 containerd 에는 이미 기본 seccomp 프로파일이 있다. 실제로 우리도 그것이
걸려 있음을 확인했었다 (위협 모델 항목 10).

문제는 **기본 프로파일이 범용이라는 것**이다. 세상의 모든 컨테이너 워크로드가 돌아야
하므로 넓게 열려 있다. 데이터베이스도, 웹 서버도, 빌드 도구도 돌아야 한다.

우리 워크로드는 훨씬 좁다. **"입력을 읽고 계산해서 출력을 낸다"** 가 전부다.
기본 프로파일이 열어 둔 것 중 상당수는 우리에게 순수한 위험이다.

### 7.3 허용 목록(allowlist)으로 만든 이유

두 가지 방식이 있다.

| 방식 | 뜻 | 문제 |
|---|---|---|
| 차단 목록 (blocklist) | "이것들만 막는다" | **새 syscall 이 생기면 자동으로 열린다** |
| 허용 목록 (allowlist) | "이것들만 연다" | 필요한 것이 빠지면 프로그램이 안 돈다 |

우리는 허용 목록을 골랐다. 커널은 계속 새 syscall 을 추가하는데, 차단 목록은 그때마다
사람이 손대야 하고 손대는 것을 잊으면 조용히 구멍이 난다.

```json
{
  "defaultAction": "SCMP_ACT_ERRNO",
  "defaultErrnoRet": 1,
  ...
}
```

`defaultAction` 은 "목록에 없으면 어떻게 할까"다. `SCMP_ACT_ERRNO` = **오류를 돌려준다.**

`defaultErrnoRet: 1` 은 그 오류 번호다. 1번은 `EPERM` — "권한이 없습니다"다.

> **왜 프로세스를 죽이지 않고 오류를 돌려주나?**
> `SCMP_ACT_KILL` 이라는 선택지도 있다. 하지만 프로그램이 그냥 죽으면 사용자에게는
> 원인 불명의 실패로 보인다. `EPERM` 을 돌려주면 대부분의 런타임이 "권한 없음"을
> 예외로 처리해서 스택 트레이스가 남는다. 그리고 정상적인 풀이가 어쩌다 목록에 없는
> syscall 을 건드려도(예: 라이브러리가 선택적으로 시도하는 최적화 경로) 프로그램이
> 죽지 않고 다른 경로로 넘어간다.

### 7.4 300개를 열고, 무엇을 닫았나

허용 목록에는 **300개**가 들어 있다. `read`, `write`, `open`, `mmap`, `clone` 같은
프로그램이 살아 있으려면 반드시 필요한 것들이다.

기본 프로파일이 **열어 두지만 우리가 닫은** 것들이 이 작업의 실체다.

#### `ptrace`, `process_vm_readv`, `process_vm_writev`

다른 프로세스의 메모리를 읽고 쓰는 syscall 이다. 디버거(gdb)가 쓰는 것이다.

채점 프로그램이 다른 프로세스를 디버깅할 이유가 없다. 반대로 공격자에게는 같은
컨테이너 안 다른 프로세스(예: SQL 문제의 PostgreSQL, 래퍼 셸)의 메모리를 훔쳐보고
조작하는 통로다.

#### `userfaultfd`

**페이지 폴트를 사용자 공간이 가로채는** syscall 이다.

페이지 폴트는 "아직 메모리에 없는 주소를 건드렸다"는 신호로, 원래 커널이 처리한다.
`userfaultfd` 는 그 처리를 사용자 프로그램에게 넘긴다.

공격자에게 이것이 왜 값진가: 커널 취약점의 상당수는 **타이밍 경쟁(race condition)** 이다.
"커널이 A 를 확인하고 A 를 쓰는 사이에 A 를 B 로 바꾸면 뚫린다" 같은 것인데, 그 창은
보통 마이크로초 단위라 맞히기 어렵다. `userfaultfd` 는 **커널을 그 지점에서 멈춰 세울 수
있게** 해 준다. 확률 싸움이 확정 공격으로 바뀐다.

커널 익스플로잇 코드에 거의 항상 등장하는 이유다.

#### `io_uring_setup`, `io_uring_enter`, `io_uring_register`

io_uring 은 리눅스의 최신 비동기 I/O 방식이다. 빠르지만 **커널 안에 매우 큰 새 코드
덩어리**를 들여왔고, 도입 이후 취약점이 계속 나오고 있다.

우리는 15개 런타임 전부를 이 프로파일로 돌려서 **아무것도 필요로 하지 않는다는 것을
확인**하고 닫았다.

#### `open_by_handle_at`, `name_to_handle_at`

파일을 경로가 아니라 **"파일 핸들"** 이라는 숫자로 여는 syscall 이다.

경로로 파일을 열면 마운트 경계가 지켜진다 — 컨테이너의 `/` 밖으로는 못 나간다.
그런데 파일 핸들은 **파일 시스템 전체를 기준으로 한 식별자**라서, 핸들만 알면
마운트 경계를 건너뛰고 열 수 있다.

컨테이너 탈출의 고전적 경로다 (2014년 "Shocker" 공격이 이것을 썼다).

#### `kcmp`, `move_pages`, `mbind`, `set_mempolicy`

NUMA 메모리 배치 조정과 프로세스 비교용이다. 채점에는 쓸 일이 전혀 없고,
`kcmp` 는 커널 메모리 배치를 알아내는 정보 유출에 쓰인다.

#### `seccomp`

자기 자신에게 seccomp 필터를 새로 다는 syscall 이다. 이미 필터가 걸린 프로세스가
다시 걸 이유가 없다.

#### 그 밖에 닫혀 있는 것들

허용 목록 방식이라 **적지 않은 것은 전부 닫힌다.** 위험한 것 중 눈에 띄는 것만 꼽으면:

| syscall | 무엇 |
|---|---|
| `mount`, `umount2`, `pivot_root`, `chroot` | 파일 시스템 재배치 — 탈출의 핵심 도구 |
| `unshare`, `setns` | 새 namespace 를 만들거나 남의 namespace 로 들어간다 |
| `bpf` | 커널 안에서 프로그램을 돌린다. CVE 다발 지대 |
| `keyctl`, `add_key`, `request_key` | 커널 키링. 컨테이너 사이에 공유되는 부분이 있다 |
| `perf_event_open` | 커널 성능 계측. 정보 유출과 CVE 가 많다 |
| `init_module`, `delete_module`, `kexec_load` | 커널 모듈·커널 교체 |
| `reboot`, `swapon`, `settimeofday`, `sethostname` | 호스트 상태 변경 |

### 7.5 `personality` — 값별로 여는 특수 사례

`personality` 는 "이 프로세스를 옛날 커널처럼 굴게 해 줘"라고 요청하는 syscall 이다.
호환성을 위한 기능인데, 공격자에게는 **커널의 잘 안 쓰이는(=덜 검증된) 코드 경로를
깨우는** 수단이다. 특히 주소 공간 무작위화(ASLR)를 끄는 값이 있다.

그래서 완전히 막지 않고 **인자 값별로** 연다. 런타임이 실제로 쓰는 값만 통과시킨다.

```json
{ "names": ["personality"], "action": "SCMP_ACT_ALLOW",
  "args": [{ "index": 0, "value": 0, "op": "SCMP_CMP_EQ" }] },
{ "names": ["personality"], "action": "SCMP_ACT_ALLOW",
  "args": [{ "index": 0, "value": 8, "op": "SCMP_CMP_EQ" }] },
...
```

**여기 함정이 있다.** 한 항목에 인자 조건을 여러 개 넣으면 seccomp 는 그것을 **AND** 로
읽는다. "0번 인자가 0 **이고 동시에** 8" 은 성립할 수 없으므로 어떤 값도 통과하지 못한다.
그래서 항목을 값마다 따로 만들었다. 5개 항목이 그 이유다.

### 7.6 아키텍처를 둘 다 적는 이유

```json
"archMap": [
  { "architecture": "SCMP_ARCH_X86_64",
    "subArchitectures": ["SCMP_ARCH_X86", "SCMP_ARCH_X32"] },
  { "architecture": "SCMP_ARCH_AARCH64",
    "subArchitectures": ["SCMP_ARCH_ARM"] }
]
```

syscall 은 **이름이 아니라 번호**로 커널에 전달되고, **번호는 CPU 아키텍처마다 다르다.**
예를 들어 `ptrace` 는 x86_64 에서 101번, aarch64 에서 117번이다.

`subArchitectures` 가 중요하다. 64비트 CPU 는 32비트 호출 규약도 받아 준다. 32비트
규약을 적지 않으면 **같은 syscall 을 32비트 번호로 부르는 것만으로 필터를 통과한다.**
전형적인 우회 수법이라 서브 아키텍처까지 전부 덮는다.

두 아키텍처를 다 적은 이유는 개발 환경(Apple Silicon = arm64)과 운영 노드의 CPU 가
다를 수 있기 때문이다. 같은 파일이 양쪽에서 그대로 작동해야 한다.

### 7.7 프로파일을 코드에 어떻게 붙이나

실행기는 **기동할 때** 프로파일 파일을 읽는다.

```go
func NewContainerSandbox(seccompProfilePath string) (Sandbox, error) {
    profile, err := readSeccompProfile(seccompProfilePath)   // 기동 시 1회
    if err != nil {
        return nil, err     // 못 읽으면 실행기가 뜨지 않는다
    }
    ...
}
```

**실행할 때마다 읽지 않는 것이 의도다.** 매번 읽으면 파일이 사라졌거나 망가진 사실이
"첫 제출이 실패할 때"에야 드러난다. 기동에서 실패하면 배포 시점에 바로 안다.

읽은 뒤 JSON 인지도 검사한다.

```go
if !json.Valid(content) {
    return "", fmt.Errorf("seccomp 프로파일이 올바른 JSON 이 아닙니다: %s", path)
}
```

망가진 파일을 그대로 런타임에 넘기면 컨테이너 생성이 실패하고, 그 이유는 사용자에게
"채점 오류"로만 보인다.

### 7.8 끄는 것과 `unconfined` 는 다르다

```go
func (s *containerSandbox) securityOpt() []string {
    opts := []string{"no-new-privileges"}
    if s.seccompProfile != "" {
        opts = append(opts, "seccomp="+s.seccompProfile)
    }
    return opts
}
```

프로파일 경로를 주지 않으면 seccomp 옵션 자체를 붙이지 않는다. 그러면 **런타임 기본
프로파일이 걸린다.**

`seccomp=unconfined` 라는 값도 있는데, 그것은 **아무 필터도 걸지 않는다**는 뜻이다.
코드 어디에도 넣지 않았다. 실수로 켜질 수 있는 값을 애초에 두지 않는 것이 목적이다.

| 설정 | 실제 결과 |
|---|---|
| 프로파일 경로 지정 | 좁힌 300개 허용 목록 |
| 경로 없음 (`enabled=false`) | 런타임 기본 프로파일 — 넓지만 있긴 하다 |
| `seccomp=unconfined` | **아무것도 막지 않는다.** 우리 코드에 없다 |

### 7.9 배포 — 왜 ConfigMap 인가

3.2절의 구분이 여기서 결정적이다.

쿠버네티스에는 `securityContext.seccompProfile` 이라는 필드가 있다. 파드에 seccomp
프로파일을 거는 표준 방법이다. **우리는 그것을 쓸 수 없다.**

```
쿠버네티스가 아는 것          쿠버네티스가 모르는 것
────────────────────         ──────────────────────
executor 파드                 실행기가 소켓으로 만든
  ↑                           샌드박스 컨테이너
securityContext 는 여기만       ← 프로파일을 걸어야 할 곳은 여기
```

프로파일을 걸어야 할 대상은 실행기 파드가 아니라 **실행기가 만드는 컨테이너**다.
쿠버네티스는 그 컨테이너의 존재를 모르므로 손댈 수 없다. 그래서 **실행기 프로세스가
직접** 걸어야 하고, 그러려면 **파일로 읽을 수 있어야** 한다.

세 가지 방법 중에서 골랐다.

| 방법 | 왜 안 골랐나 / 골랐나 |
|---|---|
| 파드 `securityContext` | 대상이 다르다 (위) |
| 노드 파일에 두기 | 노드를 늘릴 때마다 사람이 복사해야 한다. 프로파일과 코드의 버전이 갈라져도 아무도 모른다 |
| **ConfigMap** | ✅ 차트와 함께 버전 관리되고, 파드에 파일로 마운트된다 |

```yaml
# templates/config.yaml
kind: ConfigMap
metadata:
  name: codekr-seccomp
data:
  seccomp.json: |
{{ .Files.Get "files/seccomp.json" | indent 4 }}
```

```yaml
# templates/executor.yaml
env:
  - { name: CODEKR_SECCOMP_PROFILE, value: /etc/codekr/seccomp/seccomp.json }
volumeMounts:
  - { name: seccomp, mountPath: /etc/codekr/seccomp }
```

파일은 두 곳에 있다 — `infra/sandbox/seccomp.json`(개발·검증용)과
`deploy/charts/codekr/files/seccomp.json`(배포용). 내용은 동일하다.

### 7.10 회귀를 막는 장치

허용 목록은 시간이 지나면 **넓어진다.** 어떤 런타임이 안 돌면 syscall 을 하나 추가하고,
또 하나 추가하고... 어느 순간 기본 프로파일과 다를 바 없어진다. 그런데 **그 사실을
아무도 눈치채지 못한다** — 모든 테스트는 여전히 통과하기 때문이다.

그래서 "막아야 할 것이 막히는지"를 확인하는 테스트를 따로 뒀다.

```bash
make verify-seccomp
```

이 테스트는 파이썬에서 `ctypes` 로 syscall 을 **번호로 직접** 부른다. 파이썬 표준
라이브러리에는 `ptrace` 같은 것을 부를 창구가 없기 때문이다.

```python
probes = {
    "ptrace":           117 if arm else 101,
    "process_vm_readv": 270 if arm else 310,
    "userfaultfd":      282 if arm else 323,
    "io_uring_setup":   425,
    "keyctl":           219 if arm else 250,
    "bpf":              280 if arm else 321,
    "setns":            268 if arm else 308,
}
for name, nr in probes.items():
    libc.syscall(nr, 0, 0, 0, 0, 0, 0)
    print(name, "BLOCKED" if ctypes.get_errno() == errno.EPERM else "ALLOWED")
```

하나라도 `ALLOWED` 가 나오면 실패한다.

**이 가드가 실제로 무는지도 확인했다.** 허용 목록에 `ptrace`/`userfaultfd`/`setns` 를
도로 넣은 프로파일로 돌려 보니 셋 다 잡아냈다. 통과만 확인하고 넘어가면 "테스트가
사실은 아무것도 안 하고 있었다"를 놓친다.

### 7.11 프로파일을 걸고 15개 런타임 전부를 돌렸다

허용 목록이 좁으면 정상적인 풀이가 안 돌 수 있다. 그래서 **등록된 모든 런타임의 기본
템플릿을 이 프로파일 아래에서 실제로 컴파일하고 실행했다.**

```bash

```

> **실제로 돌려서** 확인하는 쪽을 골랐다 — 결과가 같고 유지할 도구가 하나 줄어든다.

## 8. 5층 — user namespace 재매핑

가장 어려운 부분이다. 7장까지 이해했다면 읽을 수 있다.

- 이슈: **#130**

### 8.1 문제 — 컨테이너 안의 UID 는 밖에서도 같은 UID 다

4.2절에서 UID 10001 로 코드를 돌린다고 했다. 그런데 **컨테이너 안의 UID 10001 은
호스트의 UID 10001 과 같은 번호다.**

```
컨테이너 안                호스트
──────────                ──────
UID 10001    ═══════════  UID 10001    ← 같은 숫자, 같은 권한
```

평소에는 문제가 없다. namespace 가 가려 주니까. 하지만 **탈출에 성공한 순간**,
공격자는 호스트에서 UID 10001 의 권한을 그대로 갖는다. 그 UID 를 쓰는 실제 계정이
호스트에 있다면 그 계정의 파일을 전부 읽고 쓸 수 있다.

### 8.2 해법 — 번호를 통째로 옮긴다

**user namespace** 는 컨테이너 안팎의 UID 를 서로 다르게 매핑한다.

```
컨테이너 안                호스트
──────────                ──────
UID     0    ──────────▶  UID 100000
UID     1    ──────────▶  UID 100001
   ...                       ...
UID 10001    ──────────▶  UID 110001   ← 존재하지 않는 계정
   ...                       ...
UID 65535    ──────────▶  UID 165535
```

컨테이너 안에서는 여전히 UID 10001 이지만, 호스트가 보기에는 110001 이다.
**호스트에 그런 계정은 없다.** 탈출해도 아무것도 아닌 사용자가 된다.

컨테이너 안의 root(UID 0)조차 호스트에서는 100000 — 평범한 무권한 사용자다.

### 8.3 설정

```bash
CODEKR_SANDBOX_RUNTIME=containerd
CODEKR_USERNS_HOST_OFFSET=100000
```

`100000` 이 위 그림의 시작 번호다. 폭은 65536 으로 고정했다 — 이미지가 쓰는 UID 는
거의 언제나 그 아래에 있고, `/etc/subuid` 가 관례적으로 이 단위로 나눈다.

```go
const usernsRangeSize = 65536

return []specs.LinuxIDMapping{{
    ContainerID: 0,        // 컨테이너의 0번부터
    HostID:      uint32(offset),   // 호스트의 offset 번부터
    Size:        usernsRangeSize,  // 65536개를
}}, true, nil
```

### 8.4 기본값이 "꺼짐"인 이유

이 기능은 **기본으로 켜지 않는다.** 위험한 설정이 될 수 있기 때문이다.

호스트의 어느 구간을 내줄지는 노드마다 다르다. 만약 offset 을 잘못 잡아서 **실제 계정이
쓰는 구간과 겹치면**, 재매핑이 오히려 그 계정의 권한을 **주는** 셈이 된다.

그래서 구간은 `/etc/subuid`, `/etc/subgid` 로 미리 예약한 뒤 켜야 한다.

### 8.5 `0` 을 거부하는 이유

```go
if offset == 0 {
    return nil, false, fmt.Errorf("%s 는 0 일 수 없습니다 — 재매핑이 되지 않습니다", usernsOffsetEnv)
}
```

offset 이 0 이면 컨테이너의 0 이 호스트의 0 에 매핑된다. **컨테이너의 root 가 호스트의
root 다.** 설정 화면에는 "재매핑 켜짐"으로 보이지만 실제로는 아무것도 옮기지 않았다.

**켜지 않은 것보다 나쁘다** — 켰다고 믿고 운영하기 때문이다. 그래서 기동에서 거부한다.

### 8.6 containerd 에서만 되는 이유

| 런타임 | 재매핑 |
|---|---|
| **containerd** | ✅ 컨테이너를 만들 때 spec 에 한 줄 넣으면 된다 |
| 엔진 API (Docker) | ❌ daemon 전체 설정(`--userns-remap`)이라 컨테이너별로 못 고른다 |

엔진 API 에서 이 환경 변수를 주면 **실행기가 기동에서 실패한다.**

```go
if os.Getenv(usernsOffsetEnv) != "" {
    return nil, fmt.Errorf(
        "%s 는 %s 런타임에서만 쓸 수 있습니다 — 엔진 API 에서는 daemon 의 --userns-remap 설정입니다",
        usernsOffsetEnv, RuntimeContainerd)
}
```

조용히 무시하면 재매핑이 걸린 줄 알고 운영하게 된다. 8.5절과 같은 논리다.

### 8.7 idmapped mount — 성능 때문에 필요한 것

재매핑에는 숨은 비용이 있다. 이미지 파일들의 소유자가 UID 0 인데, 컨테이너 안에서
그것이 100000 으로 보여야 한다.

**옛날 방식(daemon 수준 재매핑)** 은 이미지 레이어를 통째로 다시 풀면서 모든 파일의
소유자를 바꾼다(`chown`). 이미지마다 디스크를 한 벌씩 더 먹고, 처음 쓸 때 오래 걸린다.

**idmapped mount** 는 커널 기능으로, 파일을 건드리지 않고 **마운트할 때 UID 를
변환해서 보여 준다.** 복사도 chown 도 없다.

containerd 에서 이것을 쓰려면 스냅샷에도 같은 매핑을 라벨로 붙여야 한다.

```go
opts = append(opts, oci.WithUserNamespace(mapping, mapping))
snapshotOpts = append(snapshotOpts, client.WithUserNSRemapperLabels(mapping, mapping))
//                                  ^^^^ 이것이 빠지면 레이어를 다시 푼다
```

실제로 확인한 결과, 스냅샷 수(이미지 11개 / 레이어 50개)와 실행 시간이 재매핑 전후로
같았다. 레이어 재전개가 일어나지 않았다는 뜻이다.

### 8.8 지금 상태

colima VM(리눅스 6.8, containerd 2.3)에서 검증을 마쳤지만 **운영 노드에서는 아직 켜지
않았다.** 노드의 커널이 idmapped overlayfs 를 지원하는지와 UID 구간 예약은 그 노드에서
확인해야 한다.

## 9. 6층 — 코드를 컨테이너에 넣는 과정

방어는 컨테이너 설정에만 있는 것이 아니다. **소스 코드를 컨테이너 안에 집어넣는 과정
자체**에도 공격 표면이 있다.

관련 파일: `apps/executor/internal/sandbox/script.go`

### 9.1 왜 파일 복사 API 를 쓰지 않나

컨테이너 런타임에는 파일을 복사해 넣는 API 가 있다. 그런데 4.3절에서 rootfs 를 읽기
전용으로 잠갔더니 **대상이 tmpfs 여도 복사가 거부된다.**

읽기 전용을 포기할 수는 없으므로 다른 길을 찾았다. **표준 입력으로 흘려 넣는다.**

```
실행기 ──[base64 로 감싼 tar]──▶ 컨테이너의 표준 입력
                                    │
                                    ▼
                        cd /work && base64 -d > bundle.tar
                                 && tar xf bundle.tar
                                 && rm -f bundle.tar
```

base64 로 감싸는 이유는, tar 는 임의의 바이트를 담는데 그것이 **셸을 거쳐** 지나가야
하기 때문이다. base64 는 알파벳과 숫자만 쓰므로 셸이 특수 문자로 오해할 것이 없다.

### 9.2 예약 파일 이름 — 가장 실질적인 위험

작업 디렉터리에는 소스 말고도 우리가 만든 파일들이 들어간다.

| 파일 | 하는 일 |
|---|---|
| `input.txt` | 테스트케이스 입력 |
| `compile.sh` | 컴파일 스크립트 (우리가 만든다) |
| `run.sh` | 실행 스크립트 (우리가 만든다) |

SQL 문제 같은 유형은 **문제가 추가 파일을 싣는다** (스키마, 시드 데이터, 정답 쿼리).
만약 그 파일 이름이 `run.sh` 라면?

> 우리가 만든 실행 스크립트가 덮어써진다. 그 안에 무엇이든 쓸 수 있다 = **임의 명령 실행**.

그래서 이름을 미리 예약해 두고 거부한다.

```go
var reservedFiles = map[string]bool{
    "input.txt": true, "compile.sh": true, "run.sh": true,
}
```

런타임 하네스(SQL 의 `run-sql.sh`)도 **문제 자료보다 먼저** 넣어서 예약 목록에 추가한다.
순서가 뒤집히면 하네스가 덮어써진다.

### 9.3 경로 탈출 방지

파일 이름에 `../` 가 들어가면 작업 디렉터리 밖으로 나갈 수 있다.

```go
if strings.ContainsAny(name, "/\\") || name == "." || name == ".." {
    return fmt.Errorf("파일 이름에 경로를 쓸 수 없습니다: %q", name)
}
```

슬래시 자체를 금지한다. 이 자료는 출제자(어드민)가 넣는 것이지만, **검증을 어드민
화면에만 두면 화면을 거치지 않는 경로가 생겼을 때 그대로 뚫린다.** 그래서 실행기에서도
검사한다.

### 9.4 셸 인젝션 방지

컴파일·실행 명령은 셸 스크립트로 조립된다. 명령 인자에 셸 특수 문자가 있으면 명령이
바뀔 수 있다.

```go
func quoteAll(args []string) string {
    quoted := make([]string, 0, len(args))
    for _, arg := range args {
        quoted = append(quoted, "'"+strings.ReplaceAll(arg, "'", `'\''`)+"'")
    }
    return strings.Join(quoted, " ")
}
```

모든 인자를 작은따옴표로 감싸고, 인자 안에 작은따옴표가 있으면 탈출시킨다.
작은따옴표 안에서 셸은 아무것도 해석하지 않는다.

### 9.5 nonce — 계측 값 위조 방지

실행 시간과 메모리 사용량은 **컨테이너 안에서** 재야 한다. 컨테이너 기동 시간이 섞이면
안 되기 때문이다. 그런데 `/work` 는 tmpfs 라 컨테이너 밖에서 읽을 수 없다.

그래서 계측 값을 **표준 출력 마지막 줄에 실어** 보낸다.

```
(사용자 프로그램의 출력)
...
CODEKR-a3f9e2b1c8d40e5f7a2b9c31 exit=0 wall_ms=142 mem_bytes=8912896
```

여기에 문제가 있다. 사용자 프로그램이 **이 줄을 직접 출력하면** 자기 실행 시간과 메모리를
마음대로 조작할 수 있다.

그래서 표식을 매번 새로 만든다.

```go
func newNonce() string {
    buf := make([]byte, 12)
    if _, err := rand.Read(buf); err != nil {   // 암호학적 난수
        return "CODEKR-METRICS"
    }
    return "CODEKR-" + hex.EncodeToString(buf)
}
```

96비트 난수라 사용자가 맞힐 수 없다. 실행마다 다르므로 이전 값을 알아내도 소용없다.

## 10. 7층 — 실행기 자신을 지키기

- 이슈: **#47**
- 위협 모델의 **잔여 위험 R1**

### 10.1 실행기는 노드 root 와 같다

2.6절에서 봤듯이, 컨테이너 런타임 소켓을 쥔 프로그램은 **"호스트의 `/` 를 통째로
마운트한 root 컨테이너를 만들어 줘"** 라고 부탁할 수 있다. 실질적으로 노드 root 다.

실행기는 컨테이너를 만들어야 하므로 그 소켓이 반드시 필요하다. 즉 **이 위험은 없앨 수
없다.** 없앨 수 없다면 **가둔다.**

### 10.2 걸어 둔 통제

| 통제 | 어떻게 | 무엇을 얻나 |
|---|---|---|
| 노드 격리 | `nodeSelector: codekr/workload=executor` + toleration | 실행 전용 노드에만 뜬다. 그 노드에 다른 워크로드가 없어서 노드를 통째로 버려도 서비스가 돈다 |
| 네임스페이스 격리 | `executor.namespace` 를 따로 둔다 | hostPath 를 허용하는 느슨한 Pod Security 를 그 네임스페이스에만 연다 |
| **egress 차단** | NetworkPolicy — DNS 와 Redis 만 | 아래 |
| 자격증명 없음 | 실행기가 아는 설정은 큐 주소뿐 | DB 비밀번호를 주지 않는다 (ADR-0004) |
| 읽기 전용 파일 시스템 | `readOnlyRootFilesystem: true` | 실행기는 자기 디스크에 아무것도 쓰지 않는다 |
| 권한 제거 | `capabilities: drop ALL`, `allowPrivilegeEscalation: false` | 6장과 같은 것을 실행기 자신에게 |
| seccomp | `seccompProfile: RuntimeDefault` | 실행기 자신의 syscall 도 거른다 (샌드박스 것과는 별개) |

### 10.3 egress 차단이 가장 값이 크다

침해된 실행기가 노드 root 를 얻어도, **밖으로 데이터를 보내거나 다음 단계를 내려받을
경로가 없으면** 할 수 있는 일이 크게 준다.

나갈 수 있는 곳은 둘뿐이다.

```yaml
egress:
  - to: [kube-system 네임스페이스]        # DNS — Redis 주소를 풀어야 한다
    ports: [{UDP 53}, {TCP 53}]
  - to: [codekr 네임스페이스의 redis 파드]  # 작업을 받고 결과를 돌려준다
    ports: [{TCP 6379}]
```

**들어오는 것(ingress)은 막지 않는다.** 실행기는 큐를 소비할 뿐 아무도 호출하지 않아
막을 것이 없고, ingress 를 막으면 CNI 에 따라 kubelet 의 상태 확인 프로브까지 끊긴다.
그것을 되돌리려 예외를 늘리다 보면 결국 아무것도 막지 않는 규칙이 된다.

**레지스트리로 나가는 길도 열지 않았다.** 런타임 이미지를 받는 것은 **노드의 컨테이너
런타임**이지 실행기 파드가 아니다. 소켓 너머에서 일어나는 일이라 NetworkPolicy 가
닿지 않는다.

### 10.4 실행기가 쓰는 API 는 6개뿐이다

침해되면 공격자가 **바로** 쓸 수 있는 API 목록이다.

| 호출 | 쓰임 |
|---|---|
| `Ping` | 기동 시 소켓 확인 |
| `ContainerCreate` | 샌드박스 컨테이너 생성 |
| `ContainerStart` | 실행 시작 |
| `ContainerUpdate` | 메모리 한도 조정 (5.6절) |
| `ExecCreate` / `ExecAttach` | 명령 실행과 입출력 |
| `ContainerRemove` | 폐기 |

**이미지를 받는 API 는 쓰지 않는다.** 런타임 이미지는 노드에 미리 있어야 한다.

> 소켓 프록시를 두어 이 목록만 통과시키는 방안도 검토했지만 넣지 않았다. 프록시 자체가
> 소켓을 쥐게 되어 위험이 옮겨갈 뿐이고, `ContainerCreate` **하나만으로도** 호스트
> 마운트가 가능하므로 목록을 좁혀도 실질적인 이득이 없다.

### 10.5 침해를 가정한 대응 절차

**탐지**

- NetworkPolicy 밖으로 나가려는 시도 — 실행기의 정상 동작에는 DNS·Redis 외의 egress 가
  없으므로 **한 건이라도 나오면 비정상**이다.
- 실행기가 만들지 않은 컨테이너가 실행 노드에 뜨는 것 (이름 규칙과 라벨이 정해져 있다).
- 큐에 없는 제출에 대한 결과 이벤트.

**대응**

1. 실행기 Deployment 를 0 으로 내린다. 채점은 멈추지만 제출은 큐에 쌓여 유실되지 않는다.
2. 실행 전용 노드를 cordon 하고 격리한다. **다른 워크로드가 없으므로 노드를 통째로
   비워도 서비스의 나머지는 돈다** — 노드를 격리해 둔 이유가 이것이다.
3. Redis 의 작업·결과 스트림을 보존한다 (사후 분석 자료).
4. 노드를 재생성한다. **침해된 노드를 고쳐 쓰지 않는다.**
5. DB 는 실행기가 접근할 수 없으므로 제출 기록은 별개로 확인한다. 의심되면 해당 기간을
   재채점한다.

## 11. 8층 — 공급망 (이미지)

- 이슈: **#96**, **#171**

### 11.1 태그는 움직인다

`python:3.13-alpine` 은 **이름**이지 내용물의 지문이 아니다. 같은 이름으로 다른 내용물이
올라올 수 있다.

```
오늘        python:3.13-alpine → (내용물 A)   ← 우리가 검증한 것
한 달 뒤    python:3.13-alpine → (내용물 B)   ← 노드에 실제로 들어가는 것
```

정상적인 보안 업데이트일 수도 있지만, 레지스트리 계정이 털렸다면 악성 이미지일 수도
있다. 어느 쪽이든 **우리가 검증한 것과 다른 것이 실행 노드에 들어간다.**

### 11.2 다이제스트로 고정한다

**다이제스트(digest)** 는 이미지 내용물의 해시다. `sha256:abc123...` 형태이고,
내용물이 1비트라도 다르면 값이 달라진다. 내용물의 지문이다.

```yaml
# infra/runtimes/runtimes.yaml
- id: "python:3.13"
  image: "python:3.13-alpine"
  digest: "sha256:..."      # 이 지문의 이미지만 받는다
```

`make mirror-runtimes ARGS=--pin` 이 미러링하면서 여기에 기록한다.

### 11.3 자체 미러

런타임 이미지를 우리 레지스트리로 복사해 두고 거기서 받는다. pull rate limit, 속도,
가용성 문제가 함께 풀리지만 **가장 큰 이유는 공급망이다** — 우리가 검증한 이미지가
우리 통제 아래 남는다.

### 11.4 이미 있으면 묻지 않는다

```go
if image, err := s.localImage(ctx, full); err != nil {
    return nil, err
} else if image != nil {
    return image, nil      // 노드에 있으면 그냥 쓴다
}
```

`Pull` 은 이미지가 로컬에 있어도 매번 매니페스트를 다시 해석하러 나간다. 그러면
제출마다 레지스트리 왕복이 붙고, pull 제한에 걸리고, 레지스트리가 잠깐 흔들리면 채점이
멈춘다. 노드에 미리 받아 두는 것이 전제이므로 있는 것을 쓰는 쪽이 정상 경로다.

## 12. 어떻게 "확인"했는가

### 12.1 "설정했다" 와 "걸려 있다" 는 다르다

지금까지 나온 방어는 전부 **설정**이다. 설정을 썼다고 해서 실제로 걸린다는 보장은 없다.

- 런타임 버전이 바뀌어 옵션 이름이 달라졌을 수 있다.
- 노드의 커널이 그 기능을 지원하지 않을 수 있다.
- 오타 하나로 조용히 무시됐을 수 있다.

그래서 **신뢰할 수 없는 코드가 실제로 시도하는 것을 그대로 실행해서** 막히는지 본다.

### 12.2 검사 정의를 한 곳에 둔다

검사는 테스트 파일이 아니라 **패키지**로 뺐다 — `apps/executor/internal/selftest/`.

```
selftest 패키지 (검사 정의)
       ├──▶ go test 가 쓴다        (로컬·CI)
       └──▶ executor --self-test 가 쓴다  (배포된 노드)
```

**로컬에서 통과했다는 사실이 운영 노드에서 통과한다는 보장이 되지 못한다.** 방어의
상당수가 커널·cgroup·런타임 설정에 달려 있어서다. 그래서 실행기 바이너리가 같은 검사를
노드에서 직접 돌릴 수 있게 만들었다.

```bash
kubectl -n codekr-exec exec deploy/codekr-executor -- executor --self-test
```

하나라도 실패하면 종료 코드가 1 이고, **무엇이 뚫려 있는지 전부 출력한다** —
첫 실패에서 멈추지 않는다.

### 12.3 검사 7종

`selftest/checks.go` 에 들어 있는 검사다. 각각 파이썬 코드를 샌드박스에서 돌리고 출력을
본다.

| 검사 | 실제로 하는 일 | 통과 조건 |
|---|---|---|
| non-root 와 capability | `os.getuid()`, `/proc/self/status` 읽기 | `uid 10001`, `CapEff` 전부 0, `NoNewPrivs 1` |
| 읽기 전용 rootfs | `/etc`, `/usr/bin`, `/`, `/root` 에 쓰기 시도 | 네 곳 다 `OSError` |
| 네트워크 차단 | 4개 주소에 접속 시도 | 하나도 연결되지 않음 |
| 런타임 소켓 | 4개 소켓 경로 존재 확인 | 전부 없음 |
| 프로세스 수 제한 | 500번 `fork` | 500개를 다 만들지 못함 |
| 환경 변수 비노출 | 민감한 이름의 환경 변수 검색 | 빈 목록 |
| 출력 폭주 | 50MB 출력 시도 | 잘림, 상한의 2배를 넘지 않음 |

### 12.4 명령 표

| 명령 | 확인하는 것 |
|---|---|
| `CODEKR_SANDBOX_TEST=1 go test ./internal/selftest/ -v` | 위 7종 |
| `make verify-seccomp` | 위험한 syscall 이 실제로 막히는지 (7.10절) |
| `make verify-runtimes` | 15개 런타임이 그 프로파일에서 도는지 (7.11절) |
| `executor --self-test` | **배포된 노드에서** 위 7종 |
| `make smoke` | 가입 → 제출 → 판정 종단간 |

### 12.5 CI 에서 도는 것

`sandbox-live` 잡이 PR 마다 containerd 구현으로 위 검사를 돌린다 (#172).

한 가지 장치가 있다. **통과 수를 센다.**

환경 변수를 빠뜨리면 테스트가 전부 SKIP 되는데, CI 는 그것을 **초록으로** 표시한다.
"아무것도 안 돌았는데 통과한 것처럼 보이는 것"이 가장 나쁜 결과라, 잡이 실제로 돌린
검사 수를 확인하고 모자라면 실패시킨다.

`make verify-runtimes` 와 `verify-seccomp` 는 CI 에 넣지 않았다 — GitHub Actions
러너에서 15개 이미지를 받는 비용이 크다. 사람이 돌리는 명령으로 남겼다.

### 12.6 두 구현이 같은 기준을 통과한다

로컬 개발(엔진 API)과 운영(containerd)은 다른 구현이다. **검증 기준이 다르면 한쪽에서
통과한 검증이 다른 쪽에서 뜻을 잃는다.** 그래서 같은 `selftest` 정의를 쓰고, 라이브
테스트도 `CODEKR_SANDBOX_RUNTIME` 을 따라 어느 쪽이든 돈다.

seccomp 프로파일도 **같은 파일**을 쓴다.

## 13. 아직 못 막는 것

정직하게 적는 것이 이 문서와 위협 모델의 목적이다.

### 13.1 커널 공유 (R4 — 수용)

2.4절의 그 문제다. 컨테이너는 호스트 커널을 공유하므로, **커널 취약점 앞에서는 방어가
없다고 본다.**

gVisor(커널을 사용자 공간에서 흉내 내는 것)나 Firecracker(초경량 VM) 같은 강한 격리
방법이 있지만, 홈랩 노드에서 운영 비용이 크다 (ADR-0003).

**현재는 수용하고**, 실행 노드를 다른 워크로드와 분리해서 영향 범위를 제한한다.
7장의 seccomp 는 이 위험을 없애지 못하지만 **크게 줄인다** — 닿을 수 있는 커널 코드가
줄면 밟을 수 있는 버그도 준다.

### 13.2 운영 노드에서 아직 확인하지 못했다

위협 모델의 검증 매트릭스는 **로컬(Docker Desktop, colima VM)에서 확인한 것**이다.
운영 노드의 커널·cgroup·LSM 설정은 다를 수 있다.

노드가 서면 `--self-test` 를 돌려 확인해야 한다 (#45).

### 13.3 user namespace 를 운영에서 켜지 않았다

8.8절. 노드의 커널 지원 확인과 UID 구간 예약이 남았다 (#130).

### 13.4 `/dev/shm` (R5 — 수용)

`/dev/shm`(공유 메모리용 tmpfs)이 쓰기 가능하다(기본 64MB). tmpfs 사용량은 컨테이너
메모리 한도에 포함되므로 자원 고갈로 이어지지 않고, 컨테이너와 함께 사라진다. **수용.**

### 13.5 공개 범위 정책

이 문서와 위협 모델은 **방어가 걸려 있음을 확인한 결과**만 담는다. 실제로 악용 가능한
취약점을 발견하면 공개 이슈에 재현 절차를 쓰지 않고 GitHub Security Advisory 로
전환한다.
