# 12. 문제 묶음 형식 (#479)

문제를 파일로 주고받는 형식이다. **어드민 업로드와 시드가 같은 형식을 쓴다** — 둘이
갈라지면 어느 쪽이 진짜인지 알 수 없게 되고, 스킬(#480)이 만들 파일도 둘 중 하나를 골라야 한다.

## 왜 묶음인가

테스트케이스가 백 개를 넘으면 어드민 폼으로는 만들 수 없다. 그렇다고 JSON 본문에 다 담으면

- 파일이 수십 MB가 되어 편집기로 열리지 않는다
- 한 글자를 고치려고 전체를 다시 올려야 한다
- 줄바꿈과 인코딩이 JSON 문자열 안에서 뭉개진다 — #313 이 SQL 스키마에서 겪고
  **별도 파일로 뺀** 것과 같은 이유다

## 모양

```
problem.zip
├── problem.json          문제 메타데이터
└── testcases/
    ├── 1.in              seq 가 파일 이름이다
    ├── 1.out
    ├── 2.in
    └── 2.out
```

- **`problem.json` 은 시드 파일과 같은 형식이다** (`scripts/seed-problems` 안의 json).
  그 폴더가 곧 예시다
- **테스트케이스는 파일이 이긴다.** `problem.json` 안에도 `testcases` 를 적을 수 있지만,
  묶음에 파일이 있으면 그쪽이 쓰인다 — 파일로 뺀 이유가 그것이기 때문이다
- **짝이 없으면 거절한다.** 입력만 있으면 정답이 없고, 기대 출력만 있으면 무엇으로 그 답이
  나오는지가 없다. 둘 다 테스트케이스가 아니다
- **모르는 파일이 있으면 거절한다.** 조용히 버리면 출제자는 자기가 넣은 것이 들어갔다고 믿는다
- **모르는 키가 있어도 거절한다** (#537). 같은 이유다 — `problem.json` 에 오타 난 키를
  적으면 그 값은 버려지는데, 적은 사람은 들어갔다고 믿는다

## 문제 여러 개를 한 묶음에 (#623)

zip 안에 **문제마다 폴더를 하나씩** 두면 한 번에 만든다.

```
bundle.zip
├── 01-두-수의-합/
│   ├── problem.json
│   └── testcases/1.in, 1.out
├── 02-회문/
│   └── problem.json
└── 03-정렬/
    ├── problem.json
    └── testcases/…
```

**무엇으로 가르는가 — `problem.json` 이 어디 있는지다.** 루트에 있으면 문제 하나이고
(지금까지와 같다), 없으면 맨 위 폴더 하나하나를 문제로 본다. 짐작하는 자리가 없다.

`#594` 가 벗기는 포장 폴더와 부딪히지 않는다. `python-basics/01-x/problem.json` 은
포장(`python-basics/`)을 벗기고 나면 `01-x/problem.json` 이라 폴더별로 갈린다.

- **순서는 폴더 이름순이다.** `01-`·`02-` 로 번호를 매겨 두면 문제 번호가 그 순서로
  붙는다 — 번호는 사용자에게 보이는 값이다 (#204)
- **`problem.json` 이 없는 폴더가 있으면 통째로 거절한다.** 조용히 건너뛰면 올린
  사람은 그것도 들어갔다고 믿는다
- **폴더 밖에 떠 있는 파일도 거절한다.** 어느 문제의 것인지 알 수 없다
- **묶음 안에 같은 slug 가 둘 있으면 거절한다.** 만들다가 알게 되면 늦다

### 하나라도 걸리면 아무것도 만들지 않는다

한 벌로 설계한 문제들은 **같이 들어가야 뜻이 맞는다.** 절반만 들어가면 무엇이
들어갔는지 사람이 손으로 대조해야 하고, 그것은 한 개짜리의 "실패하면 아무것도
만들어지지 않는다" 와도 어긋난다.

그래서 **먼저 다 검사하고 나서 만든다.** 세 번째에서 걸렸을 때 앞의 둘이 이미
만들어진 뒤라면, 트랜잭션이 되돌리더라도 올린 사람에게 보이는 것이 흐려진다.

### 응답은 언제나 목록이다

`POST /imports` 는 `{ "created": [{ "id": 1, "slug": "..." }, …] }` 를 돌려준다.
미리보기도 `{ "source": "ZIP", "problems": [ … ] }` 다.
**한 개짜리도 하나가 담긴 목록**이라, 부르는 쪽이 개수에 따라 다른 모양을 다루지 않는다.

## 맨 JSON 도 된다 (#537)

zip 으로 싸지 않은 `problem.json` 하나를 그대로 올려도 된다.

**형식이 둘이 되는 것이 아니다.** 위의 "테스트케이스는 파일이 이기고, 없으면
`problem.json` 의 `testcases` 를 쓴다" 규칙 그대로다 — 맨 JSON 은
**테스트케이스 파일이 없는 묶음**이다.

이 길이 필요한 이유는 **우리가 가진 파일이 대부분 zip 이 아니기 때문**이다.
`scripts/seed-problems` 의 18개도, 스킬(#480~#482)이 내놓는 것도 전부 맨 JSON 이다.
테스트케이스가 세 개인 문제까지 압축하게 하면 그 단계에서 얻는 것이 없다.

**무엇으로 가르는가 — 매직 바이트다.** 파일 이름과 `Content-Type` 은 올리는 쪽이 정하는
값이라 믿지 않는다. `.json` 이라 적힌 zip 도, 확장자가 없는 JSON 도 들어온다.

> ⚠️ **SQL 문제는 zip 이 필요하다.** 스키마가 별도 파일이기 때문이다 (아래).
> 맨 JSON 으로 올리면 읽을 파일이 없다고 거절한다.

## SQL 스키마는 파일로 온다 (#561)

`problem.json` 에 `sqlSchemaFile` 을 적으면 **묶음 안의 그 파일**을 읽어
`sqlSpec.schemaSql` 로 채운다.

```
problem.zip
├── problem.json          "sqlSchemaFile": "sql/library.sql"
├── sql/library.sql       ← 여기서 온다
└── testcases/
```

`scripts/seed-problems` 의 SQL 문제 일곱 개가 이미 이렇게 되어 있다.
**형식을 새로 만든 것이 아니라** 시드가 쓰던 키를 서버가 그대로 읽는 것이다.

왜 파일인가 — 테스트케이스를 파일로 뺀 것과 **같은 이유**다 (#313).

- 다섯 문제가 **같은 스키마를 공유**한다. JSON 에 박으면 한 글자 고칠 때 다섯 파일을 고친다
- **여러 줄 SQL 은 JSON 문자열 안에서 읽을 수 없다**

규칙 셋:

- **파일이 없으면 거절한다.** 조용히 빈 스키마로 만들면 채점이 통째로 어긋난다
- **`sqlSchemaFile` 과 `sqlSpec.schemaSql` 을 둘 다 적으면 거절한다.**
  테스트케이스는 "파일이 이긴다" 지만 그쪽은 파일을 넣기만 하면 되는 것이고,
  여기는 **손으로 적어야** 한다 — 손으로 적은 것 둘이 어긋나면 우리가 정할 일이 아니다
- **아무도 안 가리키는 파일은 여전히 거절한다.** 모아 두는 것과 받아들이는 것은 다르다

## 사람이 만든 zip 을 받는다 (#594)

이 기능은 **출제자가 자기 노트북에서 만든 zip 을 올리는** 자리다. 거기서 반드시 나오는
두 가지를 거절하면 기능이 사실상 안 쓰인다.

**맨 위 폴더 하나는 벗긴다.** `zip -r bundle.zip 내-문제` 는 이름을
`내-문제/problem.json` 으로 만든다 — 폴더를 압축하는 가장 자연스러운 방법이다.

> 이것은 "조용히 고치는 것" 이 아니다. 폴더 접두사는 내용이 아니라 **포장**이라 벗겨도
> 무엇이 들어왔는지는 그대로다. **맨 위가 둘 이상이면 벗기지 않는다** — 그때는 무엇이
> 뜻인지 알 수 없고, 짐작하면 엉뚱한 것을 문제로 만든다.

**macOS 부스러기는 무시한다** — `.DS_Store`, `__MACOSX/`, `._*`, `Thumbs.db`.
"모르는 파일을 버리지 않는다" 는 규칙이 지키려는 것은 **출제자가 넣은 것이 들어갔다고
믿게 두지 않는 것**인데, 이것들은 출제자가 넣은 적이 없다. macOS 는 폴더를 열기만 해도
`.DS_Store` 를 만든다. **목록은 좁게 둔다** — 정확히 아는 이름만 무시하고 나머지는 그대로 거절한다.

## 묶음은 손으로 만들지 않는다

```bash
python3 scripts/pack-problems.py          # 전부
python3 scripts/pack-problems.py 08 16    # 이름에 그 글자가 든 것만
```

`build/problem-bundles/` 에 문제별 zip 이 나온다.

**왜 도구가 필요한가.** 시드는 평면이고(`08-sql-seoul-members.json` + 다섯 문제가 함께
쓰는 `sql/library.sql`), 묶음 하나에는 **그 문제가 가리키는 스키마만** 들어가야 한다.
손으로 폴더를 만들면 매번 "이 문제는 어느 스키마를 쓰나" 를 판단해야 하고, 실제로 안 쓰는
`library-mariadb.sql` 이 섞여 거절당했다. `problem.json` 이 이미 답을 갖고 있으므로
그 판단을 사람에게 시키지 않는다.

시드를 폴더 구조로 바꾸지 않은 이유도 같다 — 그러면 **스키마가 문제마다 복제된다**.
#313 이 피한 것이 정확히 그것이다.

## 올리기

```
POST /api/v1/admin/problems/imports            (multipart/form-data, file=problem.zip 또는 problem.json)
POST /api/v1/admin/problems/imports/preview    (같은 형식. 읽기만 하고 아무것도 만들지 않는다)
```

**미리보기가 먼저다** (#537). 파일을 고르자마자 만들어 버리면 잘못 만든 묶음이
**문제 번호를 하나 먹고** 지워야 할 것으로 남는다 — 번호는 사용자에게 보이는 값이다 (#204).

미리보기는 제목·slug·유형·테스트케이스 개수와 **검증 위반을 모아서** 돌려준다.
첫 번째에서 멈추면 고치고 다시 올리기를 반복하게 되기 때문이다.
**저장과 같은 경로를 지나므로** 미리보기를 통과한 것은 저장도 통과한다.

미리보기 뒤 저장할 때는 **파일을 다시 올린다.** 서버가 올린 것을 들고 있지 않는다 —
아래 "원본은 남지 않는다" 를 지키려면 그래야 한다.

- **언제나 초안으로 들어온다.** `problem.json` 이 `published: true` 라고 적어도 덮는다 —
  올린 것이 바로 공개되면 잘못 만든 묶음이 그대로 사람들 앞에 놓인다
- **폼으로 만들 때와 같은 규칙을 지난다** (#59·#60·#454·#455의 검증). 여기서만 통과하는
  길을 두면 그 길로 들어온 문제가 화면에서 고쳐지지 않는다
- 문제 유형별 자료(SQL 스펙·NoSQL 스펙·파일 목록)도 `problem.json` 에 그대로 적는다

## 압축을 푸는 일은 안전한 작업이 아니다

선택이 아니라 필수다.

| 위험 | 막는 방법 |
|---|---|
| **경로 탈출** (`../../etc/passwd`) | 이름에 `..`·절대 경로가 있으면 거절. `\` 도 `/` 로 보고 검사 |
| **압축 폭탄** (몇 KB → 몇 GB) | **푸는 동안** 크기를 세고 64MB 를 넘으면 그 자리에서 중단 |
| 파일 수 폭증 | 5000개 상한 |
| **맨 JSON 이 큰 경우** | 풀 것이 없어 위 검사를 안 지난다. 그래서 **읽는 동안** 64MB 에서 끊는다 (#537) |
| 업로드 자체가 큰 경우 | 컨테이너 상한(`spring.servlet.multipart`)이 마지막 방어선 |

> 컨테이너 상한이 **6MB 였을 때 이 64MB 상한에 닿을 수가 없었다** (#537).
> 테스트케이스가 수백 개인 문제를 올리라고 만든 기능인데 컨테이너가 먼저 끊었다.
> 지금은 32MB(`CODEKR_MAX_UPLOAD_SIZE`)다. 맨 JSON 은 압축되지 않은 만큼 그대로 크다.

**다 풀고 나서 재지 않는다** — 그때는 이미 메모리를 다 먹은 뒤다.

## 원본은 남지 않는다

**어디에도 저장하지 않는다.** 받은 스트림을 그대로 풀어 문제 데이터로 옮기고 끝낸다.
저장했다가 지우는 방식은 "지우는 것을 잊는" 자리를 만들고, 그러면 저장소가
`문제 수 × 테스트케이스 크기 × 2` 로 늘어난다 (#424).

실패하면 **아무것도 만들어지지 않는다** — 한 트랜잭션 안에서 끝나므로 반쯤 들어온 문제가
남지 않는다. 다시 올리면 된다.

## 아직 없는 것

- **내려받기.** 문제를 옮기거나 백업하려면 필요하지만, 테스트케이스가 통째로 나가는
  일이라 권한을 좁히는 설계가 먼저다
- **미리보기 화면.** 지금은 올리면 초안이 만들어지고, 무엇이 들어왔는지는 편집 화면에서 본다
- **비동기 처리.** 상한이 64MB·5000 파일이라 한 요청 안에서 끝난다. 실제로 느린지 본 뒤에
  큐로 옮기는 것이 맞다 — 그때는 진행 상태를 보여줄 자리도 함께 필요하다.
  문제 여러 개(#623)를 받게 되면서 한 요청이 하는 일이 늘었으므로, **재어 보는 것이
  먼저**다
- **겹치는 slug 를 덮어쓰기.** 지금은 거절한다. 덮어쓰기는 **테스트케이스를 통째로
  갈아 치우는 일**이라 조용히 해서는 안 되고, 무엇이 바뀌는지 보여줄 자리가 먼저다
