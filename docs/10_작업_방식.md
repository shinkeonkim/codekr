# 10. 작업 방식 — 이슈와 Stacked PR

이 저장소는 **모든 작업이 GitHub Issue 에서 시작해 Stacked PR 로 끝난다.** 이 문서는
그 규칙을 정리한 것이다. 새 작업 세션을 시작할 때 이 문서를 먼저 읽는다.

> 커맨드: `/이슈` 로 이슈를 만들고, `/작업` 으로 그 이슈를 시작한다
> (`.claude/commands/`)

---

## 1. 원칙

| 원칙 | 이유 |
|---|---|
| **작업 전에 이슈가 있어야 한다** | 무엇을 왜 하는지가 코드 밖에 남는다. 나중에 "이건 왜 이렇게 했지"의 답이 된다 |
| **PR 은 쌓되 닫지 않는다** | 리뷰어가 변경을 작은 단위로 볼 수 있다. 한 번에 5천 줄을 보면 아무도 못 본다 |
| **커밋 메시지에 이슈 번호를 단다** | `git log` 만으로 맥락이 복원된다 |
| **직접 push 하지 않는다** | main 은 PR 로만 바뀐다 |
| **파일은 200줄을 넘기지 않는다** | 넘으면 대개 한 파일이 두 가지 일을 하고 있다는 신호다 |

---

## 2. 한 사이클

```
① 이슈 확인/등록  →  ② 브랜치  →  ③ 구현 + 검증  →  ④ 커밋  →  ⑤ PR  →  ⑥ 리뷰 → 머지
```

### ① 이슈

없으면 먼저 만든다 — `/이슈 <하고 싶은 것>`. 이 커맨드는 **관련 코드를 먼저 확인하고
중복 이슈를 검사한 뒤**에 만든다. 이미 구현돼 있는데 화면에만 안 보이는 경우가 실제로
있었다 (#82).

손으로 만들 때의 라벨은 영역(`area:*`)과 종류(`type:*`)를 각각 하나씩.

```bash
gh issue create --title "[영역] 무엇을" --label "area:api,type:feature,mvp" --body "..."
```

| 라벨 | 값 |
|---|---|
| 영역 | `area:api` `area:web` `area:executor` `area:judge` `area:infra` `area:docs` |
| 종류 | `type:feature` `type:chore` `bug` `documentation` `enhancement` |
| 시점 | `mvp` `post-mvp` |

이슈 본문에는 **배경(왜)** 과 **할 일 체크리스트**를 쓴다. 구현 방법을 다 적을 필요는
없지만, 판단이 필요한 지점은 적어 둔다.

### ② 브랜치

```
feat/<번호>-<짧은-설명>
```

번호는 **이슈 번호가 아니라 스택에서의 순서**다 (`feat/26-k8s-deploy` 다음은
`feat/27-...`). 브랜치는 **바로 앞 스택 브랜치**에서 딴다 — main 이 아니다.

```bash
git checkout -b feat/28-무엇 feat/27-앞브랜치
```

### ③ 구현 + 검증

**검증하지 않은 것을 했다고 말하지 않는다.** PR 본문에 실제로 돌린 명령과 결과를 쓴다.

| 대상 | 명령 |
|---|---|
| api | `cd apps/api && ./gradlew test integrationTest` |
| go | `cd apps/executor && go vet ./... && go test ./...` + `golangci-lint run ./...` |
| web | `cd apps/web && bun run typecheck && bun run lint && bun run build` |
| 차트 | `helm template ... \| kubeconform -strict` |
| 전체 | `make clean && make up && make seed && make smoke` |

### ④ 커밋

```
<type>(<scope>): <한 줄 요약> (#이슈번호)

무엇을 왜 그렇게 했는지. 특히 **다른 선택지를 버린 이유**.
검증한 것이 있으면 결과를 적는다.
```

한 커밋 = 한 논리적 변경. 리팩터링과 기능 추가를 섞지 않는다.

### ⑤ PR

```bash
gh pr create --base feat/27-앞브랜치 --head feat/28-내브랜치 \
  --title "[영역] 무엇을" --body "..."
```

**base 는 바로 앞 스택 브랜치다.** main 이 아니다.

PR 본문에 반드시 담을 것:

- `Closes #N` — 머지되면 이슈가 자동으로 닫힌다
- **왜 이렇게 했는가.** 특히 다른 방법을 버린 이유
- **검증 결과.** 돌린 명령과 실제 출력
- **하지 않은 것과 그 이유.** 이게 빠지면 리뷰어가 빠진 걸 발견해야 한다
- 스택 위치 (`#67 위에 쌓았습니다`)

### ⑥ 리뷰 지적을 받으면

- **그 PR 안에서 고칠 수 있으면 거기서 고친다.** 새 PR 로 미루지 않는다
- **구조를 바꿔야 하면** 후속 이슈로 남기고, 그 이슈 번호를 PR 에 적는다
- 스택 아래쪽을 고쳤으면 위쪽을 리베이스한다 (§4)

## 3. 지금 열려 있는 스택 보기

```bash
gh pr list --state open --json number,headRefName,baseRefName \
  -q '.[] | "#\(.number) \(.headRefName) -> \(.baseRefName)"'
```

## 4. 스택 리베이스 (아래쪽을 고쳤을 때)

스택은 **선형**이다. 아래 브랜치가 위 브랜치의 조상이어야 한다.

```bash
# 0. 되돌릴 수 있게 먼저 기록
git for-each-ref --format='%(refname) %(objectname)' refs/heads > /tmp/refs-backup.txt

# 1. 선형인지 확인
git merge-base --is-ancestor feat/26-앞 feat/27-뒤 && echo OK

# 2. 아래에서 위로 하나씩
git checkout feat/27-뒤 && git rebase feat/26-앞

# 3. 내용이 보존됐는지 확인 — 의도한 변경만 나와야 한다
git diff <리베이스전-tip> feat/27-뒤 --stat

# 4. push
git push --force-with-lease origin feat/26-앞 feat/27-뒤
```

> ⚠️ **`--force` 를 그냥 쓰지 않는다.** 반드시 `--force-with-lease` 다.
> 예전에 `feat/01-docs` 를 force push 해서 머지 커밋을 날린 적이 있다.
> 리베이스 전 tip 해시를 반드시 어딘가에 적어 두고 시작한다.

## 5. 머지 순서

Stacked PR 은 **아래에서 위로** 머지한다. 그런데 아래를 머지해도 위 내용이 자동으로
따라 올라가지 않는다 — 머지 시점의 상위 브랜치 상태만 담기기 때문이다.

**한 번에 여러 단을 main 으로 보내려면, 가장 위 브랜치를 main 에 직접 머지한다.**
(#69 가 그렇게 정리한 사례다.)

머지 후에는 다음 PR 의 base 를 다시 맞춘다.

```bash
gh pr edit <번호> --base main
```

## 6. 해야 할 일이 떠올랐을 때

작업 중에 발견한 문제를 **그 자리에서 고치지 않는다.** 지금 PR 의 범위를 넘으면
이슈로 남긴다. 그래야 PR 이 한 가지 일만 한다.

```bash
gh issue create --title "..." --label "area:web,type:chore" --body "발견 맥락: PR #NN 작업 중"
```
