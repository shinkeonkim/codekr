# 03. API 명세

베이스 URL: `http://localhost:18080` (로컬). 모든 REST 경로는 `/api/v1` 접두사를 가진다.

## 0. 공통 규약

### 인증

보호된 엔드포인트는 `Authorization: Bearer <accessToken>` 을 요구한다.

### 에러 응답

```json
{
  "code": "PROBLEM_NOT_FOUND",
  "message": "문제를 찾을 수 없습니다.",
  "fieldErrors": [ { "field": "email", "message": "이메일 형식이 아닙니다." } ]
}
```

| HTTP | 상황 |
|---|---|
| 400 | 검증 실패 (`VALIDATION_ERROR`), 읽을 수 없는 본문 (`MALFORMED_REQUEST`) |
| 401 | 미인증/토큰 만료 (`UNAUTHORIZED`) |
| 403 | 권한 부족 (`FORBIDDEN`) |
| 404 | 리소스 없음 (`*_NOT_FOUND`), 없는 경로 (`RESOURCE_NOT_FOUND`) |
| 405 | 못 쓰는 메서드 (`METHOD_NOT_ALLOWED`) — 어떤 메서드가 되는지 문구와 `Allow` 에 |
| 409 | 중복 (`EMAIL_ALREADY_EXISTS`, `SLUG_ALREADY_EXISTS`) |
| 413 | 업로드 상한 초과 (`IMAGE_TOO_LARGE`) |
| 415 | 모르는 형식 (`UNSUPPORTED_MEDIA_TYPE`) |
| 429 | 너무 잦은 요청 (`TOO_MANY_REQUESTS`, `SUBMISSION_TOO_FREQUENT`) |
| 500 | 서버 오류 (`INTERNAL_ERROR`) |

**500 은 "우리 잘못" 이다** (#324). 없는 경로·못 쓰는 메서드·깨진 본문은 전부 요청
잘못인데 500 으로 나갔다 — 오타 하나가 경보를 울리면 **진짜 장애가 그 사이에 묻힌다.**
그래서 이 넷은 `log.error` 도 남기지 않는다: 우리가 고칠 것이 없는 일이 오류 로그에
쌓이면 그 로그가 신호가 아니라 잡음이 된다.

없는 경로를 404 로 알리는 것이 정보 노출인지 — **인증 필터가 먼저 걸린다.**
비로그인에게는 401 이 먼저 가므로 그 경로가 있는지조차 알 수 없다.

### 페이지 응답

```json
{ "content": [...], "page": 0, "size": 20, "totalElements": 137, "totalPages": 7 }
```

```json
// 200
{ "status": "OK", "stdout": "3\n", "stderr": "", "runtimeMs": 24, "memoryKb": 8192, "truncated": false }
```

### POST `/{slug}/submissions` 🔒

```json
// 요청

```

`visibility` 는 소스 코드 공개 범위이며 생략하면 `PRIVATE` 이다 (아래 3.1).
이후 진행은 WebSocket 으로 받는다.

## 3. 제출 `/api/v1/submissions`

### 3.1 소스 코드 공개 범위 (#33)

**메타데이터와 소스 코드를 분리해서 다룬다.** 문제·판정·실행 시간 같은 메타데이터는
로그인한 회원에게 보인다(전체 제출 목록의 전제). 소스 코드만 공개 범위로 가린다.

| 값 | 소스 코드를 볼 수 있는 사람 |
|---|---|
| `PUBLIC` | 모든 회원 |
| `PRIVATE` | 작성자, 관리자 |
| `ACCEPTED_ONLY` | 최종 판정이 `ACCEPTED` 로 확정된 뒤의 모든 회원 |

작성자와 관리자는 공개 범위와 무관하게 항상 볼 수 있다.

**설계 결정**

- **기본값은 `PRIVATE`.** 공개는 사용자가 명시적으로 선택해야 하는 행위다. 한 번 공개된 코드는
  되돌려도 이미 읽힌 뒤일 수 있다.
- **변경은 작성자만, 시점 제한 없음.** 관리자도 남의 공개 범위를 바꿀 수 없다 — 그것은
  작성자의 결정이다. 채점 전에 골라 둔 값을 나중에 바꾸고 싶은 경우가 자연스럽다.
- 응답에서 볼 권한이 없으면 `sourceCode` 를 **빈 문자열이 아니라 아예 내리지 않고**,
  `sourceVisible: false` 로 알린다.

### PATCH `/{id}/visibility` 🔒 (작성자만)

```json
{ "visibility": "PUBLIC" }
```

→ 204. 남의 제출이면 403.

### GET `/{id}` 🔒 (본인 또는 ADMIN)

```json

  "id": 1024, "problemSlug": "two-sum", "problemTitle": "두 수의 합",
  "runtimeId": "python:3.12", "status": "COMPLETED", "verdict": "ACCEPTED",
  "passedCount": 10, "totalCount": 10, "maxRuntimeMs": 31, "maxMemoryKb": 9012,
  "compileError": null,
  "visibility": "PRIVATE", "sourceVisible": true, "sourceCode": "...", "nickname": "코더",
  "results": [ { "seq": 1, "verdict": "ACCEPTED", "runtimeMs": 24, "memoryKb": 8192, "stderrExcerpt": null } ],
  "createdAt": "2026-08-10T12:00:00Z"

```

### GET `/` 🔒

내 제출 목록. 쿼리: `problemSlug`, `page`, `size`.

### GET `/explore` 🔒 (#34)

전체 회원의 제출 목록. **소스 코드는 담기지 않으며**, 상세에서 볼 수 있는지를
`sourceVisible` 로 미리 알려준다.

| 쿼리 | 설명 |
|---|---|
| `problemSlug` | 문제 |
| `nickname` | 회원 닉네임 부분 일치 |
| `runtimeId` | 실행 환경 |
| `verdict` | 판정 |
| `from`, `to` | 제출일 범위 (`YYYY-MM-DD`, **종료일 당일 포함**) |
| `sort` | `LATEST`(기본) \| `OLDEST` \| `RUNTIME` \| `MEMORY` |
| `page`, `size` | size 최대 50 |

- 날짜 경계는 **Asia/Seoul** 기준이다.
- 정렬은 항상 `id` 를 마지막 키로 둔다 — 같은 값이 여럿일 때 페이지 사이에서 순서가 흔들리면
  중복·누락이 생긴다.
- 정답 코드 검증 제출(#39)은 어떤 조건으로도 조회되지 않는다.

## 4. 실시간 — WebSocket `/ws/submissions`

접속 후 구독 메시지를 보낸다.

```json
// client → server
{ "type": "SUBSCRIBE", "submissionId": 1024, "token": "<accessToken>" }
```

서버는 해당 제출의 소유자인지 검증한 뒤 이벤트를 흘려보낸다.

```json
{ "type": "JUDGING",   "submissionId": 1024, "totalCount": 10 }
{ "type": "TESTCASE",  "submissionId": 1024, "seq": 1, "verdict": "ACCEPTED", "runtimeMs": 24, "memoryKb": 8192 }
{ "type": "COMPLETED", "submissionId": 1024, "verdict": "ACCEPTED", "passedCount": 10, "totalCount": 10 }
```

`COMPLETED` 수신 후 서버가 연결을 유지하되, 클라이언트는 구독을 해제해도 된다.
WebSocket 을 사용할 수 없는 환경을 위해 `GET /submissions/{id}` 폴링이 항상 대안으로 존재한다.

### 재채점 결과 알림

문제를 재채점하면 대상이었던 **모든** 회원에게 결과를 알린다 (#187).

- 판정 전이를 `rejudge_submission_results` 에 **전부 남긴다** — 바뀐 것뿐 아니라 그대로인
  것도. 남기지 않으면 나중에 "그때 무슨 일이 있었나"에 답할 수 없다
- 알림은 **배치가 끝났을 때 사람마다 한 번**이다. 제출마다 보내면 같은 문제에 스무 번 낸
  사람에게 스무 번 울린다
- 본문에 전이를 그대로 적는다 — `맞았습니다 → 틀렸습니다`. "바뀌었습니다"만으로는
  유리해진 것인지 불리해진 것인지 알 수 없다

```
테스트케이스가 수정되었습니다 판정이 바뀌었습니다: 틀렸습니다 → 맞았습니다 (2건) 랭킹 점수가 20점 올랐습니다.
```

### 제출 간격 제한

같은 사람이 같은 문제에 연달아 내는 것을 막는다 (#189). 걸리면 **429** 와
`SUBMISSION_TOO_FREQUENT`, 남은 시간을 담은 메시지가 온다.

| 경로 | 간격 |
|---|---|
| 일반 제출 | 30초 |
| 대회 제출 | 대회의 `submissionCooldownSeconds` (기본 20초, **최소 3초**) |

**검증을 통과한 요청에만 간격을 따진다.** 잘못된 런타임 같은 오류는 간격과 무관하게
그대로 알려 준다 — 아니면 무엇이 틀렸는지 모른 채 간격만큼 기다리게 된다.

대회 등록·수정의 `submissionCooldownSeconds` 는 3 미만이면 400 이다. 0 을 허용하면
제한이 없는 것과 같아지고, 한 참가자가 채점 차선을 혼자 채울 수 있다.

## 5. 어드민 `/api/v1/admin` 🔒 ROLE_ADMIN

### POST `/ranking/recompute` · POST `/users/{userId}/ranking/recompute`

랭킹 집계를 제출 기록에서 다시 만든다 (#177). 점수·최고 점수(실력 티어의 근거)·뱃지를
함께 맞춘다.

```json
{ "users": 128 }                        // 전체
{ "score": 930, "solvedCount": 12 }     // 한 사람
```

**랭킹을 처음 붙인 직후에는 전체를 한 번 불러야 한다.** 그 전의 제출은 점수 표를 거치지
않았으므로, 부르지 않으면 랭킹이 빈 채로 시작한다.

여러 번 불러도 결과는 같다.

### GET `/problems`

미공개 문제를 포함한 전체 목록. 쿼리는 공개 목록과 동일.

### POST `/problems`

```json
{
  "slug": "two-sum", "title": "두 수의 합",
  "category": "ALGORITHM", "difficulty": "BRONZE_5",
  "description": "…", "inputDescription": "…", "outputDescription": "…",
  "timeLimitMs": 2000, "memoryLimitMb": 256, "published": true,
  "testcases": [
    { "seq": 1, "input": "1 2\n", "expectedOutput": "3\n", "visibility": "PUBLIC" },
    { "seq": 2, "input": "10 20\n", "expectedOutput": "30\n", "visibility": "HIDDEN" }
  ],
  "templates": [
    { "runtimeId": "python:3.12", "sourceCode": "import sys\n\ndef main():\n    pass\n" }
  ],
  "solution": { "runtimeId": "python:3.12", "sourceCode": "print(3)" }
}
```

`difficulty` 는 `BRONZE_5` ~ `RUBY_1` 의 30단계 중 하나다 (docs/02 3장).
`templates` 는 언어별 초기 코드이며, 등록하지 않은 언어는 런타임 기본 템플릿을 쓴다.
`solution` 은 선택 사항이다 — 넣으면 전체 테스트케이스를 검증할 수 있고,
**일반 사용자와 공개 API 는 그 존재조차 조회할 수 없다.**

→ 201 `{ "id": 1, "slug": "two-sum" }`. slug 중복 시 409.

### GET `/problems/{id}`

히든 테스트케이스, 언어별 초기 코드, **정답 코드와 마지막 검증 결과**를 반환한다
(어드민 편집 화면용).

```json
{
  "solution": { "runtimeId": "python:3.12", "sourceCode": "print(3)" },
  "verification": {
    "submissionId": 91, "status": "COMPLETED", "verdict": "ACCEPTED",
    "passedCount": 5, "totalCount": 5, "compileError": null,
    "stale": false,
    "results": [ { "seq": 1, "verdict": "ACCEPTED", "runtimeMs": 12, "memoryKb": 5000 } ]
  }
}
```

`stale` 이 true 면 검증 이후 테스트케이스나 실행 제한이 바뀐 것이다 — 결과를 믿을 수 없다.

### POST `/problems/{id}/verify`

등록된 정답 코드로 **전체 테스트케이스**(공개·히든 모두)를 검증한다.
사용자 제출과 같은 채점 큐를 쓰므로 진행 상황은 문제 상세의 `verification` 으로 확인한다.

→ 202. 정답 코드가 없으면 400 `SOLUTION_REQUIRED`.

### PUT `/problems/{id}`

POST 와 동일한 바디. 테스트케이스와 초기 코드는 **전체 치환**한다
(부분 수정 API 를 따로 두지 않는다 — YAGNI).

### DELETE `/problems/{id}`

→ 204. **소프트 삭제**다 — 행은 남고 `deleted_at` 만 채워진다 (ADR-0007).
따라서 그 문제로 남긴 제출 이력은 그대로 조회되며, 삭제한 slug 는 다시 쓸 수 있다.

### POST `/retention/cleanup` (#46)

보관 기간이 지난 소프트 삭제 행을 실제로 지운다. 자동 실행(매일 04:00 KST)을 기다리지 않고
결과를 확인해야 할 때 쓴다.

```json
{
  "executedAt": "2026-08-10T19:00:00Z",
  "deletedProblems": 2, "deletedTestcases": 41, "deletedTemplates": 7,
  "truncated": false
}
```

`truncated` 가 true 면 한 번에 지울 상한에 걸린 것이다 — 다음 실행에서 이어서 지운다.

| `AUTHENTICATED` | 로그인한 사용자. **자원 소유권 검사는 서비스가 따로 한다** |
| `ADMIN` | 어드민 역할. **어느 역할인지는 엔드포인트마다 다르다** (#103) |

**수준은 컨트롤러에 선언한다** (#198 — 바로 아래). 목록은 그 선언에서 끌어내므로
따로 적을 곳이 없고, 선언하지 않으면 **기동이 멈춘다.**

`EndpointAuthorizationIntegrationTest` 는 남는다. 선언한 대로 **실제로 401/403 이
나오는지**는 눌러 봐야 알기 때문이다 (#71) — 목록이 자동으로 만들어지는 지금은 그것이
유일한 검증이다.

### 내 설정 (#104)

`GET`/`PATCH /api/v1/users/me/settings`

- **`PATCH` 는 보낸 항목만 바꾼다.** 전체를 보내게 하면 새 항목이 생겼을 때 옛 화면이
  그것을 지운다
- 제출 요청의 `visibility` 가 없으면 **서버가** 사용자 기본값을 채운다. 화면이 기본값을
  알고 보내는 방식이면 화면마다 어긋난다
- 기본값 변경은 **앞으로의 제출에만** 적용된다. 이미 낸 제출의 공개 범위는 그대로다
- **랭킹에서 빠지는 설정은 없앴다** (#207). 아무도 켜지 않았고(운영·로컬 모두 0건),
  "여기 없는 사람이 있을 수 있다" 는 것만으로 순위표 전체를 못 믿게 만든다. 지금
  랭킹에서 빠지는 사람은 탈퇴자뿐이다

### 아직 못 푼 사람도 순위표에 있다 (#391)

#207 이 위의 설정을 걷어냈는데도 **0점인 사람은 여전히 안 보였다.** 설정이 아니라
**집계 구조로** 빠지고 있었기 때문이다 — 질의가 `user_problem_scores`(사용자 × 푼 문제
= 1행)에서 시작해서, 푼 문제가 없으면 행이 없고 행이 없으면 순위표에 없었다.

가입만 한 사람에게는 **자기가 목록에 없으니 올라갈 곳도 보이지 않았다.**

| 판단 | 결정 | 왜 |
|---|---|---|
| 기준 표 | `users` 에서 시작해 왼쪽으로 잇는다 | 순위표의 모집단은 사람이지 점수 행이 아니다 |
| 누가 오르나 | 탈퇴자만 뺀다 (그대로) | "전체 노출" 은 **랭킹에 낄 자격이 있는 사람 전부**라는 뜻이다 |
| 0점에 등수를 주나 | **준다** | 안 주면 "전체 노출" 의 절반만 하는 것이다 |
| 마지막 동점 처리 | **가입이 이른 순** (닉네임 아님) | 아래 |
| 월간에도 적용하나 | **적용한다** | 이번 달에 아직 못 푼 사람이야말로 자기가 어디쯤인지 봐야 한다. **기간이 거르는 것은 점수지 사람이 아니다** |
| 기간 조건 | `WHERE` 가 아니라 **`JOIN` 조건** | `WHERE` 에 두면 왼쪽 조인이 안쪽 조인이 되어 고치려던 것이 그대로 돌아온다 |

#### 동점 처리에서 닉네임을 뺀 이유

전에는 `… last_solved_at ASC, nickname ASC` 였다. 둘이 문제가 됐다.

1. **0점이 대다수가 된다.** 그들끼리는 `last_solved_at` 이 없어 사실상 **가나다순으로
   줄 세운** 순위표가 된다
2. **닉네임은 이제 바뀐다** (#307). 바뀌는 값으로 등수를 가르면 이름을 고친 사람 때문에
   **남의 등수가 함께 움직인다.** 가입일은 바뀌지 않는다

#### 크기

모집단이 "푼 사람" 에서 **가입자 수**로 바뀐다. 페이지 수가 늘고 전체 개수 질의도
`users` 를 센다. 지금 규모에서는 문제가 없다 — **언제 바꿀지를 미리 적어 둔다**:
목록 질의가 p95 300ms 를 넘으면 집계 표를 만든다 (#105 가 그 대가를 적어 두었다).

### 문제 목록 필터 (#239)

`?kind=`·`?acceptanceFrom=`·`?acceptanceTo=`·`?solversFrom=`·`?solversTo=`·`?solved=`
(태그 `?tag=` 는 #232 에서 이미 있다).

- **`solved` 는 로그인해야 뜻이 있다.** 비로그인이 넘기면 **조용히 무시한다** — 여기서
  401 을 내면 공개 목록이 로그인해야 열리는 화면이 된다. 누를 수 없는 필터를 보여 주지
  않는 것은 화면의 몫이다
- **정답률 범위를 걸면 제출자가 없는 문제가 빠진다.** 정답률이 `NULL` 이라 어느 범위에도
  들지 않는다 — `0/0` 은 0% 가 아니다 (#205). 화면이 그 사실을 적어 둔다
- **"허용 언어" 필터는 없다.** 이 저장소에는 문제별 허용 언어라는 것이 없다 —
  `problem_runtime_limits` 는 제한 오버라이드이지 목록이 아니고(#97), 어떤 언어로 풀
  수 있는지는 **문제 유형**이 정한다. 없는 데이터로 필터를 만들면 걸어도 아무 일이
  일어나지 않는 칸이 생긴다

### 문제 목록 정렬 (#132, #205)

`?sort=` 로 아홉 가지 — 최신·오래된·쉬운·어려운·많이 풀린·적게 풀린·정답률 높은·낮은·제목순.

**방향을 값에 담는다.** 기준과 방향을 두 파라미터로 나누면 "제목순 내림차순" 같은 뜻
없는 조합이 생기고, 주소에 남는 상태도 둘이 된다. #132 의 "기준마다 자연스러운 방향
하나만" 은 **뒤집혔다** — 많이 풀린 순과 적게 풀린 순은 찾는 목적이 다르다.

정답률·풀이 수 정렬을 위해 문제별 집계를 **저장한다**(`problem_stats`). 한 페이지분을
세는 것과 전체를 정렬하는 것은 다른 일이다.

- **원자료는 여전히 `submissions` 하나다.** 저장된 값은 캐시이고 언제든 다시 센다
- 채점이 끝날 때마다 **그 문제를 다시 센다.** 증분이 아니다 — 재채점으로 판정이
  뒤집히면 정답자 수가 **내려가야** 하는데 증분은 그때 틀린다
- 어긋났을 때를 위해 두 경로를 둔다: `POST /api/v1/admin/problems/stats/recompute`(전부
  다시 세기)와 `GET .../stats/drift`(저장된 값과 센 값이 다른 문제 목록).
  **어긋나도 아무도 모르는 것이 가장 나쁘다**
- 제출자가 없는 문제의 정답률은 **`NULL` 이다** — `0/0` 은 정답률이 없는 것이지 0% 가
  아니다. 정렬에서 뒤로 보낸다
- 화면에 보이는 숫자는 그대로 조회 시점에 센다 (#84). 저장된 값이 어긋나도 **차례**가
  틀릴 뿐 신뢰할 수 없는 숫자가 보이지는 않는다

### 문제 번호 (#204)

`problems.id` 를 그대로 공개 번호로 쓴다. 별도 번호 컬럼을 두지 않는다.

- `GET /api/v1/problems/{key}` 의 `key` 는 **번호이거나 slug** 다. 사람은 문제를
  "1000번" 이라고 부르고, 그렇게 부른 것을 주소창에 넣었을 때 열려야 한다
- **번호가 정본 주소다.** 화면의 모든 문제 링크가 `/problems/{번호}` 로 간다.
  slug 도 계속 받는다 — 이미 공유된 링크가 죽으면 안 된다
- 그래서 제출·게시글·문제집·대회 응답에 **문제 번호를 함께 싣는다.** 링크를 만들려면
  필요하고, 전에는 slug 만 내려가고 있었다
- 검색창의 숫자는 **제목 검색을 대체하지 않고 더한다** — "3" 을 넣은 사람이 3번 문제를
  찾는지 제목에 3이 든 문제를 찾는지 알 수 없다
- 번호로 여는 길이 공개 여부를 우회하지 않는다. 미공개·삭제는 그대로 404

**번호에 구멍이 난다.** 소프트 삭제된 문제와 미공개 초안이 번호를 먹는다 — 상관없는
것으로 정했다 (#204). 대신 **한 번 노출한 번호는 바꾸거나 재사용하지 않는다.**
### 엔드포인트를 추가할 때 (#198)

**접근 수준을 컨트롤러에 선언한다.** 경로는 매핑에 이미 있으므로 다시 적지 않는다.

```kotlin
@PublicApi                          // 토큰 없이 누구나
@AuthenticatedApi                   // 로그인하면 누구나
@AdminApi(UserRole.PROBLEM_SETTER)  // 이 역할 이상 (위계는 RoleHierarchy 가 잇는다)
@GetMapping("/{id}")
fun detail(...)
```

선언하지 않으면 **기동이 멈춘다.** 기본값으로 막고 넘어가면 아무도 다시 보지 않는다 —
"이건 누가 쓰는가" 를 한 번은 답하게 만드는 것이 이 장치의 목적이다 (#71).

클래스에 붙이면 그 컨트롤러의 기본값이 되고, **메서드 선언이 이긴다** — 핸들러 하나만
공개인 경우가 흔하다.

**자원 소유권은 이것으로 표현되지 않는다.** `@AuthenticatedApi` 는 "로그인했는가" 까지다.
*자기 것인가* 는 서비스가 따로 본다. 대회 관리자가 자기 대회만 만지는 것(#103)도 마찬가지다.

집행은 필터 체인에서 일어난다 — `@PreAuthorize` 가 아닌 이유는 그것이 **본문 바인딩
뒤에** 돌아서, 권한 없는 요청이 400(검증 실패)을 먼저 받고 막혔다는 사실조차 알 수
없기 때문이다.

### 어드민 회원 관리 (#223)

`GET /api/v1/admin/users`(목록·검색) · `GET /api/v1/admin/users/{id}`(상세)

**읽기와 쓰기의 권한이 다르다.**

| 하는 일 | 역할 |
|---|---|
| 목록·검색·상세 | `ADMIN` |
| 역할 변경(#103) · 강제 탈퇴(#140) | `SUPERUSER` |

전에는 어드민 회원 경로가 규칙에 없어 **통째로 SUPERUSER 로 잠겨** 있었다. 경로로
나누면 순서에 의존해 조용히 덮이는데, 지금은 핸들러마다 선언한다 (#198).

- **목록에 id 와 이메일을 함께 준다.** 사람을 특정하려면 둘 다 필요하고, 재계산 같은
  작업이 id 를 요구한다 — 목록에서 집어낼 수 없으면 DB 를 열어야 한다
- **검색어는 두 글자 이상.** 목록에 이메일을 보이므로 부분 일치 검색이 사실상 이메일
  목록을 훑는 수단이 된다. 한 글자를 막는 것만으로 그 값이 크게 떨어진다
- **탈퇴한 회원은 기본으로 뺀다.** `includeWithdrawn=true` 로 켠다
- 상세의 점수·푼 문제 수는 **랭킹 표에서 온다.** 여기서 다시 세지 않는다 — 세는 규칙이
  두 곳에 생기면 프로필과 어드민 화면의 숫자가 갈린다 (#269 에서 겪은 것)

### 데이터 초기화 (#285)

`POST /api/v1/admin/data/reset` — **최고 관리자만.**

문제·제출·랭킹·활동·뱃지·대회·문제집·알림을 비우고 시퀀스를 1부터 돌린다.
**회원·게시판·분류는 남는다.**

- **`TRUNCATE ... CASCADE` 를 쓰지 않는다.** 그것은 `ON DELETE` 규칙을 무시하고 참조하는
  표를 통째로 비운다 — `posts.problem_id` 가 문제를 가리키므로 **게시판 글이 함께
  사라진다.** `DELETE` 는 `ON DELETE SET NULL` 을 지켜, 문제를 가리키던 질문(#139)은
  살아남고 가리키던 곳만 비워진다
- 시퀀스는 카탈로그에서 **기본값이 `nextval` 인 칸**을 찾아 되돌린다. `id` 를 짐작하면
  복합 키만 있는 표에서 오류가 난다
- **기능 자체를 끌 수 있다** (`codekr.data-reset.enabled`, 기본 꺼짐). 꺼져 있으면
  403 이 아니라 **404** 다 — 켜져 있는지 여부까지 감춘다
- 확인 문구(`문제와 제출을 모두 지웁니다`)를 본문에 그대로 실어야 실행된다.
  화면의 입력만으로는 잘못 눌린 요청을 막지 못한다
- **언제 이 기능을 걷는지는 #303 에 적혀 있다**

### 문제마다 풀 수 있는 언어 (#419)

문제 상세의 `runtimes` 는 **그 문제로 풀 수 있는 것만** 담는다.

- 전에는 `problemKind` 하나로만 갈렸다 — 그것은 **문제의 종류**(stdio·SQL·퀴즈)이지
  언어 목록이 아니다. 그래서 "파이썬으로만 푸는 문제" 를 낼 수 없었고, 아희·엄랭(#394)이
  들어온 뒤로는 반대로 **모든 문제 목록에 그것이 떴다**
- **비워 두면 그 종류의 전부를 허용한다.** 기존 문제가 그대로 돌아야 하고, 언어를 새로
  들일 때 문제를 전부 손보게 하지 않으려는 것이기도 하다
- **서버가 제출을 막는다.** 화면이 안 보여주는 것으로는 부족하다 — API 를 직접 부르면
  통과한다. 거부 문구에 무엇을 쓸 수 있는지를 담는다
- `runtimeRestricted` 가 함께 온다. **목록이 짧은 것을 화면이 고장으로 읽지 않게** 하는
  값이다
- **`problem_runtime_limits`(#97) 와 다른 표다.** 그쪽은 "이 런타임은 제한이 다르다"
  이지 "이 런타임만 허용한다" 가 아니다. 합치면 제한을 적어 둔 런타임만 허용되는 것으로
  바뀌어 기존 문제의 동작이 조용히 달라진다
- **종류 규칙이 먼저다** (#60). 허용 목록은 그 안에서 **좁히는 것이지 넓히는 것이 아니다** —
  stdio 문제에 `sql:postgres16` 을 적어도 제출되지 않는다
- **이미 낸 제출은 그대로다.** 허용에서 뺀 언어로 낸 제출도 판정이 남고, 재채점(#107)도
  그대로 돈다 — 검증은 새 제출에만 건다. 지난 제출을 소급해 무효로 만들 이유가 없다

### 난해한 언어 전용 문제 (#420)

시드에 아희·엄랭 전용 문제가 하나씩 있다 (`13-aheui-sum`, `14-umjunsik-echo`).

- **그 언어로만 제출된다** (#419 의 허용 목록). 아희 문제를 파이썬으로 풀 수 있으면
  그 문제는 있을 이유가 없다
- **난이도는 문제 기준(브론즈 5)이다.** 언어 기준으로 올리면 **점수(#57)가 난이도로만
  정해지므로** 아희로 A+B 를 푼 사람이 실제 알고리즘 문제를 푼 사람보다 점수를 더 받는다.
  언어의 어려움을 인정하는 자리는 점수가 아니라 뱃지(#201)다
- **실행 제한을 5초로 준다.** 둘 다 JIT 없는 순수 파이썬 인터프리터라 느리다 (#394, #97)
- **엄랭은 한 줄에 두 수를 읽지 못한다.** 그래서 엄랭 문제는 입력이 하나다 —
  언어가 못 하는 것을 문제가 요구하지 않는다

### NoSQL 문제 (#455)

`problemKind: JUDGE_NOSQL` 과 `nosql:redis7` 런타임이 있다. 시드에 전용 문제가 하나
있다 (`17-redis-stock-restock`).

- **스펙이 다르다**: `nosqlSpec` 은 `seedCommands`(선택) · `answerCommands` ·
  `verifyCommands` · `ignoreOrder` 다
- **`verifyCommands` 는 비워 둘 수 없다.** 명령의 연속에는 견줄 결과 집합이 없다 —
  이것이 없으면 무엇을 정답으로 볼지가 없다
- **순서는 기본으로 지킨다.** SQL 의 행 순서와 반대다 — 정렬 집합·리스트에서 순서는
  자료의 일부다
- **어느 제품인지 적어야 한다** (#454 와 같은 규칙). 시드와 정답이 그 제품의 명령이다
- 테스트케이스는 없어도 된다 — 채점 대상이 끝난 뒤의 상태다

### SQL 문제의 데이터베이스 (#454)

`sql:postgres16` 과 `sql:mariadb11` 이 있다. **SQL 문제는 어느 것으로 푸는지 반드시
적어야 한다** (`allowedRuntimeIds` 에 하나).

- **비워 둘 수 없다.** 다른 유형과 다른 점이다 — 비워 두면 PostgreSQL 문법의 스키마가
  MariaDB 제출에서도 돌아 **출제자의 스키마가 먼저 깨진다**
- **둘을 함께 고를 수도 없다.** 스키마도 정답도 지문도 갈라지므로 문제를 둘 만든다
- **시간 제한이 기동 시간을 덮어야 한다.** MariaDB 는 뜨는 데만 3.5초를 쓴다 —
  `startupMs + 1초` 보다 빠듯하면 등록을 거부한다 (docs/plans §8.3)
- 지금 있던 SQL 문제는 이관(`V59`)에서 PostgreSQL 로 적혔다

### 난이도 투표 (#477)

```
GET  /api/v1/problems/{slug}/difficulty-vote
POST /api/v1/problems/{slug}/difficulty-vote   {"level": 12}
```

**사용자가 사이트 자체를 낫게 만드는 첫 통로다.** 지금까지 사용자가 만드는 것은
제출·글·댓글뿐이었고 전부 자기 것이었다.

- **푼 사람만 매긴다.** 안 풀고 매기는 것은 뜻이 약하고, "어려워서 못 풀었다" 와
  "풀어 보니 이 정도였다" 를 한 숫자에 섞으면 그 숫자가 무엇을 재는지 알 수 없다.
  못 푼 사람의 체감은 정답률(#84)이 이미 말한다
- **표는 바꿀 수 있다.** 문제가 고쳐지면(테스트케이스가 늘거나 지문이 명확해지면)
  옛 판단은 지금의 문제를 말하지 않는다
- **분포는 내가 투표한 뒤에만 온다.** 먼저 보면 뒤에 오는 사람이 끌려가고, 그러면 모인
  숫자는 문제의 난이도가 아니라 처음 몇 표의 메아리가 된다
- **집계는 중앙값.** 티어는 순서가 있는 값이고, 표가 적을 때 극단값 하나가 평균을 끌고
  간다 — 장난 표 한 장이 난이도를 바꾸면 그 순간 이 기능은 신뢰를 잃는다
- **`UNRATED`(#195) 만 자동으로 채운다.** 어드민이 정한 난이도는 덮지 않는다.
  난이도가 붙으면 **점수를 함께 다시 계산한다** (#194)
- 반영에 필요한 표 수는 설정이다 (`codekr.difficulty-vote.min-votes`, 기본 3). 지금은
  사용자도 문제도 적어 **문턱을 높이면 아무도 못 쓰는 상태**가 된다

### 문제 데이터 업로드 (#479)

```
POST /api/v1/admin/problems/imports   (multipart/form-data)
```

테스트케이스가 백 개를 넘으면 폼으로는 못 만든다. 묶음은 `problem.json` +
`testcases` 아래의 `{seq}.in`·`{seq}.out` 이고, **JSON 은 시드 파일과 같은 형식**이다.
자세한 것은 `docs/12_문제_묶음_형식.md` 에 있다.

- **언제나 초안**으로 들어온다. 묶음이 `published: true` 라 적어도 덮는다
- **폼과 같은 검증**을 지난다
- 압축 폭탄(64MB·5000파일 상한)과 경로 탈출을 막는다. **푸는 동안** 재고, 넘으면 중단한다
- 업로드한 파일은 **어디에도 저장하지 않는다** — 풀어서 옮기고 끝낸다

### 프로필 배지 (#475)

```
GET /badge/{handle}.svg        # 밝은 배경
GET /badge/{handle}.svg?theme=dark
```

- **`/api/v1` 아래가 아니다.** 사람이 손으로 적어 README 에 붙이는 주소이고, 한 번 남의
  README 에 박히면 **우리가 옮길 수 없다** — 버전이 붙는 자리에 두면 v2 로 갈 때 그 링크가
  전부 깨진다
- **밖의 것을 하나도 참조하지 않는다.** GitHub 은 이미지를 자기 프록시로 받는데 그 안에서는
  웹폰트도 다른 이미지도 따라오지 않는다. 글꼴은 기기에 있는 것으로만 적는다
- **테마는 질의 문자열로 고른다.** `<img>` 로 박힌 SVG 에는 보는 쪽의 `prefers-color-scheme`
  이 닿지 않는다. GitHub 의 `<picture>` + `media` 방식을 쓸 수 있게 주소를 둘 준다
- **캐시가 이 기능의 전부다.** `max-age=600` + `stale-while-revalidate=1일` — 짧으면
  README 를 여는 사람 수만큼 우리 서버가 맞고, 길면 숫자가 며칠 전 것으로 남는다
- **없는 사람·탈퇴한 사람도 200 이다.** 깨진 이미지는 그 사람의 잘못이 아니라 우리 고장으로
  보인다. 둘을 **같은 그림**으로 주는 이유는 다르게 주면 "이 handle 은 있었다" 가 새기 때문이다
- **주소(IP)로 1분에 120회.** 로그인이 없으니 사람 기준으로 셀 수 없다. 첫 방어선은 캐시이고,
  여기까지 오는 것은 그것을 지나온 요청이다
- `X-Robots-Tag: noindex` + robots.txt 의 `/badge` (#278) — 그림이 검색에 뜰 이유가 없다

### 여러 파일을 완성하는 문제 (#457, API 쪽 #497)

문제가 **파일 목록**을 갖는다. 목록이 없으면 지금까지처럼 소스 하나짜리 문제다.

- **파일 목록은 런타임마다다.** 같은 문제라도 자바는 `Main.java`·`Helper.java`, 파이썬은
  `main.py`·`helper.py` 다. 그래서 문제 상세에서도 **`runtimes[].files`** 안에 온다 —
  문제 단위로 내리면 화면이 언어를 바꿀 때 무엇이 맞는 목록인지 알 수 없다
- **첫 파일이 진입점**이다. 순서가 화면의 탭 차례이기도 하다
- **`editable: false` 인 파일은 제출에 실리지 않는다.** 서버가 문제의 시작 코드를 그대로
  쓴다 — "이 인터페이스는 건드리지 말고 구현만 하라" 가 화면의 약속이 아니라 서버의
  규칙이 되게 한다. 실어 보내도 믿지 않는다
- 제출은 `files: [{name, sourceCode}]` 로 낸다. **빠진 파일**과 **목록에 없는 이름**은
  거부한다. 파일 목록이 없는 문제에 파일을 실어 보내는 것도 거부한다 — 조용히 버리면
  사용자는 자기가 쓴 것이 채점됐다고 믿는다
- 저장은 `submissions.source_files` **한 칸**이다. 제출은 많고 대부분 파일 하나인데
  표를 만들면 그 경우에도 조인이 는다. `source_code` 에는 진입점 파일이 함께 들어가
  제출 목록·상세처럼 소스를 하나로 보는 기존 경로가 그대로 돈다 — **진실은 파일 쪽**이다
- **실행(`/run`)은 아직 파일 하나다.** 화면이 파일 탭을 갖춘 뒤(#498)에 여는 것이 맞다

### 셸 문제 (#456)

`bash:5` 런타임이 있다. 시드에 전용 문제가 하나 있다 (`15-bash-log-levels`).

- **stdin/stdout 만이다.** 파일 시스템이 입력인 셸 문제는 채점 모델이 다르고, #453 이
  낸 길(끝난 뒤의 상태를 본다) 위에 얹는다
- **이미지는 `debian:13-slim`** — GNU coreutils·sed·grep 과 mawk 다. busybox 와 동작이
  달라서 **지문이 그것을 전제하게 되므로** 고르고 고정했다 (docs/06 §5.1)
- **그 언어로만 제출된다** (#419 의 허용 목록). 셸 문제를 파이썬으로 풀 수 있으면
  그 문제는 있을 이유가 없다 — 아희·엄랭(#420)과 같은 판단이다

### 스페셜 저지 (#452)

`outputComparison: CHECKER` 면 **출제자가 쓴 코드가 판정한다.**

정답이 여럿인 문제 — 조건을 만족하는 아무 배치, 임의 순서, "성질이 맞는가" — 는
기대값과 견줄 수가 없다. 그때는 견주는 대신 **물어본다.**

| 무엇 | 어떻게 |
|---|---|
| 언어 | **파이썬 하나로 고정.** 열면 실행기가 언어마다 채점 코드를 돌리는 법을 알아야 한다(#421 이 겪는 문제) |
| 받는 것 | `input.in` · `output.out`(제출한 출력) · `expected.out` — **파일로** 온다 |
| 돌려주는 것 | **종료 코드.** 0=맞음, 1=틀림 |
| 제한 | 5초 · 256MB — **문제의 제한과 별개다** |

- **표준 출력에 사유를 적게 하지 않는다.** 사유는 곧 **정답을 흘리는 경로**다 —
  "3번째 줄의 합이 12여야 하는데 11" 은 답의 일부다. 로그에만 남긴다
- **채점 코드가 죽으면 오답이 아니다.** 문법 오류·무한 루프·약속하지 않은 종료 코드는
  전부 `SYSTEM_ERROR` — **출제자의 실수를 사용자 기록에 남기지 않는다**(#60 과 같은 판단)
- **프로그램이 먼저 실패하면 묻지 않는다.** 죽은 프로그램의 출력을 채점 코드에 넘길
  이유가 없고, TLE 를 "틀렸다" 로 바꿀 이유도 없다
- **채점 코드는 사용자에게 내려가지 않는다.** 문제 상세에도 오류 메시지에도 없다
- **부분 점수는 열지 않는다.** 판정(#107)과 랭킹 점수(#57)가 "맞았다/틀렸다" 위에 선다
- **상호작용 문제는 아니다.** 왕복은 파이프를 양방향으로 열고 교착까지 다뤄야 하는
  훨씬 큰 일이다 — 여기서는 단방향(출력을 받아 판정)만 한다

### 잘못된 질의 인자 (#132)

`?sort=POPULAR` 처럼 enum 에 없는 값을 보내면 **400 과 함께 쓸 수 있는 값 목록**을 준다.

전에는 500 이었다. 값이 잘못된 것은 요청 잘못인데 500 을 주면 사용자에게는 우리 잘못으로
보이고, 로그에는 오류가 쌓이는데 고칠 것이 없다.

### 그룹 (#401, #240 6단계)

```
GET    /api/v1/groups                       내가 든 그룹
POST   /api/v1/groups                       만들기 — 로그인한 누구나
GET    /api/v1/groups/{id}                  상세 (멤버만)
PATCH  /api/v1/groups/{id}                  이름·소개·공개 가입 (방장)
DELETE /api/v1/groups/{id}                  해산 (방장)
POST   /api/v1/groups/{id}/invite           초대 링크 새로 뽑기 (방장)
GET    /api/v1/groups/invites/{token}       초대 미리보기 — 가입 전에 보여 준다
POST   /api/v1/groups/invites/{token}/join  초대로 들어가기
POST   /api/v1/groups/{id}/members          공개 가입 (방장이 켰을 때만)
DELETE /api/v1/groups/{id}/members/me       나가기
DELETE /api/v1/groups/{id}/members/{userId} 내보내기 (방장)
POST   /api/v1/groups/{id}/owner/{userId}   방장 넘기기
```

**소속(#397~#399)과 다른 표, 다른 화면이다** (기획서 2절). 소속은 어드민이 만들고 메일
도메인이 가입을 정하지만, 그룹은 누구나 만들고 사람이 사람을 부른다.

- **이름이 소속과 같아도 막지 않는다.** 막으려면 기관 이름 목록이 필요하고 그것은
  유지될 수 없다. 대신 **화면이 소속과 그룹을 절대 같은 목록에 섞지 않는다** — 사칭의
  피해는 섞여 보일 때 생긴다
- **초대 링크가 기본, 공개 가입은 방장이 켠다.** 처음부터 공개면 스팸 가입이 온다
- **초대 링크는 방장에게만 내려간다.** 멤버 아무나 부를 수 있으면 방장이 인원을 통제할
  길이 없고, 그러면 초대 링크가 사실상 공개 가입과 같아진다
- **인원 상한 200명.** 없으면 "전체 랭킹" 을 흉내 내는 그룹이 생긴다
- **명단은 멤버만 본다.** 이름과 인원은 초대 미리보기가 보여 준다 — 가입 전에 무엇에
  들어가는지 알아야 한다
- **방장은 넘기고 나간다.** 그냥 나가면 이름도 못 고치고 링크도 못 뽑는 그룹이 남는다
- 해산은 행을 지우지 않는다 (ADR-0007). 링크는 그 자리에서 죽는다
- **그룹끼리의 랭킹은 없다** (기획서 6절). 그룹은 인원을 스스로 정하므로 소속의 점수
  방식(상위 N명 합)이 작동하지 않는다

#### 어드민이 그룹을 내린다 (#438)

```
GET  /api/v1/admin/groups?q=&page=&size=   목록 (ADMIN)
POST /api/v1/admin/groups/{id}/takedown    해산 — **사유 필수** (ADMIN)
```

- **그룹은 누구나 만들고 이름도 아무거나 쓸 수 있다** (#401). 사칭을 구조적으로 막지
  않기로 했으므로 내리는 길이 있어야 한다 — 문제가 되는 그룹의 방장이 스스로 해산할
  이유는 없다
- **사유가 멤버 전원에게 간다.** 방장에게만 알리지 않는다 — 그룹은 방장의 것이 아니라
  그 안 사람들의 것이다. 말없이 사라지면 고칠 수도 없다(#208 이 문제집에서 정한 것)
- **지우지 않고 내린다** (ADR-0007). 그룹 랭킹(#402)이 그 id 를 가리키고, 초대 링크는
  이것으로 함께 죽는다
- **명단은 어드민에게도 보이지 않는다.** 내릴지 판단하는 데 필요한 것은 이름·방장·인원까지다
- 관리 기록에 남는다 (#225)

#### 그룹 안 랭킹 (#402, #240 7단계)

`GET /api/v1/groups/{id}/rankings?metric=&period=&page=&size=` — **멤버만**

- **소속 안 랭킹(#399)과 같은 구조다.** 모집단을 좁힐 뿐 정렬을 바꾸지 않으므로 등수는
  그 안에서 1위부터 다시 매겨진다. 지표·기간·동점 규칙은 전체 랭킹과 같다
- **다른 것은 누가 볼 수 있느냐다.** 소속 랭킹은 공개지만 그룹은 멤버만 본다 —
  **그룹의 명단이 곧 그 랭킹**이고, 명단은 그 안의 일이라고 #401 이 정했다
- 그래서 경로도 `/rankings?groupId=` 가 아니라 그룹 밑이다. **접근 규칙이 다른 것을
  같은 경로의 질의 인자로 두면 그 규칙이 잊힌다**
- 나가면 빠지고, 해산한 그룹의 순위는 404 다

### 랭킹 (#57, #85, #58)

`GET /api/v1/rankings?metric=&period=&page=&size=&affiliationId=` — 공개
`GET /api/v1/rankings/metrics` — 고를 수 있는 지표·기간. 공개

- **지표와 기간 목록을 서버가 알려준다.** 축이 늘어날 때 화면을 같이 고쳐야 하는 구조를
  만들지 않는다
- 실력 점수는 **가장 어려운 100문제만** 합산한다. 전부 더하면 쉬운 문제를 무한히 풀어
  순위를 올릴 수 있고, 그때 이 숫자는 실력이 아니라 누적 시간을 나타낸다
- 동점 처리 규칙이 순서를 끝까지 정하므로 **공동 순위가 생기지 않는다**
- 프로필의 숫자들은 **모두 같은 집합을 센다** (#269) — 푼 문제 수·난이도 분포·태그 분포·
  실력 점수가 전부 `published = true AND deleted_at IS NULL` 인 문제만 본다. 어드민이
  문제를 내리면 네 숫자가 함께 줄어든다. 하나만 다른 기준이면 같은 화면 안에서
  숫자가 어긋난다
- 프로필의 `skillTier` 는 **문제 난이도 티어와 다른 개념이다.** 화면은 "실력 티어"로
  표기해 `solvedByTier`(문제 난이도별 해결 수)와 구분한다

#### 소속 안 랭킹 (#399, #240 4단계)

`affiliationId` 를 주면 **그 소속에 붙은 사람들만** 순위표에 남는다.

- **모집단을 좁히는 것이지 정렬을 바꾸는 것이 아니다.** 등수는 그 안에서 1위부터 다시
  매겨지고, 지표·기간·동점 규칙은 전체 랭킹과 같다. "우리 학교에서 3등" 이 이 기능의
  이유이므로, 전체 등수를 그대로 들고 오면 뜻이 없다
- **없는 소속 id 는 400 이 아니라 빈 목록이다.** 소속 목록은 어드민만 본다(#397) —
  id 를 넣어 보고 존재를 알아내는 길을 열지 않는다
- 전체 랭킹처럼 **공개**다. 소속은 프로필에 이미 드러나는 것이라(#398) 로그인 여부로
  가릴 것이 없다. 다만 화면은 **내가 붙인 소속만** 고르게 한다 — 남의 소속을 뒤지는
  화면이 되지 않도록
- 소속을 떼면 그 랭킹에서 사라진다. "어제까지 1등이던 사람이 오늘 없다" 가 생기지만,
  **"지금 그곳 사람들의 순위" 라는 뜻은 유지된다**

#### 소속끼리 겨루는 랭킹 (#400, #240 5단계)

`GET /api/v1/rankings/affiliations?period=&page=&size=` — 공개

- **값은 상위 5명의 실력 점수 합**이다. 합이면 사람 많은 곳이 언제나 이기고, 평균이면
  **잘하는 사람만 남기고 내보내는 유인**이 생긴다 — 뒤엣것이 훨씬 나쁘다. 상위 N명 합은
  둘 다 피한다: 여섯 번째 사람이 들어와도 순위가 안 바뀌므로 끌어들일 이유도 내보낼
  이유도 없다
- **5명 미만인 소속은 순위표에 없다.** 한 명짜리 학교가 1등이면 그 순위표는 아무 말도
  하지 않는다. 최소 인원과 점수를 세는 인원은 **같은 값**이다 — 세는 인원이 더 크면
  인원이 곧 점수가 된다
- **지표를 고르지 않는다.** 푼 문제 수로 합하면 쉬운 문제를 많이 푼 곳이 이기는데,
  그것은 사람 랭킹에서 이미 걷어낸 것이다(#85)
- 동점이면 **먼저 등록된 소속이 위**다. 인원으로 가르면 "사람을 더 넣어라/덜어내라" 가 된다
- 탈퇴한 사람은 인원에서도 점수에서도 빠지고, 내려간 소속은 겨루지 않는다
- **그룹끼리의 랭킹은 없다** (기획서 6절). 그룹은 인원을 스스로 정하므로 같은 점수 방식이
  작동하지 않는다

#### 난이도가 바뀌면 점수도 바뀐다 (#194)

점수는 맞힌 시점이 아니라 **지금의 난이도**로 계산한다. 계산식은 처음부터 그랬지만
그 식을 다시 돌리는 경로가 제출과 어드민의 수동 재계산뿐이었다 — 난이도를 올리면
**그 뒤에 푼 사람만** 오른 점수를 받았다.

지금은 어드민이 문제를 저장·삭제하면 그 문제에 걸린 점수 행 전체가 같은 트랜잭션에서
다시 계산된다. 사람 수만큼 도는 것이 아니라 문장 세 개라, 수천 명이 푼 문제라도 저장
버튼이 느려지지 않는다.

| 상황 | 점수 | 최고 점수(`peakScore`) |
|---|---|---|
| 난이도 상승 | 오른다 | 따라 오른다 |
| 난이도 하락 | 내려간다 | **그대로 둔다** — 강등을 만들지 않는다 (#58) |
| 비공개로 전환·삭제 | 빠진다 | 그대로 |
| 다시 공개 | 돌아온다. **처음 맞힌 시각도 그대로다** | 그대로 |

뱃지는 건드리지 않는다. 지금 뱃지 조건(첫 정답·최초 해결·카테고리 개수·연속일)에
**난이도가 들어가는 것이 하나도 없어서** 따라 움직일 것이 없다. 조건에 난이도를 넣게
되면 그때 "이미 준 뱃지를 회수할 것인가" 를 함께 정해야 한다 (#107).

### 대회 (#61)

`GET /api/v1/contests` — 목록. 공개. **준비 중(DRAFT)인 대회는 나오지 않는다**
`GET /api/v1/contests/{slug}` — 상세. 공개하되 **로그인 여부에 따라 내용이 다르다**
`POST /api/v1/contests/{slug}/registrations` — 참가 등록. 두 번 눌러도 오류가 아니다

- **진행 단계(SCHEDULED/RUNNING/ENDED)는 저장하지 않는다.** 시작·종료 시각과 지금을 견줘
  조회 시점에 판정한다. 스케줄러가 상태를 옮기는 방식이면 스케줄러가 1분 늦는 순간
  대회가 1분 늦게 시작한다 — **지연이 곧 사고가 된다**
- 저장하는 `status` 는 **사람이 정하는 것**뿐이다 (DRAFT/PUBLISHED/CANCELED/ARCHIVED)
- 문제는 **시작 전에는 참가자에게도 보이지 않는다.** 진행 중에는 참가자만, 종료 후에는 누구나
- 준비 중인 대회는 존재 여부조차 알리지 않는다 (404)

`POST /api/v1/contests/{contestSlug}/problems/{problemSlug}/submissions` — 대회 제출 (#62)

- **평소 제출과 경로를 나눈다.** 같은 경로에 대회 여부를 실어 보내면, 대회가 아닌 척
  제출해 평소 큐로 보내는 길이 생긴다
- 대회 제출은 `codekr:judge:contest` 로 가고 **전용 워커만** 그것을 읽는다
- 마감 판정은 **요청이 도착한 순간**의 시각으로 한다. 뒤의 검증에 걸리는 시간을 넣지 않는다
- 같은 참가자·같은 문제는 **20초에 한 번**. 문제마다 따로 센다

`GET /api/v1/contests/{slug}/scoreboard?actual=` — 순위표 (#63). 공개다 — 관전자도 본다

- **어드민의 "실제 순위 보기" 는 같은 경로에 인자 하나다.** 화면을 둘로 나누면 어느 쪽을
  보고 있는지 헷갈려 잘못된 판단을 한다 (#86)
- 권한이 없는데 `actual=true` 를 보내면 **참가자와 같은 것**을 준다. 거절하지 않는다 —
  거절하면 화면이 권한을 미리 알아야 한다
- 동결 중에는 결과만 감춘다. **시도했다는 사실은 감추지 않는다** (`pending`)
- 참가자용 응답은 10초 캐시한다. 대회 중 가장 많이 호출되는 화면이다.
  **어드민 응답은 캐시하지 않는다** — 운영 판단에 쓰는 숫자가 몇 초 늦으면 안 된다
- 동점 처리: 총점 → 마지막 득점 시각 → 등록 시각 → 사용자 ID

어드민: `/api/v1/admin/contests/**` — **`CONTEST_MANAGER` 이상.** 자원 범위(어느 대회의
관리자인가)는 아직 없다. 전역 역할만 본다.

- 문제 배정은 **전체 치환**이다. 부분 수정은 순번이 꼬인다
- 배정된 문제가 없으면 공개할 수 없다 — 참가자가 등록한 뒤 시작 시각에 아무것도 못 본다
- **최종 순위 공개(`/unfreeze`)는 자동이 아니다.** 종료 직후 발견된 문제를 바로잡을 틈이 필요하다
- 문제 제외는 배정을 **지우지 않는다.** 그 문제로 낸 제출이 남아 있다

> 널 허용 `AuthPrincipal?` 파라미터는 **비로그인도 허용**한다. 공개 화면인데 로그인 여부에
> 따라 내용이 달라지는 경우에 쓴다 — 대회 상세가 그렇다.

### 알림 (#106, #135)

`GET /api/v1/notifications?category=&unreadOnly=&page=&size=`
`GET /api/v1/notifications/unread-count` — 총합과 **카테고리별** 미읽음 수
`POST /api/v1/notifications/read-all?category=`

- `category` 를 비우면 **전체 탭**이다. 전체가 첫 번째이고 기본값이다
- `category` 와 `unreadOnly` 를 함께 걸면 **교집합**이다 — 그 탭에서 안 읽은 것
- **"모두 읽음" 은 보고 있는 탭만 읽는다.** 채점 탭에서 눌렀는데 대회 알림까지
  읽음이 되면 보지 않은 것을 읽은 것으로 만든 셈이고, 되돌릴 수 없다.
  전체 탭에서만 전부 읽는다
- 탭 목록은 **설정 응답의 카테고리 옵션**에서 만든다. 화면이 하드코딩하지 않는다
- 카테고리별 미읽음 수는 **없는 카테고리도 0 으로 채워** 내린다. 화면이 빈 값을 다루지 않게

### 비밀번호 재설정 (#315)

`POST /api/v1/auth/password/reset-requests` · `POST /api/v1/auth/password/reset` — **둘 다 공개.**

비밀번호를 잊으면 계정을 잃는 것과 같았다. 푼 문제·점수·티어(#58)·뱃지가 되돌릴 수
없이 사라진다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 없는 주소로 요청하면 | **같은 답(202)** | 다르게 답하면 **어느 주소가 가입되어 있는지 확인하는 도구**가 된다. 화면 문구는 "가입된 주소라면 보냈다" 여야 거짓말이 아니다 |
| 인증하지 않은 주소 | **보내지 않는다** | 남의 주소를 적고 가입한 계정의 비밀번호를 그 주소 주인이 가져가는 길이 된다 (#233 이 선행인 진짜 이유) |
| 만료 | **30분** (인증 메일은 24시간) | 이 링크는 로그인 수단 자체를 갈아 끼운다. 늦으면 다시 요청하면 된다 |
| 성공하면 | **기존 세션을 끊는다** | 비밀번호를 바꾸는 흔한 이유가 "남이 들어와 있는 것 같아서" 다 |
| 끊는 방법 | 액세스는 **Redis 표시**, 갱신은 **`password_changed_at` 비교** | 표시는 액세스 수명만큼만 살아서 그것만으로는 갱신 토큰이 새 토큰을 계속 받아 간다 |
| 알림 | **메일 + 웹 알림**(#106) | 본인이 안 했다면 알아야 할 일이다. 메일함이 털린 경우에는 메일이 닿지 않는다 |
| 비밀번호 규칙 | 가입과 **같은** 8~64자 | 한쪽만 고치면 재설정으로 규칙을 우회할 수 있다 |

`RevokedTokenRegistry` 는 원래 탈퇴 전용(#140)이었는데 여기서 함께 쓴다 — 이름이 한
쓰임에 묶여 있으면 두 번째 쓰임이 자기 것을 새로 만든다.

### @멘션 (#214)

`GET /api/v1/users/mention-candidates?q=` (로그인 필요)

**본문에는 사용자 id 를 저장한다** — `@{u:42}`. `@닉네임` 을 글자 그대로 저장하지 않는다.

| 문제 | 왜 풀리는가 |
|---|---|
| 닉네임 경계 (`@김 철수`) | 저장된 것이 이름이 아니다. **본문에서 이름을 잘라 낼 일이 없다** |
| 닉네임 변경 | id 가 가리키는 사람은 그대로다. 표시만 새 이름이 된다 |
| 탈퇴 (#140) | 다른 곳과 같은 규칙으로 다룬다 |

중괄호를 쓰는 이유: 본문이 마크다운인데 **대괄호는 링크 문법과 겹친다.**

| 판단 | 결정 | 왜 |
|---|---|---|
| 손으로 친 `@이름` | **멘션이 아니다** | 서버가 이름으로 찾아 바꾸면 동명이인·닉네임 변경에서 엉뚱한 사람을 가리킨다 |
| 코드 블록 안 | 멘션이 되지 않는다 | 코드 블록은 블록 단계에서 통째로 처리돼 인라인 렌더러까지 오지 않는다 |
| 색 | 브랜드색 + **`@` 를 남긴다** | 색만으로 구분하지 않는다는 규칙이 이 저장소에 있다 |
| 이름표 | **본문과 함께 내린다** | 화면이 id 로 다시 조회하면 댓글 수만큼 요청이 나간다 |
| 자기 자신 | 알리지 않는다 | |
| 같은 사람 여러 번 | 알림은 한 번 | |
| 수정으로 새로 부르면 | **새로 불린 사람에게만** | 이미 불린 사람에게 다시 보내면 오타를 고칠 때마다 알림이 간다 |
| 상한 | **한 댓글에 5명** | 알림을 끌 수 없으므로(#199) 부르면 반드시 간다 |
| 게시글 본문 | 아직 안 한다 | 댓글에서 먼저 써 보고 정한다 |

### 뱃지 규칙 엔진 (#202)

조건이 `BadgeAwarder.kt` 의 SQL 에 박혀 있었다. 이제 `badge_rules` 에 한 줄을 넣으면
**코드 변경 없이** 새 뱃지가 지급된다 (설계는 #200).

| 판단 | 결정 | 왜 |
|---|---|---|
| 동기·비동기 | **부르는 트랜잭션에 함께 든다** | 기획은 "밖으로 빼는 쪽" 이었는데, 빼 보니 **지표가 방금 쓴 점수를 보지 못한다** — 아직 커밋되지 않은 바깥 트랜잭션 안에 있다. 통합 시험이 잡았다 |
| 실패 | **밖으로 내보내지 않는다** | 뱃지는 곁가지다. 여기서 잡으므로 트랜잭션이 롤백으로 표시되지 않는다 |
| 비용 | 이미 가진 뱃지는 **지표를 계산하기 전에** 건너뛴다 | 정답을 100번 맞힌 사람에게 `FIRST_ACCEPT` 조건을 100번 확인할 이유가 없다 |
| 지표 캐시 | 이벤트 안에서 한 번 | `STREAK_7`·`STREAK_30` 이 함께 걸려도 스트릭을 두 번 읽지 않는다 |
| 깨진 규칙 | **아무에게도 주지 않는다** | 잘못 주는 것보다 낫다. 특히 `all` 이 배열이 아닌 것을 그냥 넘기면 **"언제나 준다" 로 읽힌다** — 빈 조건에 뜻이 있기 때문이다 |
| 기록 | 준 것과 **안 준 것**을 함께 | 안 주면 "왜 안 나왔는지" 를 물었을 때 답할 수 없다 |
| 소급 | 하지 않는다 | 한 번에 수만 건의 뱃지와 알림이 생긴다 (#106). 필요하면 재계산(#177)이 그 자리다 |

### 뱃지 규칙 편집기 (#203)

`GET /api/v1/admin/badge-rules/vocabulary` · `POST .../dry-run` · CRUD — **`SUPERUSER` 만.**

| 판단 | 결정 | 왜 |
|---|---|---|
| 편집기 형태 | **폼 기반** (①) | #200 이 언어를 `지표 op 값` 으로 좁혀서 폼으로 다 담긴다. 텍스트 편집기를 함께 두면 두 벌을 유지하게 된다 |
| 목록 | **서버가 내려준다**(`vocabulary`) | 이벤트가 늘 때마다 화면을 고치는 구조를 만들지 않는다 |
| 지표 고르기 | **그 이벤트에서 쓸 수 있는 것만** | `is_first_solver` 를 `STREAK_UPDATED` 에 걸면 언제나 거짓이 된다 |
| 검증 | **틀린 자리를 짚는다** | "잘못된 규칙입니다" 로는 고칠 수 없다 |
| 드라이런 | **표본 200명** | 전체를 훑으면 운영 DB 가 느려진다. 목적은 "정확히 몇 명" 이 아니라 "말이 되는 규칙인가" 다 |
| 권한 | `SUPERUSER` | 뱃지는 모두에게 보이는 것이라 아무 어드민이나 바꾸면 안 된다 |
| 끄기 | 있음, 삭제는 없음 | 지우는 것보다 끄는 것이 먼저다 |

### 뱃지 정의를 데이터로 (#201)

`GET /api/v1/badges`(공개) · `GET|POST|PUT /api/v1/admin/badges`

이름·설명이 `Badge.kt` 에 있었다 — **오타 하나를 고치려고 배포했다.** 뱃지는 운영이
손대는 물건인데 손댈 방법이 배포뿐이었다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 코드 | **만들 때만 정하고 잠근다** | `user_badges` 에 박히는 값이라 한 번 준 뒤에 바꾸면 가리키는 대상이 달라진다 |
| 삭제 | **길을 두지 않는다** | 이미 받은 사람이 있다. 대신 `visible` 을 끈다 — 다시 켜면 돌아온다 |
| 문구 변경 | **이미 받은 사람에게도 바뀐다** | 받은 시점의 사본을 두면 원래 구조("코드만 저장")로 돌아간다. 받아들이고 화면이 경고한다 |
| 모르는 코드 | 코드를 그대로 이름으로 | 정의가 지워졌거나 옛 코드의 뱃지를 가진 사람이 있다 — 프로필이 깨지면 안 된다 |
| 정렬 | **정의가 정한다** | 받은 순서대로면 사람마다 목록이 달라진다 |
| 카테고리 뱃지 | 정의를 **일곱 줄로 펴 둔다** | 그래야 "SQL 문제 10개" 의 문구만 따로 고칠 수 있다. 규칙 키는 하나(`CATEGORY_10`)다 |
| 캐시 | 한다, 고칠 때 비운다 | 프로필마다 읽히는데 바뀌는 일은 드물다 |
| 아이콘 | 넣지 않는다 | 이미지 업로드(#115)를 얹기 전에 문구부터 |

`rule_key` 는 지금 **코드 규칙의 이름**이다. #200 의 DSL 이 오면 이 자리가 규칙으로
대체된다 — 그때 갈아 끼울 수 있게 문자열로 뒀다.

### 대회 관리 (#335)

`GET|POST /api/v1/admin/contests` · `PUT /{id}` · `PUT /{id}/status` ·
`POST /{id}/unfreeze` · `PUT /{id}/problems/{problemId}/exclusion` — **`CONTEST_MANAGER`.**

API 는 처음부터 있었는데 **명세에도 화면에도 없어서** `CONTEST_MANAGER` 가 할 일이
없었다. "만들어 두고 아무도 모르는" 상태였다.

**진행 중인 대회는 고칠 수 없다** (#335). 대회 중에 시작 시각이나 문제 목록이 바뀌면
**이미 제출한 사람과 아닌 사람이 다른 대회를 본 것**이 된다.

- **서버가 막는다** (`AdminContestService.update`) — 화면만 막으면 API 는 열려 있다
- 막히는 것은 **수정**이지 운영이 아니다. 공지·질의 답변(#147)과 순위 공개(#86)는
  다른 경로라 대회 중에도 그대로 된다 — 함께 막으면 대회를 운영할 수 없다
- 준비 중·시작 전·끝난 대회는 그대로 고쳐진다

### 게시판 관리 (#336)

`GET /api/v1/admin/board/posts` · `.../comments` · `DELETE` — **`BOARD_MANAGER`.**

**"지울 수 있다" 와 "지울 것을 찾을 수 있다" 는 다르다.** `BOARD_MANAGER` 는 남의 글을
지울 수 있었지만, 지울 대상을 찾으려면 **그 글을 우연히 보고 있어야** 했다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 목록 | **게시판 구분 없이 최근 순** | 게시판이 셋이고 문제별 질문(#139)이 또 있다. 나눠 두면 "최근에 올라온 것" 을 볼 수 없다 |
| 댓글 | **따로 목록을 둔다** | 글 안에 숨어 있으면 어디에 무엇이 달렸는지 알 방법이 없다 |
| 문제별 질문 | **같은 목록에** | `posts` 에 함께 있다. 화면은 글/댓글만 탭으로 나눈다 |
| 삭제 | **기존 권한 판정을 그대로 쓴다** | `PostService`·`CommentService` 에 이미 있다 — 여기서 다시 적으면 두 곳이 갈린다 |
| 소프트 삭제 | 그대로 (ADR-0007) | 지워도 스레드가 무너지지 않는다. 정말 지워야 하는 내용은 별도 절차가 필요하다 |
| 기록 | **사유 필수** (#225) | 남의 글을 지우는 일이고, 지운 뒤에는 무엇이었는지 알 길이 없다 |
| 대회 질의(#147) | 여기 없다 | 대회 운영의 일부라 #335 쪽이다 |

### 공개 문제집 (#208)

`GET /api/v1/collections`(공개 목록) · `POST /api/v1/admin/collections/{id}/takedown`

문제집(#87)은 **일부러 공개를 열지 않았다** — "스팸·중복·방치가 즉시 생기는데 신고도
정리도 할 수 없다" 는 근거였다. **그 판단을 뒤집는다.** 링크 공유만으로는 아무도 새
문제집을 발견할 수 없고, 그러면 문제집을 만드는 이유의 절반이 닿을 길이 없다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 정렬 | **최신순** | 인기순은 담은 사람 수나 조회수가 필요한데 둘 다 없다. 대신 **어드민이 내리는 속도가 곧 목록의 품질**이 된다 |
| 내리기 | **비공개로 되돌린다** (①) | 남이 만든 것을 지우는 것과 목록에서 빼는 것은 다르다. 되돌릴 수 있다 |
| 내린 사실 | **주인에게 알린다** (사유 포함) | 말없이 사라지면 고칠 수도 없다 |
| 미공개 문제 | **공개 전환을 막는다** (②) | 감추면 "5문제" 인데 3개만 보이고 주인은 이유를 모른다 |
| `UNLISTED` | 남긴다 | 링크 공유는 "아직 다듬는 중" 에 쓰임이 있다 |
| 문제 2개 규칙 | **공개에도 그대로** | 공유의 규칙이므로 `PUBLIC` 도 같다 |

프로필 응답(`GET /api/v1/users/{nickname}`)에 **그 사람의 공개 문제집**이 함께 온다
(#209). 프로필은 사람으로부터 문제집에 닿는 유일한 길이다 — 목록에서 좋은 문제집을
봤을 때 "이 사람이 만든 다른 것" 을 찾을 방법이 그것뿐이다.

**내 프로필에서도 공개된 것만 보인다.** 비공개까지 보이면 `/collections`(내 문제집)와
겹치고, 남에게 보이는 화면과 내가 보는 화면이 달라진다.

### 문제의 출제자·검수자·출처 (#236)

문제가 어디서 왔고 누가 만들었는지 남지 않았다. **출처를 적을 칸이 없으니 적을 수 없고,
적을 수 없으니 안 적는 것이 기본**이었다 — AI 로 지문을 붙여 넣는 도구(#230)가 오면
더 커질 문제다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 인원 | **처음부터 다대다** (`problem_credits`) | 문제 하나를 둘이 만드는 일은 흔하고 검수는 더 그렇다. 한 명으로 시작하면 늘리는 마이그레이션이 또 필요하다 |
| 출처 | **라벨 + 링크** (컬럼 두 개) | 사람이 아니라 바깥의 무언가다. 링크만 있으면 무엇인지 모르고, 라벨만 있으면 확인할 수 없다 |
| 출처 필수 여부 | **선택** | 필수로 두면 자체 제작 문제에 "자체 제작" 을 매번 적게 된다 |
| 지정 방법 | **닉네임으로 찾아 고른다** | id 를 손으로 치게 하지 않는다 (#223 이 같은 문제를 겪었다). 찾는 경로는 멘션(#214)과 같은 것을 쓴다 |
| 저장 | **통째로 갈아 끼운다** | 더하기·빼기를 따로 두면 화면이 차이를 계산해야 하고, 그 계산이 어긋나면 지운 사람이 남는다 |
| 탈퇴한 사람 | "탈퇴한 사용자" (#140) | 만든 사실 자체는 남는 것이라 이름만 가린다 |
| 검수 자동 기록 | **하지 않는다** | 정답 코드 검증(#39)은 기계가 도는 것이고, 사람이 읽어 본 것은 별개다 |

출처 링크는 **바깥으로 나간다** — `target="_blank"` + `rel="noreferrer noopener nofollow"`.

### 댓글 트리는 잘라서 내린다 (#213)

`GET /api/v1/posts/{id}/comments?after=&around=` · `GET /api/v1/comments/{id}/children?after=`

전에는 글의 댓글을 **전부** 내렸다. 깊이 제한이 없는 구조(#138)에서 그것은 **두 사람이
주고받은 스레드 하나가 다른 사람들의 댓글을 화면 밖으로 밀어내는** 결과가 된다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 자르는 기준 | **깊이와 개수 둘 다** | 깊이만 보면 넓고 얕은 스레드(한 댓글에 답글 50개)가 안 잡히고, 개수만 보면 깊게 파고든 2인 대화가 안 잡힌다 |
| 이어받기 | **커서**(마지막으로 받은 id) | 오프셋은 읽는 사이에 새 댓글이 달릴 때 **이미 본 것을 다시 주거나 건너뛴다.** 트리에서는 같은 댓글이 두 번 그려지는 쪽이 더 나쁘다 |
| 자르는 단위 | **부모 기준** | 부모를 자르면 자식도 함께 빠진다 — 자식만 남고 부모가 없는 응답이 나오지 않는다 |
| 남은 개수 | 자리마다 함께 내린다 | 없으면 화면이 "더 있는지" 를 알 수 없고, 펼칠 이유도 모른다 |
| 전체 수 | **서버가 센다** | 화면이 받은 트리를 세던 방식은 잘라 내리기 시작하면 곧바로 틀린다 |
| 지목한 댓글 | `around` 로 조상을 편다 | 알림·링크로 들어온 자리가 접혀 있으면 안 된다 (#212) |

한 번에 내리는 수: 최상위 20 · 한 부모의 답글 3 · 깊이 3부터 접는다.

**"한 번의 조회로 트리를 만든다"(#138)는 그대로다.** 한 번에 읽는 범위가 좁아질 뿐,
부모마다 질의하는 구조로 돌아가지 않는다 — 자르는 판단은 메모리에서 한다.

화면은 받은 것을 **겹치지 않게 잇는다**(`mergeComments`) — 쓰기·삭제 응답은 앞쪽부터
다시 오므로, 이미 펼쳐 둔 자리를 잃지 않으면서 바뀐 것만 갈아 끼운다.

### 약관 동의와 개정 (#235)

`GET /api/v1/terms`(공개) · `GET /api/v1/terms/{id}`(전문, 공개) ·
`GET /api/v1/terms/pending` · `GET|POST /api/v1/terms/agreements`

**동의한 사실이 남지 않으면 동의를 받은 것이 아니다.** "언제, 어느 버전에" 가 없으면
나중에 확인할 수 없다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 버전 | **데이터로 둔다** (`term_documents`) | 파일로만 두면 개정 이력이 git 에만 남고 **누가 어느 판에 동의했는지** 알 수 없다 |
| 동의 | **판(version)에 붙인다** | 종류에만 붙이면 개정 뒤에 무엇에 동의했는지 사라진다 |
| 가입 | **필수를 다 받지 못하면 가입되지 않는다** | 동의 없이 만들어진 계정은 "받았다" 고 말할 근거가 없다 |
| 전체 동의 버튼 | 있어도 **개별 id 를 올린다** | "전체 동의" 라는 사실만 남기면 무엇에 동의했는지 말할 수 없다 |
| 시행일 | 미래면 아직 없는 것으로 본다 | 개정을 미리 넣어 두고 날짜에 맞춰 켠다 |
| 개정 | **막지 않고 배너로 알린다** (②) | 오타를 고친 개정에도 모두를 멈추면 개정 자체를 안 하게 된다 |
| 다시 받을 대상 | `reconsent` 를 켠 판만 | 중요한 개정과 사소한 개정을 나눈다 — 그 판단은 사람이 한다 |
| 선택 항목 | 두지 않는다 | 마케팅 수신처럼 보낼 것이 아직 없다 (#233) |
| 미성년자·연령 확인 | **다루지 않는다** | 범위를 넓히면 끝이 없다 — 다루지 않았다는 사실을 여기 남긴다 |
| 탈퇴 | 동의 기록은 **남는다** | 개인정보는 지우되(#140) "동의를 받았다" 는 사실은 남아야 한다. 기록에는 사용자 id 만 있고 이름·메일은 그때 지워진다 |

문안은 최소 초안이다 — **빈 약관으로 동의를 받는 것은 무의미하므로** 코드가 이미 정해
둔 것들(탈퇴 시 삭제 #140, 제출 코드 공개 범위 #33, 보관 기간 ADR-0007)을 적었다.
법적 효력이 있는 문안을 다듬는 것은 별개의 일이다.

### 이메일 인증 (#233)

`POST /api/v1/auth/email/verify`(공개) · `POST /api/v1/auth/email/verification`(재발송)

가입할 때 이메일을 받지만 **그 주소가 진짜인지 확인하지 않았다.** 비밀번호를 잃으면
계정을 잃는 것과 같고(#315), 소속 인증(#240)은 도메인 확인에 기대는데 확인되지 않은
주소로는 뜻이 없다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 발송 경로 | **발송 서비스의 SMTP** | 직접 MTA 를 운영하면 스팸 처리·바운스·평판을 통째로 떠안는다(#106 이 피한 것). SMTP 로 붙으면 벤더 SDK 도 늘지 않는다 |
| 설정이 없으면 | **보내지 않고 로그에 찍는다** | 저장소(#115)와 같은 규칙이다. 로컬에서 메일 서버 없이 전체가 돌아야 한다 |
| 토큰 | 32바이트 난수, **표에는 SHA-256 해시만** | 표를 읽을 수 있는 사람이 남의 계정을 인증할 수 있으면 안 된다 |
| 수명 | 24시간, **한 번만** | 길게 두면 새어 나간 링크가 오래 산다 |
| 확인 API | **공개** | 메일을 받은 기기와 로그인한 기기가 다를 수 있다. 토큰이 본인 확인 수단이다 |
| 두 번 누르면 | **조용히 성공** | 사용자가 링크를 두 번 누른 것뿐이다 |
| 안 한 계정 | **쓰기만 막는다** | 로그인을 막으면 재발송을 누를 화면조차 못 연다. 제출은 주소 확인과 상관이 없다 |
| 보낼 수 없으면 | **요구하지도 않는다** | 요구만 하고 못 보내면 아무도 인증할 수 없는 계정이 생긴다 |
| 기존 계정 | **인증된 것으로 본다** | 전부 미인증으로 두면 켜는 순간 지금 쓰는 사람들이 다 막힌다 |
| 재발송 | 60초 쿨다운 · 하루 5통 | 발송량이 곧 비용이고 평판이다 |
| 발송 실패 | **가입은 성공한다** | 메일 때문에 가입이 실패하면 안 된다 — 실패는 로그로 간다 |

무엇이 "쓰기" 인지는 회원 정지(#224)의 `SuspendedAction` 이 이미 정해 두었다.
같은 판정을 두 번 적으면 언젠가 갈린다.

### 부르는 이름과 가리키는 주소를 나눈다 (#307)

`GET /api/v1/users/{handle}` · `PATCH /api/v1/users/me/profile` (`displayName`)

이름 하나가 **표시 이름이자 주소**였다. 그래서 이름을 바꾸면 주고받은 링크와 검색
색인(#278)이 끊기고, 끊기지 않게 하려니 **이름을 아예 바꿀 수 없었다.**
#204 가 문제에서 같은 것을 나눴다 — 가리키는 것은 번호, 부르는 것은 제목.

| 판단 | 결정 | 왜 |
|---|---|---|
| `handle` | **바뀌지 않는다** | 바꿀 수 있게 두면 "바뀌지 않는다" 가 규칙이 아니라 약속이 되고, 약속은 깨진다 |
| 규칙 | 소문자·숫자·하이픈 2~30자 (`Handles`) | 대문자를 허용하면 `Kim` 과 `kim` 이 다른 주소가 된다. **가입과 백필이 같은 규칙을 쓴다** |
| 가입 | **비우면 이름에서 만든다** | 두 칸을 받으면 처음 오는 사람에게 설명할 것이 는다. 직접 정하고 싶은 사람만 적는다 |
| 한글 이름 | 임의값을 준다 | 한글은 그대로 주소가 될 수 없다 |
| 충돌 | **그렇게 알린다** (400) | 유니크 제약 위반을 그대로 흘리면 500 이 된다 |
| 옛 주소 | **닉네임으로도 한 번 더 찾는다** | 링크를 이미 주고받은 사람에게 404 보다 낫다. 다만 이름은 바뀌므로 그 길은 언젠가 끊긴다 |
| 아바타 색 | **handle 에서 뽑는다** | 이름이 바뀔 때마다 색이 바뀌면 목록에서 사람을 구분하는 단서가 사라진다 |
| 순위표 "내 줄" | handle 로 찾는다 | 대회 중에 이름을 바꾸면 자기 줄을 잃는다 |
| 탈퇴 | **handle 도 지운다** (`withdrawn-{id}`) | 사람이 정하는 값이라 실명이 들어 있을 수 있다 (#140) |
| 컬럼 이름 | `nickname` 그대로 | 이름 바꾸기는 **롤백이 안 되는 변경**이다(#266 과 같은 이유) — 값의 뜻은 이미 갈렸고, 물리 이름은 다음 정리에서 바꾼다 |

### 소속과 도메인 관리 (#397, #240 2단계)

`GET|POST /api/v1/admin/affiliations` · `DELETE .../{id}` ·
`POST|DELETE .../{id}/domains[/{domainId}]` — **`ADMIN`.**

**목록이 있어야 인증이 붙는다.** 사용자가 학교 메일을 확인하면(#396) 그 도메인이
어느 소속인지 여기서 찾는다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 누가 만드나 | **어드민만** | 자동이면 `@gmail.com` 이 "지메일 대학" 이 되고 오타 도메인이 쌓인다 |
| 도메인 | **소문자로 저장하고 `@` 를 걷어 낸다** | 사람은 `@snu.ac.kr` 이라고 적는다. 그대로 두면 **메일 주소의 도메인과 영영 안 맞고**, 인증이 조용히 실패한다 |
| 검사 | **완벽하게 하지 않는다** | 도메인 규칙을 정규식으로 다 적으면 맞는 것을 막는 날이 온다. 막는 것은 사람이 흔히 하는 실수(`@`, 메일 주소 전체, 점 없음)뿐이다 |
| 한 도메인 | **한 소속에만** | 둘에 붙으면 같은 메일로 두 소속을 얻는다 |
| 소속 삭제 | **소프트 삭제, 도메인은 함께 뗀다** | 이미 붙은 사람들이 있어 행을 지울 수 없다(ADR-0007). 다만 도메인을 남기면 **내린 소속에 새 사람이 계속 붙는다** |
| 기록 | 남긴다 (#225) | **잘못 넣으면 그 도메인을 가진 모두가 그 소속을 얻는다** |

### 확인한 메일 주소 여러 개 (#396, #240 1단계)

`GET|POST /api/v1/users/me/emails` · `DELETE /api/v1/users/me/emails/{id}`

**소속 인증(#240)이 여기에 통째로 기댄다.** 학교·회사 메일을 확인해야 소속이 붙는데,
로그인 주소를 그것으로 바꾸게 하면 **졸업하는 순간 로그인을 잃는다.**

| 판단 | 결정 | 왜 |
|---|---|---|
| 토큰 장치 | **#233 의 것을 그대로 쓴다** | 해시 저장·만료·쿨다운·하루 상한이 이미 있다. 갈라 두면 한쪽만 고쳐지는 날이 온다 |
| 어느 주소인지 | `email_verifications.email` — **비우면 로그인 주소** | 가입 때 보내는 그것과 같은 흐름이다 |
| 확인 전 | **표에 행이 없다** | 그래서 `user_emails` 의 존재 자체가 "확인됨" 을 뜻한다 |
| 추가 주소를 확인하면 | 로그인 주소의 확인 여부는 **그대로** | 학교 메일을 확인했다고 가입 주소가 확인된 것은 아니다 |
| 이미 쓰는 주소 | **409** | 같은 학교 메일로 두 계정이 같은 소속을 얻으면 안 된다. **남의 로그인 주소도 본다** — 내 추가 주소로 확인해 버리면 그 사람의 소속을 가져가는 셈이다 |
| 확인 직전에 남이 먼저 | 그때도 **409** | 메일을 보낸 뒤 누르기까지 사이가 있다 |
| 탈퇴 | **함께 지운다** (#140) | 학교·회사 메일이라 실명이 든 경우가 많다 |

#### 쿨다운을 주소별로 잰다

시험이 잡은 것이다. 쿨다운이 막으려는 것은 **"같은 주소로 계속 보내기"** 인데 사람
단위로 재면 **다른 주소를 더하는 것까지 막힌다** — 학교 메일과 회사 메일을 이어서
넣을 수 없다.

하루 상한은 그대로 **사람 단위**다. 그쪽이 막으려는 것은 발송량이고, 그것은 주소를
바꾼다고 줄지 않는다.

### 글에 붙는 이미지 (#389)

`POST /api/v1/attachments` (multipart, 로그인·주소 확인 필요) → `{ url }`

"이 코드가 왜 틀렸나요" 는 코드 블록으로 되지만 **오류 화면·그림·표는 안 됐다.**
그래서 남의 이미지 호스팅에 올리고 링크를 붙이는 수밖에 없었고, **그 링크는 언젠가 깨진다.**

올릴 곳은 이미 있었다 — #115 의 오브젝트 스토리지, 그리고 **쓰는 곳이 없던**
`ImagePolicy.ATTACHMENT`(1600px·JPEG).

| 판단 | 결정 | 왜 |
|---|---|---|
| 누가 올리나 | 로그인 + **주소 확인**(#233) | 경로를 따로 적지 않아도 그렇게 된다 — `SuspendedAction` 이 안 적힌 쓰기를 전부 `WRITE` 로 보고(#224) 인증 판정이 같은 것을 쓴다. **빠뜨릴 수 없는 구조**다 |
| 한 장 크기 | `ImageLimits` 그대로 (5MB·4천만 픽셀) | 다시 인코딩하는 과정이 곧 검증이다 |
| **한 글에 몇 장** | **10장** | 크기 제한만으로는 안 막힌다 — 5MB 짜리 백 장은 같은 결과다 |
| 하루에 몇 장 | 50장 | **로그인만 하면 누구나 파일을 올릴 수 있는 경로**다 |
| 어디서 세나 | 글 저장할 때 **서버가** | 올리는 시점에는 어느 글에 붙을지 모른다. 화면이 세면 화면을 안 거친 요청에는 제한이 없다 |
| 어떤 이미지를 그리나 | **우리 저장소의 것만** | 남의 주소는 추적 픽셀과 혼합 콘텐츠를 들여온다. 아닌 것은 **링크로** 남긴다 — 주소를 지우면 무엇을 가리켰는지조차 알 수 없다 |
| 주인 없는 파일 | **이레 뒤 정리 배치** | 본문 파싱은 마크다운 규칙이 바뀔 때마다 함께 바뀌어야 하고, **틀리면 쓰고 있는 이미지를 지운다** |

정리 배치는 키가 본문에 **글자로** 들어 있는지만 본다 — 규칙이 바뀌어도 **안 지우는
쪽으로** 틀린다. 그리고 파일을 먼저 지우고 행을 지운다: 반대로 하면 행이 사라진 뒤
삭제가 실패했을 때 그 파일을 다시 찾을 길이 없다.

### 채점 파이프라인 조정 (#40, #390)

`GET /api/v1/admin/workloads` ·
`POST /api/v1/admin/workloads/{key}/scale` (파드 수) ·
`POST /api/v1/admin/workloads/{key}/workers` (워커 수) — **전부 `ADMIN`.**

전에는 `/admin/executors` 였고 **실행기 하나만** 조정할 수 있었다. 그런데 채점
파이프라인의 워크로드는 셋이고, **막히는 곳이 다르면 늘릴 것도 다르다** —
실행이 느리면 실행기를 늘리지만 **채점기가 큐를 못 빼면 실행기를 늘려도 소용없다.**
그리고 대회 중에는 대회 채점기만 늘려야 한다 (#62 가 큐를 나눈 이유다).

#### 두 축이 듣는 곳이 다르다

| | 무엇 | 듣는 곳 | 어떻게 바뀌나 |
|---|---|---|---|
| **파드 수** | 배포의 replica | 처리량과 격리 | 쿠버네티스 API |
| **워커 수** | 한 채점기가 동시에 처리하는 건수 | **대기 시간** | Redis 값을 채점기가 5초마다 읽는다 |

화면이 그 차이를 적어 둔다 — 안 적으면 운영자가 무엇을 눌러야 할지 모른다.

#### 워커 수는 재시작 없이 바뀐다

`JUDGE_CONCURRENCY` 는 기동할 때 한 번 읽는 값이라 전에는 배포를 다시 해야 했다.
**늘리려는 상황이 곧 재시작하면 안 되는 상황이다** — 큐가 밀린 때이고, 재시작하면
진행 중인 채점이 끊긴다.

Redis 에 두는 이유: 이미 큐로 쓰고 있고(ADR-0002) **파드가 여럿이어도 전부가 같은
값을 본다.** 채점기마다 엔드포인트를 두면 모든 파드에 따로 보내야 한다.

**줄일 때 진행 중인 채점을 끊지 않는다.** 루프마다 ctx 를 따로 주고 그것을 취소하면,
그 루프는 지금 처리 중인 것을 끝낸 뒤 다음 차례에 빠져나간다.

#### 두 곳에서 자른다

| 어디 | 무엇을 막나 |
|---|---|
| API (1~64) | **화면의 실수** |
| 채점기 (1 ~ 기동값 × 8) | **잘못된 값이 흘러들어온 경우** — 노드가 죽으면 안 된다 |

**0 을 허용하지 않는다.** 0 이면 그 차선의 채점이 통째로 멈추는데, 화면에서 그것은
"적체" 로 보인다 — 원인이 조정이라는 것을 아무도 모른다.

**Redis 를 읽지 못하면 지금 값을 유지한다.** 기본값으로 되돌아가면 늘려 둔 것이
조용히 사라지고, 그것을 아무도 모른다.

#### 아무 배포나 만질 수는 없다

경로가 이름을 받지만 **설정의 허용 목록(`codekr.scaling.targets`)에 있는 것만** 조정된다.
없는 이름은 `503` 이다. 일반화의 편의와 안전을 둘 다 가지는 방법이다.

**누가 무엇을 몇으로 바꿨는지 남는다** (#225, `SCALE`). 전에는 실행기 조정도 기록이 없었다.

### 어드민 문제집 관리 (#393)

`GET /api/v1/admin/collections` (목록·범위 필터) ·
`GET /api/v1/admin/collections/{id}` (담긴 문제까지) ·
`POST /api/v1/admin/collections/{id}/takedown` — **전부 `ADMIN`.**

대회(#335)·글과 댓글(#336)에는 어드민이 보는 곳이 있는데 **문제집만 빠져 있었다.**
공개 목록이 없을 뿐 링크로는 남에게 보여지고 있었고, **거기 무엇이 담겼는지 볼 방법이
없었다.**

| 판단 | 결정 | 왜 |
|---|---|---|
| 비공개까지 보나 | **아니다** | 남이 혼자 쓰는 목록을 들여다보는 것은 다른 문제다. 그리고 **우회로가 없다** — 링크를 뿌리려면 `UNLISTED` 가 되어야 한다 |
| 비공개로 좁혀 부르면 | **빈 목록** (400 아님) | 거절하면 "비공개를 보는 길이 어딘가 있다" 는 인상을 준다. 조건 자체가 비공개를 빼고 시작한다 |
| 역할 | `ADMIN` 하나 | **새 역할을 만들지 않았다.** 지금 여섯인데 쓸 화면이 없는 것이 이미 있었다 (#103) |
| 조치 | **내리기**(비공개로 되돌리기) | 지우는 것과 목록에서 빼는 것은 다르다. 되돌릴 수 있어야 하고, 주인은 그대로 갖고 있는다 |
| 링크 공유 문제집의 조치 | **없다** | 목록에 오른 적이 없으므로 내릴 것이 없다 |
| 주인에게 알리나 | **알린다, 사유와 함께** | 말없이 사라지면 고칠 수도 없다 (#208) |

상세가 **담긴 문제까지** 주는 이유: 무엇이 문제인지는 내용을 봐야 안다 — 이름만 보고
내리면 잘못 내린다.

### 지문에서 초안 만들기 (#230)

`POST /api/v1/admin/problems/draft` — **`PROBLEM_SETTER` 이상.**

문제 하나를 등록하려면 제목·slug·유형·난이도·지문·입출력 설명·제한·테스트케이스·정답
코드를 채워야 한다. 이 중 여럿은 **지문 안에 이미 있고**, 지금은 사람이 그것을 다시
나눠서 칸마다 옮겨 적는다.

**자동 등록이 아니다.** 초안을 돌려줄 뿐이고 저장은 사람이 한다 — 잘못 뽑힌 예제
하나가 그 문제의 모든 제출을 틀리게 만든다. 마지막 방어선은 정답 코드 검증(#39)이고,
이 도구는 그 앞의 옮겨 적기만 덜어 준다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 어디서 부르나 | **API 서버** | 웹이 부르면 키가 브라우저로 나간다. api 에는 egress 정책이 없다 — 막아 둔 것은 실행기다(#47) |
| 키가 없으면 | **404** (`FEATURE_DISABLED`) | 저장소(#115)·메일(#233)과 같은 규칙. 안 켜도 서비스는 돈다 |
| 모델 출력 | **믿지 않는다** | 길이·값 범위·개수를 서버가 자른다. 모델의 출력은 사용자 입력과 같은 급이다 |
| 고를 수 있는 값 | **enum 에서 가져온다** | 손으로 베끼면 유형이 하나 늘 때 조용히 갈라진다 |
| 못 찾은 것 | `missing` 으로 돌려준다 | **지어낸 값은 검토를 그냥 통과한다.** 빈 칸이 낫고, 빈 칸보다 "왜 비었는지" 가 낫다 |
| 붙여 넣은 지문 | **자료지 지시가 아니다** | 구분선으로 감싸고 시스템 쪽에 못박는다. 완전한 방어는 아니지만 결과는 어차피 사람이 검토한다 |
| 지문 본문 | **모델이 다시 쓴 것을 쓰지 않는다** | 붙여 넣은 원문을 그대로 넣는다. 다시 쓰면 원문과의 차이를 사람이 알아채기 어렵다 |
| 호출 기록 | 남긴다 (#225) | 바깥으로 나가고 돈이 든다. **지문 본문은 남기지 않는다** — 길고, 남의 저작물일 수 있고(#236), 기록은 지우기 어렵다 |
| 반복 호출 | 사람마다 분당 10회 | 버튼을 두 번 누르는 것은 흔한 일이고 이 호출은 돈이다 |

화면은 **채워진 칸이 초안임을 보여 준다** — 구획 제목 옆에 "AI 초안 — 확인하세요" 가
붙고, 사람이 그 칸을 손대면 사라진다. 구분되지 않으면 검토가 형식이 된다.

**등록할 때만 보인다.** 이미 있는 문제를 고치는 중에 초안을 덮어쓰면 사람이 쓴 것을 잃는다.

### 프로필은 공개다 — 어디까지가 공개인지 (#333)

`GET /api/v1/users/{handle}` · `GET /api/v1/users/{handle}/activity` — **둘 다 공개.**

전에는 둘 다 로그인이 필요했다. 그런데 게시판·랭킹·공개 문제집은 **비로그인에게
이름을 보여 주고 링크를 건다.** 누르면 로그인 화면으로 튕겼다 —
**누르면 튕기는 링크는 고장으로 보인다** (#131 이 어드민 메뉴에서 같은 판단을 했다).

#### 이슈의 전제 하나가 틀렸다

#333 은 "전체 제출 목록(#34)은 비로그인에게 열려 있고 프로필은 아니다" 라고 적었다.
확인해 보니 **제출 목록도 로그인이 필요하다.**

```
GET /api/v1/submissions   (비로그인) → 401
GET /api/v1/rankings                 → 200
GET /api/v1/posts                    → 200
GET /api/v1/collections              → 200
```

그래서 "한쪽만 열려 어긋나 있다" 가 아니라 **"사람 이름은 공개인데 그 사람 화면만
닫혀 있다"** 가 실제 어긋남이었다.

#### 선은 "센 숫자냐 한 줄 한 줄이냐" 로 긋는다

| 공개 | 로그인 |
|---|---|
| 이름·아바타·가입일·소개 문구 | **제출 목록** — 어떤 문제를 어떤 결과로 냈는지 (#34) |
| 점수·순위·실력 티어 (랭킹이 이미 공개) | |
| 푼 문제 수·제출 수·태그별 분포 | |
| 연속 기록과 날짜별 활동 **개수** | |
| 뱃지, 그 사람이 만든 **공개** 문제집 (#209 가 이미 공개) | |

프로필이 주는 것은 **개수**다. "누가 어떤 문제를 언제 냈는지" 는 여기서 나오지 않으므로
제출 목록의 우회로가 되지 않는다. 그 시험을 프로필 시험 안에 뒀다 —
**제출 목록이 열리는 순간 이 결정의 근거가 무너지기 때문**이다.

화면도 같은 선을 따른다. 비로그인에게 최근 제출 자리는 **빈 목록이 아니라 한 줄
안내**다 — 비어 있으면 "제출이 없는 사람" 으로 읽힌다.

소개 문구(#310)는 **순수 글자 100자에 링크가 열리지 않는다.** 그 판단은 원래
"프로필은 공개" 를 전제로 내려진 것이라, 이 변경으로 다시 볼 것이 없다 —
오히려 전제가 이제야 맞다.

### 프로필 소개 문구 (#310)

`PATCH /api/v1/users/me/profile` · `DELETE /api/v1/admin/users/{id}/bio`(`ADMIN`, 사유 필수)

**프로필에 그 사람이 직접 쓴 것이 한 글자도 없었다.** 닉네임·아바타 말고는 전부
서버가 센 숫자다. 게시판(#137)·댓글(#138)이 붙으면서 프로필을 여는 이유가 "몇 문제
풀었나" 만이 아니게 됐다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 형식 | **순수 글자**, 줄바꿈만 살린다 | 마크다운을 열면 제목·목록·이미지가 들어와 프로필 상단의 모양이 사람마다 달라진다 |
| 길이 | **100자** | 한 줄 소개가 되어 모양이 고르고 스팸이 앉을 자리도 좁다. 늘리기는 쉽고 줄이기는 이미 쓴 글을 자르는 일이다 |
| 링크 | **따로 열지 않는다** | 순수 글자라 주소를 적어도 글자로 남는다. 자리를 정해 둔 칸(깃허브·블로그)은 별도로 본다 |
| 안 쓴 사람 | **`null` 로 내린다** (빈 문자열 아님) | 화면이 빈 자리를 그리면 "안 쓴 사람" 이 아니라 "고장 난 화면" 으로 보인다 |
| 저장 자리 | `/users/me/profile` (설정과 나눔) | 설정은 **나만 보는 값**, 이쪽은 **남에게 보이는 값**이다. 닉네임 변경(#307)이 여기 붙는다 |
| 탈퇴 | **함께 지운다** | 가장 개인적인 내용이 들어갈 곳이다 (#140) |
| 어드민 | **지우기만** 된다, 사유 필수 | 신고 기능이 없어도 광고·사칭을 지울 길은 있어야 한다. 남의 글을 대신 고치는 것은 다른 일이다 |
| 검색 메타데이터 | **넣지 않는다** | 사용자가 쓴 글이 검색엔진에 그대로 올라간다. 스팸을 막는 장치가 서기 전에는 이르다 |

지운 뒤에는 무엇이 적혀 있었는지 알 길이 없으므로, **관리 기록(#225)이 지워진 내용을
그대로 들고 있다.**

### 회원 정지 (#224)

`GET|POST /api/v1/admin/users/{userId}/suspensions` ·
`DELETE /api/v1/admin/users/{userId}/suspensions/{id}` — **`ADMIN`.**

**할 수 있는 일이 "그대로 두기" 와 "되돌릴 수 없이 지우기"(#140) 둘뿐이었다.** 댓글
스팸 하나에 계정을 영구히 지우는 것은 과하다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 막는 단위 | **쓰기 / 제출 / 둘 다** | 댓글 스팸 때문에 문제 풀이까지 막을 이유가 없다. 채점기를 괴롭히는 계정이라면 제출만 막으면 된다 |
| 읽기 | **막지 않는다** | 로그아웃하면 그대로 보이므로 막는 시늉이다. 게다가 자기가 왜 막혔는지 볼 길까지 없앤다 |
| 무엇을 막을지 정하는 곳 | **`SuspendedAction` 한 파일** | 핸들러마다 선언하게 하면(#198 처럼) 빠뜨린 곳이 곧 구멍이 된다 |
| 기한 만료 | **조회에서 판단** (배치 없음) | 상태를 뒤집는 배치가 멈추면 아무도 모르는 채로 정지가 이어진다 |
| 이미 발급된 토큰 | **표를 읽는다** (탈퇴처럼 Redis 표시가 아니다) | 정지는 기한·범위가 있고 중간에 풀린다 — 토큰에 담을 수 없다. 대신 **쓰기·제출 요청에서만** 읽어 읽기 트래픽은 그대로 둔다 |
| 기간 | **3·7·30일·기한 없음** | 임의로 적게 하면 사람마다 기준이 달라진다 |
| 영구 정지 vs 강제 탈퇴 | **정지는 되돌릴 수 있고 기록이 남는다** | 강제 탈퇴는 마지막 수단으로 좁힌다 |
| 거는 권한 | `ADMIN` | 되돌릴 수 있는 조치다. 실제로 게시판을 지키는 사람이 쓸 수 있어야 한다 (역할 변경·강제 탈퇴는 `SUPERUSER`) |
| 본인 통지 | **알림을 보낸다** (#106) | 막혔을 때만 보이면 긴 글을 다 쓴 뒤에 알게 된다. 알림은 끌 수 없으므로(#199) 반드시 닿는다 |
| 랭킹·프로필 | **그대로 노출** | #207 에서 "탈퇴자만 제외" 로 정했다. 정지는 사람을 멈추는 것이지 쓴 것을 지우는 것이 아니다 |

막히면 `403 SUSPENDED` 이고, **메시지에 사유와 언제 풀리는지가 실려 온다.** 말없이
실패하면 고장으로 보인다.

정지 중에도 되는 것: 로그인·로그아웃·토큰 갱신, **스스로 탈퇴**, 자기 설정과 알림
읽음 표시. 정지가 떠날 자유까지 뺏지는 않는다.

### 어드민 관리 기록 (#225)

`GET /api/v1/admin/audit-logs` — `targetUserId` / `actorId` 로 거른다. **`SUPERUSER` 만.**

**로그로는 안 된다.** 지나가고, 찾을 수 없고, 화면에 없다. 역할 변경(#103)과 강제
탈퇴(#140)가 일어난 뒤에 "누가 왜" 를 물을 곳이 없었다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 저장 위치 | **표에 남긴다** (로그 아님) | 찾을 수 있어야 기록이다. 로그는 보존 기간이 지나면 사라진다 |
| 고치기·지우기 | **길을 두지 않는다** | 고칠 수 있는 기록은 기록이 아니다. `GET` 만 선언한다 — 시험이 선언 목록으로 확인한다 |
| 대상 이름 | **그때의 값을 사본으로** | 강제 탈퇴가 닉네임을 그 자리에서 지운다 (#140). 참조만 두면 숫자만 남는다 |
| 사유 | **되돌릴 수 없는 것에만 필수** | 전부 필수로 하면 의미 없는 사유를 적게 된다. 지금은 강제 탈퇴만 |
| 기록 시점 | **같은 트랜잭션 안** (`MANDATORY`) | 조치는 됐는데 기록이 없는 상태를 만들지 않는다 |
| 조회 방향 | **대상과 집행자 둘 다** | "이 회원에게 무슨 일이 있었나" 와 "이 어드민이 무엇을 했나" 는 다른 질문이다 |

지금 남는 것은 **역할 변경**과 **강제 탈퇴** 둘이다. 회원 정지(#224)와 문제 삭제처럼
뒤에 붙는 조치는 `AdminAction` 에 항목을 더하고 같은 표에 남긴다.

### 회원 탈퇴 (#140)

`DELETE /api/v1/users/me` · `DELETE /api/v1/admin/users/{id}` (강제 탈퇴)

**글과 댓글은 남는다.** 대화에서 한쪽 말만 사라지면 남은 말이 뜻을 잃는다 —
답이 달린 질문을 지우면 답을 쓴 사람의 글까지 무의미해진다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 식별 정보 | **익명 값으로 덮어쓴다** | 개인정보를 남기지 않는 것이 탈퇴의 뜻이다. **여기서 정한 것이 곧 개인정보 처리 방침이 된다** |
| 작성자 표시 | **참조는 두고 상태로 판단** | 참조를 끊으면 집계(제출·통계)가 함께 깨지고 되돌릴 수 없다 |
| 유예 기간 | **두지 않는다** | 두면 "탈퇴했는데 아직 데이터가 있다" 는 상태가 생기고, 그 사이의 규칙을 또 정해야 한다. 대신 **되돌릴 수 없다는 것을 화면에서 분명히 말한다** |
| 닉네임 재사용 | **가능하다** | 덮어쓰므로 유니크 제약이 풀린다. 나간 사람이 닉네임을 영구 점유하지 않는다 |
| 랭킹·활동 | **랭킹에서 뺀다** (제출 기록은 남긴다) | 없는 사람이 순위에 있으면 눌렀을 때 갈 곳이 없다. 제출은 문제 통계의 원자료다 |
| 강제 탈퇴 | **같은 경로**, 단 `reason` 필수 | 두 벌로 두면 한쪽만 고치는 일이 생긴다. 되돌릴 수 없으므로 사유 없이는 실행되지 않는다 (#225) |
| 로그인 실패 문구 | **일반 인증 실패와 같다** | "탈퇴한 계정입니다" 라고 알리면 그 이메일이 쓰였다는 사실이 새어 나간다 |

#### 발급된 토큰을 즉시 막는다

JWT 는 상태가 없어서 그냥 두면 만료까지 통한다. 액세스 토큰 수명이 한 시간이면
**탈퇴 후 한 시간 동안 계속 쓸 수 있다.**

요청마다 DB 에서 사용자 상태를 읽으면 모든 인증 요청에 조회가 하나 붙는다. 대신
**Redis 에 탈퇴한 사용자 id 만** 담고 액세스 토큰 수명만큼만 둔다 — 그 뒤에는 토큰
자체가 만료되므로 더 기억할 이유가 없다.

표시 이름은 `WithdrawnUser.LABEL` **한 곳**에서만 만든다. 화면마다 문구를 따로 쓰면
어떤 곳은 "탈퇴한 회원", 어떤 곳은 "(알 수 없음)" 이 되고 읽는 사람이 오해한다.

### 게시판 (#137)

`GET /api/v1/posts?board=&q=` (공개) · `GET /api/v1/posts/boards` (공개) ·
`GET /api/v1/posts/{id}` (공개) · `POST` · `PUT` · `DELETE`

| 판단 | 결정 | 왜 |
|---|---|---|
| 게시판 개수 | **셋** (자유·질문·공지) | 나중에 늘리기는 쉽지만 **합치기는 어렵다** — 글이 쌓인 뒤 합치면 그 글들이 어디로 갈지 사람이 하나씩 정해야 한다. 태그는 정리하는 사람이 있어야 유지되는데 지금은 없다 |
| 본문 형식 | **마크다운 원문 저장** | 저장 시점에 HTML 로 바꾸면 렌더링 규칙을 고칠 때 이미 쌓인 글을 전부 다시 만들어야 한다 |
| XSS | **HTML 문자열을 만들지 않는다** | 아래 |
| 읽기 권한 | 공개 | 로그인해야 읽을 수 있으면 검색으로 들어온 사람이 아무것도 볼 수 없다 |
| 공지 | 운영자만 씀 | 아무나 쓸 수 있으면 공지가 아니다 |
| 운영자의 권한 | **내릴 수는 있고 고칠 수는 없다** | 고치면 그 사람이 쓴 것으로 남는데, 실제로 쓴 사람은 다른 사람이다 |

#### XSS 를 원천 차단한다

사용자가 쓴 것을 그대로 그리는 첫 기능이다. **여기서 새는 구멍은 나중에 붙는
댓글(#138)·질문(#139)에 그대로 이어진다.**

`dangerouslySetInnerHTML` 을 쓰지 않고 마크다운을 **React 엘리먼트로 직접 만든다.**
사용자가 쓴 `<script>` 는 문자열로 그려질 뿐 실행되지 않는다.

마크다운 라이브러리를 들이면 sanitize 설정을 정확히 맞춰야 하고, 설정 하나가 어긋나면
구멍이 난다. **구멍이 날 수 없는 방식**을 골랐다.

남는 구멍은 링크 주소 하나뿐이라 `http`/`https`/사이트 내부 경로만 링크로 만든다 —
`javascript:`·`data:`·`//evil.com` 은 글자 그대로 둔다.

#### 문제 지문도 같은 렌더러를 쓴다 (#338)

`description`·`inputDescription`·`outputDescription` 은 **값 그대로** 그려졌다.
그래서 `**굵게**` 는 별표가, 코드 블록은 백틱이 그대로 보였다.

같은 사이트에서 **글을 쓰는 자리마다 규칙이 다르면 출제자는 어느 쪽인지 알 방법이
없다.** 실제로 시드 문제 `a-divided-by-b` 는 이미 `**정답은 실수입니다.**` 라고
쓰고 있었다 — 마크다운이라고 여기고 쓴 것이다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 범위 | 지문 세 칸 전부 | 한 칸만 마크다운이면 규칙이 또 갈린다 |
| 예제 입출력 | **그대로 `<pre>`** | 그것은 글이 아니라 **값**이다. 마크다운으로 그리면 값에 든 `*` 이 사라진다 |
| `hideCode` | 쓰지 않는다 | 질문 글의 코드는 답이 될 수 있어 접지만(#139), **지문의 코드 블록은 지문의 일부**다 |
| 굵게(`**x**`) | **더했다** | 위의 이유. 게시글·댓글에도 같이 생긴다 |
| 기울임(`*x*`·`_x_`) | **넣지 않았다** | 지문에는 `loans.member_id` 같은 식별자가 흔하다. 시드의 SQL 문제 다섯이 전부 그렇다 — 켜면 그 이름들이 조용히 기울어진다 |
| 표 문법 | 넣지 않았다 | 표 구조는 코드 블록으로 충분하다(#60 이 그렇게 쓴다). 표 파서는 렌더러를 두 배로 키운다 |
| 편집기 | **미리보기를 둔다** | 마크다운을 여는 순간 "쓴 대로 보이지 않는" 일이 생긴다. 게시글 편집기가 같은 이유로 같은 것을 둔다 |

이미 등록된 문제가 깨지지 않는지 DB 로 확인했다 — 제목 표기(`# `), 목록(`- `),
백틱을 쓰는 지문은 하나도 없다. 밑줄은 SQL 문제 다섯에 있는데, **기울임을 넣지
않았으므로 영향이 없다.**

### 문제별 질문 (#139)

`GET /api/v1/posts/by-problem/{problemId}` (공개). 작성은 `POST /api/v1/posts` 에
`problemId` 를 실어 보낸다.

**게시글을 새로 만들지 않고 붙인다.** 질문은 게시글이고 답변은 댓글이다 — 같은 것을
두 벌 만들면 렌더링·권한·삭제 규칙이 둘로 갈라진다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 정답 코드 노출 | **기본 가림, 펼치면 보임** | 아직 못 푼 사람에게 답이 보이면 그 문제의 값이 떨어진다. "푼 사람에게만" 으로 막으면 **질문하려면 먼저 풀어야 한다** 는 모순이 생긴다 |
| 답변 채택 | **두지 않는다** | 댓글 모델에 상태가 붙는다. 답이 쌓인 뒤 "무엇이 답인지 모르겠다" 가 실제로 생기면 넣는다 — **넣기는 쉽고 빼기는 어렵다** |
| 대회 중인 문제 | **질문을 막는다** | 질문이 곧 힌트가 되고, 참가자마다 그것을 본 사람과 못 본 사람이 갈린다 |
| 커뮤니티 목록 | **함께 보인다** | 분리하면 질문이 두 곳에 흩어지고, "다음 사람이 먼저 읽고 간다" 는 목적이 약해진다 |

### 댓글 (#138)

`GET /api/v1/posts/{postId}/comments` (공개) · `POST` · `PUT /api/v1/comments/{id}` ·
`DELETE /api/v1/comments/{id}`

| 판단 | 결정 | 왜 |
|---|---|---|
| 깊이 제한 | **저장에는 없다. 화면에서만 접는다** | "대댓글까지만" 으로 막으면 세 번째 발언부터 누구에게 하는 말인지 사라진다 |
| 자식이 있는 댓글 삭제 | **자식은 남긴다** | 자식까지 지우면 남의 글이 함께 사라진다 |
| 자식이 없는 삭제된 댓글 | **아예 내리지 않는다** | 자리만 차지한다 |
| 삭제된 댓글의 본문 | **내리지 않는다** (DB 에는 남긴다) | 잘못 지운 것을 복구할 방법이 없으면 삭제가 되돌릴 수 없는 선택이 된다 |
| 삭제된 댓글의 작성자 | **내리지 않는다** | 지운 사람이 누구인지 남길 이유가 없다 |
| 익명 댓글 | 받지 않는다 | |
| 운영자 | **내릴 수는 있고 고칠 수는 없다** | #137 과 같은 이유 |

**쓰기·수정·삭제 응답이 트리 전체다.** 한 건만 돌려주면 화면이 트리의 어디에 끼워 넣을지
다시 계산해야 하고, 그 규칙이 서버와 갈라진다.

트리는 **한 번의 조회**로 만든다. 부모마다 질의하면 댓글 수만큼 쿼리가 나간다.
목록의 댓글 수도 글마다 세지 않고 한 번에 센다.

삭제된 댓글에는 답할 수 없다 — 무엇에 답하는지가 사라진 자리다.
다른 글의 댓글에도 답할 수 없다 — 트리가 두 글에 걸친다.

### 코드 열람 알림 (#136)

내 공개 코드를 **몇 명이** 읽었는지 하루 한 번 알린다.

| 판단 | 결정 | 왜 |
|---|---|---|
| 닉네임까지 알릴까 | **수만** | 닉네임을 알리면 조회자 쪽 프라이버시를 그만큼 가져간다. 수만 알려도 "읽히고 있다" 는 목적은 이룬다 |
| 판정 조회도 셀까 | **코드가 실제로 내려간 것만** | 판정은 목록에서도 보인다. 무게가 다른 둘을 한 숫자로 합치면 그 숫자가 뜻을 잃는다 |
| 켜고 끄기 | **없앴다** (#199) | 기본이 끔이었고 아무도 켜지 않아, 기능 전체가 실제로는 꺼진 코드였다. 지금은 **모두에게 켜져 있다** |
| 쓰기 폭주 | (제출, 조회자, 날짜) 하루 한 줄 | 설정으로 막던 것을 기본키가 막는다. 같은 사람이 하루에 백 번 봐도 upsert 한 번이다 |
| 중복 | (제출, 조회자, **날짜**) 가 기본키 | 새로고침·뒤로가기가 숫자를 부풀리지 않는다 |
| 조회자에게 알릴까 | **알린다** | 기록에 남는다면 보기 전에 그 사실을 알아야 한다. 제출 상세의 `viewNotified` |
| 제외 | 자기 제출, 어드민 조회 | 운영 행위가 알림이 되면 안 된다 |
| 보관 | 30일 | 알림을 만들고 나면 원자료가 할 일은 끝난다 (ADR-0007) |

알림은 **건별이 아니라 하루치를 묶어** 하나로 만든다. 인기 문제의 공개 코드는 하루에
수백 번 읽힐 수 있고, 한 건마다 알림이면 알림함이 이것으로만 찬다.

카테고리는 `SUBMISSION_VIEW` 로 따로 뒀다. 채점 알림은 **내 기록이 바뀐 것**이고
이것은 **남이 내 것을 본 것**이다 — 뜻이 다르면 알림함에서 나뉘어 보여야 한다.

### 알림 끄기 (#199 에서 삭제)

카테고리별 수신 거부(`notification_mutes`)와 열람 알림 토글은 없앴다. 설정 화면에
있었지만 **운영·로컬 통틀어 켠 사람이 한 명도 없었고**, 그 대가로 알림을 만드는 모든
경로가 "이 사람이 이 카테고리를 껐는가" 를 먼저 물어야 했다. 아무도 쓰지 않는 분기는
검증되지 않은 채로 남는다.

알림 자체가 시끄러워지면 그때는 **끄는 스위치가 아니라 덜 보내는 쪽**으로 고친다 —
열람 알림을 하루치로 묶는 것처럼.

스키마도 **한 배포 뒤에 지웠다** (#266) — `notification_mutes` 표와
`users.view_notification_enabled`·`users.ranking_opt_out`. 코드와 함께 지우지 않은
이유는 되돌릴 수 있어야 하기 때문이다(#246): 그 배포를 되돌리면 옛 이미지의 엔티티가
없는 컬럼을 매핑해 기동에서 실패한다.

### 프로필 아바타 (#116)

`PUT /api/v1/users/me/avatar` (multipart) · `DELETE /api/v1/users/me/avatar`

- **본인 것만.** 경로에 남을 지정할 방법이 없다
- 올린 이미지는 정사각 256px PNG 로 **다시 만들어** 저장한다 (#115) — 그 과정이 곧 검증이다.
  확장자와 선언된 Content-Type 은 믿지 않는다
- 바꾸면 **옛 이미지를 지운다.** 다만 같은 이미지를 다시 올리면 키가 같으므로 지우지 않는다
- 응답에는 키가 아니라 주소(`/api/v1/files/...`)가 나간다. DB 에는 **키만** 저장한다 —
  저장소 주소나 서빙 경로가 바뀌면 URL 은 모든 행을 고쳐야 한다
- 올리지 않았으면 `avatarUrl` 이 null 이다. **화면이 기본 표현(닉네임 첫 글자 + 색)을 그린다** —
  회색 실루엣 하나로 두면 목록에서 모두가 똑같아 보이는데, 아바타를 넣은 이유가
  사람을 구분하려는 것이다

### 문제집 (#87)

`GET /api/v1/collections/me` · `GET /api/v1/collections/{id}` ·
`GET /api/v1/collections/shared/{shareToken}` (공개) · `POST` · `PUT` · `DELETE`

- **회원 누구나 만든다.** 어드민 전용이 아니다
- **공개 목록이 없다.** 1차에는 `PRIVATE` 와 `UNLISTED`(링크 공유)뿐이다 —
  누구나 공개 문제집을 만들 수 있게 하면 스팸·중복·방치가 즉시 생기는데,
  신고도 정리도 할 수 없는 채로 열면 목록이 곧 쓸 수 없게 된다
- 링크는 **추측할 수 없는 토큰**으로 연다. id 를 쓰면 번호를 바꿔 가며 남의 것을 찾을 수 있다.
  토큰은 **주인에게만** 내린다
- **최소 2개 제약은 공유할 때 본다.** 만드는 중에는 0개인 순간이 반드시 있고,
  저장 시점에 막으면 이름만 정해 두고 나중에 채우는 흔한 흐름이 불가능해진다
- 담긴 문제가 소프트 삭제되면 **목록에서만 뺀다.** 행은 남긴다 — 복구되면 다시 나타나야
  하고, 여기서 지우면 순서 정보까지 사라진다 (ADR-0007)
- 진행률은 제출 기록에서 센다. 랭킹 점수 표(#57)를 쓰지 않는 이유는 그 표가 **공개된
  문제만** 담기 때문이다 — 문제집에는 비공개 문제가 들어갈 수 있다

### 역할 (#103)

```
SUPERUSER ─▶ ADMIN ─▶ PROBLEM_SETTER
                   ─▶ CONTEST_MANAGER
                   ─▶ BOARD_MANAGER
```

한 사람이 여러 역할을 가질 수 있다. 위계는 위에서 아래로만 흐른다 —
**문제 출제자는 인프라를 만질 수 없다.**

| 경로 | 필요한 역할 |
|---|---|
| `/api/v1/admin/problems/**` | `PROBLEM_SETTER` |
| `/api/v1/admin/queues/**`, `/executors/**`, `/retention/**` | `ADMIN` |
| **그 밖의 `/api/v1/admin/**`** | `SUPERUSER` |

마지막 줄이 **안전한 기본값**이다. 규칙을 적지 않고 어드민 API 를 늘리면 아무도 못 쓰게
되지, 모두가 쓸 수 있게 되지 않는다.

> 인가를 메서드 보안(`@PreAuthorize`)이 아니라 경로 규칙에 둔 이유: 메서드 보안은
> **본문 바인딩 뒤에** 돌아서, 권한 없는 요청이 400(검증 실패)을 먼저 받는다.
> 막혔다는 사실조차 알 수 없고, 남의 영역의 요청 형식을 탐색할 수 있게 된다.

**자원 범위(어느 대회의 관리자인가)는 아직 없다.** 대회 도메인이 생길 때 함께 만든다 (#61).
