# 05. 로컬 개발 가이드

## 1. 사전 요구사항

| 도구 | 최소 버전 | 비고 |
|---|---|---|
| Docker / Docker Compose | 24 / v2 | 실행기가 호스트 컨테이너 런타임 소켓을 사용한다 |
| Make | — | 진입점 |
| (선택) JDK | 21 | `apps/api` 를 IDE 에서 직접 돌릴 때 |
| (선택) Bun | 1.2+ | `apps/web` 을 직접 돌릴 때 |
| (선택) Go | 1.24+ | `apps/judge`, `apps/executor` 를 직접 돌릴 때 |
| (선택) golangci-lint | v2.6 | `make lint-go` 는 컨테이너로 돌리므로 설치하지 않아도 된다 |

컨테이너로만 돌린다면 Docker 와 Make 만 있으면 된다.

## 2. 포트 표

로컬에서 흔히 쓰이는 포트(3000, 5432, 6379, 8080)와 충돌하지 않도록 의도적으로 옮겼다.

| 서비스 | 컨테이너 포트 | 호스트 포트 | URL |
|---|---|---|---|
| web | 3000 | **13000** | <http://localhost:13000> |
| api | 8080 | **18080** | <http://localhost:18080> |
| executor | 8081 | **18081** | <http://localhost:18081/healthz> |
| judge | 8082 | **18082** | <http://localhost:18082/healthz> |
| postgres | 5432 | **15432** | |
| redis | 6379 | **16379** | |

### `/api` 는 web 을 거쳐 간다 (#314)

브라우저는 **`http://localhost:13000/api/...`** 로 부른다. web(Next)이 그것을 api 로
넘긴다(`next.config.ts` 의 rewrite). 운영에서 Ingress 가 하는 일과 같은 모양이다.

전에는 브라우저가 api(:18080)를 직접 불렀는데, 그러면 **`<img src>` 처럼 접두사가
닿지 않는 자리**가 생긴다 — 아바타 주소가 web 으로 가서 404 가 났다.

- 컨테이너로 띄우면 `API_INTERNAL_BASE_URL=http://api:8080` 이 **빌드 인자**로 들어간다.
  Next 가 rewrite 를 빌드 때 굳히므로 실행 시 환경 변수로는 바꿀 수 없다
- 호스트에서 `bun run dev` 로 띄우면 기본값 `http://localhost:18080` 을 쓴다

## 3. 기동

```bash
cp .env.example .env      # 필요하면 값 수정
make pull-runtimes        # 코드 실행용 런타임 이미지 미리 받기 (최초 1회)
make up                   # 전체 스택 기동
make logs                 # 로그 따라가기
make seed                 # 데모 계정 + 시드 문제 주입 (사칙연산 넷 #280, SQL 다섯 #313)
```

기동 후:

- 사이트: <http://localhost:13000>
- API 헬스: <http://localhost:18080/actuator/health>

### `make seed` 는 그대로다 (#342)

시드가 두 스크립트로 갈렸지만 **로컬 사용법은 달라지지 않았다.** `make seed` 가
계정을 준비하고 문제 주입을 부른다.

가른 이유는 운영이다 — `scripts/seed-problems.sh` 는 주소와 토큰을 받아 어디서든
돌고, **데모 계정을 만들지 않는다.** 운영 절차는 `docs/09_배포_가이드.md` §6.3 에 있다.

> **운영에 데모 계정(`admin@codekr.dev`·`user@codekr.dev`)을 만들지 않는다.**
> 지금은 주입 스크립트에 가입 코드가 없어서 구조로 막혀 있다. 다음에 옵션을 더하고
> 싶어지면 이 줄을 먼저 읽을 것 — 옵션은 실수로 켜진다.

### 메일은 기본으로 보내지 않는다 (#233)

`CODEKR_MAIL_HOST` 가 비어 있으면 **보내지 않고 본문을 로그에 찍는다.** 인증 링크는
`make logs-api` 에서 그대로 읽을 수 있다.

실제 발송까지 보려면 메일 싱크를 띄우고 값을 준다.

```bash
docker run -d --rm --name codekr-mailsink -p 11025:1025 -p 18025:8025 axllent/mailpit
# api 는 컨테이너 안이라 localhost 가 자기 자신이다. 호스트를 가리켜야 한다.
CODEKR_MAIL_HOST=host.docker.internal CODEKR_MAIL_PORT=11025 make up
# 받은 메일: http://localhost:18025
```

**설정이 없으면 인증을 요구하지도 않는다** — 로컬에서 글쓰기가 막히지 않는다.

### 붙었는지 기동 로그로 안다 (#355)

발송은 실패해도 예외를 삼킨다 — 가입이 메일 때문에 실패하면 안 되기 때문이다.
그래서 **켜 놓고도 안 되는 것을 모르는 상태**가 생긴다. 기동할 때 한 번 붙어 보고
결과를 남긴다.

```
메일 준비됨 host=host.docker.internal port=11025 ssl=false     ← 붙었다
메일 서버에 붙지 못했습니다 host=... 원인=MailConnectException  ← 안 붙었다
메일 설정이 없습니다. ... 로그로만 남깁니다                      ← 끈 상태
```

**465 를 쓸 때는 `CODEKR_MAIL_SSL=true`** 가 필요하다. 붙자마자 TLS 를 하는 포트라
STARTTLS 로는 붙지 못한다. 빠뜨리면 기동 로그가 그것을 짚어 준다.

### 모델 프록시는 기본으로 뜨지 않는다 (#648)

문제 초안 만들기(#230)는 **키가 있어야** 쓸 수 있다. 그 앞에 LiteLLM 프록시를 둘 수
있는데, `profiles: [ai]` 라 `make up` 은 건너뛴다 — 키가 없는 사람에게 늘 실패하는
컨테이너가 하나 보이는 것은 나쁘다.

```bash
make ai-up      # 프록시만 띄운다 (http://localhost:14000/v1)
make ai-down
```

켜면 `.env` 의 셋을 바꾼다. **api 코드는 고치지 않는다.**

```
CODEKR_DRAFT_BASE_URL=http://litellm:4000/v1
CODEKR_DRAFT_API_KEY=${LITELLM_MASTER_KEY}
CODEKR_DRAFT_MODEL=문제-초안          ← 모델 이름이 아니라 일 이름
```

**제공자 키는 프록시만 안다.** api 가 드는 것은 master key 뿐이라, 새면 그것만 돌리면
되고 제공자 계정 전체가 열리지 않는다. 무엇이 그 일을 하는지는
`infra/litellm/config.yaml` 이 정한다 — 모델을 바꿔도 api 는 그대로다.

```
$ curl -H "Authorization: Bearer $LITELLM_MASTER_KEY" http://localhost:14000/v1/models
{"data":[{"id":"문제-초안",...},{"id":"문제-초안-예비",...}],"object":"list"}
```

**프록시가 없어도 스택은 그대로 뜬다.** `CODEKR_DRAFT_BASE_URL` 의 기본값이 OpenAI 이고,
키가 없으면 그 기능만 없다(404).

### SQL 시드 문제 (#313)

다섯 문제(`08`~`12`)가 **같은 스키마**를 쓴다 — 도서관(`members`·`books`·`loans`).
표 구조를 한 번만 익히면 되고 문제 사이에 흐름이 생긴다.

`schema_sql` 은 문제마다 DB 에 저장되므로, 시드에서는 **한 벌만 두고 끼워 넣는다.**

```
scripts/seed-problems/sql/library.sql     ← 스키마와 시드 데이터 한 벌
scripts/seed-problems/08-*.json           ← "sqlSchemaFile": "sql/library.sql"
```

`seed.sh` 의 `assemble_problem` 이 보내기 전에 `sqlSpec.schemaSql` 로 옮긴다 —
`sqlSpec` 은 어드민 API 의 규격이라 필드 이름을 바꿀 수 없다.

**채점은 값만 비교한다.** 하네스가 `psql -tA -F'|'` 로 뽑으므로 열 **이름**은 보지
않고, 열 **순서**와 (`ignoreRowOrder=false` 일 때) 행 순서는 지켜야 한다.

## 4. 자주 쓰는 명령

```bash
make up            # 빌드 후 기동 (백그라운드)
make down          # 중지 및 컨테이너 제거
make clean         # 볼륨까지 삭제 (DB 초기화)
make logs          # 전체 로그
make logs-api      # 특정 서비스 로그
make ps            # 상태 확인
make seed          # 시드 데이터 주입
make smoke         # E2E 스모크 테스트 (가입→제출→판정)
make test          # 전체 단위 테스트
make test-api      # api 테스트만
make coverage      # 커버리지 측정 → build/coverage/index.html
make lint          # 전체 정적 검사
make lint-go       # golangci-lint (컨테이너로 실행하므로 별도 설치 불필요)
make build-runtimes    # 공식 이미지가 없는 언어(kotlin, csharp) 이미지 빌드
make verify-runtimes   # 등록된 모든 런타임의 기본 템플릿이 실제로 돌아가는지 확인
```

### 커버리지 보기 (#642)

```bash
make coverage                                  # 셋 다 (api 는 Docker 필요)
make coverage ARGS=web                         # 하나만 (api | web | go)
SKIP_INTEGRATION=1 bash scripts/coverage.sh api   # Testcontainers 없이
open build/coverage/index.html
```

| 스택 | 도구 | 줄 단위로 보이나 |
|---|---|---|
| api | JaCoCo | **된다** — `build/coverage/api/index.html` |
| web | bun | 표에 안 덮인 줄 번호가 나온다. `lcov.info` 는 편집기가 읽는다 |
| go | `go tool cover` | **된다** — `build/coverage/go/*.html` |

**api 는 단위와 통합을 합쳐서 잰다.** 나누면 숫자가 뜻을 잃는다 — 시험 파일 114개 중
95개가 통합 시험이라, 단위만 재면 8.8% 가 나오고 합치면 89.5% 다. 그래서 `make coverage`
는 Docker 를 요구한다. 없으면 `SKIP_INTEGRATION=1` 로 단위만 볼 수 있고, **그때는
스크립트가 그렇다고 말한다.**

**web 의 숫자는 실제보다 높다.** bun 은 시험이 불러들인 파일만 세고, 한 번도 import 되지
않은 파일은 0% 가 아니라 **아예 빠진다.**

**문턱은 걸려 있지 않다.** 지금 걸면 숫자를 채우려고 값싼 시험이 들어오고, 그것은 시험이
없는 것보다 나쁘다 — 덮였다고 말하는데 아무것도 막지 않는다.

## 5. 개별 서비스만 로컬에서 돌리기

인프라(postgres, redis)만 컨테이너로 띄우고 나머지는 네이티브로 실행할 수 있다.

```bash
make infra-up                     # postgres + redis 만

# api
cd apps/api && ./gradlew bootRun

# web
cd apps/web && bun install && bun run dev

# executor / judge
cd apps/executor && go run ./cmd/executor
cd apps/judge && go run ./cmd/judge
```

이때 필요한 환경 변수는 `.env.example` 에 전부 나열돼 있다.

## 6. 코드 실행기와 컨테이너 런타임 소켓

executor 컨테이너는 호스트의 런타임 소켓(`/var/run/docker.sock`)을 마운트해 **형제 컨테이너**로
샌드박스를 띄운다. 채점 대상 코드는 executor 컨테이너 안이 아니라 별도의 격리 컨테이너 안에서 돈다.

> ⚠️ 런타임 소켓 마운트는 호스트에 대한 강한 권한이다. 로컬 개발과
> **실행 전용으로 격리된 k8s 노드**에서만 사용한다. 운영 환경의 런타임은 containerd 이며,
> 자세한 내용은 [ADR-0003](adr/0003-샌드박스-런타임.md) 을 참고한다.

## 7. 트러블슈팅

| 증상 | 원인 / 해결 |
|---|---|
| `port is already allocated` | 위 포트 표의 호스트 포트가 이미 사용 중. `.env` 에서 `*_HOST_PORT` 를 바꾼다 |
| 제출이 계속 `PENDING` | judge 컨테이너 로그 확인 (`make logs-judge`). Redis 연결 실패가 흔한 원인 |
| 실행이 항상 `SYSTEM_ERROR` | `make pull-runtimes` 를 실행했는지 확인. 런타임 이미지가 없으면 실패한다 |
| api 기동 실패 (Flyway) | `make clean` 후 재기동하면 DB 가 초기화된다 |
| web 에서 CORS 오류 | `.env` 의 `CODEKR_CORS_ALLOWED_ORIGINS` 에 웹 오리진이 포함돼야 한다 |
| Apple Silicon 에서 런타임 이미지 pull 실패 | `docker pull --platform linux/arm64` 로 확인. 대부분의 공식 이미지는 arm64 를 제공한다 |

## 오브젝트 스토리지 (#115)

사용자가 올린 이미지는 **직접 띄운 MinIO** 에 둔다. 로컬도 운영(홈랩)도 같은 것이다 —
**AWS S3 를 쓰지 않는다.** MinIO 가 S3 프로토콜을 말할 뿐이고, 그 덕에 표준 클라이언트를
그대로 쓴다.

**로컬은 MinIO 가 `make up`(또는 `make infra-up`)에 함께 뜬다** — 외부 계정 없이 전체가
돌아야 한다.

| 주소 | 용도 |
|---|---|
| `http://localhost:19000` | 오브젝트 API. api 가 쓴다 |
| `http://localhost:19001` | MinIO 콘솔. 눈으로 확인할 때 |

기본 자격증명은 `.env.example` 에 있다. 버킷은 **처음 올릴 때 자동으로 만든다** —
MinIO 는 버킷을 미리 만들어 주지 않는다.

```bash
make verify-storage   # 실제로 올리고 받고 지우는지 확인
```

**로컬에서만 다른 저장 방식을 쓰지 않는다.** 그러면 로컬에서 되던 것이 운영에서 안 되는
일이 생기고, 그때 원인을 찾기 어렵다.

스토리지 설정이 비어 있으면 업로드 API 만 503 이 되고 나머지는 그대로 돈다 —
아바타 때문에 서비스 전체가 뜨지 못하면 안 된다.

## Docker 없이 컨테이너 런타임 쓰기 (#70)

**결론: 절반만 된다.** macOS 에서 Docker Desktop 없이 containerd 를 띄울 수 있고
호스트 프로세스가 그 소켓에 붙어 **컨테이너를 만들고 띄우는 것까지 된다.**
다만 **표준 입출력은 VM 경계를 넘지 못한다** — 아래 "실제로 해 보고 알게 된 것".

#45 가 containerd 구현(#68)을 미룬 근거는 "로컬에서 검증할 방법이 없다" 였다.
그 근거는 **부분적으로만** 유효하다: 제어(컨테이너·스냅샷·spec)는 로컬에서 검증할 수 있고,
실행 결과를 거두는 부분은 **실행기가 리눅스 안에 있어야** 검증된다.

### 설치와 기동

```bash
brew install colima
colima start --runtime containerd --cpu 2 --memory 4 --disk 20
```

소켓은 **호스트 경로로 노출된다** — VM 안에 들어가지 않아도 된다.

```
unix:///Users/<이름>/.colima/default/containerd.sock
```

### 조사 결과

| 기준 | 결과 | 확인한 방법 |
|---|---|---|
| Docker 제품 의존 없음 | ✅ | VM 안에 `dockerd` 가 **아예 없다** (`command -v dockerd` → 없음) |
| containerd 소켓을 직접 만질 수 있는가 | ✅ | 호스트의 Go 프로세스가 `client.New(sock)` 로 붙어 **containerd v2.3.1** 응답을 받았다. 네임스페이스 목록도 읽힌다 |
| cgroup v2 가 동작하는가 | ✅ | `stat -fc %T /sys/fs/cgroup` → `cgroup2fs`. `--memory 64m --pids-limit 16` 을 걸고 컨테이너 안에서 `memory.max=67108864`, `pids.max=16` 을 확인했다 |
| 네트워크 차단 | ✅ | `--network none` 으로 루프백만 남는다 |
| 팀원이 재현할 수 있는가 | ✅ | brew 한 줄 + colima 한 줄. 기계에 고유한 설정이 없다 |
| `--self-test` 7개 통과 | ⛔ 호스트에서는 불가 / ✅ VM 안에서는 통과 | 아래 |

### 실제로 해 보고 알게 된 것 (#68)

containerd 구현을 만들어 여기서 돌려 봤다. **호스트에서는 컨테이너 생성·스냅샷·OCI
spec·태스크 시작까지 통과했고, 표준 입출력에서 막혔다.** VM 안에서 돌리면 전부 통과한다.

containerd 는 프로세스의 입출력을 **FIFO 파일**로 주고받는다. 그 FIFO 는 클라이언트가
만들고 containerd-shim 이 여는데, **둘이 같은 커널의 파일 시스템을 봐야 한다.**

- 기본 경로(`/var/run/containerd`)는 클라이언트 쪽(macOS)에 만들려 해서 실패한다
- 공유 마운트(`$HOME` → virtiofs)로 옮기면 shim 이 경로는 찾지만 **FIFO 를 열지 못한다**
  (`opening w/o fifo ... failed: context deadline exceeded`) — 이름 있는 파이프는
  가상 파일 시스템을 건너지 못한다

즉 **원격 소켓으로는 채점기를 검증할 수 없다.** 운영에서는 실행기가 노드 위에서 돌아
같은 커널을 쓰므로 해당하지 않는 제약이다.

### 그래서 #68 을 어떻게 검증했나

실행기를 **리눅스 안에서** 돌린다. 시험 바이너리를 크로스 컴파일해 VM 안에서 실행했다.

```bash
cd apps/executor
GOOS=linux GOARCH=arm64 go test -c -o ~/codekr-selftest.test ./internal/selftest/
GOOS=linux GOARCH=arm64 go test -c -o ~/codekr-sandbox.test  ./internal/sandbox/

colima ssh -- sh -c 'cd /Users/<이름>/004-Projects/codekr/apps/executor/internal/sandbox && \
  CODEKR_SANDBOX_TEST=1 CODEKR_SANDBOX_RUNTIME=containerd \
  CONTAINERD_ADDRESS=/run/containerd/containerd.sock \
  CODEKR_CONTAINERD_FIFO_DIR=/tmp/codekr-fifo \
  CODEKR_SECCOMP_PROFILE=/Users/<이름>/004-Projects/codekr/infra/sandbox/seccomp.json \
  ~/codekr-selftest.test -test.run TestLive -test.v'
```

**런타임 매트릭스는 `internal/sandbox` 디렉터리에서 돌려야 한다** — 런타임 정의 파일을
상대 경로로 찾기 때문에 다른 곳에서 돌리면 조용히 건너뛴다(SKIP).

user namespace 재매핑(#130)까지 확인하려면 `CODEKR_USERNS_HOST_OFFSET=100000` 을 함께 준다.

`CODEKR_CONTAINERD_FIFO_DIR` 은 VM 안의 쓰기 가능한 경로면 된다. 기본 경로
(`/run/containerd`)는 root 만 쓸 수 있어 `mkdir ... permission denied` 가 난다.

이 문서가 확인한 것은 **"macOS 에서 Docker 없이 containerd 를 쓸 수 있는가"** 이고,
답은 제어 평면에 대해서는 예다. 채점기 검증은 리눅스 안에서 한다.

### 다른 후보를 고르지 않은 이유

| 후보 | 왜 안 골랐나 |
|---|---|
| `lima` 직접 | colima 가 lima 위에 있고, containerd 설정과 소켓 노출을 대신 해 준다. 직접 쓰면 `lima.yaml` 을 사람마다 맞춰야 한다 |
| Rancher Desktop | GUI 앱이다. `make` 로 기동할 수 없고 CI 에도 못 쓴다 |
| k3d / kind | 안의 containerd 는 쿠버네티스가 관리한다. 우리가 만드는 컨테이너와 CRI 가 섞이면 **무엇이 우리 것인지** 구분이 어렵다 |

### Docker Desktop 과 함께 쓸 때

colima 는 Docker Desktop 을 대체하지 않고 **나란히 뜬다.** 지금 로컬 스택(`make up`)은
엔진 API 를 쓰므로 Docker Desktop 이 계속 필요하다.

containerd 쪽을 쓰려면 실행기에 이렇게 준다.

```bash
CODEKR_SANDBOX_RUNTIME=containerd \
CONTAINERD_ADDRESS="$HOME/.colima/default/containerd.sock" \
  ...
```

**호스트에서 이 소켓에 붙으면 컨테이너는 뜨지만 출력을 거두지 못한다** (위 FIFO 제약).
macOS 에서 실제로 채점을 돌려 볼 때는 기본값인 엔진 API 를 쓰고, containerd 쪽은
VM 안에서 확인한다.

소켓에 닿지 못하면 실행기는 **기동에서 실패한다** — 조용히 엔진 API 로 넘어가면 운영
노드에서 잘못된 런타임에 붙은 채로 뜬다.
