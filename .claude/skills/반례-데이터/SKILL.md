# 반례 데이터 만들기 (#482)

**테스트케이스를 손으로 만들면 경계를 빠뜨린다.** 오류 신고(#478)가 받게 될 가장 흔한
제보가 "테스트케이스가 빠졌다 — 틀린 코드가 통과한다" 이고, 그것은 대개 **사람이 생각하지
못한 입력** 때문이다.

## ⚠️ 저장소에 커밋하지 않는다

테스트케이스는 정답만큼이나 새면 안 된다. `.problem-drafts/` 안에만 쓴다 (#424, #480).

## 반례는 "정답과 다른 답" 이다

이 스킬이 단순한 입력 생성기와 다른 점이 여기 있다. 경진 프로그래밍의 관례를 따른다.

```
무작위 입력을 만든다
  → 확실하지만 느린 풀이(브루트포스)로 답을 낸다
  → 의도한 풀이로 답을 낸다
  → 다르면 그것이 반례다
```

그래서 **정답 코드(#481)가 재료다.** 없으면 입력만 있고 정답이 없는 것이 되고, 그것은
테스트케이스가 아니다 — 먼저 `정답-코드` 스킬을 돌린다.

**브루트포스도 필요하다.** 확실하지만 느린 풀이를 따로 쓴다. 두 풀이가 같은 답을 내야
"의도한 풀이가 맞다" 를 말할 수 있고, 다르면 **어느 쪽이 틀렸는지**를 그 입력으로 본다.

## 1. 제약에서 입력을 만든다

초안(`problem.json`)에 제약이 있다 — `1 ≤ N ≤ 100,000`, `-10^9 ≤ A_i ≤ 10^9`.

**제약을 넘는 입력을 만들면 안 된다.** 그것은 반례가 아니라 잘못된 테스트케이스이고,
맞는 풀이를 떨어뜨린다.

작은 입력부터 시작한다 — `N ≤ 8` 정도면 브루트포스가 빠르고, **반례를 찾으면 사람이
눈으로 읽을 수 있다.** 큰 입력에서 찾은 반례는 무엇이 문제인지 알 수 없다.

## 2. 손으로는 못 찾는 것들

무작위만으로는 잘 안 나오는 모양이 있다. 따로 만든다.

| 모양 | 왜 |
|---|---|
| `N=1`, 빈 입력 | 반복문의 첫 바퀴가 특별한 경우 |
| 전부 같은 값 | 중복 처리 |
| 이미 정렬 / 역순 | 정렬 기반 풀이의 최악 |
| 최댓값·최솟값만 | **오버플로** (#280) |
| 0, 음수 | 부호를 안 본 풀이 |

## 3. 크기를 잰다

수천 개를 만들면 파일이 커진다. 묶음 형식(#479)이 zip 인 이유가 그것이고, 이 스킬은
**그 안에 들어갈 파일들**을 만든다 — `testcases/{seq}.in`·`{seq}.out`.

상한을 넘지 않게 한다: 푼 크기 **64MB**, 파일 수 **5000개**. 넘으면 업로드가 거절된다
(`docs/12_문제_묶음_형식.md`).

**그리고 큰 것보다 다양한 것이 낫다.** 같은 모양 천 개는 하나와 같은 것을 확인한다.

## 4. 공개할 것과 감출 것

`visibility` 를 정한다. 예제로 보일 것만 `PUBLIC` 이고 나머지는 `HIDDEN` 이다 —
전부 공개하면 **입력을 보고 답을 박은 풀이**가 통과한다.

## 5. 끝내며 알린다

- 몇 개를 만들었고 **무엇을 겨냥한 것인지** (경계·최대·무작위 각각 몇 개)
- 반례를 찾았다면 **그 입력과 두 풀이의 답**. 그것이 이 스킬이 만든 가장 값진 것이다
- 못 찾았다면 **못 찾았다고 말한다.** "반례가 없다" 와 "못 찾았다" 는 다르다
